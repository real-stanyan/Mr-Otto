# ADR-0242：「工作区」进档位 —— 判据放 plan 表，不写死 {pro, max}

- 状态：已接受
- 日期：2026-09-07
- Issue：#1024
- 相关：ADR-0217（工作区的订阅闸，两道闸缺一不可）、ADR-0203（价目由服务端下发；
  决定 18 换档只走 Portal）、ADR-0239「不做的」第一条（#1022 为什么故意没画这枚 chip）、
  ADR-0134（「只能维护者拍板」这类判断先验前提本身）

## 背景

维护者在 #1022 的设计评审里定的：**Pro 和 Max 可以用工作区，Lite 不可以**，Free 自然也不可以。

#1022 那一轮故意没做，因为它不能只画一枚 chip：卡上说 Lite 没有工作区、而 Lite 用户
实际还建得出来，就是 #722「撒谎的勾」的一般形式。

## 先化解掉那个「要维护者先拍板」

#1024 的 issue body 把「存量 Lite 用户已经建好的工作区怎么办」列成阻塞项（继续能用 /
转只读 / 到期失效，三条路的迁移写法完全不同）。

**查了真库，这个问题不存在**（数据贴在 #1024 的评论里）：

| | |
|---|---|
| 用户 | 8 |
| 工作区 | 2 |
| 订阅行 | 1（`max` / `active`） |
| **Lite 订阅** | **0 —— 从来没有过** |

两个工作区，一个属于 max active，另一个属于一个**完全没订阅**的账号（建于 ADR-0217
那道闸落地之前，是闸之前的遗留物，0 条会话）。三条路在今天的数据上给出同一个观测结果，
所以这个决定可以不做 —— 按「只收窄新建」写，存量那一个自然继续存在。

这是 AGENTS.md「读到『只能维护者做』这类判断时先花五分钟验前提本身」的又一例：
上一班把它写成 blocker，实际上一条 SQL 就化解了。

## 决定

### 1. 判据是 `plan.capabilities.workspace`，不是写死的 `{pro, max}`

「哪一档有什么」是 plan 表的事实，同 ADR-0203 对价格的规矩：改价改档不发版。

写死档位 id 的代价不是丑，是**这句话会有两份** —— 一份在 `workspaceAccess.ts`、
一份在 RLS 策略里 —— 而它们只会在改档那天分家，且分家不报错：界面说能建、RLS 拒，
或者反过来。放在 plan 表之后，两道闸读的是同一行。

顺带：文案里那句「Pro 或 Max 可以」也从这里现取（`plansWithWorkspace`），
查不到就整句省掉 —— 宁可少半句，也不说一个可能已经不成立的档位名。

### 2. `plan_too_low` 是独立一态，不能并进 `no_subscription`

**两者该给的路不一样**：没订阅的人走 checkout，已经订着的人走 Customer Portal 换档。
ADR-0203 决定 18 写得很直白 —— 对已有订阅的人再开一张 checkout 会变成第二条订阅、
两笔一起扣，网关那侧直接回 409。

所以合并成一句「去订阅」，等于给 Lite 用户一颗**点了必然失败的钮**。文案与按钮
因此各分一支：「你当前的档位不带工作区，Pro 或 Max 可以」+「去升档」。

这与 ADR-0217 给 `unknown` 单列一态是同一条纪律的第二次应用：**长得像的两个状态，
只要该做的动作不同，就不许合并。**

### 3. 服务端一格都没下发时，退回改动前的行为

`plansWithWorkspace(me).length === 0` = 这一版 edge 或 plan 表还没有这个概念，
此时 `workspaceAccess` 退回「有活跃订阅就放行」。

**这不是 fail-open 的漏子**：RLS 那道真闸在同一时刻同样还是旧的（0028 没跑过），
于是两道闸在任何一个时刻都说同一句话。反过来（缺席按拦）才是真事故 —— 客户端一发版，
所有 Pro/Max 用户在数据落地之前建不了工作区，而 RLS 明明放行。

注意这个降级判据挂在**整张价目表**上，不是挂在单个字段的默认值上：后者会与
`image`/`video` 的 `=== true` 解析规则不一致（那两格的「读不到」确实该按关），
而「服务端有没有这个概念」是一个关于整张表的问题。

### 4. RLS 另起一个函数名，不改 `has_active_subscription`

0028 加的是 `can_create_workspace(u)`（join `plan` 判 capability），
`has_active_subscription` 原样留着。让后者顺带判能力就成了一个名不副实的函数，
下一个人照名字用它会用错。

### 5. 只收窄 insert，存量一行不碰

同 0020 的理由：降档不该让一个群消失 —— 那是删数据，不是收权限。
`workspace_members` 的策略不动（owner 拉人、成员退群照旧），参与也不受档位限制
（规则二：工作区走创建者的额度，成员自己订不订与这本账无关）。

## 后果

- **migration 0028 要人手跑**（Supabase Studio SQL editor，见 `supabase/README.md`）。
  没跑之前客户端走决定 3 的降级分支 = 行为一字不变，所以发版顺序不构成事故。
- 价目卡的能力行现在画两格（`图像` / `工作区`）。真库里三档的 `image` 目前**全是 false**，
  所以「图像」那格今天一张卡都不画 —— 这是数据的事，不是代码的事，单开 issue。
- `PlanInfo.capabilities` 多一格，三端（shared / edge / 测试夹具）同步改。
- 哪天要给 Lite 也开工作区，只改 plan 表一行，客户端与 RLS 都不用动。
