# ADR-0003: /compact 的输入用摘要专用压缩投影，不用全保真

## 状态

已接受（2026-08-16）

## 背景

/compact 把整段历史投影发给模型换一份摘要。最初的决定是全保真投影（「摘要质量优先，
反正这次调用本来就贵」）。对真实会话 s-20260815044135 的输入做尸检后发现，输入里的
大头是对摘要毫无贡献的字节：

- `write_file` 的 `content` 参数：703 字符的文章全文进了输入，占近 1/3。
  摘要只需要「写了文章3.txt，703 字符，主题慢生活」
- 同一内容的三次重复：参数里一遍全文，assistant 收口消息再引用一遍，
  工具输出确认一遍
- `ls -la` 原始 stdout：权限位、`.`/`..`、total 行，摘要人一个字都用不上

## 决定

1. `CompressionOptions` 增加 `maxOldToolArgChars`：老区 tool_call 的参数
   （序列化后的 JSON 字符串）超限截断，与工具输出同款「原 N 字符」标记。
   截断处 JSON 不完整没有关系——这是给模型读的历史，不再被执行。
2. `fidelityBoundary` 特判 `keepRecentTurns: 0` = 无保真区（整段历史可压）。
3. 新增 `COMPACT_COMPRESSION` 档（keepRecentTurns: 0 / 输出 800 / 参数 200），
   `engine.compact()` 用它做投影；`runTurn` 继续用 `DEFAULT_COMPRESSION`
   （保真 2 turn / 输出 400 / 参数 400）。

两档参数不对称的理由：输出上限放宽（800 > 400），因为工具输出可能是某段信息的
唯一载体（assistant 复述可能撒谎或省略），截太狠摘要就写不出来；参数上限收紧
（200 < 400），因为参数是 agent 自己生成的，它总会在正文里交代意图，路径开头
那截通常就够。

## 与硬规则的关系

压缩仍住在投影层：确定性纯函数，同 events + 同 opts 永远同输出，
「模型看到了什么」依旧可从日志 + 代码推导，不需要新事件。
结构神圣不变：只瘦 content / arguments 字符串，消息数量与 tool_call_id 配对不动。

## 代价

- 摘要质量有真实风险：若关键信息只存在于被截断的中后段（长 diff、长文件内容），
  摘要人看不到它。标记能让摘要人知道「这里折叠过」，但补不回内容。
  接受此风险的理由：输入 token 是 compact 的主要成本，而被截内容绝大多数
  是重复或噪音；真出现质量问题，调大 COMPACT_COMPRESSION 的上限即可，
  一行改动，不动结构。
- 参数从头截断对 key 顺序敏感：模型把 `content` 放前、`path` 放后时
  （DeepSeek 实际这么发过），路径可能被截掉。未做 per-key 精细截断，
  复杂度不值得——工具输出通常会复述路径。

## 被否决的备选

- **整条删除老区 tool 消息**：违反结构神圣——tool_call_id 配对是 API 协议，
  删消息会废掉整个请求。
- **per-key 精细截断参数**（只截长 value、保住 path 等短 key）：更聪明，
  但引入对参数 schema 的假设，每个工具一套规则。等真实痛点出现再说。
- **compact 前先跑一次 LLM 预清洗**：双倍模型调用，成本反向。
