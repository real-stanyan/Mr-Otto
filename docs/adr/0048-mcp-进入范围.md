# ADR-0048：MCP 进入范围 —— 做 client 那一半，不做 server

- 日期：2026-08-21
- 状态：已接受
- 相关：ADR-0007（skill 是纯提示词注入，不算插件系统）、ADR-0034（L1 的 PR 评论同意路径）
- 设计文档：`docs/superpowers/specs/2026-08-21-mcp-design.md`
- 协议缺口：#132

## 背景

`AGENTS.md` 开头写着「明确不做：多 agent 编排、MCP、插件系统」。这条边界立的
时候，MVP 完成标准是"单 agent + 3 工具 + event-sourced 日志 + replay + 审批 UI +
模型切换 + ExecutionWorld"——MCP 没在那份清单里，是因为它不是把 MVP 撑起来
必需的那一块，不是因为它被判定有害或者与架构冲突。边界当时是用来**守住范围**的，
不是用来**否定 MCP** 的。

现在 ExecutionWorld、事件日志、审批 UI、工具中间件管线都已经落地并且稳定
（terminal / browser 两次挂上 world seam 都没动过这套骨架，见 ADR-0031 / 0035）。
MCP 要接的东西——外部工具、外部资源、外部提示词模板——形状和"再多几个内置工具"
没有本质区别，缺的只是一个标准协议客户端。继续把它挡在"明确不做"里，挡住的
不是复杂度，是能连的第三方生态。

## 决定

v1.x 实现一个 **MCP client**，不实现 MCP server。tools / resources / prompts
三样能力都接：

- **tools** 包成本仓的 `Tool`，走既有的工具中间件管线（审批、事件、`available()`）。
- **resources** 由模型主动发起一次工具调用去读（`mcp_read_resource`），不做
  连上就自动注入进 system prompt 那种事——这一条的完整理由记在下面，因为它
  直接撞硬规则,不是单纯的产品取舍。
- **prompts** 走输入框的斜杠命令面，展开成一条普通 `UserMessage`。

## 「不做插件系统」为何仍然成立

MCP server 是一个**跨进程的外部程序**，通过标准协议（stdio 或 HTTP）和 Otto
对话——`connectMcpClient`（`src/main/mcpClient.ts:83`）拿到的始终是一条连接
（`McpClientConn`：`callTool` / `readResource` / `getPrompt` 几个方法），
从没有一行代码、一个模块、一段可执行逻辑被加载进 Otto 自己的进程空间。

这与 skill（ADR-0007：纯提示词包，注入 = 把 markdown 说明书拼进模型上下文，
"没有代码执行、没有扩展 API、没有生命周期钩子"）是**同一种克制的两种形态**：
两者都在讲同一件事——可执行扩展面必须留在进程外，不能钻进程内。skill 靠"它
从头到尾就只是文本"做到这一点；MCP 靠"它是另一个进程，只能通过协议对话"做到
同一点。真正会破掉这条边界的是"允许第三方 native 模块 / 动态库 / 脚本被
`require`/`import` 进 Otto 主进程"——MCP 客户端不做这件事,`@modelcontextprotocol/sdk`
提供的只是协议编解码和进程/连接管理,不是一个加载点。

## 本版不做，及为什么

- **sampling**（server 反过来向 Otto 请求一次模型调用）。MCP 协议里有这个原语，
  但接了它就等于让 server 变成一个会花用户账上的钱的第三方——谁能触发、触发多少、
  算谁的账，这是一个独立的授权模型，不能顺手塞进这版。留到需要时单独设计。
- **roots**（把工作区目录声明给 server）。产品价值本版用不上，下一版再看。
- **完整 OAuth**。`needs-auth` 状态和 Authorize 按钮先画出来，但点击行为本版
  只支持"打开浏览器让用户自己去授权，再把 token 粘回来"这条土路——
  `isAuthError`（`src/main/mcpClient.ts:75`）负责把 401/403 从"这台连接失败"
  里挑出来标成"需要授权"，但拿 token 之后仍要用户手工填回配置。
- **server 进程管理面板**（重启 / 看日志 / 改 env 热重载）：本版只有连 / 断
  两个动作，`mcpHub.reconnect()`（`src/main/mcpHub.ts:247`）就是全部。
- **per-会话启用哪几个 server**：全局一份 `~/.otter/mcp.json`，全会话共用。

## 代价

- **多一棵依赖树**。`@modelcontextprotocol/sdk` 是这个仓库的新依赖，但锁在
  `src/main/mcpClient.ts` 一个文件里（见 ADR-0049）——换实现、评估供应链风险，
  改动面都收在这一处。
- **冷启动之后的首个会话装配要多等一次连接**。`agent.ts` 在拼工具表之前
  `await world.mcp.ready()`（`src/main/mcpHub.ts` 的 `ready()`），并发连所有
  `enabled` 的 server，单次 10 秒超时兜底——正常路径（npx 包已缓存的 stdio
  握手 / 一次 HTTP 请求）是几十到几百毫秒，10 秒是给"server 挂了/网不通"这类
  真故障准备的,不是常态延迟。超时不等于失败：没连完的 server 留在
  `connecting`，继续在后台跑，只是这一次会话装配时它的工具还不存在
  （§ ADR-0049 详述"挂载一次定终身"的后果）。

## 一个值得单独说清楚的实现事实：resources 为什么不自动注入

设计阶段本想让"连上就把 server 的 resource 塞进 system prompt"，但这直接撞
硬规则——append-only 事件日志是唯一事实来源，先落盘再喂模型（model-visible
means logged）。自动注入会造出一份模型看得见、却不在事件日志里的内容；要合规
就得为"注入了哪些 resource"造一个新 `SessionEvent`，并保证重放时能拿回**当时
那一版**的内容（server 上的文件随时可能已经变了）——代价远大于收益。

改成模型主动调用 `mcp_read_resource` 工具去读，天然合规：读取动作就是一次
`ToolExecutionStarted` + `ToolResult`，内容原样落盘，重放拿到的是当时读到的
那一份，不需要新的事件类型。

## 什么会推翻这个决定

如果"不做 server"这半条边界要动——比如 Otto 自己要暴露一个 MCP server 给
别的工具消费——那是一个新决定,不是这份 ADR 的自然延伸,需要单独走一次
L1（server 意味着 Otto 要对外承诺一份协议兼容性，风险形状和"client 连出去"
完全不同）。如果 sampling 的授权模型有了答案，本版排除的那条也需要单独一份
ADR 记录,不是回来改这一份。
