# 0143 记忆判据换向：单源正文 + 全局档点名项目即拒

Issue: #589

## 背景

三档记忆（ADR-0116）上线首日对真实用户数据的审计：全局 MEMORY 990/1100 字符，
6 条里 4 条是项目级事实；唯一一次项目档写入方向恰好写反（机器级 PATH 事实进了
mandys_bubble_tea 的项目档，且与全局条目重复）；维护者被迫手编文件搬家。

两个成因：

1. **判据偏置失效**。「拿不准就写 memory」设计意图是防「错放项目档丢失」
   （ADR-0116 代价三），实际效果是模型几乎从不「拿不准」——一律写全局。项目
   事实堆在最小的那档里互相驱逐，互相驱逐正是三档要治的病。
2. **判据正文三处各写一份**（memory 工具描述 / memory-reviewer 指令 /
   deriveMessages 的 system 尾部），措辞已经各自漂移。

## 决定

### 1. 判据正文单源：`tierRuleText`（shared/memoryStore.ts）

三个注入点共用一份。正文换向：删掉「拿不准就写 memory」，判据收成一个可回答的
问题——**换个项目还成立吗？成立写 memory，不成立写 project**——并把两条此前没
说破的规则明说：机器/环境事实（PATH、CLI 登录态）不进项目档；一个事实只住一档。

### 2. 写入守卫：全局档条目点名当前项目 = 拒

`projectMentionInGlobal(content, projectRoot)`（纯函数，shared 层）：内容含项目根
绝对路径、或含根目录名（大小写不敏感，≥3 字符才认）即命中。memory 工具在
`target === "memory"` 且有项目根时对 add/replace 的新内容做这个检查，命中就拒，
报错指路 `target: "project"`。

**模型坚持写全局的出路是改写内容**：把项目名/路径去掉。这不是绕过，是守卫想要的
行为——真正跨项目成立的事实本来就不该点名具体项目；点了名还想留全局，说明这条
要么该进项目档，要么该换个不绑项目的说法。

三个边界，都是故意的：

- **remove 不拦**：old_text 是在定位既有条目。拦它会把「清理错放存量」的路堵死。
- **反方向不拦**（机器事实写进项目档）：没有可靠的文本判据能认出「这是机器事实」，
  交给判据文案。守卫只做有把握的那半边。
- **没有项目根时不设防**：分不出「点名项目」，宁可不拦。

### 3. 只做子串匹配，不做聪明的判断

误伤存在（比如全局条目想说「所有叫 xxx 的项目都……」恰好含当前 repo 名）。接受：
误伤的代价是模型换个措辞重写一次，漏放的代价是错档条目住进 1100 字符的紧档并
参与驱逐。短目录名（<3 字符）不认，是同一权衡的另一半。

## 接受的代价

- 判据文案变长约 40%。三档判据本来就是模型每次写记忆都要过的判断，多花的字符
  买的是可执行性（一个能回答的问题 vs 一句抽象分类）。
- 存量错位条目守卫管不到——它只拦新写入。本次审计的存量已手工搬家；将来的存量
  错位靠 reviewer 的 replace/remove（不受守卫影响）收敛。
- `deriveMessages` 的 system 尾部文案变了：旧会话重放时这段提示词跟着新版本走。
  与 ADR-0116 代价一同理——硬规则要的是「旧日志永远可重放」，不是「投影逐字节
  不变」；这段文案本来就不落日志（memory_loaded 事件记的是内容快照，不是指引文案）。

## 推翻它的前提

- 守卫误伤率实测显著（模型反复被拒、被迫写出别扭的绕行措辞）→ 收窄匹配（只认
  路径不认目录名），或把拒改成警告附在成功结果里。
- 换向后项目档开始被机器事实污染（反方向误写成为主流）→ 说明文本判据管不住方向，
  该上 ADR-0116 不做清单里的检索层/分类器，而不是继续加字。
