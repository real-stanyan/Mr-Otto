# ADR-0151：好友代理——经中继接替身份操作 MCP 服务，密钥不出门

- 状态：已接受
- 日期：2026-08-28
- 关联：issue #622（好友代理任务）；#611 / ADR-0147（@好友分享会话——本决策的上游，
  分享的是「上下文」，本决策分享的是「能力」）；ADR-0129/0130（edge relay 盲管道）；
  ADR-0094/0095/0096/0097（手机远程投影与审批，本决策复用其加密与配对机制）
- 后续 PR：A（relay 跨户+角色模型）/ B（代理帧+A 侧执行器+白名单）/ C（B 侧代理
  McpCapability+身份绑定）/ D（审计+撤销 UI+真机联调）

## 背景

`@好友` 分享会话（ADR-0147）交付后，stanyan 提出更进一步的需求：好友 fork 会话后，
要能**以分享者的身份**继续操作「之前已接通的所有服务」——典型是 Shopify 后台、
Google Ads 后台这类经 MCP 接入、凭证存于分享者本机 `~/.mr-otto/mcp.json`（0600）的
服务。「字面意义上接着上一个会话接着干」，不是用自己的账号重连。

这本质上是**委托（delegation）**：把「操作我的服务的能力」临时授给另一个人。
摆过三条路（见 issue #622 决策表）：平台侧子账号（① 手动，不写代码）、随包移交
密钥（③ 密钥进包=可能进不可删事件日志=永久泄漏，被否）、**代理/中继（②，选定）**。

## 决策

好友的 MCP 工具调用**不在他本机执行**，而是端到端加密后经 edge relay 转发到
**分享者一直在线的 Mr Otto**，由分享者机器用自己的凭证执行，结果加密传回好友。
**密钥从开机到关机不离开分享者的 `~/.mr-otto/`。**

### 1. 传输：复用 edge relay，但鉴权放握手层，不放进 relay

relay 是刻意的**盲管道**（ADR-0129/0130：不解析负载、不落盘、不打印负载），
它不知道 friendships、也不该知道。「B 有权代理 A」的授权判断**不下放到 relay**，
而是：

- relay 只改成「支持任意频道 id + 同角色可互发」（现在是 `getByName(userId)`
  一户一 DO、`desktop`/`mobile` 两角色同角色禁发，A↔B 两个桌面互连被这层硬挡）。
- 「B 有权代理 A」由 **A 的代理执行器**判断：查 friendships（关系还在吗）+
  本地白名单（这次授了哪些服务/工具）。friendships 被删除 = 代理权限跟着死。

relay 职责不被污染，改动从「加 friendships 鉴权」降为「频道 id + 角色模型」。

### 2. 信任来源：密码学身份（pin 公钥），friendships 只是授权目录

复用现有的配对哲学（pairing.ts 头注：「目录不是信任来源」）：

- 握手用 Noise KK 形状（Ed25519 签临时 X25519，前向保密），信任来源是调用方
  pin 住的 `peerIdentityPub`（TOFU）。
- 好友配对复用 pairing.ts 的「一次性邀请 + 持有证明」机制，把「手机扫桌面码」
  换成「好友邀请码」；配对时互相记录 `(supabase userId ↔ 对端 Ed25519 identityPub)`。
- friendships 表只负责「这段好友关系还存在/已删除」的撤销语义，**不是信任来源**。

### 3. 角色模型：新增 host/guest 角色对

现有 `RelayRole = "desktop" | "mobile"`、握手 `deriveSession` 同角色拒连（防反射），
角色还进了 KDF salt/info。A↔B 需要新角色对（`host`=被代理的分享者 / `guest`=好友），
KDF 的 salt 拼接与 info 字符串相应新增一套，前向保密与防反射性质原样保留。

### 4. B 侧接入：ExecutionWorld withX 装饰器，工具层零改动

最干净的拦截点是 seam 惯例（executionWorld.ts 的 `withMcp`/`withBrowser` 同款）：
给 B 的会话焊一个**代理 McpCapability**——`servers()` 报 A 授权的工具清单、
`callTool(serverId, tool, args)` 转成发给 A 的代理请求帧、等 A 结果帧再 resolve、
AbortSignal 转成取消帧。工具层（mcpTool.ts）一行不改，「工具只认 ExecutionWorld」
的硬规则原样成立。

### 5. 执行闸：白名单内全自动（stanyan 知情接受的风险）

分享时圈定白名单（按 好友身份 + server + tool），圈内操作**不逐笔打扰**、圈外直接拒。
已知限制：MCP 工具粒度到「工具级」（`update_product` 能改库存也能改价），到不了
参数级——白名单全自动意味着圈内写操作好友不受实时拦截地做。三道防线兜底：

1. **审计**：每一笔代理执行的调用（尤其写）完整记账——谁、何时、哪个工具、
   什么参数、什么结果，分享者可查。
2. **撤销**：一键吊销，好友的代理通道立即失效；分享者关机/离线 = 天然断开。
3. **白名单**：分享时圈定范围，圈外拒绝。

### 6. 一期范围：读+写都做

stanyan 拍板一期连写一起做（写工具在白名单内全自动）。风险已知情接受（见上）。

## 能复用 vs 必须新写（侦察结论）

**直接复用**：sealedStream/crypto（端到端加密）、wsTransport 传输骨架、wire.ts
cid 编址、pairing.ts 一次性邀请+持有证明、remoteBridge 逐 cid 状态机骨架、
frames.ts 白名单解码范式、ExecutionWorld withX seam、friendships 表 + presence/心跳
在线判断。

**必须新写**：relay 跨户房间（频道 id + 同角色互发）+ host/guest 角色模型、
代理帧（B→A 请求 / A→B 结果 / 取消）+ A 侧代理执行器 + 白名单策略存储、
身份绑定（userId↔identityPub）+ friendships 撤销联动、审计 + 撤销 UI。

## 后果

- **好**：密钥不出门、可随时收回、范围可圈、每笔可审计；复用了现有加密与配对
  机制的大半；工具层零改动。
- **代价**：分享者机器必须开机+联网好友才能用（这是「可收回」的固有代价）；
  4 个 PR 的架构级工程；relay 要改 Cloudflare Worker 并重新部署；加密握手加一套
  角色对，安全敏感，实现与测试都需极谨慎。
- **撤回**：A 侧代理执行器 + B 侧代理 capability + relay 角色模型是新加的层，
  不污染现有「手机远程看自己电脑」的链路；整个功能可通过不接线（B 侧不焊代理
  capability）整体关闭。
