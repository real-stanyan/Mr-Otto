# ADR-0024：德州动效用 GSAP，且只用在牌桌

- 状态：已接受
- 日期：2026-08-18
- 相关：#59，AGENTS.md「Changing the protocol itself」L1 层
- 授权：维护者 stanyan 在 2026-08-18 会话中明确指定「德州游戏动效用 gsap 做」

## 背景

引入 GSAP 是 **Tech stack 变更，属 L1**：按 AGENTS.md 的规矩要 issue + ADR + PR，
且合并前需要维护者明确同意。同意已在会话中给出（原话见上），本仓库是单人仓库，
会话内同意对 L1 有效（ADR-0034/0042 的例外只适用于多人协作仓库）。

## 决定

牌桌的动效用 GSAP，**其余界面继续用 CSS transition**。

现有 UI 的动效全是 CSS（`@starting-style` 进场、`transition` 收敛、`ease-strong` 曲线），
那套东西的优点是跑在合成器上、不占主线程、可被打断后从当前值继续。牌桌不一样：

- 发牌是一串**有先后、要编排**的动作（六个座位依次各两张，间隔几十毫秒）。
  用 CSS 得靠一堆 `transition-delay` 硬编时间点，改一次节奏要重算所有延迟。
  GSAP 的 timeline 就是为这件事存在的。
- 推筹码、收池、翻公共牌之间有依赖（收池必须等摊牌亮完），
  timeline 能表达"接着上一个"，CSS 只能表达"从现在起第 N 毫秒"。

反过来说，一个按钮的按下反馈、一张卡片的进场，用 GSAP 是杀鸡用牛刀，
还把本来在合成器上的动画拉回主线程。所以边界画在牌桌里。

## 代价

- 多一个 42 KB（min+gzip 约 24 KB）的依赖，且渲染层从此有两套动效范式，
  改动效时要先问"这是牌桌吗"。边界不清会漂移 —— 这是这条决定最主要的成本。
- GSAP 走 JS 驱动，主线程忙的时候会掉帧。牌桌不像会话流那样在动效期间还要
  同时渲染流式文本，风险可接受。

## 什么情况下该推翻

- 如果哪天 CSS 有了原生的、可编排的时间线（Web Animations API 的
  `timeline` 提案落地并被 Electron 采用），GSAP 的唯一理由就消失了。
- 如果牌桌动效最后收敛成三两个互不依赖的独立动画，那也不需要 timeline，
  该退回 CSS。
