# ADR-0234：仓库配置从云会话头部搬进工作区设置（协议 8）

- 状态：已接受
- 日期：2026-09-06
- 关联：#991；推进 ADR-0199（cs 帧协议）/ ADR-0200（clone 决策表）/ ADR-0233（云会话只走订阅额度）/ ADR-0218（工作区里开会话和本地一个开法）

## 背景

维护者看着真机上的云会话页头说：「右上角的“配置仓库”应该改为“设置”按钮，点开显示工作区的所有设置。并不是所有工作区都会有 GitHub 仓库，有些可能是文案工作。」

这句话点的是两件事，第二件才是根：

1. 头部那颗钮的**名字**不对——它叫「配置仓库…」，而人在那个位置想找的是「这个工作区的设置」。
2. 更要紧的是**位置**：仓库配置此前挂在**会话房**的 `config` 帧上（ADR-0199 起就是这样），于是配它的前提是「手上正开着一条这个工作区的云会话」。头部因此常驻一格「未配仓库」——对一个做文案、做运营的工作区，那句话说的是一件它永远不需要做的事，读起来像一个没配完的半成品。

「不是每个工作区都有仓库」这条事实此前在界面上一个字都没有：`repoStatusText(null)` 说的是「这个工作区还没有配仓库，水獭的工作目录是空的」——「还没」两个字把一个正当的终态说成了待办。

## 决策

### 1. 仓库配置改走控制房，协议 7 → 8

`config` 帧从会话房搬到控制房（`cs-ctl`），带上 `workspaceId`；新增一对读帧 `workspace{workspaceId}` → `workspace_state{workspaceId, repo, modelRoute}`；`config_result` 也带上 `workspaceId`。会话房里出现 `config` / `workspace` 一律 `denied not_authorized`，与 `create` 同一条待遇。

判据是**这个东西属于谁**：仓库是工作区的属性（同 ADR-0202 的模型 key、ADR-0231 的 `sandbox_approval`），不是某一条会话的。让它挂在会话房上，等于给一个工作区级的设置强加一个「先开一条会话」的前置条件——而这个前置条件在界面上表现为「设置项藏在会话头部」，也就是维护者看到的那个症状。

**减一次往返不是理由，去掉一个假前提才是**：控制房本来就是「关于某个工作区的动作」那一类帧的家（`create` 早就在那儿），三条帧共用一副骨架反而少了一份代码。

否决的两条：
- **保留会话房那份、只在设置页里额外开一条临时云会话**——那是为了配一个设置去建一条真会话（落库、开房、烧配额），荒谬；
- **走 Supabase 直连**（像 `relay_max_depth` / `sandbox_approval` 那样落 workspaces 表）——PAT 是凭据，它此刻存在 VPS 的 `workspace-config.json` 里、只回一个 `hasPat` 布尔（ADR-0199）。搬进 Supabase 等于把一份凭据挪进一张 RLS 表，那是另一个决定，不该顺手做。

### 2. 桌面：新开「仓库」tab，头部只剩「设置」

`WorkspacePage` 加第三个 tab「仓库」（会话 / 智能体 / **仓库** / 连接器 / 成员 / 用量 / 记忆）：状态给所有成员看（同 ADR-0199 「welcome 带 repo」的口径——「水獭在哪个仓库上干活、拉下来没有」是每个成员都该看得见的事实），表单只给 owner。

云会话头部因此只剩三样：归档 · 模型路由 · 「设置」。那颗钮打开的是这个工作区的设置抽屉，也就是侧栏 ⚙ 打开的同一扇——**同一个东西只有一个位置**。为此 `openWorkspaceId` 从 `AppSidebar` 的本地 state 搬进 store：两个消费方（侧栏 ⚙、主区的云会话头部）不在同一棵子树上，最近的公共层是 store。

### 3. 「不用仓库」是一个正当状态，文案得这么说

「仓库」tab 顶上第一句话就是「**不是每个工作区都需要仓库**——做文案、运营这类活留空就行，水獭在一个空目录里干」；`repoStatusText(null)` 的全文从「还没有配仓库」改成「没有配仓库……不是每个工作区都需要仓库」。

「还没」预设了一条所有人都该走完的路。真实情况是这条路有一半的人根本不该走，而界面此前把他们的正常状态画成了未完成。

## 后果

- 协议 8：已装的正式桌面（协议 4）本来就连不上，dev 与 runtime 必须一起更新——runtime 要 `npm run runtime:deploy`。
- `cloudSessionClient` 的 `config()` 没了，换成 `workspaceState()` / `workspaceConfig()` 两个控制房 RPC；三条控制房 RPC（create / workspace / config）共用 `ctlRequest`，`#829`（没发出去当场失败，不白等超时）与终审 C1（JWT 只发第一个 host 通告）两条纪律在骨架里各留一份，不再各写一遍。
- 会话房不再有 `pendingConfig` 那套挂起态（含三条终态收口）——控制房 RPC 每次开一条新连接，连接自己的 `onGone`/`onClose` 就是收口，少了一整类「保存中…永远转下去」的失败模式。
- 「保存」不再是弹窗按钮而是 tab 内的按钮，`saved` 那 2 秒确认留在原地（ProviderKeyDialog 的手法）。
- 已知代价：设置页每次打开「仓库」tab 都要走一次控制房往返（15 秒超时），比读一份已经在手上的 `welcome.repo` 慢；换来的是「不开会话也能配」。失败时画一句原因 + 一颗「重试」，不落 `workspaceGroupsError`（那一格是整页共用的，会被一件不相干的成功抹掉）。
