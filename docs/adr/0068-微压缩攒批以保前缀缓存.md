# 0068 微压缩攒批以保前缀缓存

日期：2026-08-23 ｜ 状态：已接受 ｜ 关联：issue #220（审计）、#213（命中率基线）、ADR-0064（微压缩）

## 背景

各家模型 API 的 prompt cache 全部是 **prefix-based**：请求的 token 前缀与上次逐字节相同才命中（DeepSeek 磁盘 context caching、GLM 自动前缀缓存、OpenAI 自动缓存，命中价 1/10 ~ 1/2）。所以「模型无关的缓存优化」收敛为一条 harness 纪律：**投影出来的消息序列尽量 append-only、前缀字节稳定**。

issue #220 对 deriveMessages 投影做了前缀稳定性审计：

| 触点 | 判定 |
|---|---|
| skill_invoked / image_described / subagent_briefed 注入 | 无害——user 消息落在事件位置，append-only |
| memory_loaded 拼 system 尾部 | 无害——只在 session 创建时落一次，会话内前缀稳定 |
| context_compacted 清场 | 固有一次性 miss，接受 |
| 滚动 clip 边界（DEFAULT_COMPRESSION，保真边界每 turn 前移） | 断点只在尾部约 2 turn 处，损失小，接受 |
| **micro_compacted（ADR-0064）** | **每 turn 收口跑一次：吸收区每 turn 长大 + running summary 每 turn 重写整段替换文本 → 投影从第 2 个 user 消息起每 turn 变化，前缀缓存几乎全废** |

微压缩的问题量化：不开微压缩时，长会话的历史几乎全部命中缓存（DeepSeek 按 1/10 计价）；开着时，历史被换成一条**每 turn 都在变**的摘要消息，位置又在投影极前部——省下的是上下文长度，付出的是整段历史每 turn 全价重算，在支持缓存的供应商上很可能**净亏**，还外加每 turn 一次便宜模型调用。

## 决策

微压缩从「每 turn 吸收一个 exchange」改为**攒批**：

1. `nextMicroExchange` 改为**整段 backlog 一次吸收**——返回从最老未吸收 exchange 到保真区边界前最后一个可吸收 exchange 的整个区间，一条 `micro_compacted` 事件覆盖全部；
2. 新增门槛 `MICRO_BATCH_MIN_EXCHANGES = 4`：可吸收（带 assistant/tool 内容的）exchange 攒够 4 个才动手，不够就返回 null、这一 turn 不产生任何投影变化。

效果：投影中段的重写频率从每 turn 一次降到约每 4 turn 一次，其余 turn 前缀完整、缓存命中回到滚动 clip 的地板水平；便宜模型调用也降到 1/4。事件 schema、absorbedIndexes 语义、投影替换规则全部不变——变的只是「何时落、覆盖多宽」。

门槛参数放在纯函数层（`session/microCompact.ts`）作为可选参数（缺省 1 = 只改区间语义不设门槛，测试用），生产默认值由 loop 层（`loop/microCompact.ts`）注入——与 keepRecentTurns 走 DEFAULT_COMPRESSION 的既有分层一致。

## 备选与否决理由

- **cache-aware 动态门控**（近期 usage.cachedTokens 命中率高才攒批，不报 cache 的端点维持每 turn）：#213 的基线刚落，还没有真实命中率数据支撑阈值设计；且让「要不要压缩」依赖账单字段会把计费观测耦合进投影策略。先用固定批量拿到数据，将来有据可依再议。
- **append-only 分段摘要**（每段落一条独立摘要、旧段摘要字节不变，替代 running summary 重写）：前缀断裂的主因是「吸收这个动作把中段消息拿走了」，发生在落 micro 事件那一刻——摘要是重写还是追加不改变断裂频率。攒批已经把频率降下来，分段化只剩边际收益，不值得推翻 ADR-0064 的 running summary 设计。
- **关掉微压缩**：上下文无界增长的问题（ADR-0064 的立项理由）还在，本地/无缓存端点也依然受益于瘦上下文。

## 推翻条件

- #213 基线数据显示攒批后命中率仍显著低于滚动 clip 地板 → 重查投影里其他不稳定源；
- 供应商缓存机制普遍转向非前缀式（如内容寻址分块缓存）→ 本决策的前提消失。
