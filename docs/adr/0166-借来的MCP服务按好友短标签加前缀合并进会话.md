# ADR-0166：借来的 MCP 服务按好友短标签加前缀，合并进会话——不换掉本地那份

- 状态：已接受
- 日期：2026-08-28
- 关联：issue #670；ADR-0151（好友代理宪法，§4「B 侧接入：ExecutionWorld withX 装饰器」）；
  ADR-0041（审批记忆按完整工具名记）；issue #349（模型可见工具名的统一分配）

## 背景

`proxyMcp` 早就是一份可用的 `McpCapability`，但它被锁在 `proxyManager` 的闭包里，
**没有任何出口**——所以 B 的水獭调不到 A 的工具：不是「调了失败」，是工具表里
压根没有那些刀。这是好友代理最后一个功能缺口。

接上去只有一处 seam（`agent.ts` 的 `withMcp`），但 `withMcp` 是**整份替换**：
直接换，B 自己接的 MCP 服务全没了。要合并，而合并撞上同名问题——
B 自己有 `shopify`，A 借来的也叫 `shopify`，下游有两处按不同字段认人：

- **名字**：`createMcpTools` 拿 `server.name` 分配模型可见名，`assignMcpToolNames`
  规则 ① 把「同 server 名 + 同 tool 名」当重复项**静默跳过**——不是重命名，是丢掉
  一个，留哪个看列表顺序；
- **派发**：那把刀的 `run` 闭包调 `callTool(server.id, ...)`，合并层只收到一个
  `"shopify"`，判断不出该本地跑还是打帧发给 A。

## 决策

**借来的服务一律加好友前缀，本地那份一个字不改。** id 和 name 都加：

- id：`proxy:<短标签>:<A 那边的真 id>` —— 派发的路由键，剥掉前缀还原成真 id 发走；
- name：`<真名>@<短标签>` —— 过 `safe()` 之后是 `shopify_3f2a1b9c`，
  模型看到的刀就是 `mcp__shopify_3f2a1b9c__get_orders`。

### 短标签取 uid 的前 8 位，不取昵称

两条理由，都是硬的：

1. **昵称过不了 `safe()`**（`[^A-Za-z0-9_-]` → `_`，见 `mcpToolName`）：中文昵称整串
   变下划线，两个中文名好友还会塌成同一串——正好撞回上面那条静默丢弃。
2. **昵称会变**，而审批记忆是按完整工具名记的（ADR-0041）。改一次昵称就换一把刀，
   「永久允许」静默失效。uid 不会变。

好友的人话名字进**工具描述**：`【好友代理·小明】这次调用在小明的机器上执行、
用小明的凭证。` —— 模型和审批弹窗都看得见，而它不进名字、不影响记忆。

### 通道没了就抛错，**不回落到本地**

前缀对上了但那条通道不在（好友撤销/断线），`callTool` 抛错。
回落等于把「调小明的 shopify」悄悄执行成「调我自己的 shopify」——
同一把刀在两个账号之间静默漂移，是这套设计里最坏的失败模式。

### 通道清单是取函数，不是快照

`mergeProxyMcp(own, () => channels)`。好友通道随时来去，而 `buildTools` 每 turn
现算一次工具表（`agent.ts`）。传数组等于把「此刻有哪些好友」冻在装配那一刻。
好处是白送的：A 握手后才推来的授权清单、A 中途改授权，下一轮自动出现。

### A 执行时用的仍是本地 hub，不是合并的那份

`index.ts` 里 host 侧的 `mcp:` 必须是 `mcpHub` 本尊。换成合并的等于允许
**传递性代理**：B 借 A 去调 C 的服务，而 A 圈给 B 的白名单里从来没有 C 那些工具。

### 邀请码带上 A 的 uid

B 要贴标签就得知道对方是谁，而邀请码里原来没有 uid。加一段。它是**自报**的，
和 `hostIdentityPub` 一样由这张带外传来的码背书——拿到码的人本来就能冒充码里的
一切，多一个字段不改变信任模型。顺带补上 ADR-0151 §2 说的「配对时**互相**记录」
里 B 欠的那一半，以及一道 B 侧的好友闸：主人不在 B 的好友里就不接——
A 那边本来就有同样一道（ADR-0164），这一道纯粹是为了**把话说清楚**。

## 后果

| | |
|---|---|
| ✅ | B 的水獭真的能调 A 的工具了；同名服务不再有一把被静默吞掉 |
| ✅ | 工具名稳定（uid 不变），审批记忆按好友分开——「永久允许小明的 shopify」不会顺带允许你自己的 |
| ✅ | 子 agent 的 `allowTools` 与设置页的工具目录都看得见借来的刀（`knownMcpToolNames` / `probeToolDefs` 改读合并后那份），否则点名会被静默剔除 |
| ⚠️ | 模型看到的名字里有一串 8 位十六进制，不好读。补偿在描述里；真正读那串的是审批记忆，不是人 |
| ⚠️ | 一次只代理一个好友（`guest` 是单条）。合并层本身支持多条，等 B 侧持久化那一步再放开 |
| ⚠️ | 借来的服务的 `prompts` 不进 `listMcpPrompts`（代理第一期不做提示），斜杠面板里看不到——与 `proxyMcp` 明确抛错的那几条一致 |

## 被否掉的路

- **只在撞名时才加前缀**：名字最短，但同一台服务的工具名会因为 B 那边装没装同名
  server 而变。审批记忆、子 agent 白名单点名都按完整工具名记，会时灵时不灵——
  一个只在特定安装组合下才复现的 bug。
- **一个会话二选一（用自己的 或 用某个好友的）**：零撞名、实现最简单，也贴合
  「好友 fork 了 A 的会话接着干」那个原始场景。否掉是因为它把「混用」这条路彻底封死，
  而 B 想一边查自己的库一边操作 A 的 Shopify 是完全正当的用法。
- **前缀用昵称**：见上面两条硬理由。
