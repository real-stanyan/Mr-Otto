# ADR-0021：额度按 token 计、按型号分桶

- 状态：已接受
- 日期：2026-08-18
- 相关：issue #55；ADR-0019（官方 key 走网关）、#48（token 德州）
- 推翻：ADR-0019 决定二里"金额单位 micro-USD"那一条（账本 append-only 的部分不变）

## 背景

维护者裁定（2026-08-18 会话）：余额不按美金计，按 token 计——之后的德州要拿它当筹码，
美元额度每押一注都得换算一次。进一步裁定：**flash 和 pro 分开计费**。

## 决定一：单位从 micro-USD 换成 token

余额、账本、UI 一律以 token 计数。

代价是账面不再直接等于成本。收益是它能直接当筹码：整数、可加可减、押注不需要中间单位。
德州是本仓库确定要做的功能（#48），为它选单位不是过度设计。

## 决定二：按型号分桶，两桶互不流通

**token 不是等价的**。同样 1 个 token：

| | 输入 | 输出 |
|---|---|---|
| flash | 0.28 USD/1M | 0.42 USD/1M |
| pro | 0.55 USD/1M | 2.19 USD/1M |

最贵与最便宜差 7.8 倍。**一个统一的 token 余额等于开着套利口子**：用户全切 pro，
扣同样多的额度，平台付 7.8 倍的钱。德州那边更明显——赢来的筹码换成 pro 输出，
比换成 flash 输入值钱得多，等于让人拿汇率差当收益。

分桶之后两边互不流通，每个桶的最坏成本 = 桶容量 × 该型号最贵那一档，封死。

**什么情况下该推翻**：如果将来各型号价差收敛到可忽略（比如统一定价），
分桶就只剩复杂度，该合回一个余额。

## 决定三：桶内输入/输出按 1:1，不再加权

桶内仍有价差（flash 1.5 倍、pro 4 倍）。考虑过按方向加权，否决：桶容量已经把
最坏成本封住了，再套一层权重只是把"整数好算"这个唯一的好处又还回去。

赠额按**最坏成本**折算，让"送 20 刀"这句话在最坏情况下也成立：

    flash 2000 万 × 0.42 = $8.40
    pro    500 万 × 2.19 = $10.95
    合计最坏 $19.35

正常用量远低于此。两档赠额都可用 env 调（`OTTO_GRANT_FLASH_TOKENS` / `OTTO_GRANT_PRO_TOKENS`）。

## 决定四：型号不在桶里 → 400 拒收

旧实现对表外型号"按已知最贵的算"。换成直接拒收，因为分桶之后没有一个正确的桶可扣：
扣哪个都是替用户做了一次他不知道的选择。顺带堵住拿官方 key 代理任意模型。

桶按**请求的**型号判，不按上游回报的：别名解析在上游那边，用户下单前就该知道
这次花的是哪个桶（实测 `deepseek-chat` 回报 `deepseek-v4-flash`，所以别名进 flash 桶）。

## 决定五：旧账本不改，只封口

`token_ledger` 的 micro-USD 旧行**一个字不动**（append-only 是硬规则），
新增 `tier` / `delta_tokens` 两列，新行走新列。余额投影换成新表 `token_balances`，
按 `(user_id, tier)` 分行——旧的 `token_wallets` 从此不再读写。

micro-USD 时代的三个函数（`ensure_wallet` / `charge_tokens` / `rebuild_wallet`）
直接 drop：数据留着，写入口收掉。留着它们等于留两套记账法，迟早有人调错那套。

**代价**：迁移这一刻，已有用户的美元余额不折算成 token，而是按新规则重新发一份赠额。
本仓库当下只有一个测试账号、四条测试账目，这个代价是零；真有存量用户时
这条得改成写一笔折算进账，而不是重发。
