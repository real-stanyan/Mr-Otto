# ADR-0206：超限图片先缩再入库，缩不动才拒

- 状态：已采纳
- 日期：2026-09-03
- issue：#882

## 背景

一张 11.7MB 的图片被 `AttachmentStore.save` 的 `IMAGE_MAX_BYTES`（10MB）当场拒掉，
界面回一句「图片超过 10MB 上限(实际 11.7MB)」。

拒收本身没错，错的是**把「这张图能不能用」当成了用户的问题**：图是能用的，只是大了一圈，
而缩它是一件机器该干的活。用户在 app 里没有下一步可做 —— 只能自己去别处压完再回来。

手机端早就不是这样了：`mobile/src/attach.ts` 的 `prepareForUpload` 一级一级降边长/画质，
每级量真实字节数，缩到能过为止。桌面这侧缺同一台机器。

## 决定

### 一、缩的目标定在 4MB，不是 10MB

入库成功 ≠ 送得到模型。Anthropic 单张图的 API 上限是 5MB，一张 8MB 的图今天「入库成功」，
发出去多半 400，而用户看到的是一条与图片无关的报错。既然要缩，就该缩到真能送到那一端的
数值；4MB 也正好是手机那条路早就在用的口径（`UPLOAD_LIMITS.maxBytes`）。

`IMAGE_MAX_BYTES`（10MB）**保留不动**：它是附件库自己的存储闸，现在只对「缩不动的」生效。

### 二、阶梯与手机端共用一份表

`IMAGE_FIT_LADDER` 搬进 `src/shared/imageFit.ts`，mobile 改成 import 它。
两侧各写一张表的话，同一张照片从手机传和从桌面传会得到不同画质，而这种差别没人会去查
—— 同 `src/shared/images.ts` 那张签名表的理由。

共用的只有**表**：手机上干活的是 `expo-image-manipulator`（按 uri 工作、顺带解 HEIC），
桌面上是 Electron 的 `nativeImage`（按字节工作），不是同一台机器，各自走各自的阶梯。

### 三、编解码器是注入的，纯逻辑留在 shared

`fitImage(data, cap, encode)` 是纯函数，`FitEncoder` 由调用方给。于是：
- `src/shared/imageFit.ts` 继续满足硬规则五（不碰 node builtin / electron，手机端 import 同一份）
- `src/main/attachmentIntake.ts` 继续是有单元测试的纯逻辑层
- 四种结局在 `tests/shared/imageFit.test.ts` 里全测得动，不需要 electron 运行时

`intakeFile` 的 `encode` 参数**必填、无默认值**：给个默认值等于「忘了接线时静默不缩」，
而那个失败模式是无症状的 —— 用户只会看到一条「图片太大」（同 ADR-0201 对
`FrameHandlerDeps.rateLimit` 的立场：忘接线该编译不过，而不是静默拆闸）。

### 四、结局是 kind 不是 ok+reason

`FitOutcome` 四种，调用方对每一种要做的事都不同：

| kind | 含义 | intakeFile 的动作 |
|---|---|---|
| `unchanged` | 本来就够小 | 原样入库，**一个字节不动** |
| `shrunk` | 缩过了 | 入库缩后的字节，名字改 `.jpg` |
| `undecodable` | 这个格式解不了 | 原样入库，能不能过交给 10MB 那道闸 |
| `stillTooBig` | 压到阶梯底仍超 | 拒，报最小那一版的真实字节数 |

「成功了吗」这个问法答不了「该拿它怎么办」（同 ADR-0193 / ADR-0200 的立场）。
特别是 `undecodable` 和 `stillTooBig`：前者是「这条路走不通，走老路」，后者是
「路走到头了」，混成一个布尔的话，一张 5MB 的 webp（今天能传）会跟着一起被拒。

### 五、没超上限的图一个字节都不动

`fitImage` 在 `data.byteLength <= cap` 时直接回 `unchanged`，编解码器一次都不调。
截图是 PNG，白转一道 JPEG 会把小字糊掉 —— 转码的代价只在「不缩就传不了」的那些图上付。

## 天花板（实测，不是漏做）

**`nativeImage.createFromBuffer` 只解 png / jpeg**：webp 与 gif 进去出来是一张
`isEmpty()` 的空图（Electron 43 本机验过）。所以这两种格式走 `undecodable`。

不去补这一半的理由：11.7MB 的 webp 基本不存在（webp 本身就是压缩格式），而一张动图
缩完只剩第一帧 —— 那时「传进去了」比「没传进去」更能骗到人。超 10MB 的 webp/gif 仍然拒，
但理由改成了「本机压不动这个格式——转存成 png/jpg 再传」，这句话用户能照着做。

第二条：JPEG 没有 alpha，带透明的 PNG 缩完透明处会变黑。同样只在「已经超上限」时才付。

## 为什么不是 sharp / jimp

app 里已经装着一整个 Chromium，为了缩张图再拖一个原生依赖进 DMG 不划算
（#820 记着 electron-builder 会把 `dependencies` 整个打进包）。

## 验证

`npm test` 之外，本机用真 Electron 跑过一遍端到端（`fitImage` + `nativeImageEncoder`）：

| 输入 | 结果 | 耗时 |
|---|---|---|
| 19.7MB PNG（6000px 照片） | shrunk → 0.27MB / 2048×1152 | 176ms |
| 15.3MB JPEG（同一张） | shrunk → 0.27MB | 166ms |
| 0.1MB webp | unchanged | 0ms |
| 0.19MB PNG | unchanged | 0ms |

## 没做的

- **工具产出的图**（`src/main/imageIntake.ts`）还是超限就跳过那一张。它同属一类问题，
  但不是这次的现象，也没有用户在等 —— 要做的时候把同一个 `nativeImageEncoder` 递进去即可。
- 手机那条路的 4MB 上限不动：它是线上/内存性质的闸，不是模型口径的。
