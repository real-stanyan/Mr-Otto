# ADR-0042：失败的 turn 不进模型上下文；重试原样重发附件

日期：2026-08-20
状态：已接受

## 背景

一次真实会话（`s-20260820012854`）的日志尾巴：

```
179 user_message  收到这个文件说一个字「收」就行（带图 + json）
180 turn_ended    aborted
185 user_message  收到这个文件说一个字「收」就行（带图 + json）   ← 重发
186 turn_ended    error 429
187 user_message  收到这个文件说一个字「收」就行（纯文本）        ← 重发
188 turn_ended    error 429
190 user_message  收到这个文件说一个字「收」就行（纯文本）        ← 重发，这次成功
191 assistant_message  收
```

同一句话在模型看到的上下文里出现了 **4 遍**。`deriveMessages` 只跳过 `turn_ended`
本身，不看它的 outcome —— 于是每失败一次、重发一次，上下文就多囤一份，而那几份
里没有一份对话是真的发生过：模型压根没读到过它们，一个字也没回。

第二处，同一段日志暴露的：187/190 是**纯文本**的，图和 json 没跟着回来。因为
`lib/retry.ts` 判定"原消息带附件 → 只把正文填回输入框，不重发"。可那两个附件
**就在 179/185 这两条事件里**：图片是内容寻址的 ref（`sha256:…`，附件库里那份没
动），文本文件是全文快照。原样再发一遍完全做得到，这个降级从一开始就是没必要的。

两件事咬在一起：不修 ①（重试不带附件）就不能做 ②（丢掉失败的那几条），否则
成功的那一条（190，纯文本）会连带把文件从上下文里整个抹掉。

## 决定

### 一、重试 = 原样重发，包括附件

`retryLastUserMessage` 从被重试的那条 `user_message` 事件上取回 `attachments`
（image ref 原样）和 `textFiles`（全文快照原样），拼成 `OutgoingAttachment[]`
重发。`lib/retry.ts` 的两档判断（`resend` / `fill`）随之删除 —— 它的两条理由都
不成立了：

- "原消息带附件，附件本体没法凭空重读" —— 能读：ref 和快照都在事件里；
- "输入框暂存区里有待发的附件，重发会把它们静默塞进去" —— 重发不再走
  `send()`（那条路读 `get().staged`），走一条**只吃显式附件**的路，暂存区碰不到它。

代价：图片的本体在附件库里被删过（手工清理 / 换机器）时，重发会失败在读附件那一步，
而不是像以前那样退化成填回输入框。这是可接受的：失败会说出来（turn 报错），
而"悄悄少发一个文件"不会。

### 二、什么也没产出的 user_message 不进模型投影

`deriveMessages` 跳过满足以下全部条件的 `user_message`：

1. 它之后、下一条 `turn_ended` 之前，没有任何 `assistant_message` 或 `tool_result`；
2. 那条 `turn_ended` 的 outcome 是 `error` 或 `aborted`。

没有后继 `turn_ended`（turn 还在跑、或日志被截断）就不跳 —— 判不出来的事不猜。
紧挨在它前面的 `image_described` 一并跳过：那句话的原文是"以下是**随后**消息附带
图片的解析"，随后的消息没了，它就是一句悬空的话。

`skill_invoked` 不跳：它是"给模型的说明书"，重试并不会重新注入 skill，留着它，
重发的那条才有说明书可依。

**日志一个字节不改。** 这是投影层的规则，不是日志层的：那几条 `user_message` 是
事实（用户确实按了发送），UI 照旧显示它们、回放照旧走它们，只是不喂给模型。
这正是"日志是唯一事实来源、投影可以有自己的取舍"的分工（ADR-0001）。

## 后果

- **旧日志的投影会变**：同一份日志，今天算出来的模型上下文比昨天短。硬规则要求的是
  "旧日志必须永远可重放"，不是"投影结果逐字节不变" —— 可重放性没有受影响。
  代价是老的 `deriveMessages` 快照测试要跟着更新（同一 PR 内，L2）。
- 失败重试不再是"每试一次贵一点"。一条带大文件的消息连失败三次，以前会把那份文件
  囤三遍，现在只留最后成功的那一份。
- `lib/retry.ts` 及其测试删除；`RetryPlan` 那两档语义不再存在，`TurnErrorState` 的
  按钮文案固定为「重试」（不再有"填回输入框"这一档）。

## 备选方案

- **只做 ①，不做 ②**：上下文照旧囤失败的那几份，只是重试不再掉附件。省事，但用户
  看到的那个症状（答一个"收"字要 13.8k 输入）一点没改善。
- **在日志层删掉失败的 user_message**：违反 append-only 硬规则，不考虑。
- **让压缩层去收拾**：`context_compacted` 确实会把老内容折成摘要，但它是按 token
  水位触发的事后清理，而这里的重复是**当场**就能判定的噪音 —— 能不产生的东西，
  不该等着别人来打扫。
