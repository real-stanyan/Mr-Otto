# 0064 微压缩是追加事件 + 投影替换

日期：2026-08-23 · Issue #179 · 相关：ADR-0062（自动压缩）、ADR-0058（架构门禁）、ADR-0072（型号目录/方言，原 0031）

参考：hermes-agent 的 micro-compaction（`agent/context_compressor.py`）

## 背景

自动压缩（ADR-0062）是"撑到阈值再一次性折叠全部历史"：省下来的空间是台阶式的，代价是一次贵调用 + 一次大幅失忆。
hermes 的 micro-compaction 是另一条路——每轮把最老的一段对话并进一条 running summary，上下文占用变成缓慢下降的锯齿而不是悬崖。

问题在于 hermes 的实现是**原地改写历史**：消息数组里那几条被摘要替换掉，原文没了。
本仓的 Hard rule 正好挡在这里：append-only 事件日志是唯一事实来源，任何投影必须可从日志推导。
照抄等于删日志。

## 决定

1. **微压缩 = 追加 `micro_compacted` 事件 + 投影替换**，一条原始事件都不动。事件带
   `{summary, coversUpTo, model, usage?}`；`deriveMessages` 遇到它时把被吸收的事件换成一条
   `[对话摘要]` assistant 消息，日志本身完整保留（replay/时间线仍看得到全部原文）。
2. **只认最新一条**（running summary）：新摘要包含旧摘要的内容，旧的自然作废。不做增量合并，
   合并逻辑的每一个 bug 都是静默失忆。
3. **`coversUpTo` 存 seq，不存下标**：下标是"这次 load 出来的数组里的第几个"，一旦 fork /
   过滤 / 少读一条就全盘错位；seq 是事件自己的身份，怎么切片都不变。
4. **吸收集合与用量估算共用 `absorbedIndexes`**（`src/session/microCompact.ts`）：投影和圆环
   同一把尺子，不能一个认为吸收了、另一个还在算原文。
5. **跑在 turn 锁外、按会话串行**：与分区分类/跟进建议/记忆审查同构的第四条 turn 后外挂
   （`microCompactAndAppend` / `enqueueMicroCompact`，`src/main/index.ts`）。串行是必需的——
   两次并发的 `microCompactOnce` 各自看不到对方还没落的 `micro_compacted`，会对同一个 exchange
   摘两次，后落的那条 running summary 丢掉先落那条的内容（= 静默失忆，正是本 ADR 要防的）。
6. **便宜模型通道抽成 `cheapAdapter`**（`src/main/cheapAdapter.ts`）：分区分类/跟进建议/微压缩
   三家共用一套规矩（目录查型号、没 key 不出门、thinking 显式关、带超时信号）。
   每跑一次现造——它带的 `AbortSignal.timeout` 从构造那刻走表，提到闭包外面 = 开机 30 秒后必超时。
7. **开关挂 `auto-compact.json.micro`，默认关**，主进程每次现读（设置页一关当场停）。
   默认关的理由写在开关旁边：每轮改写已发送的历史 = 模型的前缀缓存每轮失效。
8. **`src/loop` 不许 import `src/main`**，落成 `tests/architecture.test.ts` 的第四条断言
   （ADR-0058 的路子：架构约束跑在门禁里，错误信息带修法）。微压缩正好踩线——型号 id
   （`MICRO_MODEL = SECTION_MODEL`）和 adapter 都由 main 装配时注入，loop 只管"喂什么、收什么"。

## 理由

选"追加 + 投影"而不是"原地改写"，不只是守规矩：日志完整意味着摘要出错时**可回溯**——
用户在时间线上仍能看到被并进去的原文，而 hermes 那条路一旦摘错就永久性地错了。
代价是投影层复杂度（吸收集合 + 保护区 + 估算扣除），换的是"事实层永远不脏"。

裁定记录（实现期间做的、非默认的选择）：

- 摘要消息插在被吸收区**之后**：让所有被吸收的 user 原话先出现，模型读到的顺序才是
  "我问过这些 → 这段发生了什么"，倒过来会让摘要显得像在预告未来。
- `user_message` 永不吸收；`skill_invoked` / `image_described` / `subagent_briefed` 这些
  user-角色注入同样不吸收——它们是用户侧的事实，摘要模型没资格改写。
- 没有 assistant/tool 的 exchange 直接跳过（没有可压的东西）。
- 测试路径是 `tests/session/microCompact.test.ts` / `tests/loop/microCompact.test.ts`，
  不是 spec 写的 `engine.micro.test.ts`——逻辑不在 engine 里（它不在 turn 的闭环上）。

## 后果

- **每轮前缀缓存失效**：历史被改写了，缓存命中不了。这是默认关的唯一理由，也是开关说明的原话。
- **圆环在下一次账单前按估算扣除**：`contextEstimate` 只在最新 `micro_compacted` 落在计费锚点
  （最后一条带 `usage` 的事件）之后时扣减，且只扣两笔：① 这次新折进去的那段原文（上一条
  `coversUpTo` 之后、这一条之内）；② 锚点 prompt 里带着的上一条摘要（被新摘要顶掉）。
  `absorbedIndexes` 的集合是累计的，照它全扣就是每轮把更早已折的段再扣一遍——稳态几轮后读数
  探底到 0，连带 ADR-0062 的自动压缩再也不触发。估算与真实用量必然有偏差，靠下一次真账单自愈。
- **保真区名额不算空跑**：`fidelityBoundary`（投影和微压缩各一份，同一定义）数"最近 K 轮"时跳过
  ADR-0042 的空跑 user_message——它不进投影，模型没见过它；否则两次断线重试就把一轮真实对话挤出保真区。
- **注入面（残余风险，没堵死）**：摘要落盘后会作为一条 assistant 消息进模型**自己的投影**，
  不是旁路元数据——是模型之后每轮都会读到的"自己说过的话"。而摘要的原料里混着 `tool_result`
  的原文输出：一条精心构造的工具输出可以自带 `---` 把 prompt 围栏提前收口、伪造出「当前摘要：」
  之类的下一段。三道缓解、都不指望摘要模型识破：① `renderExchange` 把任何单独成行、trim 后
  等于 `---` 的内容行改写成 `— — —`（视觉仍是分隔线，但不再是可解析的围栏字面量），摘要回流进
  prompt 时同样过这道；② `EXCHANGE_MAX_CHARS` / `MICRO_SUMMARY_MAX_CHARS` 两级硬顶，围栏没守住
  时至少限住体积；③ `user_message` 原文永远不被吸收——摘要不是模型看到的唯一信源。
  **没堵死的部分**：摘要模型仍可能被工具输出的内容"说服"而改写摘要措辞本身（提示注入，不是围栏
  注入）。接受这个残余风险，理由是①③把它限制在"措辞被带偏"而不是"用户原话被替换"。
- **compact 之后迟到的旧摘要会被丢掉**：微压缩跑在 turn 锁外、compact 跑在 turn 里，所以一条
  微摘要可能排在 `context_compacted` 之后落盘，读的却是 compact 之前的日志。光看事件位置
  识别不出来，`latestMicroCompacted` 因此还要求 `coversUpTo > 那条 context_compacted 的 seq`——
  否则投影会把 compact 刚折叠掉的历史用微摘要的形式再注回去一遍（两份措辞不同的重复记忆）。
  代价：那一次微压缩的钱白花了，下一 turn 从零重新起跑。
- **暂缓（parked）**：手写 `coversUpTo` 的孤儿防护只覆盖可达形状——日志里若出现一个指向不存在
  seq 的 `coversUpTo`（只可能来自手工编辑或未来的日志迁移 bug），投影会退化成"什么都不吸收"，
  不会崩，但也没有显式告警。等真出现这种日志再补，现在加的检查没有触发路径。

## 推翻条件

服务端提供原生的"增量上下文压缩 + 缓存友好"能力时，本地微压缩退为兜底；
或前缀缓存的定价/命中模型变了（改写历史不再昂贵），默认关这一条就该翻过来。
