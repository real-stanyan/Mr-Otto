# 0070 CONTEXT.md 收产品域术语，协议与产品分两节

- 状态：已接受
- 日期：2026-08-23
- 相关：issue #98（Protocol gap）、ADR-0019（定义豁免）
- 层级：L1（CONTEXT.md 的定位是 Working agreement 那句「Look up domain-term definitions in CONTEXT.md」指向的对象），维护者本会话内明确同意

## 背景

#98 撞到的是：AGENTS.md 写着「域术语查 CONTEXT.md，遇到新词就加」，而 CONTEXT.md 当时
20 条全是 Gearbox 协议术语（handoff / lane / L1-L2 / frontier task…），好友系统、牌桌、
额度钱包这些跑了七八个班次的产品概念一条都没进过。那一班没有单方面加，也没有单方面
装没看见，立单等答案——这份 ADR 就是答案。

（记一笔：#98 立单之后又有几班往表里加过产品术语——终端面板、轨迹、MCP、工作区在场、
长期记忆、自动压缩、微压缩等十来条。所以事实上的实践早就是「收」，只是没有规则背书，
也没有分节。这份 ADR 追认并规范它。）

## 决定

1. **CONTEXT.md 收产品域术语**，它是本项目全部域词汇表，不是协议词汇表。
2. **分两节**：`## 协议术语（Gearbox）` 和 `## 产品 / 技术术语（Mr Otto）`，各自一张表。
3. **不追补历史**：新增术语即日按节归位；七八个班次欠下的旧词不在这一次一次性补齐。
   谁写到哪个概念、发现表里没有，就顺手补一条——这正是 AGENTS.md 那句「add new terms
   as they come up」的本意。

## 理由

- 选「收」而不是「改 AGENTS.md 的指向」：产品术语确实需要一个共享落点。牌桌档位、
  额度钱包这类词在 ADR 里各有出处，但 ADR 是决策记录不是词典——查一个词要先知道它是
  哪次决策引进的，那不叫词汇表。
- 选「分两节」而不是「混一张表」：两类词的读者不同。下一班找「什么是牌桌档位」，
  不该先滑过十几条讲 issue 角色的定义；反过来，开班检查协议时也不想在产品词里翻找。
- 选「不追补历史」：追补是一次性的大工程，而且补的人多半不是当初做那块的人，写出来
  的定义准确度存疑。让定义跟着写代码的人走，比让它跟着补表的人走可靠。

## 代价与推翻点

- 代价：表会变长，且两节之间偶尔有边界模糊的词（比如「工作区」既是产品概念也在协议
  的 trusted workspace 里出现）。边界模糊时按「读者是谁」归——协议节只放读规则的人
  要查的词。
- 推翻点：如果产品术语多到一张表也翻不动（经验阈值 ~50 条），那时该拆成
  `CONTEXT.md` + `docs/glossary/`，而不是继续往一份文件里堆。
