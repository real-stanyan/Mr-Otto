# ADR-0182：进门闸看的是「有没有登录记录」，不是「此刻登录着没有」

> 原为 ADR-0181 —— 合并前 re-fetch 发现 #722 的 ADR 先落了这个号，按 AGENTS.md 的规矩改成当时最大号 +1。

- 状态：已接受
- 日期：2026-08-29
- 关联：issue #723；推进 ADR-0028（身份两份数据）与 #95 的首登引导

## 背景

登录/注册原来只是「设置 → 账号」里的一张卡：不登录一样能用整个 app，卡片上还写着
「登录后可在多台设备同步配置（即将上线）」。产品要求把它翻过来 —— 登录成为进门的
前提，**没登录记录的人第一眼看到的就是这一屏**，看不到里面任何页面。

要做成闸门，得先回答一个问题：闸门读什么？直觉答案是 `account.signedIn`。这个答案
是错的，两处坑都不会报错、只会表现成"偶发的怪"：

1. **冷启动时它几乎必然是假的。** `AccountManager.restore()` 在 `src/main/index.ts`
   里是 fire-and-forget（`void manager.restore()`），而它内部调的是
   `auth.getUser()` —— 一次真实的网络往返。渲染层 `boot()` 里的 `getAccount()`
   基本都会跑在它前面，拿到的是恒为 `EMPTY` 的初值；真登录态由 `onAccountChanged`
   晚一个 RTT 才推来。照 `signedIn` 判定，**已登录用户每次开 app 都要先被闪一屏
   登录页**，网络越慢闪得越久。
2. **断网时它永远是假的。** `restore()` 拿不到 user 一律静默保持未登录（这是它
   刻意的设计，冷启动没登录不是异常）。照 `signedIn` 判定，一次断网就等于把人
   锁在自己的桌面软件外面 —— 而这软件里的会话、日志、文件全在本机。

## 决策

**闸门的判据是「这台机器上有没有登录记录」**，即 `userData/auth.json` 里存没存过
东西（`authStorage.hasAny()`）。用户原话就是这个词：「如果检测到用户没有登录记录，
先跳这个页面出来」。

这个判据同步、只读本地文件、离线可用，正好补上 `signedIn` 缺的那两块。

- main：`createAuthStorage` 多一个 `hasAny()`；`createSupabaseAuthClient` 把它作为
  `hasAuthRecord` 一起返回；新 IPC `CHANNELS.hasAuthRecord`。
- 渲染层：`authRecord` 进 `boot()` 的 `Promise.all`（和 `getAccount()` 并排取 ——
  它决定首屏画哪一屏，晚一拍就是"先闪一下再跳"）；`onAccountChanged` 跟着登录态
  起落（登录成功 = 从此有记录，登出 = 记录被 supabase 删掉）。
- 判定收在 `lib/identity.ts` 的 `needsSignIn(account, authRecord)` 一处，和
  `needsOnboarding` 做邻居 —— 两条都是「这个登录态该看哪一屏」。

### 闸门放在 App() 的返回值里，不是包在 main.tsx 外层

`boot()` 挂在 `App` 的 effect 上。把 `App` 换成 `{记录 ? <App/> : <SignInScreen/>}`
的话，没登录时 `App` 不挂载 → `boot()` 不跑 → 登录记录永远取不到 → 闸门把**所有人**
关在外面，包括已登录的。

所以 `App` 照常挂载、hook 照常跑，只是**返回值**换成 `<SignInScreen />`。这样下面
那棵树（侧栏 / 会话 / ⌘K 搜索框 / 各种 Dialog）一个都不挂 —— 没登录的人按 ⌘K
不会有个会话搜索框浮在登录卡上面。挂在 window 上的那几个快捷键监听还在，但它们
只改 store，UI 不在，改了也没人画。

早退位置卡在 `phase === "connecting"` 那条之后：boot 没回来之前 `authRecord` 还是
初值 `false`，那一拍判出来的"没登录"是假的（那一拍的画面本来也被 Splash 盖着）。

### 背景沿用启动画面那套

`SignInScreen` 用的是同一个 `DitherBackground`（shader 在 `shared/dither.ts`）。
这不只是"风格统一"：冷启动的顺序是 Splash 盖在上面淡出、这一屏在底下等着，两层
背景不是同一个东西的话，那 360ms 淡出会变成一次换皮的闪动。

顺带两处只有无边框窗口才会踩到的：整屏要铺 `.drag-region`（这一屏没有 `HEADER`，
不铺就连窗口都挪不动），以及错误必须画在这一屏上（密码错这类失败走 `store.error`，
卡片自己不显示它，不画 = 点了登录毫无反应）。

## 取舍

**接受：session 被服务端吊销、而 auth.json 还躺在本地的人仍然进得来。** 他进去之后
处处是未登录态 —— 账号页画的还是登录卡（所以 `SignInCard` 抽成独立组件，两个渲染点
共用同一张，而不是各写一份）。用「拦不住少数过期 session」换「断网不锁人 + 冷启动
不闪」，这笔账是故意这么算的。

推翻它的前提：如果哪天 app 的价值真的在服务端（订阅计费 #696、云端同步），
"本地有记录就放行"就不够了，那时该换成"离线宽限期 + 到期强制重验"，而不是回到
裸 `signedIn`——那两个坑不会因为需求变化而消失。

**接受：老用户升级后会撞上这道墙。** 这正是需求本身；没有做"稍后再说"的逃生门，
留了逃生门的闸不叫闸。

## e2e 怎么过这道闸

33 条既有用例都起一台全新的 app（临时 `HOME` + 新 `OTTO_PROFILE`），照定义就是
"没有登录记录"，会被整整齐齐挡在登录屏上。`launchOtto` 因此多一个
`authRecord`（**默认 true**），起 app 前把一条记录播进 `userData/auth.json` ——
既有用例零改动。

播的 key 刻意**不是** `sb-<ref>-auth-token`：写成 supabase 认得的形状，supabase-js
会拿着这把假 token 去刷新，e2e 就真的出网了，而这套用例的第一条规矩就是不碰网络
（`harness.ts` 顶部的三条隔离）。闸门读的是"文件里有没有东西"，与 key 叫什么无关，
所以一个 supabase 永远不会读的 key 既满足闸门、又不会把它叫醒。

`userData` 路径要在起 app **之前**算出来（`app.evaluate` 拿得到真值，但那时渲染层
可能已经问过 `hasAuthRecord` 了），算法照抄 main 里那句 `setPath`，目录名从
`profileDirName` 现取。算错了不会静默：记录播不进去 = 每条用例都撞在登录屏上，
当场全红。

## 被否掉的路

- **闸门读 `account.signedIn`** —— 冷启动闪屏 + 断网锁人，见上。
- **把 `restore()` 改成 await 进 boot** —— 断网时它要等到超时，等于把冷启动挂在
  网络上；启动画面的进度条会停在最后一格不动。
- **渲染层自己在 localStorage 记一笔「曾经登录过」** —— 不用改 main，但真相就有了
  第二份：手删 auth.json 的人照样放行，两份还会各自漂移。
- **e2e 用环境变量开后门（`OTTO_E2E_SIGNED_IN=1`）** —— 产品代码里多一条只有测试
  会走的分支，而且它绕过的正是要验的那道闸；播一条真的登录记录走的是同一条代码路径。
