# ADR-0129：中继按连接寻址，几台手机可以同时连着

- 状态：已接受
- 日期：2026-08-26
- 推翻：ADR-0095 的「一户一桌面一手机、同角色重连顶掉旧的」，以及 ADR-0128
  最后一节「明确不做：同时在线多台」
- 相关：ADR-0094（远程投影）、ADR-0100（在场信号）、ADR-0123（被挡下的握手）、
  ADR-0128（配对多台）

## 背景

ADR-0128 让一台桌面能**信任**多台手机，但同时只连得上一台：中继的槽位是
`{ desktop, mobile }` 两个，同角色重连顶掉旧的；桥的状态机（`self` / `sealer` /
`opener` / 去重基线）也只有一套。

于是「手机和 iPad 都开着」这种最普通的场景，表现是后开的把先开的顶下线，
而先开的那台**毫不知情** —— 它接着往一根用作废密钥封的管子里发。

## 决定

### 1. 中继按连接 id（cid）寻址

`{ desktop, mobile }` 两个槽换成 `Map<cid, Conn>`。每条连接分一个 cid，中继：

- `:cid <自己的>` —— 接上就告诉它自己是谁
- `:peer <对端的>` —— 对端每条连接各一条；对端上线/下线时两侧都通知
- `:gone <对端的>` —— 那条没了，把对应的密钥丢掉

发送方 POST 上带 `to=<cid>`（发给谁）和 `from=<自己的 cid>`（我是谁）。

**必须寻址，不能广播。** 每条连接有自己一套会话密钥，广播过去的帧在别人那儿
解不开；而 sealedStream 还带计数器校验 —— 收到别人的帧不是无害的噪音，是会被
判成异常的。

**中继仍然是盲管道。** cid 是它自己编的连接号，路由用的就是这个号，内容一个
字节都不碰。ADR-0095 当年担心「多设备会让中继不再是纯粹的盲管道」——
那句过虑了，路由和解析内容是两回事。

### 2. 收件人要知道发件人是谁：`event: <cid>` 行

桌面接着几台手机时，收到一帧却不知道是谁发的 = 不知道该用哪套密钥解。
所以中继在载荷前加一行 `event: <发件人 cid>`。

**这一行只发给声明了 `v=2` 的连接。** 老解析器是整块前缀匹配的，两行的事件
它会整条丢掉 —— 表现是「连上了却一帧都收不到」。所以不能由中继单方面改格式，
必须客户端自己声明认这套。共用的 `sse.ts` 也跟着从整块匹配改成按行解析。

`from` 是发件人自称的，**而且只用来路由**：收件人拿它挑用哪套密钥去解，
挑错就解不开，谁也占不到便宜；端到端身份始终只由握手签名决定。而这一切都在
同一个已鉴权的账号内部 —— 冒充别人的 cid 骗不到自己以外的人。

### 3. 桌面侧一条连接一套会话状态

`remoteBridge` 里原来那些模块级变量（`phase` / `self` / `sealer` / `opener` /
`lastEncoded` / `lastTimeline` / `lastPeerHello` / `usedPeerEphs`）全部搬进
`makePeer(cid)`，外层持 `Map<cid, Peer>`。ADR-0123 那套「取对端最新的 hello」
的逻辑一字未改，只是现在**每条连接各跑一份**。

推送分成两类，这是这份 ADR 里最容易搞错的一处：

| 推什么 | 给谁 | 为什么 |
|---|---|---|
| fleet | 广播 | 所有人共享的那份状态 |
| timeline | 只给订它的那一台 | 广播等于把 A 正在看的会话推到 B 的屏幕上 |
| notice / stats | 只给问的那一台 | 它们是"回答某一次操作"，不是共享状态 |

`watchedSession: string | null` 相应变成 `Map<cid, sessionId>`。

### 4. 手机侧刻意**不**对称：只维持一条

桌面接几台手机是常态；手机同时看两台电脑的舰队在界面上没有位置放 —— 一屏就是
一份 fleet。所以手机取**最近到场的那一条**，别的连接来的帧丢掉（并且说一声，
不静默：静默解不开会在日志里表现成"篡改/重放"，把排查带偏）。

### 5. 命令不加锁，谁先按谁算

两台手机同时批同一个审批：`UIApprover.resolve` 本来就是幂等的（"没有对应挂起项
= 重复点击/过期卡，忽略"），所以第一次生效、第二次是空操作。**这不是新加的保护，
是本来就有的**，多设备只是让它从"同一个人点两下"变成了"两个人各点一下"。

没有做「控制权」这种概念：谁能操作由**配对**决定，配对过的就是可信的，
再加一层"此刻谁说了算"只会让两台手机的用户互相等对方松手。

## 兼容

升级期三方（中继 / 桌面 / 手机）各自独立发版，所以两个方向都得留路：

- **老客户端 + 新中继**：裸 `:peer` 照发一条；POST 不带 `to` 时，对端只有一条
  就照旧转发。对端不止一条而 `to` 缺席时**丢弃** —— 猜一条发过去，收的那端解不开
  而发的那端以为成功了，是最难查的那种失败
- **新客户端 + 老中继**：收不到 `:cid`，于是 `addressed` 一直是 false，
  裸 `:peer` 仍然当在场信号用，`send` 也不带 `to` —— 退化成原来的单连接行为

## 代价

- 中继从两个槽变成一张表，多了 `MAX_CONNS_PER_USER = 16` 这个上限（挡内存，
  不是"不合法"）
- 一帧到桌面要先按 cid 查表。查不到就丢 —— 中继保证 `:peer` 排在对端任何一帧
  之前，到不了这个顺序说明对面不是通过中继来的
- 时间线投影按会话缓存了一次：两台手机看同一个会话时只算一遍

## 什么前提失效会推翻它

- 手机端出现「同时管几台电脑」的界面 —— 那时第 4 节的不对称要拿掉
- 出现真正需要互斥的操作（不是审批这种幂等的）—— 那时才需要"控制权"，
  而它应该建在事件日志上（谁在什么时候拿到了锁），不是建在连接上
