# ADR-0258：服务端部署接进发版，且「部署成功」的判据换成线上亲口报出的内容指纹

- 原为 ADR-0257（合并前 re-fetch **看见**了另一条 lane 的 0257，但那次检查只打印不拦，merge 照跑了 —— 是操作失误不是竞态。提交信息改不了，这一行是让旧引用还解析得出来的那半，ADR-0074）
- 状态：已接受
- 日期：2026-09-08
- 关联：issue #791（#790 的病根）；撞号处理见 ADR-0074；沿用 ADR-0215 把失败点往便宜处挪的顺序思路；三态纪律同 ADR-0243 / ADR-0251

## 背景

#790 的形状：ADR-0151/0129 给 relay 加了 host/guest 角色，**代码合了、门禁绿了、客户端发版了，线上 worker 还是旧的**——好友代理真机握手从没成功过。而桌面那侧唯一的信号是「云端无响应」，方向指向 VPS 宕机。

这套东西今天有三个部署目标，只有一个跟着发版走：

| 目标 | 怎么出门 |
|---|---|
| 桌面 app | `npm run release`（ADR-0215） |
| edge worker | `npm --prefix services/edge run deploy` —— 记得跑 |
| 云 runtime daemon | `RUNTIME_SSH=… npm run runtime:deploy` —— 记得跑 |

「记得跑」不是一条机制。2026-09-08 又踩了同一件事的另一面：`CS_PROTOCOL_VERSION` 从 12 进到 13，VPS 上那份 daemon 停在 12，于是一个从 main 构建的桌面连不上任何云会话——而在真机上试之前，没有任何一处会说这件事。

## 决策

### 1. 有害的偏差方向只有一个，把它按构造关掉

**客户端比服务端新**是唯一会坏事的方向：发出去的 app 去打一个对不上的服务端。反方向（服务端比客户端新）本来就该这样——线协议进位时服务端先到位是前提。

`npm run release` 正是客户端出门的那一刻。所以两个服务端的部署接进 release，**排在升版之前**：这一步失败时还没有版本提交、没有 tag、没有推过任何东西，收拾成本是零（同 ADR-0215 把失败点往便宜处挪）。

**edge 先于 runtime**：runtime 的 `EDGE_BASE` / `RELAY_BASE` 指着 edge，反过来是把新 daemon 接到旧网关上。

### 2. 缺凭据一律拒绝发版，不给跳过开关

`RUNTIME_SSH` 没设就停在第一步并说清楚怎么办。**没有 `--skip-deploy`**：一个用过一次的逃生门下次就是默认，而这条 issue 修的正是「忘了部署」。真遇上 Cloudflare 挂了那天，正确的动作是不发版。

### 3. 「部署成功」的判据不是退出码，是线上亲口报出的指纹

#790 坏的其实不是部署，是**证据层**：命令打印了成功，没有任何一处核过线上真的动了。所以两个部署脚本各加一段自检：

- **edge**：`wrangler deploy --var BUILD_STAMP:<戳>` 之后轮询 `/healthz`，直到它回出这一次的戳（90 秒）。
- **runtime**：戳由 esbuild `define` 进 bundle，daemon 起来时打进那行「就绪」；部署脚本从 journal 里把它读回来（60 秒）。**判据落在跑着的那个进程上不落在磁盘那个文件上**——rsync 成功而 systemd 起不来（或崩溃重启循环里跑的还是上一份）时，文件说的话是假的。

`就绪` 那行同时报 `CS_PROTOCOL_VERSION`：桌面连不上时第一个要对的就是它。

### 4. 指纹是**真实模块图的内容**，不是 git sha，也不是路径启发式

判据必须回答的问题是「此刻部署上去会不会改变什么」。

- **git sha 答错**：一次 app-only 的发版不该把 worker 判成陈旧。
- **按路径猜（`services/edge/**` 变了才算）也答错**：协议进位那种提交（只改 `src/shared/remote/cloudSession.ts`）一个字都没碰 `services/`——2026-09-08 那次就是这个形状。把路径集合放宽到 `src/**` 又会让指纹天天变，于是天天误报。

所以 `scripts/deploy-stamp.mjs` 用 esbuild 打一遍（`write: false`，只要 metafile），把**实际编译进去的每一个文件**按路径排序、逐个哈希内容再哈希一遍。改动任何一个进得了 bundle 的文件（含 `src/shared/` 里那些）指纹就变；改 README、改测试、改另一个服务，指纹不动。

**没有路径启发式，也就没有假警报**——而一条会误报的警报，用不了几次就没人看了。

同一份 `STAMP_TARGETS` 供部署与检查两侧共用：分家的话「部署时算的指纹」与「检查时算的指纹」永远对不上，而那个失败看起来像「线上是陈旧的」，成了一条永远喊狼来了的警报。

### 5. `npm run deploy:check` 回三态，`unknown` 两边都不并

- `current` 线上报的 = 本地现算的
- `stale` 线上报的是另一个指纹——确凿的「该部署了」
- `unknown` **问不出来**（没登录 / 没配 `RUNTIME_SSH` / 打不通 / 线上那份还没有报指纹的能力）

`unknown` 不许并进 `current`——「没有证据」被读成「没有问题」正是这条 issue 的病根。也不许并进 `stale`——那会让一次网络抖动看起来像一次漏掉的部署，喊几次狼来了之后这条检查就没人看了。退出码分别是 0 / 1 / 2。

### 6. 自检要核的地址从客户端那份常量现读

`edgeBaseUrl()` 从 `src/shared/edgeConfig.ts` 里正则抠出 `DEFAULT_EDGE_BASE_URL`，读不出来直接抛。在脚本里抄第二份的话，两边分家那天没有任何一处会报错——只会让自检对着一个空气地址报「通过」。

### 7. 否决：GitHub Actions 按路径自动部署

issue 里列的另一条候选。否掉的理由有三条，任何一条单独成立：

1. **盖不住 runtime**：那个要 ssh 进 VPS + `docker build`，Actions 够不着。两个部署目标只解决一个，另一个仍然靠「记得跑」——而 2026-09-08 那次栽的正是它。
2. **要往 repo secrets 放一把有部署权的 Cloudflare token**，而本仓的发版模型是单人本机（ADR-0215 明写「管线越短越不容易断」）。
3. **它解决的是无害的那个方向**：合进 main 就部署，关掉的是「服务端落后于仓库」，而真正会坏事的是「客户端比服务端新」——那一刻在 release 里，不在 merge 里。

## 代价 / 已知天花板

- **发版从此要 Cloudflare 登录 + `RUNTIME_SSH`**。换台机器发版要先把这两样准备好。这是有意的：那台机器不该能发出一个它没法同时更新服务端的版本。
- **每次发版都会重新部署两个服务端，哪怕它们已经是当前的**。`wrangler deploy` 与 rsync + `systemctl restart` 各自幂等，但 runtime 那次重启会把此刻连着的云会话房断一下（客户端会重连）。没有做「指纹一致就跳过」——那等于给这条链路加回一个判断，而判断错的那一次就是 #790。
- **`scripts/deploy-stamp.d.mts` 是手写的**：`.mjs` 那侧改了签名这里不会自动红，只有调用点会。两个导出、签名极稳，代价接受。
- **edge 的自检信的是 `/healthz`**：如果那个地址前面挂着缓存或另一个 worker，自检会一直读到旧戳并超时——它会说「没被证实」而不是「失败」，措辞上分开了，但它确实分不出「传播还没到」与「部署到了别处」。
- **runtime 的自检读的是 journal**，所以要 `sudo journalctl` 可用（那台机器 sudo 免密）。换一台不给 sudo 的机器要另找出口。
- **协议版本本身没有被比对**。`就绪` 那行报了 `CS_PROTOCOL_VERSION`，但 `deploy:check` 只比指纹——指纹不同必然包含协议不同，所以不是漏，只是错误信息里不会直接说「协议对不上」。
- **`deploy:check` 没进门禁**。它要打网络、要 SSH 凭据，进 CI 只会变成一条常年红的检查。它是发版前和排查时手跑的那一条。
