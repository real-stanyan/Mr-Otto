# ADR-0169：代理的反馈面 —— 撤销要说出口，「正在被用」要当场看得见

- 状态：已接受
- 日期：2026-08-28
- 相关：issue #680（本决策）、ADR-0151（好友代理总体）、ADR-0165（取消不能靠沉默表达）、ADR-0168（断线的那条仍在列表里）

## 背景

好友代理功能上已经通了（#657 / #670 / #672 / #674 / #676）。剩下的一批问题不是「不能用」，
而是**用起来看不见、说不清**：

- A 授出去之后，「有没有人连着」「此刻是不是正在用我的凭证」在界面上完全没有痕迹，
  只能事后打开对话框翻审计账；
- A 撤销之后，B 那边看到的是「工具表空了 + 连接断了」——和「A 关机了」一模一样；
- 改一次白名单要重发一张邀请码，且勾选表从零开始，原来勾过的得一个不漏地重勾；
- 登出之后借来的刀还留在工具表里。

这些单看都是打磨，合起来是同一件事：**代理是「别人用我的凭证」，而它的反馈面
一直是单向的**——B 侧在 #676 补齐了推送与状态，A 侧一直只有一份要手动去翻的台账。

## 决策

### 1. 撤销是一帧要真发出去的话（`proxy_revoked`）

新增第五种代理帧：

```ts
export interface ProxyRevokedFrame {
  kind: "proxy_revoked";
  v: typeof PROXY_FRAME_VERSION;
  reason: string;   // 必填，解码时缺了整帧丢掉
}
```

`proxyRevoke` 由三步变四步：**清存储 → 推空授权清单 → 推撤销帧 → 关房间**。

为什么不能省掉第三步、靠前两步推断：`servers: []` + 连接断开，与「A 把电脑合上了」
在 B 那边**产生的观测完全相同**。而这两件事该做的动作相反——一个是等，
一个是别等了、要用得重走一次邀请码。这与 ADR-0165 是同一条原则的第二次应用：
**取消/撤销这类「A 那边的决定」不能靠沉默表达**，因为沉默已经被「掉线」占用了。

`reason` 必填不是形式：没有它这一帧退化成一个 bit，和静默断线的信息量一样。

发不出去（对面此刻不在线）就算了，只记一条日志——这是尽力而为的一句话，
不是必达的协议保证。对面下次连回来握不上手（pin 已清），会停在「没连上」，
比现在好，但不如收到帧那么明确。

### 2. 被撤销的那条，标记而不是删除

`ProxyBorrow` 加一个 `revokedReason?: string`。有值时：

- **不再自动重连**：`usableBorrows`（`resume()` 用的那份）把它排除掉。
  留着只会握手失败然后无限重试。
- **仍然在界面上**：`allBorrows`（`borrowStatus()` 用的那份）包含它，配着那句理由。

直接删掉的话，用户看到的是「那条不见了」——又一次和「对方今天没开机」撞脸。
这是 ADR-0168「断线的那条仍然留在列表里」的同一条道理再走一遍：
**列表里的缺席从来不是一句话，它是好几句话的公共外观。**

重新接受一张邀请码时 `setBorrow` 整份替换该条，撤销标记跟着没——不必单独清。

### 3. A 侧的实况表：授权台账是底本，活着的通道往上贴状态

新增 `ProxyManager.hostStatus()`，与 `borrowStatus()` 严格对称，
四个字段各自对应用户不同的下一步：

| 字段 | 说的是 |
|---|---|
| `connected` | 好友此刻握上手没有 |
| `inflight` | **此刻正在跑几笔** —— >0 = 正在用我的凭证动我的账号 |
| `lastCallAt` | 最近一笔（含被拒的），从审计账现取 |

底本是 `grants` 而不是「活着的通道」：反过来的话，好友没上线的那些授权在界面上
就不存在了，而「授出去了但对方没连」恰恰是 A 最该看见的一格。

`inflight` 需要一个新的信号源：审计是在**结果出来之后**才写的，
所以 0→1 那一刻没有任何事件。`proxyHost` 因此多一个 `onActivity` 钩子
（起跑与收尾各喊一次）+ 一个 `inflight()` 读数，返回值从一个退订函数改成
`{ stop, inflight }`。

推送口径也随之收成一份：`proxyChanged` 从「B 侧的借来清单」改成
**全景快照 `{ borrows, hosts }`**，拉取端 `proxyBorrows()` 相应改名 `proxyStatus()`。
同一台机器既借进来也借出去，那是同一件事的两个方向（ADR-0168 已经把台账合成一本，
这里把视图也合成一份）。

### 4. 改授权不是重新配一次对（`proxyUpdateGrant`）

新增一条不经过邀请码的路径：写白名单 + 当场推一帧新的授权清单。

`proxyCreateInvite` 会换一把一次性 secret、重开房间、逼对方再接受一遍——
那是**配对**。而「把 read 改成 read+write」根本不是配对，它只是改一个已经存在的
关系的参数。把两者混在一条路径里的代价是：每次调权限都要走一遍社交动作。

配套地，对话框打开时用 `selectionFromAllow` 把现有授权预勾上。这个函数在 #657
就写好并测过了，一直没接线——不预填的话，改授权要求用户把原来勾过的全部重勾一遍，
**漏一个就是静默降权**，而界面不会提示他漏了。

### 5. 登出 = 断开所有代理通道

安全上本来就是失败关闭的（A 侧 `friendUids()` 回 `null` 一律拒），
所以这一条不是补洞，是补一致性：账号都换了，借来的那些刀不该还留在工具表里，
等模型调了才报错。台账不动，下次登录 `resume()` 照常连回来。

顺带补一句 `sendToolDefs()`：它原本只挂在 `mcpHub.onChange` 上，
而代理来的服务不经 `mcpHub`——不补的话，好友刚授的刀要等下一个 turn
重算工具表时才在界面上出现。

## 后果

- 代理帧多一种。解码器对未知 `kind` 一律回 `null`，所以老版本的 B 收到撤销帧
  只会丢掉它，退化成本 ADR 之前的行为——向后兼容。
- `proxyChanged` 的载荷形状变了（数组 → 对象）。这是进程内的 IPC 契约，
  没有跨版本兼容要求。
- `proxyHost` 的返回值形状变了（函数 → 对象），调用点只有协调器一处。
- `hostStatus()` 每次现算，`lastCallAt` 走一次 `audits.find`。审计上限 500 条
  （AUDIT_CAP），线性扫描的代价可以忽略；而推送频率被 #674 的令牌桶挡在
  30 笔/分钟以内。

## 没做什么

- **邀请死角**：A 发码后退出 app，B 才接受 → A 重启时因为没有 pin 而跳过这个好友，
  房间再也不开，两边都不显示原因。这是一个真死锁，另开 issue。
- **`sessionMcp` 的可见范围**：借来的刀此刻所有会话（含子会话）都看得到。
  那是接线时的默认结果，不是决定过的，等产品判断。
- **逐次审批**：白名单内依然是全自动的（ADR-0151 的原始决策）。本 ADR 只让
  「已经发生/正在发生」看得见，没有增加一道问人的闸。
