# 0051 内置子智能体住代码里，改它就是 materialize

日期：2026-08-21
状态：已接受

## 背景

装完 app、什么都没配的用户，子智能体清单是空的。空清单还有一个连带后果：`task`
工具压根不挂（`agent.ts` 里"挂没挂一次定终身"那段），于是模型连"可以派活"这件事
都不知道。要用这个特性，用户得先自己手写一份带 YAML frontmatter 的 `.md`——
一个先要读文档才迈得出第一步的特性，等于没有。

## 决定

随 app 发两份内置定义：`general-purpose`（除 `task` 外全部工具）和 `Explore`
（只读那 5 把）。

### 1. 住代码里，不是首次启动往磁盘写

`src/main/builtinSubagents.ts` 两份常量，`withBuiltins` 在列清单时并进去。

被否掉的做法是"首次启动往 `~/.otter/agents` 写两个文件"。它有两个都不能接受的
后果：写出去的那一刻它们就是用户的文件，以后升级改了正文或工具集，装过老版本的
人永远跟不上；而用户删掉它们之后，下次启动又会凭空长回来——那看着就是个 bug。

### 2. 磁盘同名定义盖住它

跟"工作区盖用户"同一条覆盖规则，不分大小写（落地的是 macOS 文件名，APFS 大小写
不敏感）。

合并**不写进 `scanSubagents`**：那个函数还被 `subagentSlotTaken` 用来查"落点这一层
占了没"。内置混进去的话，新建 `general-purpose` 会被拦掉，下面第 4 条那条路从第一步
就走不通。

### 3. 新增 `approval: "inherit"` —— 跟父会话此刻那一档走

内置的 `general-purpose` 带 `bash` 和 `write_file`，而子 agent 没人盯着屏幕。
三档现有的都不对：`deny` 让它名不副实（一个动不了手的"全能"agent），`auto` 是
背着用户放权，`ask` 在用户已经开了免审批时又多此一举。

新加一档，派活那一刻现问父会话的 `approvalMode`。

**不复用 `ask` 来表达这件事**：那等于让所有已有的 `approval: ask` 定义在用户开
bypass 时静默变成放行，而写 `ask` 的人意思就是问我。这是改别人已经写下的定义的
语义，不是加一个特性。

老文件解析不到 `inherit`，默认仍是 `deny`，向后兼容。

`deny` 不受影响：它换掉的是整条审批链（`denyingApprover`），到不了拨模式那一步。

### 4. 改内置 = materialize 成真文件

那一行的模型选择器一动，或者点「改成我自己的一份」，就在当前作用域的可写根里写出
一份同名 `.md`（内置那份的完整内容 + 选的型号），从此它是用户自己的定义、盖住内置
那份。

被否掉的是"单独存一份模型覆盖偏好"。它更省事，代价是内置这一层从此有两种状态：
代码里那份，加一张谁也推导不出来的覆盖表——而那张表不在事件日志里，与"任何投影
必须可从日志推导"直接冲突。materialize 之后，磁盘上那份 `.md` 是自解释的。

## 接受的代价

- **`task` 工具从此永远挂着。** 清单不再可能为空，于是每个会话都带着 `task` 的
  def，常驻上下文。以前不配 subagent 的用户，模型没有派活这个选项；现在有了。
  这是要的效果，但它不是纯增量——不想要的人只能靠不派活来回避，没有关掉它的开关。
- **materialize 之后跟不上升级。** 用户只是想换个模型，代价却是整份定义从此冻结在
  这一版：以后内置的正文或工具集改了，他这份不会跟着变，而界面上只在动手那一刻
  说了一次。
- **一个下拉框会在磁盘上留下文件。** 换模型这个动作的副作用比它看上去重。选择它
  是因为另一条路（覆盖表）要在日志之外再开一处状态。
- **`inherit` 对用户的定义也开放。** 原计划只给内置用、界面上不给编，但那样内置行
  展开时审批那一组会一个都不选中，看着像坏了。列出来之后就没道理不让选——于是
  用户可以写出一个"我开免审批它就免审批"的子 agent，这条链比 `ask` 长一节。
