# ADR-0187：本机数据按登录账号分抽屉，换号靠重启

> 原为 ADR-0186 —— 开分支时 0186 还空着，合并前发现 PR #751（issue #750）先落在了这个号上。
> 编号在合并时 claim（项目 ADR-0074）；提交信息改不了，所以留这一行让旧引用还能解析。

日期：2026-08-29
状态：已接受
相关：issue #749；推进 ADR-0182 / 0183（进门闸），沿用 ADR-0057（`.otter` → `.mr-otto`）、ADR-0116（`root.txt` 自描述目录）

## 背景

在同一台 Mac、同一个 macOS 用户下退出账号 1、登录账号 2，账号 2 看到的是账号 1 的会话、
记忆、审批记忆，并且能**直接使用**账号 1 的模型 API key 和已授权的 MCP OAuth 令牌。

这不是"同步过去的"—— 本地会话与记忆没有任何云同步（服务端只有显式的「分享会话」会上传，
`sessionShareApi.ts`）。是**从来没分开过**：

- `AccountManager.signOut()` 只做两件事：调 supabase `auth.signOut()`、把内存里的 `account`
  置空。跟着登录态起落的全是**服务端**子系统（friends 订阅、远程传输、好友代理通道），
  本地磁盘一个字节都不动。
- 所有本地存储的路径里没有一处出现过 uid：`userData` 只按 `OTTO_PROFILE` 分，
  `~/.mr-otto/` 连 `OTTO_PROFILE` 都不分（一台机器一份），`events` 表没有 owner 列，
  会话列表也没有任何按人过滤。

实际泄漏面（本机核对过）：`sessions.db`、`attachments/`、`memories/`、`keys.json`、
`mcp-auth.json`、`mcp.json`、`permissions.json` / `execPolicy.json`、`proxy-store.json`、
`remote-identity.bin`、`skills/`、`agents/`、`checkpoints/` 以及各项设置。
这些文件是 0600 —— 挡的是**别的 macOS 用户**，挡不住同一个 macOS 用户下的第二个 Mr Otto 账号。

顺带记一条：`docs/dev-two-accounts.md` 那套 `OTTO_PROFILE` 双开验收同样漏 `~/.mr-otto/`
这一层（文档里只提了 mcp.json 共用），记忆和 MCP 令牌两个实例一直是共享的。

## 决定

### 一、每个账号一个抽屉；auth.json 留在门口

```
~/Library/Application Support/mr-otto/
  auth.json                 ← 留在根：它是 uid 的来源
  updates/                  ← OTA 下载缓存，机器级
  accounts/
    <sha256(uid) 前16位>/    ← 抽屉
      who.txt               ← 名片
      sessions.db  keys.json  attachments/  permissions.json  proxy-store.json …

~/.mr-otto/
  accounts/
    <同一个抽屉名>/
      who.txt
      memories/  mcp.json  mcp-auth.json  skills/  agents/  checkpoints/
```

工作区级的 `<工程>/.mr-otto/`（`configDir(workspace)`）**不动** —— 它跟着项目走，不跟着人走。
别家产品的安装位（`~/.claude/skills`、`~/.codex/skills`）也不动，那是机器级的事实。

### 二、uid 在开机第一行就取得到，不必拆两阶段装配

看起来有个先有鸡先有蛋：`app.setPath("userData")` 跑在 `ready` 之前，那时 `AccountManager`
还没造出来，uid 似乎要等 `restore()` 的网络往返。

不必。supabase 落在 `auth.json` 里的那份 session **自带 `user.id`** —— 和进门闸（ADR-0183）
读的是同一个文件，同样同步、同样离线答得出。于是 `sessionIdentity()` 在 `whenReady` 之前
就能定下这次开机打开谁的抽屉，三千行的装配根照旧一次成型。

判据的形状扫描（跳过 `*-code-verifier`、`access_token` 非空字符串）抽成
`authStorage.ts` 的 `sessionValues`，`hasSession` 和 `sessionIdentity` 共用一份 ——
这个判断已经错过一次（#729），不能有第二份。

### 三、换号靠重启，不做热切换

抽屉在装配那一刻钉死（二十来处 store 各持一条绝对路径），登录态却是运行时才变的。
`AccountManager.onChange` 里发现"现在登录的人 ≠ 开机时打开的抽屉"就
`app.relaunch(); app.quit()`。

**否决的两条路**：
- 把二十来处路径改成 getter —— 每个 store 都要能中途换根，改动面大且每一处都是新的出错点。
- 在装配根中间拆一刀，分"只有登录 IPC"和"账号相关的全部"两阶段 —— 三千行的函数里
  划一条正确的界线，比这次修的 bug 本身更容易出错。

重启换得**干净**：没有半初始化状态，没有"这个 store 换了那个没换"的可能。
代价是登录/换号时闪一次重启，接受。

三条边界：
- 判据 `needsRelaunch(bootUid, signedInUid)` 是纯函数，`signedInUid === null` 恒为 false ——
  **登出不重启**：进门闸自己会挡，同号登出再登入不必空转一趟。
- 重启**先于** `send(accountChanged)` 且直接 return：渲染层不该在上一个账号的数据上多活一帧。
  进门闸的 `authRecord` 只在开机问一次，收不到 `accountChanged` 的渲染层会一直停在登录屏上。
- 一次进程只重启一次（`relaunching` 标志）。判据本身是收敛的，这是防死循环的兜底。

`AccountInfo` 因此多一个 `id` 字段。取不到（supabase user 没有 id）就留空串 ——
空串 ≠ 任何真 uid，于是判不出换号、不会误重启，退化成本次修复之前的行为。

### 四、存量归给当前登录的账号

第一次实施隔离时，散在根下的存量整体划给此刻登录的那个人（维护者裁决，issue #749）。
理由：它本来就大概率是他的，而留在共享层等于把泄漏窗口一直开着。没有登录记录时不搬 ——
那时还不知道该划给谁。

`adoptLegacyData` 两条守则：**目标已存在就不搬**（同时兜住"搬过一次不重复搬"和
"`_signed-out` 那格里的空壳 sessions.db 绝不能盖掉真的那份"）；**单条失败吞掉**
（权限、跨设备 rename），搬不动的留在原地，不该因此拦着启动 —— 同 `configDir` 的取舍。

### 五、`~/.mr-otto/` 整个搬，用 who.txt 抵掉不可读的代价

考虑过把 `skills/` `agents/` 留在机器级（手写的东西，不含凭据，路径还是文档里写给人看的）。
否决：那要求**每加一个新文件都重新判一次"它算不算私密"**，而这个 bug 本身就是没人做过
那次判断的结果。一条规则不需要维护一张名单。

不可读的代价用 `who.txt` 抵掉（同 `memoryStore` 的 `root.txt`：目录自描述，不建中心索引）：
每个抽屉里一张名片，写着邮箱和 uid，手编 mcp.json 的人 grep 一遍就找到自己那间。

配套：界面上凡是告诉用户"文件落在哪 / 去哪手改"的地方，改成从主进程现取
（`CHANNELS.configRoot` → store 的 `configRoot`），不再写死 `~/.mr-otto/...`。
写死的话，照着提示去手改的用户会编辑一个**对本账号完全不生效**的文件 —— 这比显示得难看严重得多。

## 后果

| 事情 | 之前 | 之后 |
|---|---|---|
| 换号后看到的会话 / 记忆 | 上一个账号的 | 自己的（新账号从空开始） |
| 换号后能用的 API key / MCP 令牌 | 上一个账号的 | 自己的 |
| 登录、换号 | 无感 | 闪一次重启 |
| 手编 `~/.mr-otto/mcp.json` | 直接改 | 改 `accounts/<抽屉>/mcp.json`，路径由界面现给 |
| `OTTO_PROFILE` 双开 | 记忆 / MCP 令牌共用 | 各账号各一份（抽屉在 profile 之内又切了一刀） |

**仍然不隔离的**：同一个 macOS 用户下，第二个账号的抽屉在文件系统上是可读的（0600 挡的是
别的 OS 用户）。这道防线本来就在 OS 那一层，本 ADR 不改变它 —— 它解决的是"app 自己把
上一个账号的东西端到你面前"，不是"防止有人拿 Finder 去翻"。真要防后者，得上钥匙串/加密，
不在本次范围。

**天花板**：`updates/` 和别家产品的 skill 安装位仍是机器级，这是有意的。

## 备选与否决

- **在 events 表加 owner 列 + 列表过滤**：append-only schema 变更必须向后兼容（Hard rule），
  存量行的归属无从判断；而且 `keys.json` / `mcp-auth.json` 这类单文件仍要另想办法 ——
  等于两套机制。
- **不隔离，改成明说**（把"本机数据属于这台机器"定成产品语义，加一个"清空本机数据"按钮）：
  工作量最小，但它把用户报的这个现象定义成了设计。维护者选了隔离。
- **抽屉名用 uid 原文而不是哈希**：可读，但 uid 是 36 字符的 UUID，且把它铺进路径没有
  换来任何东西 —— 它在 `auth.json` 里本来就是明文，哈希不是为了保密，是为了长度与字符集可控。
