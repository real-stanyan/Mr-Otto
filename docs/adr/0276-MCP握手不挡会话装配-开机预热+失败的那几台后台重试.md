# ADR-0276：MCP 握手不挡会话装配——开机预热，失败的那几台后台重试

- 状态：已接受
- 日期：2026-09-09
- 关联：#1187（本决定）/ ADR-0054（工具表挂载一次定终身）/ #722（设置页那两半说同一句没信息量的话）/ `tests/main/mcpHub.test.ts` 的「ready() 分「这次要等」和「后台重试」」

## 背景

左侧栏点一条「建过、跑过、有记录」的本地会话，要卡一下才进去；第二次点同一条秒开。判据是 `agents.has(sessionId)`（`src/main/index.ts`）——不在内存里就现场重建，而重建这条路上有一句 `await mcpHub.ready()`。

`ready()` 过去的语义是「把所有 enabled 的 server 连一遍，全部落定后 resolve，封顶 10 秒」，且 **MCP 连接只由它发起**（开机不连，见 `listMcpServers` 那段注释）。两条合起来是三笔账：

1. app 起来之后**第一次点会话的那个人替所有人付握手**——而握手是网络往返，跟他点的那条会话有多大毫无关系。
2. `connectOne` 只跳过 `connected`，于是 `failed` / `needs-auth` 的那几台**每次冷 resume 重试一遍并等到底**。一台没授权的远程 server 就是每次点会话多等几百毫秒，一台真挂了的就是 10 秒。
3. 这两笔都是**静默**的：界面上只是"卡一下"，没有任何东西说它在等谁。

真机实测（playwright-electron 起真 app，塞一份真 sessions.db 的拷贝，隔离 profile，`resumeSession` 这一次 IPC 往返）：

| | 2555 条事件那条 | 7 条事件那条 |
|---|---|---|
| 没配 MCP | 39ms | 1ms |
| 3 台远程 HTTP MCP（未授权） | 292ms | **879ms** |

7 条事件的会话也要 879ms —— 这一段跟日志大小无关，就是网络。

## 决定

**1. `ready()` 的分工判据只有一条：这台问过了没有。**

- 没问过（`Entry.triedAt` 缺席）→ **这次装配等它**。它的答案决定这个会话有没有这些工具，而工具表挂载一次定终身（ADR-0054）；不等就等于替用户决定"这条会话没有这几台的刀"。
- 问过了、没连上 → **不等**，后台重试。上一次已经给出过答案，这次装配为它多付的那趟往返是纯亏。
- `needs-auth` → **一次都不后台重试**。那是"要人去点那颗授权按钮"，拿同一份凭据再打一遍答案不会变。真要重来的两条路（设置页每行的重连、`authorize` 完的自动重连）都直接调 `connectOne`，一次都不看下面那道冷却窗。
- 已连上 → `connectOne` 自己跳过（原有行为）。

**2. 后台重试带 `RETRY_COOLDOWN_MS = 30_000` 的冷却窗。** 重试本身没错（用户可能刚把 npx 装上、刚把网连回来），错的是频率：`ready()` 挂在每次会话装配上，而"点开一条不在内存里的会话"是高频动作——不设窗，连着点五条会话就是对同一台挂了的 server 打五次网络。

**3. 开机预热：装配末尾 `void mcpHub.ready()`。** 把"真正要等的那一次"挪到没人盯着的时刻，于是点击路径上通常一台都不用等。不 await（装配期也没人能 await），预热失败/超时都不影响开机。排在 `mcpHub.onChange` 接线**之后**——预热每连上一台都会 `emit()`，接线在后面的话这几发推送没人收，设置页要等下一次状态变化才对得上。

**4. 「同一个 id 不并发连两次」从单飞的 `readying` 换成按 id 的 `inflight` 表。** 这道闸原来是 `ready()` 整体单飞顺带提供的（测试「超时之后再调 ready() 不会对同一台还在连接中的 server 重复发起连接」）；重试挪到后台之后那个前提没了——后台那次还挂着时，下一次 `ready()` 会走到同一个 id 上。挡不住的后果不是慢，是 stdio 下的两个孤儿子进程。所以闸落在 id 上，不落在"这一轮 ready 等不等"上；`readying` 随之删掉，没有第二份事实。

判据分开写的一处要紧细节：`triedAt === undefined` 与"此刻正在连"**不是**一回事。「上一次 ready() 超时返回、而那次连接还挂着」同时满足两者——那时 `attempt()` 把**同一个** promise 交回来，这次装配接着等它，而不是对同一个 id 再发起一次连接。

## 效果（同一套测法，改动后）

| | 2555 条 | 7 条 |
|---|---|---|
| 3 台远程 MCP（未授权），改动后 cold `resumeSession` | 11–57ms | 1ms |

点击到 DOM 稳定：小会话 125ms、2555 条 539ms、2355 条 602ms —— 与**没配 MCP 时**改动前的基线（127 / 534 / 579ms）一致。MCP 这段成本从点击路径上消失了。

## 否决的做法

- **把 `ready()` 从装配路径上整个拿掉**（工具表等不等握手都装配）：那会让"这条会话有没有 MCP 工具"变成一次赛跑的结果——同一台机器上点两次同一条会话可以得到两张不同的工具表，而工具表挂载一次定终身，用户看不出差别在哪。
- **缩短 `READY_TIMEOUT_MS`**：治的是最坏情况的长度，治不了"每次都要等一趟"这件事本身；而把 10 秒调小会真的砍掉一次正常但慢的握手。
- **给 `ready()` 加一个 `force`/`retryAll` 参数让设置页那条路照旧全量重试**：多一个只有一个调用点用得上的旗标，而它想要的（每台的状态是真的、不是"还没试过"）预热之后本来就有了；失败那台要立刻重来，每行的重连按钮一直都在。

## 已知代价

1. **失败的那台在冷却窗内不会因为"打开设置页"被重试**（那条路也走 `ready()`）。换来的是状态本身已经是真的（预热跑过），且每行有重连按钮。
2. **开机就会对配置里的每台 server 发起连接**，哪怕这次开 app 根本不开会话。这不是新增的出网面（同一批地址、同一份凭据、以前也会在第一条会话时连），只是时机提前了。
3. **`needs-auth` 的那台再也不会自己转正**——必须点授权（或重连）。这正是它的语义，但过去那种"每次冷 resume 白试一遍"至少在 token 恰好被别的路径刷新过时能碰巧连上；现在不会了。
4. **点击路径上仍然可能等**：预热那一发还在飞的时候点会话，照旧要等（那台仍然是"没问过"）。这是有意的——那一次的答案确实还没有。
5. 剩下那半没修：整条时间线一次全画（没有虚拟化），2555 条事件首渲约 400–500ms。另开 issue。
