# ADR-0109：后台任务在 UI 上是一等公民——起止都落事件，回注消息记住自己驮的是哪几个

- 状态：已接受
- 日期：2026-08-26
- 相关：issue #452（本次）、issue #389（后台回注）、issue #428 / ADR-0103（回注消息的身份）、ADR-0073（不 mid-splice）、issue #395（前台自动转后台）、issue #454（要不要停止自动回注，待定）

## 背景

维护者的两句话，是这个决定的全部由来：

> 「以现在的 UI，我都不知道还有后台任务这个东西」
>
> 「自动回复这个功能，用户体验不是很好，因为用户会觉得自己莫名其妙发一条消息，但其实自己没有发」

查下来两句话指的是两个独立的洞：

1. **跑着的任务在 UI 上完全不存在。** `BackgroundTasks.live()` 的注释写着「UI/调试用」，
   但全仓零调用；ShellBridge 里一个 background 字段都没有。任务在跑的那几分钟，
   界面上没有任何痕迹。
2. **回注消息还长得像用户气泡。** ADR-0103 已经把身份记在事件上（`origin: "background"`），
   渲染层分得清，但只拿它做了「静音气泡 + 一行小标签」——形状、对齐、位置全没变。
   标签是弱药：气泡还在右边、还是那个圆角，扫一眼仍然是「我发的」。

第 1 条比预想的重。从真实日志里捞的一串（`background_task_completed`）：

| id | 命令 | exit |
|---|---|---|
| bg-1 | `npm install three @react-three/fiber …` | 127 |
| bg-2 | 同上，钉版本号重试 | 127 |
| bg-3 | 补 `PATH` 后再装 | 1 |
| bg-4 | `npm run build` | 0 |
| bg-5 | `npx vercel@latest --prod --yes` | 0 |

五个全是**前台命令跑满 30 秒自动转的**（issue #395），用户一个都没点过。
所以这块 UI 治的不是「我起的任务在哪」，是「我压根没起、系统替我起了，而我不知道」。

## 决定

### 一、后台任务的起点也落事件

新增 `BackgroundTaskStartedEvent`（`ignorable: true`，与 completed 对称）：

```ts
export interface BackgroundTaskStartedEvent extends SessionEventBase {
  type: "background_task_started";
  taskId: string;
  cmd: string;
}
```

起点落了事件，UI 面板就是**日志的投影**，不是主进程另开的一路推送——这正是硬规则要的
（「任何投影（模型上下文/UI）必须可从日志推导」）。elapsed 从事件的 `ts` 算，不用另存
startedAt；标题就是 `cmd`。

`ignorable` 的理由同 completed：模型不消费。模型知道自己起了后台任务，是因为 `bash`
工具的返回值当场就说了（「后台任务 bg-N 已启动」），不需要再来一条事件重复告诉它。

### 二、回注消息记住自己驮的是哪几个任务

`UserMessageEvent` 加可选字段：

```ts
/** 这条回注消息驮的后台任务 id。只在 origin === "background" 时出现 */
backgroundTaskIds?: string[];
```

数组而非单值：turn 在跑时完成的任务会攒进 `pendingBg`，收口后**合并成一条**注回
（index.ts 的排空逻辑），一条消息驮多个任务是常态不是例外。

这一条让两件事从「猜」变成「读」：

- **面板什么时候该把一行摘掉**：结果真的进了对话才摘，不是完成的那一刻摘。
  两者之间隔着一整个 turn（`pendingBg` 攒着），这段时间该显示成 `ready`——
  「跑完了，等这轮说完就注进来」。

**面板的行不可点。** 一度想让「点一行跳到那条结果卡片」，但这两个状态凑不到一起：
`ready` 的行意味着结果**还没进对话**，跳无可跳；等它进了对话，这一行按上面的规则
就已经被摘掉了。加一颗点了没反应的钮不如不加。真要导航，那张卡片就在时间线上。

**刻意不靠正文前缀 `[后台任务 bg-N 完成]` 反解**——ADR-0103 已经把这条路否掉过一次：
那是给模型读的文案，不是身份，让渲染挂在一句随时会改的中文上是自找的。同一个错误
不在同一个子系统里犯第二次。

字段的写入权同 `origin`：`handleSendMessage` 的参数不经 IPC 透传，渲染层伪造不出来。
两者合并成一个参数 `background?: { taskIds: string[] }`——传了就是后台来源，
省掉「传了 origin 却没传 ids」这种拼不出意义的组合。

### 三、`live()` 从死代码变成「谁还真的活着」的判据

事件日志会把上一次 app 运行留下的 started-without-completed 一起重放出来，但那些进程
早随 app 一起没了。渲染层分不出「还在跑」和「上次跑崩了」——**这个判据只有主进程有**，
就是 `live()` 那张 map。

所以 ShellBridge 加一路 `liveBackgroundTasks(sessionId)`。投影规则：

| 日志里的状态 | 在 live 集合里 | 面板显示 |
|---|---|---|
| 只有 started | 是 | `running` |
| 只有 started | 否 | 不显示（进程已随上次 app 退出而死，显示它是撒谎） |
| started + completed，未回注 | — | `ready` / `failed`（按 exitCode） |
| started + completed，已回注 | — | 不显示（结果已经在对话里了） |

### 四、回注消息不再是用户气泡，改系统卡片

`origin === "background"` 的消息从「右对齐的静音气泡」改成**居中的系统卡片**，
默认折叠成一行（`bg-5 的结果 · 不是你发的`），点开看全文。

标题只用事件上的 taskId，不去正文里认 `[后台任务 bg-N 完成]` 那个前缀——同上一条，
ADR-0103 已经把那条路否掉过一次。退出码和命令原文不进这一行：它们在输入框上方的
面板里已经露过脸，展开的全文里也有，折叠行只需要一个「结果落地了」的锚点。

默认折叠的理由是正文长度：回注文案是命令的完整输出（上限 8000 字符，见
`formatCompletion`），摊在时间线上会把真正的对话挤没。

这一条推翻了 issue #428 那次的一个判断。原话是：

> 位置和对齐不动（它仍然是这一轮的开场白，挪到左边会让时间线读起来像模型在自言自语）

**那句话反对的是「挪到左边」，不是「居中」**，而居中恰恰是时间线上系统事件的惯用位——
读起来是「发生了一件事 → 模型回应它」，不是「模型自言自语」。原判断的顾虑成立，
但它没覆盖到居中这一档。

## 代价与边界

- `UserMessageEvent` 上又多一个只服务于 UI 的可选字段。理由同 ADR-0103：
  「这条消息驮着什么」和「这条消息说了什么」是两件事，挤进正文才是把它们混在一起。
- 多一个事件类型 = 日志变长。started 事件很小（两个字段），且 `ignorable`
  意味着模型投影一眼都不看它。
- 面板只显示「本会话」的后台任务。跨会话的后台任务（另一个会话里起的）看不到——
  `BackgroundTasks` 本来就是每个 agent 一份，跨会话聚合是另一个决定，等有人真被咬到再说。
- **不碰自动回注契约**。「完成即以新 turn 注回」（issue #389 / ADR-0073）原样保留。
  要不要改成「攒着等用户领」记在 issue #454，且明确挂了 `Blocked by: #452`——
  先把形态修好，再回来看时机那半还剩多少不适。很可能大部分不适来自形态。
