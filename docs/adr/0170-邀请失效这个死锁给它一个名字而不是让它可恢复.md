# ADR-0170：邀请失效这个死锁，给它一个名字，而不是让它「可恢复」

- 状态：已接受
- 日期：2026-08-28
- 相关：issue #682（本决策）、ADR-0162（一次性 secret 为什么不落盘）、ADR-0169（A 侧那块表）

## 背景

A 生成邀请码之后**在对方接受之前退出 app**，这条代理关系就永远建立不起来了：

- 一次性 secret 只活在内存里（ADR-0162：落了盘就不是一次性的了），随进程消失；
- A 重启走 `resume()`，`pinnedIdentities(...).length === 0` 把这个好友跳过——B 从没连上过，
  所以没有 pin，房间开出来也握不了手；
- **房间再也不开**。B 那边 WS 无限重连、界面显示「没连上」；A 那边那条 grant
  看着一切正常。

两边都不知道修法是「A 重发一张邀请码」。这不是缺一句提示——这是一个**没有名字的状态**：
在台账里它和「一切正常，只是好友今天没上线」长得一模一样。

## 决策

### 1. 不让它「可恢复」——两条看起来更聪明的路都拒绝

- **把 secret 落盘**，这样重启后还能接受那张邀请 —— 否决。落盘一个一次性的东西，
  它就不再是一次性的了（ADR-0162 的原话）。为了省用户一次「重发」而把信任根的
  生命周期从「一个进程」拉长到「一个文件」，代价和收益完全不成比例。
- **重启后照样开房间，允许无证明配对** —— 否决，而且是危险的否决。
  channelId 会落盘、也在线上可见，它从来不是信任凭证（`proxyConnection.tryPair`）。
  允许无证明配对 = 任何知道频道号的人都能拿到 A 的凭证。这正是 ADR-0162 修掉的那个洞。

`resume()` 跳过它是**对的**。要改的不是行为，是它在界面上叫什么。

### 2. 给这个状态一个名字：`pairing` 三档

`ProxyHostStatus` 加一格，判据全在已有数据里，不需要任何新的持久化：

| 档 | 判据 | 用户的下一步 |
|---|---|---|
| `paired` | 有 pin | 无事（连没连看 `connected`） |
| `waiting` | 无 pin + 房间开着 + 邀请没过期 | 等对方粘码 |
| `needsInvite` | 其余 | **重发一张** |

`needsInvite` 覆盖两种成因（邀请过了 10 分钟 TTL、app 重启把内存里的 secret 带走了），
不再细分——**因为用户要做的事完全一样**。这与 ADR-0169 里「四档不能合并」不矛盾：
那条的判据是「对应的下一步动作是否不同」，不是「成因是否不同」。

内存里多一张 `pendingInvites`（好友 uid → 过期时刻）。它**不落盘**，和那把 secret 同生共死——
进程一没这张表跟着没，而那正是 `needsInvite` 要表达的事实本身。

### 3. 状态行里，这两档排在「连没连」前面

`hostStatusLine` 的判定顺序：`inflight > 0` → `needsInvite` → `waiting` → `connected`。

配对没成立时说「没连上」是**误导**：那句话暗示等一等就好，而实际上等到天荒地老
也不会连上。同一个字面事实（`connected === false`），在配对成立与否两种前提下
是两条相反的建议。

### 4. 出路就在那一行上

「已授权」页里 `needsInvite` 那条多一个「重发邀请码」按钮，**原样用这份已有的白名单**
重发（`proxyCreateInvite(uid, g.allow)`），码就地摆出来能复制。不必让用户回到分享页
把工具再圈一遍——他上次圈的东西台账里存着，重发的语义是「同样的授权，换把新钥匙」。

## 后果

- 零新增持久化，零协议改动。判据是既有数据的一个函数。
- `pendingInvites` 只在本进程内准确。这是特性不是缺陷：跨进程「准确」恰恰要求
  落盘 secret 的影子，而那正是第 1 节否决掉的那条路。
- 一张邀请过了 10 分钟 TTL 却还没人接，界面会从 `waiting` 变成 `needsInvite`——
  这是对的，那张码此时确实已经不能用了（`verifyWith` 会拒）。
