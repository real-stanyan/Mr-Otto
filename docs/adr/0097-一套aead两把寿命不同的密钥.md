# ADR-0097: 一套 AEAD，两把寿命不同的密钥

## 背景

原方案是两套算法：实时流用 libsodium secretstream，推送负载用 AES-GCM。
本机实测（Node 22）后推翻，改成**一套 ChaCha20-Poly1305-IETF**。

推动改动的是两件事：桌面侧的依赖账，和 iOS 通知服务扩展（NSE）逼出的密钥寿命问题。

## 决定一：算法只有一个，ChaCha20-Poly1305-IETF

选它而不是 AES-GCM，理由是**三家的交集**：

| 实现 | ChaCha20-Poly1305 | AES-GCM |
|---|---|---|
| `node:crypto`（桌面） | ✅ 原生 | ✅ 原生 |
| CryptoKit（iOS NSE，Swift） | ✅ `ChaChaPoly` | ✅ |
| libsodium（Expo / RN） | ✅ chacha ietf **恒有** | ⚠️ 要 AES-NI 硬件支持 |

最后一格是决定性的：libsodium 的 AES-GCM 在没有 AES-NI 的 ARM 上
`crypto_aead_aes256gcm_is_available()` 会回 false。照原方案写，在真机上才会踩。

顺带的收获：`node:crypto` 原生就有 X25519 / Ed25519 / HKDF / ChaCha20-Poly1305，
**桌面侧一个新 npm 依赖都不需要**（`libsodium-wrappers` 删掉）。
`RemoteCryptoPrimitives` 是个注入接口，桌面实现在 `src/main/remoteCryptoNode.ts`，
RN 侧实现 `react-native-libsodium`，而握手与流封装那些**我们自己写的逻辑**
只依赖接口，单测里塞假原语就能跑——既不慢，也不把平台依赖拖进 `src/shared`。

代价：丢掉 secretstream，nonce 管理和乱序/重放检测从"库送的"变成"自己写的"。
所以它们住在一个纯文件（`sealedStream.ts`）里，并被逐条钉住：
**nonce = 4 字节前缀（握手派生，每方向一条）+ 8 字节大端计数器**，
计数器不回绕（到顶抛错、断开重连），收端拒收不严格递增的计数器，
且**水位线只在验签通过后才推进**（否则伪造一个大计数器就能把后续真帧全饿死）。

## 决定二：两把寿命不同的密钥，因为推送到达时连接不存在

NSE 是原生 iOS 扩展，**跑不了 RN 的 JS**，解密必须 Swift 写
（仓库已有 Swift 链，CryptoKit 零第三方依赖）。而推送到达手机时，那条加密连接
根本不存在——临时密钥还没生成。于是推送负载**不能用连接密钥**，必须用长期密钥：

```
pushKey = HKDF-SHA256( X25519(mobile_kx_priv, desktop_kx_pub), "otto-push-v1" )
```

| 信道 | 密钥 | nonce | 前向保密 |
|---|---|---|---|
| 实时流 | 每连接临时派生 | 前缀 + 递增计数器 | **有** |
| 推送负载 | `pushKey`（静态派生） | 每条随机 12 字节 | **没有** |

每台设备因此有两把静态密钥：identity（Ed25519，签握手临时公钥）和
kx（X25519，推送密钥协商）。**不做 Ed25519 → X25519 转换**——libsodium 能转，
但显式两把不容易出错。

## 后果

- **推送负载没有前向保密。静态私钥日后泄漏，历史推送密文全部可解。**
  唯一缓解，也是本 ADR 最要紧的一条约束：**推送负载只放摘要**
  （动词 + 目标 + 会话标题，截断），**永不放文件内容、命令全文、工具输出**。
  APNs 上限 4KB，摘要绰绰有余——体积从来不是放全文的理由。
  实时流那一路的前向保密不受影响。
- 一套算法意味着 NSE 侧 `ChaChaPoly.open` 就能读，不用在 Swift 里手搓任何东西。
- 计数器明文出现在帧头，是故意的：收端要先知道 nonce 才能验签。
  它泄漏的只是"这是第几帧"，而帧数本来就是网关可见的元数据（ADR-0095 威胁模型第四行）。

## 会推翻它的前提

- **若哪天需要在推送里放摘要以外的东西**：那一刻起"没有前向保密"就不再是可接受的代价，
  必须先给 `pushKey` 设计轮换（例如每次连接顺带协商下一把推送密钥并落 Keychain），
  再谈放什么。**不要先放内容再补密钥轮换。**
- **若 libsodium 的 AES-GCM 在目标机型上恒可用**（或 Expo 侧换成一个自带 AES 软实现的库）：
  算法交集这条论证的最后一格塌了，但也没有理由换回去——两套算法本身就是负担。
- **若 RN 侧最终用的不是 libsodium**（比如 Expo 出了官方 crypto 模块）：
  `RemoteCryptoPrimitives` 这个接口正是为这一天留的，换实现不动握手与流封装。
- **若单向流需要支持乱序到达**（例如将来换 QUIC 或多路复用）：
  "严格递增才收"会开始丢真帧，那时得换成滑动窗口 + 重放位图，
  而窗口大小是个需要论证的新参数。
