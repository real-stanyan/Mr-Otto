# ADR-0302：`cs.chat` 收成三态，名单从日志推导

日期：2026-09-21
状态：已采纳
相关：#1301 / #1302（#1280 的真机验收撞见的两条）、ADR-0297（名单是日志事实）、
ADR-0298（主场全免审批）、ADR-0217 / 0240 / 0243（三态纪律的前三次）、ADR-0300（尾巴分页）

## 背景

#1280 六片合完之后第一次真机验收（2026-09-21，协议 20 的 runtime）撞见两条 bug，
落在**同一格** `cloudSession.chat` 上，两个相反的失败方向：

- **#1301**：`welcome` **之前**那一格是 `null`，而 `null` 同时是「这是团队会话」（确定
  的事实）与「welcome 还没到、还不知道」（读不到）。页面把后者当成前者，于是打开任何
  一条聊天的头几秒画的是**团队壳**——真机上这个窗口**超过 10 秒**。
- **#1302**：`welcome` **之后**那一格不再更新。`cs.chat` 全仓唯一的写入点是 welcome，
  `chat_update` 成功之后没有任何一条路会碰它，于是改完名单头部是「新标题 + 旧名单」，
  「添加智能体」**按不动**且说「名册里的智能体都在群里了」——而名册里明明有一只不在。
  后果是移出去的那一只**加不回来**，除非离开这条聊天再进来。

两条的危害不对称。#1302 是每次改群名单都会撞上的；#1301 更锋利的一点是它露出的那颗
「免审批」开关在个人主场里**点得动**（owner 就是自己），而 ADR-0298 写着主场
「一次都不查 `sandbox_approval`」——一颗点了不产生任何效果的开关，正是 #722 那颗撒谎的勾。

## 决策

### 1. `chat` 那一格收成三态，一路带到渲染层

`undefined` = 还不知道 / `null` = welcome 到了、说这是团队会话 / 值 = 一条聊天。
三处同步：`ActiveSession.chat`（主进程）、`CloudSessionStatus.chat?: CsChatInfo | null`
（IPC）、`CloudSessionState.chat`（store）。

这是这个仓库第四次在同一条纪律上立规矩：`workspaceAccess` 必须有 `unknown`（ADR-0217）、
`sandboxApproval` 的 `null` = 读不到（ADR-0243）、`planBadge` 的 `null` 不许退成 free
（ADR-0240）。判据每次都一样：**两个失败方向不对称**时，少答一句永远比答错一句便宜。

### 2. 状态推送对这一格的规矩与 `gapNote` / `hasOlder` **相反**

那两格是「照抄推送、缺席即最新结论」，因为它们每一次推送都重算——缺口补齐时主进程
正是靠**不带**它来说「补齐了」。这一格反过来：`welcome` 每条连接只说一次，所以
**缺席 = 还没说**，渲染层留着手上那份种子不清。

这条写进代码注释与两条用例里，因为它看起来像是一处不一致，下一个人很容易「顺手改对」。

### 3. 打开那一刻先种一份（`chatSeedOf`）

种子来源两个，都是**已经在手**的数据，不多打一次网络：

- 正在建的那一条按我们自己递的 `CsChatSpec` 算——那不是一次读，是我们刚刚要求的东西；
  spec 缺席 = 我们要的就是一条团队会话。
- 已有的那一条查 `cloudSessionList` 那一行（`workspace_sessions.chat_kind / agent_ids`，
  ADR-0297 明写它就是给「没开着这条聊天」的桌面看的投影）。

清单里没有这一行 = `undefined`，**不猜成团队会话**。

`chatKind === null` 在这里当团队会话用是安全的，虽然那一格同时也是「这两列读不到」
（`fetchCloudChats` 容错回空 Map）：读不到时整份 map 是空的，于是 `rosterRows` 的私聊
全成「没聊过」、`groupRows` 一个群都不列——**一条聊天都点不进来**，走不到这里。
这是个会随代码变化的论证，所以写在函数注释里挨着它。

### 4. 还不知道的时候，**两种壳都不画**

`CloudSessionMain` 早退成一行「正在进入这条会话…」。团队壳在那一刻是一句猜测，而猜错
的代价是上面那颗撒谎的勾 + 把个人主场的内部名「我的智能体」写在头部（同 ADR-0235 给
Default 定的那条）。种子覆盖了其余每一条路，所以这一屏在正常使用中不出现。

### 5. 名单从日志推导（`chatRosterNow` → `chatViewOf`）

硬规则写着「任何投影必须可从日志推导」，而名单正是日志事实（`chat_roster_changed`，
ADR-0297），纯投影 `chatRosterOf` 早就在，桌面也**已经收到**那条事件——时间线上
「你把「客服」移出了群聊」那一行就是从它画的，只是头部没去读它。

`chatRosterNow(events, fallback)` = 日志里最后一条胜出，**一条都没有时退回 welcome
那份快照**。后半不是可选的：ADR-0300 之后进房只拉尾巴，一条聊了半年的线上名单事件
多半落在窗口外面，那时 `null` 的意思是「这一段历史里没人改过名单」而不是「这条聊天
不收窄」——照 `null` 画就是把一条私聊当成团队会话，#1301 换个形状回来。

注意 `[] ?? fallback` 是 `[]`：移空之后是空名单、不退回快照。空群是合法终局
（0037 给 group 那条 CHECK 写的是 `cardinality 0..6`）。

**群名仍从清单那一行来**：群名不是日志事实，改名走的是库。头部这一行因此有两个来源
——这正是 #1302 的形状（新标题配旧名单），所以名单那一半必须跟着最新的那份事实走，
不能两半各自陈旧一半。

## 否决的

- **只修 #1302**。两条同根，修完一条另一条会换个形状回来：种子不做的话，改名单那条
  修法在 welcome 之前仍然读着一个被当成「团队」的 `null`。
- **让 `chat_update` 成功之后自己更新 `cs.chat`**。那是给同一件事造第二个写入点，而
  别人改名单（同一个群、两台设备）走不到这条路——今天连这个都不对。
- **按 `isHomeWorkspace(ws)` 判「主场里没有团队会话」**。结论多半为真（主场的 ＋ 不在
  侧栏上），但它是个「实际上没人这么建过」的经验断言，不是结构保证；存量日志里真有
  一条主场团队会话的话，这条会让那一屏永远卡在「还不知道」。
- **`fetchCloudChats` 失败时给 `chatKind` 加第三态**。决策 3 那段论证说明走不到，
  加一档要动 IPC 形状与两个既有消费方，换不回任何东西。

## 代价

- `CloudSessionStatus.chat` 的语义变了（缺席从「团队会话」改成「还不知道」）。它是
  主进程↔渲染层的 IPC、跟着同一次构建走，**不是** cs 线上协议，所以不进协议位、
  也不存在一新一旧的两端。既有那条用例跟着改了断言（同一 PR 内、跟着产品代码走 = L2）。
- 还不知道的那一屏会**重挂** `CloudSessionPage`（今天是同一棵树换 props）。种子之后
  这条路在正常使用中走不到，所以没为它做保留挂载。
- 侧栏那一行仍从清单来，所以**别人在另一台设备上改了名单**时，侧栏要等下一次
  `focus` 刷新才对——头部这一半从此是对的，两处因此可能短暂不一致。修它要给
  `workspaceGroups` / `cloudSessionList` 接一条推送通道，是另一件事。
- 私聊里那只被删掉时仍然退回团队壳（`chatViewOf` 回 `null`），在主场里那一瞬间照样
  露出那颗开关。删智能体的第 1 步就是删它的私聊，所以这是个半路失败的窗口，没有为它
  再加一档。
- **真机一次没跑过**：这两条都是真机才撞得见的时序/陈旧问题，用例钉的是判据。
