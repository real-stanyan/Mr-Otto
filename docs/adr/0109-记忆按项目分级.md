# ADR-0109：记忆按项目分级——USER / MEMORY / PROJECT 三档

- 状态：已接受
- 日期：2026-08-26
- 推翻：`docs/superpowers/specs/2026-08-22-memory-design.md` 决策表里的
  「文件作用域 | 全局一份 `~/.mr-otto/memories/`，不分 workspace」这一行
- 相关：ADR-0060（记忆快照进 system 尾部）、
  spec `docs/superpowers/specs/2026-08-26-tiered-memory-design.md`、
  计划 `docs/superpowers/plans/2026-08-26-tiered-memory.md`

## 背景

`MEMORY.md` 是一份 2200 字符的全局文件，而项目数量线性增长。真正的缺陷不是「项目 A 的
记忆在项目 B 里显得吵」，而是**互相驱逐**：`applyOps` 超限时报错、不自动淘汰（逼模型
自己 remove/replace 腾地）——所以在项目 B 里写记忆，模型为了腾空间会去删项目 A 的条目。
项目越多，记忆越是一份不断自我覆写的滚动窗口。

Otto 已经有项目轴（`session_created.workspace` 是一等会话事实，`projectInstructions.ts`
按 workspace 注入 AGENTS.md/CLAUDE.md），只有模型自己能写的那份笔记没接上去。

抄来的那份（hermes-agent）没有项目这一档：它的分级轴是**人格/身份**（profile），
「装不下」的正式答案是**检索层**（provider 的 `prefetch(query)`），不是分级。它不需要
项目档，是因为它不知道自己在哪个项目里；Otto 知道。照抄等于照抄一个空缺。

## 决定

五条，每条连同「会被什么前提推翻」——那半句是这份 ADR 的承载部分，不是装饰。

### 1. 作用域键 = workspace 向上第一个 `.git`，**worktree 折叠回主仓**

新模块 `src/main/projectRoot.ts`，纯读文件不起 `git` 子进程。`.git` 是目录 = 普通仓库根；
是文件就读 `gitdir:`：含 `/worktrees/` 折叠回主仓，含 `/modules/`（submodule）不折叠
（子模块是独立仓库，约定不属于父仓）；认不出形状就地当根，不猜。

worktree 必须折叠，因为 worktree 是一次性的（合并后 `gearbox prune` 删掉）。不折叠的话
项目记忆跟着每次换班出生、死亡，**永远学不到东西**——比现状更差。
（`projectInstructions.ts` 今天不折叠，那对它是对的：worktree 里的 AGENTS.md 本就该读
worktree 那份。所以两边不共用函数。）

**推翻前提**：出现「一个项目横跨多个 repo」或「一个 repo 里几个互不相干的子项目」的
真实用法——那时作用域键就不该是 git 仓库，而该是用户显式指定的某种项目声明。

### 2. 三档：`USER` / `MEMORY`（全局）/ `PROJECT`

全局档保留而不是两档了事，因为「本机环境」这类记忆真实存在且跨项目为真
（`gh CLI 已登录 real-stanyan`、`跑 npm 要先 export PATH`）。两档方案下它们只能挤进
1375 字符的 USER，语义被迫变成「关于用户和他的机器」。hermes 的 profile clone 把
`MEMORY.md` 当身份的一部分，是同一判断的独立佐证。

**推翻前提**：实践中全局档长期只有两三条——那说明这一档不值一个独立预算，该并回 USER。

### 3. 预算 `USER 1375` / `MEMORY 1100` / `PROJECT 2200`，且**不做成可配置**

合计 4675（原 3575，+31%）。全局档从 2200 降到 1100：三档之后它的职责变窄了（项目约定
全搬走），不该还占原额。

不可配置（hermes 是可配的，`config.yaml` 的 `memory.*`）：紧上限不是为了省 token
（三档合计才 ~1200 token），是为了**逼出策展**。做成可配置，第一次超限时人会去调大数字
而不是合并条目——那正是这套设计要防的行为。加容易，收回难。

**推翻前提**：某一档在正常使用下频繁顶到上限、而里面每一条都仍然为真（不是没策展，是
真装不下）。那时正确的动作也不是开放配置，是上检索层——按需注入才是「装不下」的答案。

### 4. 没有 `.git` 时**没有项目档**，`target` 枚举里不出现 `project`

`createMemoryTool(project: {root, dir} | null)`：`null` 时枚举里没有 `project`，工具描述
里那句三档判据也不出现。看不见的档就不会误写，比给它一个必然报错的选项干净。

**推翻前提**：非 git 工作区变成主流用法（比如大量在裸目录里跑），那时得另找作用域键
（见第 1 条的推翻前提），而不是给它一个哑档。

### 5. 存量**不迁移**，靠写入时收敛 + 设置页「移到项目档」手搬

迁移代码跑一次就废，最容易带 bug 又最难测，还得永远躺在仓库里。

**推翻前提**：收敛路径被证明走不通——用户拿不到一条「从今天的状态到三档状态」的可行
路径。这个前提**当场就差点成立了**，见下面的代价一。

## 事件与投影：只加可选字段，绝不加新类型

`memory_loaded` 加 `project?` / `projectRoot?`；`memory_user_edit` 加 `projectRoot?`
（三档之后 `target: "project"` 在多个项目之间不再唯一——不带它，两个不同 repo 的手编
在日志里分不开，而这条事件的存在理由正是「记忆文件可从日志重建」）。

**必须可选，理由是向前兼容**：`assertReplayable`（issue #383 的拒读）拒的是未知**事件
类型**，已知类型上的多余字段它认得。新开一个 `project_memory_loaded` 类型会让旧版本
直接拒读整个会话。

## 代价（明写出来，不粉饰）

### 代价一：spec 里「投影与今天逐字节一致」这句话是错的

spec §三 用「旧日志没有这两个字段 ⇒ 投影与今天**逐字节一致**」论证可选字段方案。这句话
与它自己第 3 条决策（`MEMORY 2200 → 1100`）自相矛盾：`memoryBlock` 把 limit 渲进标题，
所以一份 1800 字符的旧日志现在渲成 `[164% — 1,800/1,100 chars]`，而不是
`[81% — 1,800/2,200 chars]`。

**真正让可选字段方案成立的是向前兼容**（上一节），不是逐字节不变。硬规则要的是「旧日志
必须永远可重放」——重放不失败、结构不变（没有 `project` 字段就不多渲一块），这两条都成立；
「投影每个字节都不动」从来不是硬规则的内容，而降上限本身就必然改动那个数字。
`tests/session/deriveMessages.test.ts` 里那条测试原本按错的说法命名，已改成它真正验的东西。

### 代价二：存量超限的档一度会被静默锁死，本次一并修掉

第 5 条决策依赖「上限只在写入时校验，存量超限文件照样完整注入，第一次写入时模型被自然
逼着整理」。**这条预测不成立。**复审用真模块跑出的实证：一份存量 1806 字符的 `MEMORY`
（新上限 1100），模型删掉一条降到 1203 —— 老判据 `used > limit` 让**整批被拒，一个字都
不写**；而 `src/tools/memory.ts` 连续失败 3 次后返回终态「本轮放弃」，模型就此停手。

实际发生的不是「被逼着整理」，是**静默锁死**，受害人群恰好是所有在旧上限 2200 下写满过
的用户。这是 spec 推理的缺陷，不是任何实现者的错。

修法：`applyOps` 只在「结果超限**且**结果不比开工时更小」时才拒。仍然不自动淘汰、不截断
——只是不再惩罚「有进展但没到位」；报错文案把 before/used/limit 三个数都说出来，模型才知道
自己还得继续减。`assertMemoryFits` 不跟着放宽：它唯一的调用方「移到项目档」是纯增操作，
放宽的那半个分支永远走不到，而往一份已超限的档里再加东西任何时候都是错的。

同一批还修好了这条收敛路径的另一半：设置页的「移到项目档」原本在**最需要它的场景**
（新仓库、项目约定正堵在超限的全局档里）恰好不可用——`root.txt` 只有 memory 工具真的写过
项目档才会出现，`listProjectMemories` 跳过没有 `root.txt` 的目录，而设置页的一切都从那个
列表推导。现在当前会话的项目根即使还没有目录也是一个可选目标，且 `saveMemory` 这条路径
自己补写 `root.txt`（原本它能造出目录却不写自描述文件——那样的目录设置页永远看不见，
却仍然会被注入会话，因为注入按哈希查目录、不看 `root.txt`）。

### 代价三：错放项目档是**丢失**

判据是「拿不准就写 `memory`」，故意偏向全局：错放全局只是噪音，错放项目档换个项目就再也
看不见。代价接受，但它意味着项目档的实际利用率会低于理论值。

### 代价四：权限错的 worktree 不折叠

`projectRoot.ts` 的 `readFile` 把**任何**读失败都当成「不是文件」（不只 EISDIR/ENOENT，
还有 EACCES / ELOOP / EIO）。在普通仓库下「读不了的 `.git` 就是这一层」是正确答案，不值得
为区分错误码加一层；代价是一个 `.git` 文件读不了的 worktree 会拿到自己那份项目记忆，而
不是折叠回主仓。

## 不做

- **检索层**（hermes 的 `prefetch(query)`）：每轮注入会打穿 ADR-0060 买到的前缀缓存，另开一件事
- **上限可配置**：见决策 3
- **跨项目记忆共享 / 软链**：等真出现「一个域横跨多个 repo」的实际需求
- **自动迁移**：见决策 5
- **按 profile/人格分档**（hermes 的第 2 层）：Otto 的 bot 身份模型还没到那一步
