# ADR-0120：渲染层引入组件测试（jsdom + testing-library）

> 原为 ADR-0115。合并前 origin/main 上另一条车道先落了 0115 这个号，按项目 ADR-0074 在本 PR 内顺延改号；照旧号来的引用按这行解析。

日期：2026-08-26
状态：**待仓主同意**（L1 技术栈变更，AGENTS.md「Changing the protocol itself」）
相关：设计文档 `docs/superpowers/specs/2026-08-26-mcp-oauth-agent-config-design.md`（§6 UI）、ADR-0117（OAuth 授权，本功能的 UI 入口就是它的授权按钮）、gearbox ADR-0020（测试类门禁的 L1/L2 映射）、ADR-0058（GUI 改动的 PR 贴 e2e 结果）

## 背景

本次功能（MCP 的 OAuth 授权）在 GUI 上**只有一个入口**：`McpSettings.tsx` 里 `needs-auth` 状态旁边那颗「授权」按钮。要钉住的行为是三条：

1. 只有 `needs-auth` 状态才显示这颗按钮
2. 点击它会调桥，且带的是**正确的 server id**
3. 授权失败时把原因显示出来，而不是静默回到原状

这三条没有一条能用纯函数测试钉住——它们全是「组件在某个状态下渲染成什么 / 点下去发生什么」。

而本仓的 `tests/renderer/` 此前**只测纯函数**：`mcpForm.test.ts` / `mcpPromptMenu.test.ts` / `mcpPromptSubmit.test.ts` 都是把逻辑抽出来测，没有任何一份真的 `render` 过一个组件。渲染层的能力边界是「只能测纯函数」。

## 决定

给测试栈补上「能 render 组件」这一类能力：

- 新增四个 devDependency：`jsdom`、`@testing-library/react`、`@testing-library/user-event`、`@testing-library/jest-dom`
- `vitest.config.ts` 的 `include` 从 `tests/**/*.test.ts` 扩到同时收 `tests/**/*.test.tsx`
- `vitest.config.ts` 的 `resolve.alias` 补 `@` → `src/renderer/src`，与 `electron.vite.config.ts` 的渲染进程别名对齐
- 单文件用 `// @vitest-environment jsdom` 声明环境，不改全局 `environment`——绝大多数测试是 node 环境的纯逻辑，为几个组件测试把全仓都搬进 jsdom 是白付启动成本

第一份是 `tests/renderer/McpSettings.test.tsx`（4 条断言，钉住上面那三条行为）。

### 为什么保留而不是砍掉

控制方的裁决是**保留**。理由：没有组件测试就没法钉住这个功能**唯一界面入口**的行为。砍掉测试换取程序上的省事（避免走 L1 流程）是本末倒置——协议存在是为了让决策留痕，不是为了让人绕开它删测试。

顺带说明为什么 e2e 不能替代：`tests/e2e/`（ADR-0058）跑真 GUI，但**不在门禁里**。「`needs-auth` 才显示按钮」这类行为如果只由 e2e 看着，一次回归要等到有人手动跑 e2e 才发现。门禁里的组件测试和门禁外的 e2e 是两层，不是一层的两种写法。

### 分级：一半 L1，一半 L2

这份 ADR 覆盖的改动其实横跨两档，必须说清，否则将来读的人会以为整块都要仓主点头：

| 改动 | 档位 | 依据 |
|---|---|---|
| **新增四个 devDependency** | **L1** | 往测试栈里加**一整类能力**（渲染层从「只能测纯函数」到「能测组件」）= 改 Tech stack。AGENTS.md：Tech stack 属 L1 严格层，需 issue + ADR + PR，且要等仓主明确同意才能合 |
| `vitest.config.ts` 的 `include` 从 `.test.ts` 扩到 `.test.tsx` | L2 | 这是**加覆盖面**（多认一种文件后缀，之前压根没有任何 `.tsx` 测试文件被 include 命中过）。gearbox ADR-0020：测试类门禁的 config 层「收紧 = L2」。单独看不需要仓主同意 |
| `resolve.alias` 补 `@` | L2 | 同上，是把「这条别名只在打包时存在、测试时不存在」的分叉补平，不放宽任何断言 |
| 新增 `McpSettings.test.tsx` | L2 | 测试与它跟随的产品代码在同一个 PR 里 = 常规开发（gearbox ADR-0020 的动机分层） |

被卷进 L1 的是**新增依赖**那半。因为它们打包在同一个 PR 里，整个 PR 按最高档走 L1。

## 被否掉的路

- **砍掉组件测试，只留纯函数测试**：程序上最省事（全程 L2），但这个功能的唯一界面入口就此无人看守。见上「为什么保留」。
- **把逻辑从组件里抽成纯函数再测**：对「按钮该不该显示」这类，抽出来的纯函数就是 `status === "needs-auth"`——测它等于测一个恒等式，真正会坏的（组件有没有真的用这个判断、点击有没有真的接到 handler）恰好在抽出去的那一半里。
- **全局 `environment: "jsdom"`**：写起来省一行注释，代价是每个纯逻辑测试文件都要付 jsdom 的启动成本。
- **改用别的组件测试方案**（如 happy-dom）：更快，但 testing-library 的生态和文档是这一类里最厚的，而本仓此前零经验——第一次引入不该同时挑一条冷门路。

## 推翻它的前提

- 渲染层整体迁到别的测试方案，或组件测试被证明长期无人维护（写了就烂在那儿，红了就 skip）。**「删测试换绿」是 L1**（gearbox ADR-0020），届时同样要走这套流程，不能静默 skip。
- 四个依赖里出现供应链问题或长期失修——那时是换实现，不是退回「不测组件」。

## 后果

- `npm ci` 多装四个包，装机时间与 `node_modules` 体积上涨（devDependency，不进产物）。
- `tests/renderer/` 从此有两类文件：`.test.ts`（纯函数，node 环境）与 `.test.tsx`（组件，jsdom 环境）。写新测试的人要先判断自己在测哪一类。
- 组件测试比纯函数测试更容易因为无关的 DOM 结构调整而红。缓解写在第一份测试的注释里：查询用 `screen.getByRole` / 可见文本这类语义查询，不挂在 class 名或 DOM 层级上。
- 门禁时间变长（jsdom 启动 + React render）。眼下只有一份 `.tsx` 测试，影响不可测；若将来组件测试成规模，值得单独评估要不要拆一条更快的通道。
