# ADR-0168：「借进来的」与「借出去的」记在同一本台账；断线的那条仍然在列表里

- 状态：已接受
- 日期：2026-08-28
- 关联：issue #676；ADR-0162（A 侧：channelId 落盘、secret 不落盘）；
  ADR-0166（借来的服务按好友加前缀合并）；ADR-0151（§2「配对时**互相**记录」）

## 背景

A 侧早就能重启后自己把房间开回来（`resume()` 读落盘的 channelId + pin）。
B 侧对称的那一半一直没做：`proxyAcceptInvite` 把通道存在一个**单条变量**里，
既不落盘（重启就得让对方重发一张 10 分钟就过期的邀请码），也只装得下一个好友
——尽管 `mergeProxyMcp` 从第一天起就支持多条。

同时 B 侧没有任何状态出口：`proxyMcp.onGrantsChanged` 声明了很久没人接，
没有推送频道，界面只能永远停在「已连上，等对方推来授权清单」。

## 决策

### 1. 「借进来的」记在同一本台账，另起一栏

`proxyStore` 多一栏 `borrows`（`hostUid` + `channelId` + 对方身份公钥）。

不另开一个文件：同一台机器既可能借出去也可能借进来，那是**同一件事的两个方向**，
一本台账两栏比两本台账一个方向更好理解，也少一处 0600 落盘要维护。
栏目名字直说方向——`grants`/`pins`/`channels` 是借出去的，`borrows` 是借进来的。

**secret 依然不落盘。** 重连走两边的 pin：A 早就 pin 了 B（ADR-0162），
B 这边 pin 的是台账里那把公钥。所以恢复路径**不消耗邀请**，也不需要它。
顺带这一栏就是 ADR-0151 §2「配对时互相记录 (userId ↔ identityPub)」里 B 欠的那半。

### 2. 断线的那条**仍然在列表里**

`borrowStatus()` 以台账为底本，把活着的通道往上贴状态，而不是列举活着的通道。

所以 `connected: false` 的那条照样显示。用户得看得见「配过、但现在没连上」——
让它凭空消失，等于把「对方下线了」和「我从来没配过」显示成同一个样子，
而这两件事该做的动作完全不同（等一等 vs 重走一次邀请码）。

同一个理由，「没连上」和「连上了但对方一个服务都没授」在界面上也是两句话。

### 3. 状态推送：三处触发，一条频道，全量快照

协调器的 `onStateChange` 在三处触发——握手完成、对端离场、收到新的授权清单——
汇到 manager 的 `onChange`，再由装配根推一条 `proxyChanged` 全量快照。
另配一个 `proxyBorrows` 查询（重载后补齐推送之外的空白，同 ADR-0133 的口径）。

全量而不是增量：量小（一个人能借几个好友），快照比增量简单。

### 4. 主动断开 = 关通道 + 从台账删掉

`proxyDisconnect` 两件事一起做。只关不删的话，下次启动 `resume()` 又把它连回来——
用户按「断开」的意思不是「断到重启为止」。

## 后果

| | |
|---|---|
| ✅ | B 重启不用重走邀请码；可以同时借多个好友的服务（合并层本来就支持） |
| ✅ | 界面能如实说三种状态：没连上 / 连上了但没授权 / 连上了且授了 N 个 |
| ✅ | `onGrantsChanged` 终于有了接手的人——对方改授权，B 的界面跟着变 |
| ⚠️ | 借来的通道数 = 常驻 WebSocket 数（A 侧同理）。好友多起来是笔账：连接、心跳、重连退避都乘以条数 |
| ⚠️ | 台账里那把公钥认死了对方那台机器。对方重装/换机 = 换身份密钥 = 连不上，且**没有提示**，得靠对方重发一张邀请码。这条留着 |

## 被否掉的路

- **B 侧单开一个台账文件**：见决策 1。
- **列表只显示活着的通道**：见决策 2——它把「对方下线」和「从没配过」显示成同一个样子。
- **断开只关通道、台账留着**：那是「断到下次重启为止」，不是用户按那颗按钮的意思。
