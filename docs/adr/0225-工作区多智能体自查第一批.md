# ADR-0225：工作区多智能体自查第一批——五路审计的裁决（compaction 接线、depth 与补跑可从日志推导、护栏只在云端硬停、审批与记忆三态化、migration 0025 待点头）

- 状态：已采纳
- 日期：2026-09-06
- 关联：issue #957；审计台账 `.superpowers/audit/LEDGER.md` 与五份明细 `A-runtime-core.md` / `B-security.md` / `C-desktop.md` / `D-billing.md` / `E-adversarial.md`；实现计划 `docs/superpowers/plans/2026-09-06-workspace-multi-agent-audit-1-runtime.md`；先例 ADR-0219/0220/0221/0222/0223/0224（切片 1–6，本批是切片落地之后的自查修复）；编号按 ADR-0074 在合并前复核

## 背景

切片 1–6（ADR-0219–0224）把工作区多智能体的骨架、白名单、记忆、接力、代建都接上了线之后，对 `services/runtime/` 与相关桌面/边缘代码做了一轮**五路并行审计**（opus）：A 跑时核心、B 安全、C 桌面、D 计费、E 对抗性测试。五份明细合起来是 1 个 Critical（A-1 压缩接线缺失）、3 个 Critical（B 的 C1–C3）、若干 Important/Minor。分级之后拆成三个 PR + 一份待维护者点头的 migration：

- **PR-1（runtime/服务端，本 ADR 覆盖的主体）**：A-1/A-3/A-4/A-5/A-6/A-9/A-10/A-11、E-F1–F5/F7、B-C3/I1/I3/I4/I5/I7、D1–D4/D7。
- **PR-2（桌面 + 共用校验）**：B-C1/C2/I2、C-*、#935/#938——不在本 ADR 范围。
- **PR-3（stop 帧）**：A-2/A-8、cs 协议 5→6——不在本 ADR 范围。
- **migration `supabase/migrations/0025_workspace_hardening.sql`**：随 PR-1 一起进仓，**不在本批次执行**。

本 ADR 记 PR-1 那组决策——它们的共同主题是**每一条判据都要能从日志重放推导**（AGENTS.md 硬规则），本机会话行为字节不变（新增全是可选字段），以及「云端没有人盯着屏幕」这一条 spec §8 反复出现的前提如何改写了几个原本只在本机成立的假设（ADR-0212 的护栏、ADR-0202 的现读纪律）。

## 决策

### 1. 压缩接线（A-1）与 `agent_briefed` 最新一条胜出 + 压缩幸存（A-3）

云会话此前压根没有自动压缩——`engine.ts` 的 `autoCompact` 判定依赖 `contextWindow()`，而 `CloudSessionOpts` 原来没有这个口子，云会话的上下文只会无限增长直到打爆上游。`contextWindowOf(model: string): number | undefined` 成为**必需**字段（同 `memory`/`isMember` 的纪律：忘接线该编译不过，不是安静地跑一条永远不压缩的云会话），`engine.ts` 的 `contextWindow` 现读 `opts.contextWindowOf(此刻 adapter 的 model)`——不定死，因为一只 agent 的模型可能在会话中途被改（同 ADR-0202「每次 `chat()` 现读」的教训）。

`agent_briefed` 的投影从「事件位置一条 `role:user` 消息」改成「拼在 system 消息尾部、最新一条胜出、`context_compacted` 不清」，排在 `workspaceMemoryPrompt` 之前——与 ADR-0222 `workspace_memory_loaded`「最新一条胜出、压缩幸存」是同一形状（同一族问题：`briefIfNeeded` 只在 instructions 变了才重发，日志里可能有好几条 `agent_briefed`，旧投影方式会让压缩后的历史仍然带着一条本该被摘要掉的原始 brief 消息，且当有两条时模型会同时看到新旧两份自我认知）。**否决**继续把 brief 当一条普通事件位置消息处理——那等于压缩窗口一关，agent 连自己是谁都会失忆。

### 2. 护栏硬停只在云端（E-F5）

ADR-0212 的退化循环护栏（周期重复注一句话不停）在本机成立的前提是"用户就在屏幕前，看见提示就会手动叫停"。云会话没有这个前提——spec §8 明说群里可能没人盯着。`LoopEngineOptions.loopGuardMaxNudges?: number` 是可选项、缺席 = 现状（本机永不停），云端 `engineFor` 设 **5**：命中次数到达时 `throw new Error("退化循环：护栏连续提醒 N 次仍在原地打转，本轮停止")`，走既有 `turn_ended{error}` 路径收口——不新造一条失败出口。**否决**改本机默认值——那会改变本机既有行为，与"本机会话字节不变"的约束冲突。

### 3. 接力 depth 与补跑上限都从日志重放推导，否决内存状态（A-4、A-9/#933）

**depth（A-4）**：`openingDepth = max(relay.depth ?? 0)`，取自「日志里 `mentions` 含本 agent、且还没被本 agent 的 `turn_ended.readUpToSeq` 收口」的全部 `user_message`——与 ADR-0220 `openTurns` 同一收口口径，纯函数放 `src/shared/agentRelay.ts`。**否决**内存 `pendingDepth`：daemon 重启即丢，那时新落地的开场白会被算成 depth=0，绕过棒数上限。

**补跑上限（A-9/#933）**：daemon 重启时会把之前未收口的开场白重新排队（"补跑"）。这是一条没有任何人发起、可能真花钱的模型调用，如果上一次补跑的死法是确定性的（比如那个模型端点本身返回 500），daemon 每次重启都会原样重放同一次失败，永远补跑、永远死。上限**记号也从日志推导**：补跑前先落一条 `turn_ended{outcome:"interrupted", agentId, readUpToSeq, error:"重启补跑第 N 次"}`——**每只 agent 一条，不是每条开场白一条**（同一只 agent 可能同时欠着两条未收口的开场白 U1/U2；若各开一条按自己的 seq-1 收口，晚开的 U2 那条记号会把更早的 U1 也顺手收了口，U1 从此再也不会被补跑捞回来，静默消失——见「Ruling」一节）。计数 = 该 opening 之后、该 agentId 的 `interrupted` 条数；`>= MAX_CATCHUP_ATTEMPTS`（3，导出常量）时改落真正收口（`outcome:"error"`），停止补跑。**否决**内存计数器——重启即丢，等于没有上限。daemon 启动时按会话线性错峰（`start + i * 1500ms`），避免同一台 VPS 上一堆会话同一 tick 起飞。

> **Ruling（复审 Critical 修正，见 progress.md Task 4c）**：记号改成每 agent 每次补跑一条，`readUpToSeq` = 该 agent**全部**待补跑开场白里最早那条的 `seq − 1`（对全部开场白中性，不会误收口更晚的那条）；`attempts(t)` = 该 agent `seq > t.seq` 的 `interrupted` 数（晚开的自然少算）；到顶收口 `readUpToSeq = t.seq`（只收它与更早的——更早的必然也已经到顶）；错峰按 `start + i*1500` 线性算，不是逐项累加等待（那样会变成 O(n²)）。代价：同一 agent 的多条开场白共用一个计数器，晚开的那条最多晚 1 次到顶。

### 4. 在籍复查（B-I1）与降级名单不挂连接器（B-I7）

`runJob` 起跑前 `await opts.isMember(job.fromUid)`，不在籍就落一条说得出原因的 `turn_ended{error:"发起人已不在这个工作区，这条 turn 不跑"}`（`readUpToSeq` = 日志尾）并 return，不起 turn；补跑段对每条 `t.fromUid` 同样过一遍，但那一段的 `readUpToSeq` 取**被踢/到顶那条开场白自己的 seq**（不是日志尾——日志尾此刻已经越过同一只 agent 更晚、仍然有效的开场白），**且同一只 agent 还有可跑的开场白时不单独落被踢收口**（终审 Important 1：反过来的顺序「在籍的 U1 在前、被踢的 U2 在后」时，U2 那条 `readUpToSeq = U2.seq ≥ U1.seq` 会把 U1 也关掉；它那轮自己的 `turn_ended` 收口时 `readUpToSeq` = 日志尾，本来就把被踢那条一起收了）。`isMember: (uid: string) => Promise<boolean | "unknown">` 是必需字段

**三态不是两态**（终审 Critical 1）：`"unknown"` = 在籍查询这一刻**查不出来**（Supabase 抖了），与 `false`（确认不在籍）分开——两者该做的动作相反。`membershipCache` 因此有两个出口：`isMember`（fail-closed，收帧路径用）与 `isMemberOrUnknown`（catch → `"unknown"`，daemon 接给 `CloudSessionOpts.isMember`）。`runJob` 见到 `"unknown"` 仍然不跑（发送者在线、看得见错误、能重发），只是文案换成「暂时确认不了你还在不在这个工作区，这条没跑，请重发」；**补跑段见到 `"unknown"` 什么都不写**（开场白留着、`console.warn` 一行，下次重启再问）。**否决**继续 fail-closed：daemon 启动时 N 条会话错峰补跑正是 Supabase 最不稳的那一刻，把一次抖动读成"被踢了"的代价是 append-only 的——每条排队消息一条永久收口，用户看到的是"你被移出了工作区"。——这是"退群/被踢之后还能用他的身份继续跑 turn"这个洞的唯一闸（B-M2 记的是同一个洞的另一半：`membershipCache.invalidate` 从未接线，见「已知代价」）。

`AgentSpec.degraded?: true`：`workspace_agents` 查询失败时的占位名单。见到 `spec.degraded` 就**不挂任何 px 刀**（`cachedPxTools = []`）并 `console.warn`——查询失败时名单是猜的，猜错的名单去拉真授权，等于用一份不确定的身份去动可能很贵的外部服务。**否决**"降级也照常拉授权、拉不到再报错"——那是在故障放大路径上再加一层隐式重试，读起来像正常运作。

### 5. 接力棒上的连接器要点火者批（B-C3）

`job.opening.relay` 存在（即 `openingDepth > 0`）时，`buildPxTools(..., { requiresApproval: true })`；人自己 @ 起的 turn 照旧 `false`。审批人仍是点火的那个人（`router.setInitiator(job.fromUid)` 不变，同 ADR-0223 决策"开场白的 `fromUid` 是点火的那个人"）。**否决**"接力棒上不挂 px 刀"——功能损失太大，一条接力链里的 agent 会突然什么外部服务都碰不到；也**否决**"按创建者取授权"——语义不明（创建者与点火的人是两个不同的人，用谁的授权说不清楚）。判据从最初实现的 `job.opening.relay`（布尔存在性）改成 `openingDepth > 0`（复审 Minor）：前者会被"折叠进同一个 opening 里的多次 relay 判定"绕过，后者与整条 depth 推导共用一份口径，归档跳过用的是同一个判据。

### 6. 型号白名单只在托管路生效，自带 key 路一律用 owner 配的 `modelId`（D1/D2）

`HostedRuntimeAdapterDeps.preferredModel?: () => string | undefined`（agent 白名单第一个，现读）。**只用于 hosted 分支**；**workspace（自带 key）分支一律用 `ws.modelId`**，不看 agent 白名单——`daemon.ts` 的 `cfg` 回到纯 `workspaceConfigStore.load(workspaceId)?.model ?? null`。**否决**"自带 key 路也读白名单"：自带 key 是 owner 一个人配的一把钥匙，接哪个模型端点是他的决定，agent 白名单管的是"这只 agent 该用哪一档"，两件事在不同的账户边界上，混在一起会让"owner 明明配了 GLM 的 key，某只 agent 却在打 Claude 的端点"这种事发生且没有任何界面能解释。

- **RouteMemo 每会话一份，放 daemon 不放 adapter 工厂的闭包里**（复审 Critical）：`adapterFor` 每 turn 重建一个 adapter，"上一次路由是什么"若存在那个闭包里就每次都是空的——回调因此**永不触发**，生产上一条 `route_changed` 都不会有，而测试里手工复用同一个 adapter 时它是绿的。

### 7. 换轨落账（D3）

`HostedRuntimeAdapterDeps.onRouteChanged?: (from, to, reason) => void`，`from`/`to` 取 `"hosted"|"workspace"`，`reason` 取 `"probe_failed"|"no_subscription"|"quota_exhausted"|"subscription_active"`。`decide()` 记上一次 `route.kind`，变了就回调；`route_changed` 事件的 `from`/`to` union **加** `"workspace"`，`reason` union **加**这三个值——只加不删（AGENTS.md 硬规则：事件 schema 只增不改）。daemon 的回调落 `store.append({type:"route_changed", ignorable:true, from, to, reason})`。`createHostedProbe.me()` 返回 `BillingMe | null | "unreachable"`——探不到与没订阅分开，`decideRuntimeRoute` 把 `"unreachable"` 当 null 用，只有 reason 不同（同 ADR-0221 #945 那条"`route` 为 `null` 不是 edge 抖了"的口径）。额度耗尽改道（D4）：hosted 路的 `resolveEndpoint` 第二次（reroute）调用时带 `exhausted: true` 重新 `decide()`，有自带 key 就回 workspace 端点，没有就抛原错；`decideRuntimeRoute` 加可选入参 `exhausted?`，为 true 时跳过 hosted 分支。

- **改道只在 `next.model === route.model` 时进行**（D2 边界，复审）：额度耗尽改道换的是**端点**不是**型号**——白名单型号与工作区型号不同时，改道会让这一轮悄悄换一个模型答话。代价写在明处：这种情形下该 turn 硬停（原错抛出），但 `noteExhausted` 已经在 `onReroute` 那一刻记下了这扇窗，**下一 turn 直接走自带 key**，不会卡死。

### 8. 用量按 agent 归因（D7，已落地）

`CloudSession` 加 `currentAgentId(): string | null`，daemon 的 `recordUsage` 展开 `...(agentId ? { agentId } : {})`——`ModelUsageEvent` 加的是可选字段，旧日志没有这个字段照常重放。与 ADR-0221 的 `usage_event.agent_id`（网关侧计费归因）是同一主题的两半：那边管的是托管路由花了谁的钱记在哪只 agent 名下，这边管的是本地 `model_usage` 事件本身该不该带上 agentId。

### 9. 共享记忆写入前置条件 + 重试一次（B-I3/B-I4）

`WorkspaceMemoryStore.write(ws, agentId, content, expected: string | null)`：`expected` = 这次 read 到的原文（缺行 = null）。Supabase 实现：`expected === null` 走 insert（撞 `23505` 视为冲突），否则 `update ... .eq("content", expected)` 并 `.select("agent_id")` 校验行数，0 行 = 冲突；冲突抛 `MemoryConflictError`。`workspaceMemoryTool` 在锁内整段 read→apply→write **重试一次**，第二次仍冲突才抛「记忆刚被别人改了，重试一次仍冲突」。**否决**乐观地直接覆盖——共享档是多写者可变状态（ADR-0222 已经点出这一点），不带前置条件的写会把另一只 agent（或桌面手改）刚落的内容静默冲掉。共享档条目写入前把 `[\r\n]+\s*` 折成单个空格（署名只盖一次，条目单行）——同 ADR-0224 决策 2 那条"短字段禁换行、否则能伪造出假卡片"的病，这里是记忆条目版本。

### 10. 审批拒绝三态可诊断（A-11/#927）

`ApprovalRouter.resolve` 与 `CloudSession.approve` 的返回类型从"成功与否"收窄成 `"ok" | "no_pending" | "not_allowed"`。`frameHandler` 按类型分两句人话（各自 `deps.log`）：`no_pending` → 「这条审批已经处理过或已过期。」；`not_allowed` → 「只有发起人或 owner 能批这条审批。」**否决**继续用一句笼统的「批准失败」——那会让"点晚了"和"你没有权限"这两件动作完全不同的事看起来一样，人分不清该重试还是该找别人。

### 11. 限速按点名数扣（B-I5）

`say` 帧的 `turn` 令牌按 `max(1, msg.mentions?.length ?? 1)` 扣（`rateLimit.allow(kind, uid, n)` 加可选第三参，缺省 1）。**否决**"一帧只扣一格不管点了几个人"：一句话 @ 三只 agent 会即时起三条 turn，产出的模型调用量是单点名的三倍，桶按帧计数量不出这个差别。

## 已知代价（本批接受、留给下一轮）

以下是审计发现但本批**不修**的项目，按台账（LEDGER.md）留言原样记录，理由各自不同：

- **A-7 审批冻结（Important）**：`drain()` 严格串行，一条挂起的审批会让整个群聊冻结最多 `DEFAULT_TIMEOUT_MS`（10 分钟）——排队中的其他 agent 一个都不跑，且能解锁的只有点火者或 owner（他很可能已经切走了）。本批不改协调器的串行模型（spec §2 的明确决定），但**这笔账必须写在这里**：至少要在审批卡上说清「超时会自动拒绝」，把「冻结」从无声变成有声。**决策 5（接力棒上的连接器要点火者批）把它从偶发变成了常态**——一条接力链只要碰到连接器就要点火者批一次，而点火者常常已经不在场，每次调用冻结群聊最多 10 分钟；缩短接力棒审批的超时另开 issue。
- **D5 `MAX_INFLIGHT` 按人不按档位（Important）**：ADR-0217 把扣费对象从发起人换成 owner 之后，并发槽位也跟着换了主——一个工作区所有成员、所有云会话，一起挤 owner 的 4 个槽位。这是产品档位决策（该不该按订阅档给更多槽位），留 issue 让 edge 团队定。
- **D8 自带 key 路的接力链没有花费天花板（Minor）**：托管路的隐含刹车是 owner 的 5h/周窗会把失控的链掐死（`quota_exhausted` → turn 失败 → 不再接力）；自带 key 路没有这个兜底，唯一的刹车是 `relay_max_depth`（上限 20）——`N=3, depth=20` 理论分支上限是 34 亿条 turn。留给下一轮加一个会话级总量刹车。
- **E-F6/F8（Minor，观测类）**：F6——链子中途插进一条人话点名会清空周期护栏的历史但不清空 depth，两层刹车不对称地重置；F8——接力起的 turn 完全绕过帧级限速桶（设计如此，写下来只是确认"限速桶保护的是帧处理成本，不是模型花销"这句话准确）。都不是本批阻断项。
- **`parseMentions` 的最长前缀会吃掉尾巴（Minor）**：名单里有「运营」时，一句 `@运营助理x` 被解析成点名「运营」+ 一段垃圾尾巴——匹配规则是 `text.startsWith(name, i + 1)`（前缀，不是整词），而 token 贪婪吃到下一个空白。@ 错人不会静默（群里看得见是谁答的），但确实点了一个人没打算点的 agent。留给下一轮。
- **B-M1/M2（Minor）**：M1——`profiles.name` 无约束，理论上能在开场白正文里塞进一段伪造的 `[管理员]: ` 前缀（署名解析本身不会被骗，但模型读到的是完整正文）；M2——`membershipCache.invalidate` 从未接线，踢人有 60 秒生效窗口（配合本批新加的 B-I1 在籍复查，窗口比"完全不查"小得多，但没有归零）。都留给桌面/安全那批的下一轮。

## 推翻它的前提

- 若 D5/D8 的并发/花费问题在真实使用中频繁触发（不是理论上限）——那时该谈的是给 `MAX_INFLIGHT` 按档位分级、或者给自带 key 路补一个会话级总量刹车，而不是继续把它们记在"已知代价"里不动。
- 若 A-7 的审批冻结在真机上造成过用户可感知的抱怨（群里长时间没人说话，实际是有人在等审批但没人知道）——那时该做的是把超时缩短并把"正在等谁批"广播进群聊，而不是只在卡片上加一句文案。
- 若 Task 6（D1–D4 的实现）落地后发现"型号白名单只在托管路生效"这条边界让自带 key 路的用户困惑（他们也想按 agent 分模型）——那时该重新评估是否给自带 key 路开一个独立的、不经过白名单的按 agent 选模型通道，而不是简单地把白名单judgment 挪过去。
- 若补跑记号的"每 agent 一条、按最早未收口开场白收口"这个折衷在实践中导致晚开的那条开场白经常被提前判定到顶（这是接受的代价，但如果频率高到影响可用性）——那时该考虑真正按 opening 分别计数，代价是要解决"更晚的记号误收口更早的开场白"这个 Critical 级别的坑（当初否决它的理由）。
