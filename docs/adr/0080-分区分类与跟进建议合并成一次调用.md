# ADR-0080: 分区分类与跟进建议合并成一次便宜模型调用

日期：2026-08-24
状态：已接受
关联：issue #284（勘察自 #283 的会话链路审查）；前身 ADR-0043（跟进建议）、issue #112（分区分类的自愈/围栏）、issue #279（尾段读取）

## 背景

turn 收口后有两次独立的便宜模型往返：sectionClassifier（章节标题）和 followUpSuggester（跟进建议）。同型号（helperModel）、同时机（turn 锁外、收口即排）、上下文高度重合（都以最后一轮问答为主）。每 turn 两次往返 = 双倍延迟、双倍最低计费开销。

## 决定

新增 `turnAnnotator.annotateTurn`：一份提示词两个任务块、一次 chat、一份 JSON 三字段 `{newSection, title, suggestions}`。**合并的是调用，不是判定逻辑**——跨度锚点、摘要、解析、清洗全部原地留在两个旧模块里当纯函数，annotateTurn 只做拼提示词 + 把同一份回复分别喂给 `parseSectionReply` 和 `parseSuggestions`。

两个解析器天然兼容合并回复：前者只认 `newSection`/`title` 两键、忽略其余；后者本来就接受 `{suggestions: [...]}` 形状。任一边形状烂掉只废那一边——分类靠锚点自愈（下轮把漏掉的跨度一并吃进来），建议下个 turn 自然有新的一批。

事件 schema 零改动：仍旧各落各的 `section_classified` / `suggestions_generated`，旧日志重放不受影响。

## 权衡

1. **建议跟着分类进串行队列**（原来即发即跑，无队列）。排队期间新 turn 收口的话，本次跑时读到的已是更新的最后一轮——结果一样，只是到得稍晚。省一次往返换这点延迟，值。
2. **失败耦合**：一次调用挂掉 = 这个 turn 两个功能都没有。二者都有独立的降级路径（自愈 / 下轮再生），耦合不放大伤害。
3. **账单只挂一条**：一次调用一份 usage，只落在先 append 的那条事件上（分区优先），否则 deriveUsage 会把同一笔算两次。代价是逐事件看账时建议那条显示为"没记用量"——deriveUsage 对缺省 usage 的语义本来就是"不出现在账里"，总账不失真。
4. **单边空的退化**：跨度空/问答空时提示词只含活着的那个任务块，回复形状随之缩窄，解析端天然兼容（缺键 = 那一边 null）。不为单边情形退回旧的单任务调用路径——少一条分叉，代价是单任务提示词里多几行框架文字。

推翻前提：若两个外挂日后换不同型号（比如建议换更便宜的），或时机分叉（建议改成输入框聚焦时才生成），合并的前提（同型号同时机）即失效，按此 ADR 反向拆回两次调用即可——纯函数都在原模块，拆的成本就是重写一个 20 行的调用壳。
