# ADR-0030：附件的三条入口共用同一道闸门

- 状态：已接受
- 日期：2026-08-19
- 相关：ADR-0009（附件库与日志的取舍）、ADR-0029（附件从气泡里搬出来）
- 授权：维护者 stanyan 在 2026-08-19 会话中要求「input 框可以让用户 paste 图片」「没做的也做」

## 背景

附件原本只有一条入口：＋ 按钮走系统文件选择器，主进程 `readFileSync` 后过
`intakeFile` 分类闸门（图片嗅探入库 / 文本读全文 / 其余拒收带理由）。
现在多了粘贴和拖拽两条——它们拿到的是 `File` 对象，不是路径。

## 决定

### 1. 闸门只有一道，在主进程

新增 `intakePastedFiles(files: {name, data}[])`：渲染层把字节递过去，主进程用**同一个**
`intakeFile` 分类。渲染层不判断"这是不是图片""够不够小"——判断散成两份，早晚会漂移成
两套策略（＋ 按钮收的东西粘贴收不了，或者反过来）。

代价是粘贴大文件要把字节过一次 IPC。可接受：图片上限本来就在闸门里，
真正的大文件会在那里被拒。

### 2. 限额逻辑在渲染层纯函数里共享

`lib/staging.ts` 的 `mergeStaged()`：并入暂存区 + 执行图片 ≤4 张/条 + 生成给人看的错误。
三条入口都调它。超额时**保留先来的**、裁掉后来的（"最后一张顶掉第一张"违反直觉），
被拒和被裁都必须出声——静默丢弃会让用户以为传上了。

### 3. 暂存区是全局状态，所以新会话 composer 也能收附件

`store.staged` 不属于某个会话。于是在欢迎页粘进去的图，`startSession` 之后由
`send()` 原样带走，不需要"先建会话才能贴图"这条多余的顺序约束。
同理，只贴图不打字也算一条消息——附件本身就是内容（两个 composer 同口径）。

### 4. 拖拽必须在 window 层兜底

Electron 里把文件拖到没人接的地方，Chromium 会把窗口导航到 `file://`，整个 app 就没了。
`main.tsx` 在 window 上捕获 `dragover`/`drop`，凡是没被投放区 `preventDefault` 过的一律吞掉。
这是保命的，不是体验优化。

## 什么情况下该推翻

- 如果将来要收超大文件（视频/数据集），"字节过 IPC"就不成立了，
  该改成渲染层只递一个临时路径、主进程自己读。
- 如果暂存区需要按会话隔离（比如同时开两个 composer 草稿），
  第 3 条的前提就没了，得让 staged 变成 per-session。
