# ADR-0198：工作区一期——连接器池是 escrow 群组化，发布制会话是包机制群组化，不新造执行面

日期：2026-08-30
状态：已接受
关联：issue #811（工作区一期设计对话）、ADR-0197（好友代理云端执行器凭证托管）、
ADR-0177（分享会话连带借出它用到的服务——确认前置，不自动全授）、
ADR-0162（好友代理的信任根是邀请码的一次性 secret，不是频道号）、
`docs/superpowers/specs/2026-08-30-workspace-phase1-design.md`（本 ADR 是它的决策摘要）

## 背景

工作区（团队频道）一期要做「成员名单 + 连接器授权池 + 会话列表」三样东西。这三样
听起来是新功能，但拆开看，好友代理（ADR-0151/0162/0164/0166/0168/0197）和分享
会话（ADR-0177）已经把「一个人把自己接通的东西借给另一个人」这件事的全部机制
——信任根、闸序、撤销级联、隐私剥离、上传/导入链路——实现过一遍了。工作区要回答
的问题只是「借给对象从『一个好友』换成『一群人』，机制要不要跟着换」。

设计对话过程中出现过两条会把工作区做成独立子系统的路：workspace 专用的
Escrow DO、会话快照走新的 jsonb 字段。这两条路都被否——本 ADR 记录为什么，
以及推翻 spec §1.2 初稿（jsonb 快照）的原因。

## 决策

### ① 连接器池 = EscrowGrant 加一个变体，不新造执行面

`src/shared/remote/pxEscrow.ts` 的 `EscrowGrant` 从只有 `{ friendUid, allow }`
一种形状，加一个 `{ workspaceId, allow }` 变体。贡献者依然是**自己的** escrow
箱子（ADR-0197 的 `(hostUid, serverId)` 托管单元不变），只是箱里多一种 grant。
edge 执行面（`services/edge/src/px.ts`）、`pxEscrowSync` 的四触发源 + 防抖上传、
`pxCloudClient` 的借用路由，全部原样复用——工作区连接器在执行链路上和好友代理
连接器走的是同一根管子，只是关系闸查的表不同（见②）。会话发布同理：`workspace_
sessions` 一行 = 分享会话包机制（0014/0015，见④）在「发给一群人」场景下的复用，
不新造存储、不新造脱敏/隐私闸。

一句话：**工作区不是第四个执行面，是好友代理 + 分享会话的群组化推广**。

### ② 关系闸现查在籍，不把成员名单复制进 DO

edge 的三道闸（身份 → 关系 → 白名单，ADR-0164 定的顺序）里，关系闸原本查
`friendships`；grant 是 `workspaceId` 变体时改查 `workspace_members`，要求
fromUid 和 hostUid 都在籍。

这里有一个岔路：把成员名单**复制**进 Escrow DO（省掉每次调用打一次 PostgREST），
还是**现查** Supabase（多一跳网络）。选了后者，理由是 ADR-0162/0168 已经定过的
同一条原则——**「撤销要说出口，而且要立刻生效」**。复制品必然滞后：owner 踢人
之后，DO 里的副本还认那个人在籍，直到下一次同步窗口。工作区场景踢人是常见操作
（不像好友关系那样近乎单向增长），滞后期就是一段「明明被踢了还能借用」的窗口，
比好友代理场景更难接受。所以代价——每次 call 多一跳 PostgREST——认了，60 秒
缓存兜底（与 ADR-0197「拿不到 ≠ 被清空」同一条查询失败语义），把常态下的额外
延迟压到可接受范围，但不允许缓存掩盖「已经不在籍」这个事实。

### ③ 任何成员都能贡献连接器，edge 编排零改动

好友代理的执行模型天然是「每个人管自己的箱子」——A 借给 B，箱子在 A 那儿。
工作区把这个模型原样搬过来：贡献连接器不是 owner 的特权，是**任何成员**都能做的
动作，因为贡献的本质只是「往自己的 escrow 箱里多写一条 grant」。这意味着一个
工作区的连接器池可能来自多个不同成员的箱子，而不是汇总到某个中心节点——edge
那边不需要知道「工作区」是什么，它看到的还是「hostUid 的箱子里有一条
workspaceId grant」，闸序、审计、撤销级联全部复用①②不变的机制。

代价对称地落在关系闸上：贡献者本人退群/被踢，他贡献的那些连接器跟着失效
（②的现查保证这一点立即生效），和「删好友 = 代理权限跟着死」同构。

### ④ 会话发布复用 session-packages 包机制，推翻 spec §1.2 初稿的 jsonb 快照

spec 初稿里 `workspace_sessions.doc` 是一个 jsonb 字段，直接塞脱敏后的会话快照，
并给了 2 MiB 上限。这条被本 ADR 推翻，改为 `pkg_id text`，指向
`session-packages` 桶（migration 0014）里 `{publisher_uid}/{pkg_id}/` 的包。

理由是包机制（ADR-0177 + migration 0014）已经把「一次性会话快照怎么脱敏、怎么
上传、怎么下载、怎么导入」这条链路走通了一遍：隐私闸剥离 log-only 事件、
manifest.json + events.jsonl + 附件字节的打包格式、Storage bucket 的 RLS。
jsonb 快照要把这条链路在数据库里重新实现一遍（脱敏逻辑可以共用，但存储介质、
大小限制、附件处理都得另起一套），而且 jsonb 的 2 MiB 顶不住附件——分享会话
今天已经支持带附件的包，工作区发布制会话没有理由退化成纯文字。

代价是下载权限不能再靠一条 RLS select policy 兜底：0014 的 storage policy
只认「上传者本人或 accepted 好友」，工作区成员之间不要求互为好友（spec §1.1），
所以需要一条新的 storage policy 认「上传者所在工作区的成员」。这条留给后续
migration：**复用 0014 的包机制，下载权限见 migration 0015 的 storage policy**。

### ⑤ 被否掉的路

- **workspace 专用的 Escrow DO**：把工作区的连接器托管挪到一个独立的、按
  workspaceId 分片的新 DO，与好友代理的 `Escrow`（按 hostUid 分片）并列。
  否掉的理由是撤销级联要清两处——一份凭据（贡献者的 OAuth token）如果同时
  密封进「按 hostUid 分片」和「按 workspaceId 分片」两个 DO，贡献者登出/撤销
  时必须保证两处都清干净，多一条能悄悄漏掉的路径；而①已经说明工作区连接器
  在语义上就是「贡献者自己的箱子里多一条 grant」，没有必要为它单独开一个
  存储单元。
- **自动全授**（会话发布/连接器入池时不弹确认框，默认把能借的都借出去）：
  ADR-0177 在 1:1 分享场景下否过一次，理由是「给你看我干了啥」和「你可以用我的
  身份下单」差得太远，不能靠隐式默认糊过去。工作区场景这条判断更成立——授权对象
  从「一个特定的人」变成「工作区全体成员（含未来加入者）」，知情同意的分量只增
  不减。一期沿用 ShareGrantDialog 同款确认框：默认全勾、可减，但**必须**过一次
  显式确认。

## 后果

| 面 | 结果 |
|---|---|
| 执行链路 | edge/pxEscrowSync/pxCloudClient 零新增执行路径，只多一种 grant 形状要 parse |
| 关系闸 | 每条工作区 call 多一跳 PostgREST 查 `workspace_members`；踢人立即生效，不受同步窗口影响 |
| 连接器归属 | 池内连接器分散在各贡献者自己的箱子里，没有单一中心节点；贡献者离群 = 他那部分立即失效 |
| 会话发布存储 | `workspace_sessions` 存 `pkg_id` 不存快照本体，本体在 `session-packages` 桶；需要一条新 migration（0015）补工作区维度的下载 RLS |
| 授权心智 | 「拉连接器进工作区」「发布会话带连带借用」都过一次 ShareGrantDialog 同款确认框，不做自动全授 |

## 推翻它的前提

- 若工作区场景下「踢人后短暂窗口内仍能借用」被证明可接受（比如工作区人数很小、
  成员流动率极低），②的现查代价可以重新评估，换成带失效通知的复制品。
- 若 session-packages 桶的 RLS 模型（按路径第一段 uid 判断归属）在工作区场景下
  证明扩展困难，④可能需要退回一个专门的工作区快照存储，但那时 jsonb 上限、
  附件支持这些问题需要重新设计，不是简单恢复初稿。
