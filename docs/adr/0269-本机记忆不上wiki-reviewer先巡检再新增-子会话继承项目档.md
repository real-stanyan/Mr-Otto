# ADR-0269：本机记忆的规模化路线——reviewer 先巡检再新增、子会话继承项目档、wiki 只预定给 TOPIC

原为 ADR-0268（合并前复核时与 #1152 的「别人的发言投影成群成员发言」撞号，按 ADR-0074 改到当时最大号 +1）

- 状态：已采纳
- 日期：2026-09-09
- 关联：issue #1155（本条的实现）、#1140（团队侧 LLM wiki，设计中）；承接 ADR-0060（文件是投影）/
  ADR-0116（三档与紧上限）/ ADR-0143（判据换向 + 点名守卫）/ ADR-0204（TOPIC 档，「长期不够用该上
  检索层」）/ ADR-0207（记忆跟账号走）/ ADR-0222（团队记忆，与本机不共用落点）；编号按 ADR-0074 在
  合并前复核

## 背景

团队侧（#1140）在评估把 Karpathy 式 LLM wiki（LLM 维护的互链 markdown 页 + index + log，
ingest / query / lint 三种操作）当记忆系统。维护者随即问了两个问题：本机记忆要不要也上；如果账号
重度使用了很久、记忆很多，要不要上。

先看了真机（生产账号 sessions.db，49 个会话，2026-08-17 → 09-03）：

| 项 | 数 |
|---|---|
| memory 工具调用 | 47 |
| 其中 memory-reviewer 子会话发起 | 32 |
| 写 MEMORY / PROJECT / USER / TOPIC | 41 / 3 / 3 / 0 |
| 报错 16，其中超限 | 13 |
| 全局档占用 | 1057 / 1100 字符，11 条 |

全局档 11 条里 5 条点名 Mr_Otto、另 2 条只在本项目为真，3 条与 AGENTS.md 逐字重复
（projectInstructions 每个会话本来就注入 AGENTS.md）。逼近上限、超限占报错八成，病根是**错档与
重复**，不是容量。ADR-0116 决策 3 自己写的上检索层的触发条件是「频繁顶到上限，且每一条都仍然为真」
——前半句成立，后半句不成立。

错档为什么拦不住，验出来是一个结构性的洞：`subagentRunner.run` 的 `createAgent({...})` 不传
`memory`，子会话日志里也没有 `memory_loaded`，`agent.ts` 推出的 `memoryProject` 必然是 `null`。
于是 ① `createMemoryTool(null)` 的 target 枚举里没有 `project`（ADR-0116 决策 4），reviewer 想写
项目档也写不了；② 点名守卫 `if (target === "memory" && project)` 整段跳过（ADR-0143 决策 2 的
「没有项目根时不设防」）。而 `buildReviewerTask` 在 `mem.projectRoot` 存在时照样拼 PROJECT 段、
指令里也讲三档判据——reviewer 被告知有项目档、手里却只有 memory 一格，项目事实只能落全局且不被拦。
日志里 5 条点名 Mr_Otto 的全局条目全部由子会话在 ADR-0143 落地之后写入；主会话那条被守卫拦了。
ADR-0143 把「存量错位靠 reviewer 的 replace/remove 收敛」当兜底，而 reviewer 恰恰是制造错位的那只，
且结构上搬不动。

## 决策

### 1. 本机四档不上 wiki；判据是「每个会话都用得上吗」，不是「记忆多不多」

wiki 赌的是「知识无限累积、按索引导航读」，本机记忆赌的是「小、慢变、全量注入」。两个赌注方向相反，
硬套只会把策展债藏进更大的容器。按重度、长期使用推演，四档分开看：

| 档 | 重度使用下怎么长 | 相关密度 | 结论 |
|---|---|---|---|
| USER | 有界。一个人的稳定偏好几百字写完，不随会话数长 | 每会话 | 不上 |
| MEMORY | 随工具数量长，慢、封顶几十条。重度开发者可能真顶到 1100 且每条为真 | 每会话 | 不上。真顶到了是重估上限（ADR-0116 决策 3 的推翻前提）；按需读会漏掉「跑 wrangler 前该知道的那条」，漏一次就是重蹈覆辙 |
| PROJECT | 代码项目的知识该进仓库文档：本仓 AGENTS.md 19 万字节，注入前 32KB，其余水獭自己读文件——这已经是项目 wiki 的形状，且人和别的 agent 共读。私有项目档只装本机差异，有界 | 每会话 | 不上 |
| TOPIC | 唯一无界的一档。领域知识随月份累积、状态会变；非 git 目录没有项目档，非程序员用户的全部「项目」知识也落这儿。8 桶 × 700 撑不过几个月 | 一个会话碰一两个主题 | **预定上**。ADR-0204 自己写了「长期不够用该上检索层」 |

wiki 三件套在本机的对应物：log = 事件日志（ADR-0060，本机更强）；ingest = 对话中 memory 工具 +
每 10 轮 reviewer（没有外部文档摄入，也没有这类需求的证据）；query = 全量注入 + session_search
（wiki 多一次工具往返，ADR-0204 明确否决过「注入索引 + 按需读」）；lint = reviewer 只在写入时去重
——**这是唯一真缺口**，决策 3 补它；index + 互链页 = TOPIC 档就是带上限的小 wiki（索引 + 8 桶），
今天零写入。

### 2. 子会话继承父会话的项目档（#1155 根因修法）

`createAgent` 加一格 `memoryProject?: {id, root, dir} | null`：给了就照它挂（`null` = 明确没有），
不给 = 照旧从 memory 快照 / 日志里的 `memory_loaded` 推导。`createAgent` 返回的对象把它暴露出来；
`SubagentRunnerDeps.parent()` 多带这一格，`subagentRunner.run` 原样递进 `createAgent`；两条派活路径
（task 工具 / nudge）都传。

**同一份对象，不重新解析**：键与路径必须出自同一来源（agent.ts 那段注释的原话），从 workspace 再
解析一次会造出「这个项目根配那个项目的记忆目录」的组合；子会话在 worktree 里跑时更是如此——父那份
已经按 ADR-0116 决策 1 折叠回主仓了。

**不动 ADR-0143「没有项目根时不设防」的边界**：Default 任务会话没有可搬的目标档，拦了也只是让模型
丢掉那条事实。

### 3. reviewer 先巡检再新增；巡检有证据纪律

`memory-reviewer` 指令改成两步、顺序固定。第一步逐条巡检既有条目：① 错档——MEMORY 里点名当前项目、
或只在当前项目里才成立的条目搬进 PROJECT（**先 add 进 PROJECT，成功后再从 MEMORY remove**：中途失败
不丢事实；没有项目档时不动，只在汇报里点出来）；② 与项目指令重复——项目指令节选里已经写明的事从
记忆里 remove（没附节选就不判）；③ 重复或近重复合并；④ 过时或矛盾——**只有对话或项目指令给出反证时
才改**。没有证据的一律不动：不猜、不删。第二步才是原来那件事（有没有新的、一周后仍然成立的事实值得记）。

证据纪律是这一条的承载部分：reviewer 跑在便宜档（`BUILTIN_MODEL`），一条仍然为真的事实被删掉比一条
过期的留着更贵——前者静默丢失，后者顶多让主会话多看一行。

`buildReviewerTask` 多收一格 `instructions`，把主会话本次注入的项目指令渲进任务串
（`reviewerInstructionsFrom(log)` 取日志里最后一条 `project_instructions`，渲成 `projectInstructionsText`
那同一份文案——**不另读盘**，reviewer 看见的必须是父看见的那份）。没附就不拼也不提，免得它对着一份
看不见的文档去猜。

### 4. 对团队侧（#1140）的一条约束

wiki 的纯层放 `src/shared/`——索引格式、页格式、链接规则、lint 判据；IO 两份，团队落 Supabase，本机
那天落 `memories/` 文件。照 ADR-0222 决策 3 抽 `applyEntryOps` 的先例：「超限且没变小才拒」那条教训
只有一份实现，wiki 的 lint 判据同理。本机 TOPIC 换 wiki 那天是接上去，不是重做。已作为评论留在 #1140。

### 5. TOPIC 换 wiki 的触发条件与形状（预定，不是本条实现）

触发两个并列：TOPIC 顶到上限且每条仍为真（ADR-0116 / 0204 那句）；用户开始往水獭里喂领域文档。
到那天的形状：策展纪律从「总量上限」换成「索引预算 + 单页预算」（索引满了合并页，页满了拆或压，逼
策展的精神不丢）；ADR-0204「只注入不读」限缩到 USER / MEMORY / PROJECT；`MAX_TOPICS` 与 700 上限作废；
ADR-0116「不做检索层」加一句「TOPIC 除外」；索引注入走 `memory_loaded` 的可选新字段，读页落
`tool_result`，写页落工具事件——文件仍是投影，ADR-0060 不用推翻；`MemoryTarget` 不动（手机端在用）；
云同步按文件后写胜，页是文件，天然兼容。

## 否决的备选

| 备选 | 为什么否 |
|---|---|
| 本机四档整体换成 wiki | 三档是「每会话都用得上」的有界内容，按需读会漏；PROJECT 的 wiki 已经在仓库文档里。见决策 1 |
| 加桶数加字数 | 全量注入线性涨，30 桶两万字符起步、每会话先吞五六千 token，九成与当前会话无关。ADR-0204「不是调数字」 |
| embedding RAG | 每轮按相关性换注入，system 每轮变、前缀缓存打穿（ADR-0116 否决 hermes prefetch 的理由）；新依赖；只取不整理，矛盾永远留着 |
| 子会话从 workspace 重新解析项目根 | 键与路径两个来源；worktree 里还得再折叠一次。见决策 2 |
| `project` 为 null 时全局档也拦已知项目名 | Default 会话没有可搬的目标档，拦了只是让模型丢掉那条事实；真正的洞在 reviewer 没有项目档，修那个 |
| reviewer 的巡检不给证据纪律 | 便宜档模型会把仍然为真的事实当过期删掉，静默丢失比留一条过期贵。见决策 3 |
| 项目指令节选另读盘 / 再截一次 | 读盘的那份可能已经不是主会话看见的那份；主会话注入已经过 32KB 预算，再截一次会让 AGENTS.md 后半的规则（merge commit、worktree 纪律）恰好落在截掉的那段——而重复的正是它们 |
| 现在就把 TOPIC 换成 wiki | 今天 TOPIC 零写入，它怎么长没有任何数据；触发条件一条都没出现。见决策 5 |

## 代价与天花板

| 面 | 结果 |
|---|---|
| 每次 nudge 多喂一份项目指令 | 最多 32KB（与主会话注入同一预算），跑在便宜档、每 10 个 user turn 一次。不设第二道截断，理由见否决表 |
| 恢复出来的子会话仍没有项目档 | `resumeChild.ts` 的 `createChildAgent` 没接 `memoryProject`——恢复时父可能已经不活着。reviewer 从不恢复；带 memory 工具的自定义子智能体恢复后写记忆仍是两档 |
| 存量错档要等下一次 nudge 才收敛 | 守卫只拦新写入；这份 ADR 的巡检在下一次 Mr_Otto 会话的第 10 轮才跑 |
| 巡检的证据纪律靠提示词 | 没有机制保证 reviewer 不猜；机制层只有 ADR-0143 的守卫（拦错方向的新写入）与 `applyOps` 的原子批量 |
| 手工冒烟一次都没跑 | 纯逻辑与装配契约有单测；reviewer 对两步指令的实际遵守 UNVERIFIED |
| 决策 1 的推演部分不是实测 | 「重度使用下四档怎么长」是按内容类别推的，TOPIC 零写入意味着那一行没有数据 |

## 推翻它的前提

- TOPIC 出现决策 5 的任一触发 → 按决策 5 的形状上 wiki，纯层从团队那份接。
- MEMORY 在正常使用下频繁顶到上限且每条仍为真（错档修掉之后仍然如此）→ 重估 1100 那个数
  （ADR-0116 决策 3 的推翻前提），不是上 wiki。
- reviewer 巡检实测误删（用户手改回去的次数可观）→ 收紧成「只搬不删」，删这一步交给设置页的人。
- 恢复出来的子会话真的需要项目档 → `createChildAgent` 从子会话自己的 `session_created.workspace`
  解析一次（那时接受「两个来源」的代价并写清楚）。
