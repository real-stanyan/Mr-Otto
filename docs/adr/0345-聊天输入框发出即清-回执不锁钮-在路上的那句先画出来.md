# ADR-0345：聊天输入框发出即清——回执不再锁「发送」钮，在路上的那句先画在时间线上，发送排成一条链

- 状态：已采纳
- 日期：2026-10-04
- 关联：issue #1473；回执三态的来历 ADR-0228（第四批，C2-I4）；输入栏本体 #1386（`WxComposer`）；云 runtime 搬家 #1450；网关 / DO 放置的延迟账 ADR-0301、#1304；编号按 ADR-0074 在合并前复核

## 背景

维护者口述：用户在聊天里发一条消息，要点好几下「发送」才发得出去。

查下来不是网络、不是新宿主、不是中继掉线：

- #1450 把云 runtime 搬到 WSL2 之后，那台到 Supabase / edge 的 DNS + HTTPS 往返都在 70ms 上下，与旧 VPS 同量级。
- 中继 socket 的 `code=1006` 掉线旧机每天 140–250 次、新机更少，是既有行为。
- 以 dev 号经中继进真会话量出来的数（`cloudSessionClient` 原样接线，SYD 这头）：join → ready **2.8s**；一条不碰任何状态的 `stop` 帧往返 **680–930ms**；DM 里一句 `say` 到 `say_result` **847ms**。群里不 @ 的话还要过派活分类器（ADR-0301：一发 ~1.4s），会话刚 ready 时更久。
- 而手机输入栏（`mobile/src/chat/WxComposer.tsx`）的写法是：按下「发送」→ `sending=true`、钮灰掉 → **等回执** → 回执 ok / unknown 才清空输入框。期间文字留在框里、钮按不动、每一下点击都被无声吞掉。一秒上下的回执在人眼里就是「我点了没反应」，于是再点、再点，直到回执到了字才消失——「点好几下才发出去」正是这个过程的体感。桌面云会话页是同一个写法（`CloudSessionPage.tsx` 的 `submit`），这条 ADR 先只动手机。

`stop` 往返 700ms 这个地板本身另有一笔账：这些会话房的 Durable Object 是 runtime 还在赫尔辛基时建的，DO 一旦建成就钉在那个区域，SYD 的手机与 BNE 的 runtime 都要绕去欧洲（ADR-0301 量过：从 HEL 一趟 DO 往返 ~344ms，在 SYD 是 40ms）。这是 #1304 那条线上的事，不在本 ADR 里解决——就算把它降到 100ms，等回执再清框的写法照样会在群里（分类器）与刚 ready 时让人等。

## 决策

### 1. 发出即清：输入框在 `await onSend` **之前**清空，「发送」钮没有 sending 锁

`WxComposer.submit`：取出文字 → 当场清框 → 再 `await onSend(text)`。回执三态（ADR-0228）的**语义不变**，变的只是时机：

| 回执 | 以前 | 现在 |
|---|---|---|
| ok | 清框 | 框早已空，什么都不做 |
| unknown（15s 没回执 / 断线） | 清框，原文去「不确定」那一行 | 同左 |
| 确定失败（限速、@ 太多、名单读不出来……） | 原文留在框里 | **原文摆回框里**；人已经在打下一句就先记着，等框空了再摆（离开页面时记着的那句存成草稿，不丢） |

「确定失败留原文」这条纪律的目的是让人改一改再发，摆回去与留着在这一点上等价；差别只在成功路径上少等了一次往返。

### 2. 在路上的那句先画在时间线最底下（`chatStore.outbox` + `PendingMineRow`）

框清了、真的那条事件还要几百毫秒才回来，中间屏幕上什么都没有，人会以为字丢了。所以 `sendText` 在发之前把这句挂进 `outbox`，聊天页按「我说的」那一行画、气泡旁一个小转圈（照微信）；回执落定（三态任一）就摘掉。**不按内容匹配真事件**：服务端先广播 `user_message` 再回 `say_result`，两帧走同一条连接按序到，摘掉那一刻真的那条已经在 rows 里了，看起来只是转圈消失。unknown 那一档摘掉之后接的是「不确定」那一行（既有），不会出现「什么都没有」。

### 3. 发送排成一条链（`src/shared/sendQueue.ts`）

框不锁了，人就能在上一句回执没回来时发第二句，而 `cloudSessionClient.say()` 对「上一句还没有回执」的第二次 say 是**直接拒**的（回执不带请求 id，并发在客户端分不出谁是谁的——#957 第三批定的）。把排队放在 store 那一层：`createSendQueue().run(fn)` 一句一句发，前一句的结局只交给它自己的调用方，失败不拖后一句。朋友私聊（`friendsStore.sendToFriend`，直写 Supabase）走同一条队列——不是因为会被拒，是落库顺序要跟手指顺序一致。

**否决「让客户端的 say() 自己排队」**：那是 shared 层、桌面也用；桌面还没改成发出即清，给它一条它用不到的队列只会让 `pendingSay` 那段「不排队」的注释变成假话。等桌面也改时再把队列下沉。

**否决「服务端早点回 ok」**（落盘前先 ack）：`say_result{ok}` 的定义是「这句话进日志了」（#964），提前回就是把回执变回「帧交给 socket 了」那个 #957 之前的假信号。

## 后果

- 新包（或 OTA）之后：点一下字就走、气泡带转圈当场出现，不再有「灰钮 + 字留着」的窗口；连点两下第二下看到的是空框，不会重复发。
- 排队之后两句连发的第二句要等第一句的回执（~1s）才真正出门——转圈多转一会儿，但顺序对、不会被拒。
- 朋友私聊只接了队列，**没有**本地转圈气泡（它的往返是一次 Supabase insert，一两百毫秒，框空了之后气泡几乎立刻出现）；要是真机上觉得有空档再补，同一个 outbox 形状。
- 桌面云会话页仍是等回执再清（`CloudSessionPage.submit`）——同样的病，另开 issue 按同一个形状改。
- 会话没 ready（连接中 / gone）时钮照旧禁用：那不是「在等回执」，是真的发不出去；这一段 2.8s 的 join 与 DO 放置是 #1304 那条线上的事。
- 可执行版：`tests/mobile/sendQueue.test.ts`（队列三条性质）、`tests/mobile/composerOptimisticSend.test.ts`（读源码钉住「清框在 await 之前 / 没有 sending 锁 / 确定失败摆回」与 outbox 接线——RN 组件进不了 vitest，同 activityFace.test.ts 的做法）。
