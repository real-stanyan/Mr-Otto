# ADR-0213：门禁跑在哪个 node 上要说出口，没被跑的测试文件要红

## 背景

issue #897 报的是：同一份 checkout、同一条 `npm test`，node 20 与 node 25 给出两个答案 ——
node 20 上有一批测试文件**根本没跑**。病根查得很准：better-sqlite3 13 的
`prebuilds/darwin-arm64.node` 在 node 20 上 `new Database(...)` 那一刻段错误
（`require` 是好的，构造才崩），于是每个 `new EventStore(...)` 的文件，worker 在跑
第一条断言之前就没了。CI 用 node 24，所以 CI 一直是对的，本机一直是错的。

**但它的标题只对了一半，另一半在动手前先验掉了**（AGENTS.md「读到判断先验前提」那条）。
本班在 worktree 里实测：

```
$ PATH=~/.nvm/versions/node/v20.20.2/bin:$PATH npm test ; echo $?
 Test Files  370 passed (403)
      Tests  4503 passed (4856)
     Errors  50 errors
1                      ← 退出码是 1，不是 0
```

所以「静默」不成立：**门禁在 node 20 上是红的**，`npm test` 会失败，CI 契约没有被绕过。
真正的问题是它红得**不像环境问题**——摘要行写着 `370 passed`，没有一行 `failed`，
差值只出现在括号里，读起来像「有几个用例挂了」。#897 的建议 2（「收集数与跑完数不一致
应当直接失败」）其实 vitest 已经做到了；照着它做等于加一条不改变任何结局的断言。

把前提验清之后，剩下两件**各自成立**的事：

1. 归因错位：一个环境问题伪装成代码问题，代价是下一班的排查时间（这次已经花掉一次）。
2. 一个**真的**安静的漏跑形态，与 node 版本无关：**文件名没落进 vitest 的 `include`**。
   那种情况没有错误、没有 skip 计数、没有括号里的差值，门禁全绿。
   `vitest.config.ts` 的注释里记着它已经发生过一次——补上 `.test.tsx` 之前，
   本仓压根没有任何 `.tsx` 测试被执行过，而没有人发现。

## 决定

### 一、门禁开跑前先说出 node 版本对不对（`scripts/check-node.mjs`，挂在 `pretest`）

低于门槛就早退，报错里带上：当前版本、要求、病根一句话、以及**怎么修**（`nvm use 24`）。

这不是重复 vitest 的失败，是把失败的**归因**从代码挪回环境。同一次失败，
从「50 个文件报了错，去看看是谁写坏了」变成「你的 node 版本不对」。

门槛取 **`>=22`，不取 `.nvmrc` 里的 24**：20 实测坏、22 实测好（420 files / 5000 tests 全绿），
21 没验过。下限写实测跑通的最低版本，`.nvmrc`/CI 的 24 是推荐值——两者不必相等，
把下限抬到 24 等于用一条没有证据的断言去挡一个能正常工作的运行时。

`package.json` 同时补 `engines.node: ">=22"`，让 `npm install` 也会念一句。

### 二、`tests/` 里 import 了 vitest 却不在 `include` 里的文件，直接红

`tests/architecture.testDiscovery.test.ts`。判据是「这个文件 import 了 vitest」：
本仓的 vitest 没开 `globals`，所以任何真在写断言的文件都必须显式 import 一次——
信号既准又难绕过。规则一条：**要么是配置里点名的 setupFile，要么必须落进 `include`。**

`include` / `setupFiles` 从 `vitest.config.ts` 读出来，不在断言里抄一份：抄一份就会有
一天两边不一样，而不一样的那天，正是这条断言该保护的那天。

`tests/e2e/` 不必单列例外：那批走 playwright、不 import vitest，自然过关；
而万一有人把一条 vitest 测试写进 e2e 目录（那里故意不在 gate 的 `include` 里，ADR-0138），
这条断言恰好把它接住。

## 否决掉的路

- **`.npmrc` 里 `engine-strict=true`**（#897 建议 1 的强化版）。它会让 `npm install` 在
  版本不符时直接失败——听起来更彻底，代价是这个开关**同时校验所有依赖的 `engines`**：
  任何一个声明了 `"node": "^18 || ^20"` 的传递依赖，都会在 node 24 上把 `npm ci` 打红，
  而那是 CI 装依赖的那一步。用一个能锁死 CI 的全局开关，去换一个 `pretest` 一行就能做到
  的检查，不划算。
- **照 #897 建议 2 加「收集数 ≠ 跑完数就失败」**。验完发现 vitest 已经这么做了（退出码 1）。
  加一条不改变任何结局的断言，只会让下一个人以为这里有一道闸。真正缺的闸是「文件压根
  没进 `include`」，那条另立（决定二）。
- **把门槛写成 `>=24`（对齐 `.nvmrc` 与 CI）**。见决定一：22 实测是好的，拦下它没有依据。

## 顺带核对（#897 建议 3）

`npm run rebuild-native`（electron-rebuild）跑完之后本机门禁还能跑：
`tests/session/store.test.ts` 39 passed，rc=0。原因是 electron-rebuild 把 Electron ABI 的
产物写进按 ABI 编号的目录（`node_modules/node-pty/bin/darwin-arm64-148/`），
没有覆盖 node ABI 用的那份 `prebuilds/`。所以那条路**不是**同款症状的第二个成因。

## 天花板

- 这道闸只认版本号，不认「这个 node 上 better-sqlite3 到底能不能构造」。真正的判据是后者，
  但要测它就得在 `pretest` 里起一个子进程 `new Database(":memory:")` ——为一个已知成因
  付一次每跑必付的开销，不划算。哪天出现第二个成因（另一个版本、另一个 prebuild）
  再换判据。
- 决定二只管 `tests/` 底下。测试文件放到别处（比如与源码同目录）不会被这条接住——
  不过那本来就被「测试统一放 `tests/`」那条约束挡在前面了。
