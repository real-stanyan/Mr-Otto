# ADR-0294：手机端的类型检查进根门禁，CI 在 `npm test` 之前先装 `mobile/` 依赖

- 状态：已接受
- 日期：2026-09-12
- 关联：issue #422（Protocol gap，2026-06 开着到现在）；#1237 spec §11 第 2 条（维护者 2026-09-11 拍板走 B）；收口 `tsconfig.json` 里那句「这是临时状态」
- 层级：**L1**（门禁一节 + `npm test` 断言什么，ADR-0006 / ADR-0020）

## 背景

计划 B 往仓库里加了 `mobile/`（Expo/RN，自带 package.json 与 node_modules）。当时的临时做法是
**A：根 tsconfig 排除 `mobile/`**，理由写在 tsconfig 的注释里——改动面最小、最容易回退，
因为 B 和 C 都要动 `.github/workflows/ci.yml`，而「CI == Gate 契约」恰恰没说那里能不能动。

代价当时就记下了：**在这条 gap 收口之前，`mobile/` 的类型错误进不了门禁**。

它不是一句空话。#1237（手机端三栏重设计）一个 PR 就动了 41 个手机端文件、3551 行，
全靠实现者手跑 `npm --prefix mobile run typecheck` 再把结果抄进 PR 正文。手跑的东西迟早有人忘，
而忘了不报错——**这正是本仓反复点名的那类静默失败**。

## 决策

**走 B。** 三件事：

1. **根 `package.json` 的 `typecheck` 末尾串一句** `npm --prefix mobile run typecheck`。
   于是 `npm test` 断言三件事：根 `tsc --noEmit`、手机端 `tsc --noEmit`、`vitest run`。
2. **CI 在 `npm test` 之前多一步** `npm --prefix mobile ci`。
3. **忘了装依赖由一道闸说人话**：`scripts/check-mobile-deps.mjs` 挂在 `pretest` 上。

### 为什么 tsconfig 的 `exclude: ["mobile"]` 留着不动

「排除」与「进不进门禁」是两件事，上一版把它们当成了一件。`mobile/` 那份 `@types/node`
版本与根这边不同，编进同一个 tsconfig 会把根这边的类型带歪；它该由 `mobile/tsconfig.json`
（`expo/tsconfig.base`）自己管。所以**编译单元分家照旧，门禁靠多跑一条命令合回来**——
与 `services/edge` / `services/runtime` 早就在用的形状逐字相同（那两条也是各自 `-p` 一条 tsc）。

这同时答了 issue #422 里那个问题 3（「收窄 `tsc --noEmit` 的范围算不算 ADR-0020 的 loosening」）：
收窄的那一版是 A，本 ADR 把它翻过来了；`exclude` 留着不再是收窄，因为被排除的那部分现在由
**同一道门禁的另一条命令**断言。

### 为什么这不破「CI == Gate 契约」

AGENTS.md 说的是**命令行**要与 `.github/workflows/ci.yml` 逐字一致。`npm ci` 一直就在 `npm test`
之前，ci.yml 里那行注释也早就写着「依赖安装是门禁的前置管线，不是门禁本身」。
`npm --prefix mobile ci` 与它同类：**Gate 命令仍逐字是 `npm test`**。

这答了 #422 的问题 2（「多一步安装算不算改了门禁」）：不算——改的是「跑得起来的前提」，
而那个前提从第一天起就在（没有 `npm ci` 谁也跑不了 `npm test`）。

### 为什么要有 `check-mobile-deps.mjs` 这道闸

不装的失败形态是：`npm test` 跑到最后一段，npm 回一句 `sh: tsc: command not found` 加一串它自己的
error 栈。读起来像门禁坏了、像 tsconfig 配错了，而真相是这台机器还没装 RN 依赖——
**一个只改桌面的人没有任何理由先装一遍 Expo**，所以这句话必须由我们说出口。
分工与 `scripts/check-node.mjs` 逐字相同：把失败的**归因**从代码挪回环境。

判据取 `mobile/node_modules/typescript`（`.bin/tsc` 指向的那个包）而不是 `node_modules` 目录本身：
装了一半、或只软链了外壳的目录都能让后者为真，**而它为真恰恰是这道闸最该说话的时候**。

## 否决的两条

- **A（维持现状：排除 + 手跑）**：失败模式是静默的，而它要守的是一整个正在快速长出来的客户端。
  #1237 那 41 个文件是第一个规模证据，M2–M7 还有六个子项目。
- **C（单开一个 path-filtered CI job）**：它把「门禁是哪一条命令」变成两个答案——
  本机跑 `npm test` 与 CI 上跑的不是同一套断言，而 CI == Gate 契约存在的全部理由就是不让这两者分家。
  path filter 还会让「改了 shared 但没改 mobile」的 PR 跳过手机端检查，
  而 `src/shared/` 正是两端共用的那一层（#1237 往里挪了 `mobileGate` / `authError` / `color` 等多份）。

## 后果与代价

1. **纯桌面改动的人也要装一次 RN 依赖**（`npm --prefix mobile ci`，一次即可）。这是 B 明写的代价，
   维护者拍板时接受了。闸门那句话把它从「玄学失败」降成「一句 copy 过去就能跑的命令」。
2. **CI 每次多一步安装**（`mobile/` 的依赖树不小）。没有加 cache——本仓的 `npm ci` 也没加，
   要加就两条一起加，那是另一件事。
3. **那道闸挡得住「没装」，挡不住「装旧了」。** 判据是 `mobile/node_modules/typescript` 在不在，
   而一份**过期**的安装里它照样在。2026-09-13 本条 PR 自己踩到了：把 main（此时已含 #1237 的三栏客户端）
   并进来之后，手上那份 `mobile/node_modules` 还是 #1237 之前装的，于是门禁吐出 20 条
   `TS2307: Cannot find module '@react-navigation/native'` —— 读起来像代码坏了，实际是依赖旧了。
   CI 不受影响（每次 `npm ci` 都是全新安装），**这一条只影响本机**。没有把它做成断言：
   要判「装的是不是这份 lock」就得把 npm 的活重做一遍，而它真正的修法只有一句 `npm --prefix mobile ci`。
   撞上一屏 TS2307 时先跑那一句。
4. **手机端的测试仍然不在门禁里**：`mobile/` 没有测试运行器，纯逻辑一律挪进 `src/shared/`
   由根 vitest 覆盖（#1237 spec §7）。#422 标题问的是「类型检查与测试」，这里只收口前半；
   后半不是 gap 而是设计：`mobile/` 里不该有值得单独跑的纯逻辑。
5. `mobile/README.md` 与 #1237 spec §8 第 3 条里「类型检查不在门禁」的说法从此作废。
   spec 那份属于另一条分支，合并顺序见下。
