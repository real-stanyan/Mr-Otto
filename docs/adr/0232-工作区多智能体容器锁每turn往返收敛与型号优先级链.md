# ADR-0232：工作区多智能体——同工作区多会话的容器锁、每 turn 网络往返收敛、型号白名单改成优先级链

- 状态：已接受
- 日期：2026-09-06
- 关联：issue #979；上游 ADR-0199（一工作区一容器一卷）/ 0152（桌面 workspaceExclusion：只拒绝不做魔法）/ 0161（桌面 coworkLog）/ 0202（「每次现读」）/ 0219（brief）/ 0223（接力）/ 0224（create_agent）/ 0228（stop 与 turnBoundary）/ 0231（前三条）
- 来源：ADR-0231 那次全量复审剩下的七条候选里，维护者点名的第 2、5、4 条

## 背景

复审把「已知代价」之外没记账的问题排了序，ADR-0231 做了 1/3/7。这次是：

2. **同工作区多条会话共用一容器一卷、零互斥。** 每条会话各自 `drain`，两条会话里的 agent 能同时在 `/work` 里 `cat > 同一个文件`、一边 `git checkout` 一边改文件。桌面那套 `workspaceExclusion`（ADR-0152）/ `coworkLog`（ADR-0161）在 `services/runtime` 里一处都没接。
5. **每 turn 起模型之前先打约五次网络。** `isMember`（60s 缓存）+ `agents()`（无缓存，一条会话里 `say()` / `runJob` / `relayAfterTurn` 各查一遍）+ `memory.read` + `hostUids()`（无缓存，与在籍判断是**同一条 SQL**）+ `fetchGrantedTools`（每个成员一次 edge）。「现读」的纪律没错，错的是每条读路径各打各的。
4. **型号白名单是假多值。** `workspace_agents.models` 是 `text[]`，表单写「逗号分隔，第一个是默认」，spec §3 说「具体哪一次用哪个留给会话级选择」——可只有 `models[0]` 有消费方（`daemon.adapterFor` 的 `preferredModel`），其余元素没人读，也没有任何会话级选择的入口。

## 决策

### 1. 容器锁：一个工作区一把、按会话排队、**第一次碰容器才拿**

- `services/runtime/src/workspaceLock.ts`：FIFO 锁，`acquire(owner, signal)` 可中断，放锁幂等，不可重入。daemon 按 `workspaceId` 一把（`createWorkspaceLocks`）注入 `CloudSessionOpts.workspaceLock`（**必需**，忘接线该编译不过）。
- sessionService 把 `opts.world` 包一层：`fs.read` / `fs.write` / `exec` 三条路先过 `gateContainer()`，**第一次碰容器才拿锁**，这一轮收口（`runJob` 的 `finally`）才放。只聊天不动手的 turn 一次都不排队。
- **排队等，不拒绝**——与桌面 ADR-0152「只拒绝不做魔法」故意不同。桌面拒绝的理由是「没有要 release 的锁，状态就是 `engine.runningTurnId`」；云端所有会话都在同一个 daemon 进程里，`try/finally` 就是全部的失败模式（进程死了锁跟着死）。而云会话的 turn 本来就是排队制的，「排队中」那盏灯早就在——拒绝反而要用户把话再发一遍，而那句话已经落盘、`openTurns` 欠着它一个回答。
- **等待可被停止键打断**：`abortCurrent` 除了翻 engine 的信号，还翻这一轮的 `jobLockAbort`——engine 的信号打不到一次还没起 `exec` 的等待，不翻的话「停止」要等别的会话做完才生效。
- 排队时在群里说一声（`CONTAINER_BUSY_TEXT`，`chat_message{fromUid:"system"}`，一轮一次）：不说的话「另一条会话占着容器」与「模型卡住了」在界面上长得一模一样。它是模型可见的（`agentView` 里 `chat_message` 是 keep），正在等的那只自己读得到。
- 粒度是**会话**不是 agent：同一条会话内 `drain` 本来就串行。也不是 `docker exec` 粒度：那只挡得住两条 `cat >` 撞车，挡不住「A 读了、B 改了、A 按旧内容写回」。

### 2. 每 turn 的读路径改读快照，由本进程的写路径失效、由人的动作强刷

- `services/runtime/src/ttlCache.ts`：按 key 记忆化一条异步查询。三条规矩同 `membershipCache`：抛错不写缓存；同 key 并发 `get` 合并；`refresh` 绕过缓存**也绕过 inflight**（它的语义是「此刻之后的事实」，并进一次已经在路上的查询会拿到那次开始之前的快照）。
- **agent 名单**：daemon 用 60s 快照包 `queryAgents`。`CloudSessionOpts.agents` 多一个可选参数 `{fresh:true}`——`say()` 递（人刚开口，他在设置页刚建/改的那只要能立刻 @ 到）；`runJob` / `relayAfterTurn` 不递（接力链内每一棒不再各打一次）；`create_agent` 落库后 `invalidate`（daemon 把 `agentWriter` 包了一层）。`queryAgents` 本身仍是「如实报告」，缓存住在装配点。
- **成员名单**：`membershipCache` 多一个出口 `members()`，与在籍判断共用同一份 60s 缓存；`hostUids()` 从它读。查询抛错原样抛不回空集——「拿不到」≠「没有成员」（同 ADR-0197 grants 缓存的规矩），sessionService 那侧接住、本 turn 不挂代理工具（既有路径）。
- **授权拉取**：sessionService 按（发起人，成员名单）记一份 60s 快照（`grantedFor`），只缓存成功结果。撤销不受影响——每次调用 edge 的 `pxGate` 都重判，快照里那把刀只是「摆出来给模型看」，用不了。
- **故意不缓存的**：`memory.read`（共享档是多写者可变状态，ADR-0222 的核心判据）；`sandboxApproval` / `relayMaxDepth`（只在撞门 / 接力时才读，不是「起模型前」的固定开销；且 `auto → ask` 那个方向缓存 60s 是往松的一边倒）；`hostedProbe` 已有 60s 缓存。
- 收敛后的账：第一轮 = 在籍 + 名单 + 记忆 + 成员 + N 次 edge；60s 内的每一轮 = **记忆一次**（其余全部命中）。

### 3. 型号白名单是**优先级链**，不是「第一个 + 一串没人读的」

- `decideRuntimeRoute` 的 `requestedModel: string | null` 改成 `requestedModels: readonly string[]`：按顺序取网关供着的第一个；一个都不供才退网关第一款。adapter 拼链：agent 白名单按顺序 → 工作区配的那款 → 网关第一款。
- 这条链**只喂 hosted 分支**——#957 D2 原样成立：自带 key 那条路一律用 `workspace.modelId`，白名单是群里任何成员都能改的一串字符，不能原样发给所有者自己的 provider。
- 一处行为变化：原来白名单第一个网关不供时**跳过**工作区配的那款直接退网关第一款（`preferredModel() ?? ws.modelId` 的 `??` 只在缺席时才看后者）；现在工作区配的那款排在网关第一款之前——daemon 的注释一直写的就是这个顺序，代码没跟上。
- 表单文案改成说实话：「逗号分隔，按顺序取托管网关供着的第一个；留空用工作区的型号」+ 一句「只对订阅托管那条路生效」。`create_agent` 工具的参数描述同步。
- **spec §3 的「会话级选择」这次不做**（spec 加一行注记指到本 ADR）：它需要 `cs_say` 带型号 + 每句话一个选单，产品上没人要过；数组的意思改成「优先顺序」之后它已经不是假多值了。要做会话级选择那天，链的第一环换成会话选的那款即可。

## 后果

- 容器锁把**跨会话**的互踩收成排队；**同一条会话内**两只 agent 本来就串行。代价：一条会话里一次要等 10 分钟审批的 turn 会把另一条会话的工具调用一起冻住（ADR-0231 的 `auto` 开关是这条代价的解药）。
- 快照的代价明写：桌面直连 Supabase 的建/改/删 agent（不经 daemon）在接力链内最多 60s 后可见，人自己 @ 的那一轮仍然现读；好友新授出的连接器最多 60s 后才挂上；成员被踢与在籍判断同一个 60s 窗口（本来就是）。
- 白名单链只对托管路有意义；自带 key 路仍然是单值。表单没有按路由分两个输入框——那是把「路由」这个 runtime 概念搬到设置页上。

## 验收（真机，UNVERIFIED）

1. 同一个工作区开两条云会话，两边各 @ 一只 agent 跑 `sleep 20`：第二条的时间线出现「容器正被另一条会话占着」那句，第一条跑完第二条才起；第二条等待期间按停止，它这一轮 aborted 收口且没跑命令。
2. 一条会话里连 @ 三次同一只 agent（60s 内）：runtime 日志里 `workspace_agents` / `workspace_members` / `/px/v1/grants` 各只打一次。
3. 设置页给一只 agent 填「不存在的型号, glm-5.3」（后者订阅供着）：它的 `assistant_message.model` 是 glm-5.3；工作区自带 key 时仍是工作区配的那款。
4. 管理员 `create_agent` 建出一只后，同一轮里别的 agent 接力 @ 它能接上（快照已失效）。
