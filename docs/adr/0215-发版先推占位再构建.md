# ADR-0215：发版先推 main 占位再开始构建，tag 最后才出门

- 状态：已采纳
- 日期：2026-09-03
- 关联：issue #679（发 v1.1.0 时真踩到）、ADR-0075（release.mjs 的由来）、ADR-0048（多 lane 并行是常态）

## 背景

`scripts/release.mjs` 原来的顺序是：

```
npm version（升版 + commit + tag）→ dist:mac → dist:win → SHA256SUMS
  → git push origin main --follow-tags → gh release create
```

中间两步构建约十分钟。发 v1.1.0 时，这期间另一条 lane 合了 PR #677，`origin/main` 前进了
两个提交，最后那次 push 被拒：

```
 * [new tag]         v1.1.0 -> v1.1.0
 ! [rejected]        main -> main (fetch first)
```

**这两行的顺序就是伤口**：`--follow-tags` 推 tag 和推分支不是原子的。tag 先上去了、分支被拒，
脚本 `execFileSync` 抛异常退出，`gh release create` 没跑。落地状态 = 远端一个悬空 tag +
没有 release，本地 main 领先一个提交、落后两个。

脚本文件头当时写着「任何一步失败立刻退出，已打的 tag/commit 留在本地不 push——人工收拾比
脚本自作聪明回滚安全」。**那句话描述的世界里 tag 是留在本地的**；实际在这个失败点上它已经
出门了，收拾成本比设想的高一档。

单人串行发版撞不到这条；本仓常态是多 lane 并行（ADR-0048），所以它会再来。

## 决定

### 一、升版之后立刻推 main 占位，然后才开始构建

```
npm version → git push origin main（不带 tag）→ 构建 → … → git push origin <tag> → gh release create
```

占位 push 把失败点从「贵」的位置挪到了「便宜」的位置：抢不到就在构建之前退出，十分钟没白花，
而且 tag 还在本地，收拾只要删一个本地 tag 加一个本地提交。失败时脚本把那几条命令原样打出来
（`git tag -d` / `git reset --hard HEAD~1` / `git pull --ff-only` / 重跑），照抄就能用——
建议 `reset --hard` 是安全的，因为脚本开头已经确认过工作区 clean，那一步只会丢掉刚生成的
版本提交本身。

### 二、末尾只推 tag，不再推分支

这条不是顺手收拾，是**测试逼出来的**。第一版实现末尾写的是两条：`git push origin main` 加
`git push origin <tag>`，想法是「占位之后再被超车也无害，推分支要么 no-op 要么快进」。
可执行版里那条「占位之后被超车」的用例直接把它打红了：被超车时本地 main 是**落后**的，
`git push origin main` 在 git 眼里是「把远端往回退」，直接拒——于是一次本该成功的发版倒在
最后一步，而且是在构建都跑完之后。

版本提交在占位那一步就上去了，构建期间本地不产生新提交，所以末尾推分支要么多余要么有害。
同理不能退回 `--follow-tags`：它只推「随本次被推的 ref 一起可达」的 tag，没有 ref 被推，
tag 也就不会走。

被超车之后 tag 指向的是一个已经变成历史的提交——**这正是它该指的地方**，因为二进制就是从
那棵树构建出来的（v1.1.0 那次人工收拾时也是照这条原则办的，见 #678 的关闭评论）。

### 三、可执行版真跑脚本，不读源码

`tests/scripts/releasePushOrder.test.ts`：起真临时仓 + 真裸仓当 remote + 真跑 `release.mjs`，
`gh` 和两个构建脚本换成临时目录里的假货（PATH 前置 + package.json 的 stub）。判据是
**构建脚本有没有留下脚印**，以及它跑的那一刻 `git ls-remote` 看到的远端 main 是什么。

为什么不读源码断言「`push` 那行在 `dist:mac` 那行之前」：要钉的不变量是「哪一步先发生」，
而源码里的出现顺序只是它的一个表象——把占位挪进一个 `if`、或者哪天加了提前 return，源码顺序
照旧、行为已经变了。而且真跑这一条已经证明了自己的价值：决定二就是被它逼出来的，读源码的
断言会对着那个错误实现全绿。

## 代价

**构建失败会在 origin/main 上留下一个没有 release 的版本提交。** 重跑 `npm run release` 会
再升一格，于是版本号里空一个洞（1.1.7 没有 release，直接到 1.1.8）。接受：版本号连续不是
任何消费方的前提（`src/main/updater.ts` 按 tag 认资产、按 SHA256SUMS 校验，不做连号假设），
而它换掉的是「十分钟白花 + 远端悬空 tag」。真在意的人可以在 origin 上把那个提交 revert 掉
再重来，脚本不替他做这个决定——同文件头那条原则。

## 否决掉的路

- **推迟打 tag**（`npm version --no-git-tag-version` + 构建完再打 tag 并连分支一起推）：
  它把「悬空 tag」这个伤口治好了，但**没治那十分钟**——照样是构建跑完才发现推不上去。
  伤口小了，病还在。
- **push 失败时自动 `git fetch` + `merge` 重试一次**：脚本开始替人做决定，而它此刻手里
  正握着一份刚构建完的二进制和一个指向别的树的 merge 结果。这正是文件头那句「人工收拾比
  脚本自作聪明回滚安全」拒绝的东西。

## 天花板

占位只挡住「升版到构建开始」这一小段之外的并发；**如果两条 lane 在同一秒里各自跑 `npm version`
再推占位**，仍然是后到的那条被拒——只是它此时还没开始构建，代价就是重来一次。真要连这也挡掉
就得上服务端的发布锁，为一个单人发版的仓库不值得。
