# ADR-0041：长期授权与分块审批

日期：2026-08-20
状态：已接受

## 背景

审批门（ADR-0004）只有两个答案：批准这一次、拒绝这一次。两端都被磨过：

- **太吵。** 一个 turn 里连着写五个文件，就要点五次「批准」。用户的实际应对是把审批模式
  切到「完全访问」——把逐条审批整个关掉，为了躲开一个工具的噪音，把所有工具的门一起拆了。
- **太粗。** write_file 是整份内容覆盖写。模型一次改了三处，其中两处对、一处不对，
  现在只能整体拒绝，然后用自然语言跟它解释"第二处别动"，再赌它这次听懂。

这两件事的形状是同一个：审批的**粒度**只有"这一次调用"，既没有比它更粗的（一类操作），
也没有比它更细的（一次调用里的一部分）。

assistant-ui 的 permission-grant 和 reviewable-diff 两个 element 恰好各对应一端。
选它们不是因为有现成组件，是因为这两端本来就该有。

## 决定

### 一、长期授权（三档 → 四档）

审批卡上的按钮变成：**拒绝 · 批准 · 本次会话 · 永久**。后两个都顺带批准这一次 ——
授权是"以后也别问了"，不是"这次不算"。

粒度是**工具**（`write_file` / `bash`），不是"某个路径的 write_file"。更细的粒度不是
做不出来，是说不清：参数出自模型，下一次的路径未必长得像这一次，"同一个能力"到底指什么
得先有答案。粒度粗一档、说得清，好过细一档、蒙人。

三个事实分居三处：

| 事实 | 存哪 | 为什么 |
|---|---|---|
| 授权发生的**那一刻** | `approval_decision.grant`（日志） | 是用户的一次决定，日志推不出来 |
| 本会话有效的许可 | 从日志推（`sessionGrants`） | 推得出的不落盘；resume 时扫一遍就回来了 |
| 永久有效的许可 | `userData/permissions.json` | 跨会话，日志推不出 |

永久授权**不进事件日志**，理由是硬规则本身：旧日志必须永远可重放。日志是**会话**的事实，
而"永久允许 write_file"横跨所有会话，包括还没建的那些；把它放进某一条会话日志，等于让
重放一段两年前的日志，把当时按下的"永久"再次施加到今天。

授权放行的调用**照旧流经审批门**，`approval_decision` 照常落盘，`reason` 写明是哪一档
授权放的行（`已授权（本次会话）`）。日志里永远不会出现"没人批过就跑了"的危险操作 ——
这一条与「完全访问」模式的处理方式一致（ADR-0004 的既有做法）。

### 二、分块审批（write_file）

改文件的审批卡按 hunk 拆开，每块可丢。按下批准时，实际写入的是**保留的块拼出来的内容**，
不是模型请求的那一份。

丢掉一块 = 那一段维持旧样子（它的新增行不写，它的删除行留着）；保留一块 = 照模型说的改；
未变行永远原样。拼接逻辑在 `lib/diffView.ts` 的 `composeContent`，与分块逻辑
（`diffDoc`）共用同一套分组规则 —— 两边分歧一次，块 id 就对不上号。

新文件不分块：整份都是新增，拆开之后每块都是"要不要这一段"，而拼出半个文件不是任何人
想要的结果。新文件仍用 code-diff 整份展示。

两条随之而来的诚实义务：

1. **日志必须记下真正写进去的是什么。** 模型请求的参数在 `assistant_message.toolCalls` 里，
   人改过的那份进 `approval_decision.revisedArgs`。两份都在，谁也没被改写 ——
   少了后者，日志就在说谎。
2. **模型必须知道执行的不是它请求的那份。** `tool_result` 的输出末尾追加一句说明。
   不说 = 它会照着自己的请求继续推理，而磁盘上是另一个样子 —— 这比拒绝更危险，
   因为看起来成功了。

审批门改写参数时换的是**新对象**（`ctx.call = {...ctx.call, args}`），不是原地改
`ctx.call.args`：`ctx.call` 指的就是 `assistant_message` 事件里那条 toolCall（同一个对象
引用），原地改它会把已经落盘的那条事件的内存副本也一起改了 —— DB 里的行还是老样子，
但推给渲染层的那份已经变了。这个 bug 在实现时真的出现过，由测试逮住。

## 取舍与代价

- **永久授权目前只能靠删文件撤销**，设置页还没有入口。接受：先让这一档存在，
  撤销入口是下一个 PR 的事；文件路径写在按钮的 tooltip 里。
- **授权按工具，不按参数。** 授了 `bash` 就是授了所有 bash 命令。这一档本来就该让人
  犹豫一下再按 —— 按钮文案和 tooltip 都直说了。
- **`revisedArgs` 会让日志变大**：一次分块取舍等于把文件内容存两份。只在真的丢掉过块时
  才落这个字段（一块没丢就不带），所以常态下没有额外开销。
- **schema 变更是纯增量**：`grant` 和 `revisedArgs` 都是可选字段，旧日志照常重放。

## 备选方案

- **只做分块，不做授权。** 解决不了"点五次批准"的噪音，用户还是会去按「完全访问」。
- **只做授权，不做分块。** 那"改对了两处、错了一处"仍然只能整体拒绝重来。
- **授权也落进日志、不用外部文件。** 会违反"旧日志必须可重放"——见上。
- **分块决策由主进程重算。** 渲染层只发块 id，主进程拼内容。更"权威"，但主进程要重新
  读一次旧文件（此刻的磁盘可能已经不是预览时那份），反而多一个不一致的窗口。
  现在的做法是渲染层拼好整份内容发过去 —— 与"人点头的就是这份内容"完全对齐。
