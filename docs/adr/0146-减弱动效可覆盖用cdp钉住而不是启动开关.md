# ADR-0146：系统「减弱动效」可在 app 内覆盖，用 CDP 钉住而不是启动开关

- 状态：已接受
- 日期：2026-08-27
- 关联：issue #607；ADR-0133（运行指示条那枚药丸/orb 是「agent 还活着」的唯一信号）

## 背景

Windows 上跑 turn 时那颗 canvas 球不转。查下来不是 Windows 的渲染问题：系统层的「设置 → 辅助功能 → 视觉效果 → 动画效果」关着（这台机器上是出厂如此，不是人主动开的无障碍选项），Chromium 把 `prefers-reduced-motion` 报成 `reduce`，而本仓从上到下都认这条媒体查询——Tailwind 的 `motion-reduce:` 变体、`app.css` 里十几个 `@media` 块、还有 `thinking-orbs`（它在 reduce 下只画一帧静止的，连 `requestAnimationFrame` 都不起）。

所以那台机器上不是"球坏了"，是整个界面按设计停住了。问题在于：本仓里**动效不只是装饰**——一轮跑起来时，那枚药丸和那颗球是「agent 还活着」的唯一信号（ADR-0133）。停住的界面和卡死的界面，人分不出来。

## 决策

设置 → 外观加一档「动效」：跟随系统（出厂默认）/ 始终开启。没有"始终关闭"——系统说要减弱就减弱，那是无障碍设置，不给人反向覆盖。

「始终开启」的实现是 **CDP 的 `Emulation.setEmulatedMedia`**（`src/main/motionOverride.ts`），把 `prefers-reduced-motion` 钉成 `no-preference`。

**为什么不是 Chromium 的 `--force-prefers-no-reduced-motion` 启动开关**：三条，最后一条是决定性的。
1. 命令行开关只挂得上 `app ready` 之前 —— 改完要重启，一个"点了没反应"的设置项。
2. 实测它压不过 `--force-prefers-reduced-motion`（同时给两个，结果仍是 reduce）——这个开关对本仓真正要压的那个东西（系统设置）能不能压住，无从判定。
3. **CDP 那条路当场可验**：在这台没减弱的 mac 上，同一个 API 能把 `matchMedia` 强行变成 `reduce`；再用 `--force-prefers-reduced-motion` 把系统档钉成 reduce，覆盖照样把它翻回 `no-preference`，reload 之后还在，撤掉之后回到 reduce。反向是同一条代码路径，不是推断。

**代价（接受）**：调试器通道只容一个客户端，挂着覆盖时 DevTools 开不了。所以只在**真的需要**时挂 —— `pref = always` 且渲染层此刻确实报 reduce；系统本来就没减弱的机器（mac、绝大多数 Windows）一行调试器都不挂，只多问一句 `matchMedia`。挂不上（DevTools 正开着）不抛，记一行日志继续——动效再重要也不该让窗口起不来。

## 验证

- `tests/main/motionOverride.test.ts`：四条判定（跟随系统=撤覆盖 / 需要才挂 / 系统没减弱不挂调试器 / 挂不上不抛）。
- `tests/main/motionSettingsStore.test.ts`：落盘形状，外部输入一律整形。
- 真机那半段（CDP 到底压不压得住系统档）在 Electron 里实跑验过，见上面决策第 3 条；它依赖真渲染进程，单测层面量不到。
