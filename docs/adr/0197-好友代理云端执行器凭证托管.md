# ADR-0197: 好友代理云端执行器——A 下线 B 也能用（凭证托管，推翻 ADR-0151 的「凭证不出门」）

日期：2026-08-30
状态：已接受（维护者会话内拍板，issue #794 决策 ③）
关联：ADR-0151（原信任模型）、ADR-0129（relay 零知识）、ADR-0166/0177（前缀与随分享借出）、#792（补推）

## 背景

好友代理今天的执行落点是 A 的机器：B 的调用打帧经 relay 到 A，用 A 本机凭证执行
（ADR-0151）。代价写在分享卡上：「调用时 TA 得在线」。维护者拍板把这条约束拿掉：
**A 下线（连机器都关了）B 也要能用**。#794 列过四条路线，选了 ③ 云端执行器——
①守护进程覆盖不了关机，②令牌委托受各家 provider 摆布且白名单退化。

## 决定

**edge 长出一个执行面（`/px/v1/*`），A 把「借出的服务」托管上去，B 直接打云端。**

被推翻的两根柱子，明说：

- 「凭证不出 A 的机器」→ 变为「凭证可托管进 Mr Otto 的 edge（Cloudflare）」。
  运营方（也就是 stanyan 自己）技术上可读托管凭证——这是 ③ 的定义性代价，
  不装样子用「端到端加密」遮掩（执行方必须能解密才能执行）。
- relay 零知识（ADR-0129 sealed 帧）→ 执行面看得见调用明文（服务/工具/参数/结果）。
  **中继面不变**：`/rl/v1/*` 照旧盲转，live 通道继续存在（见「执行路径的优先级」）。

### 架构

- **范围只收 http 传输的 MCP server**（square/supabase 及目录里全部 OAuth http 型）。
  stdio 进程没法搬进 Worker，也不该搬——它们依赖 A 的本机环境。
- **托管单元 = (hostUid, serverId)**：`{ url, headers, oauth: McpAuthRecord 的
  tokens+clientInformation, toolDefs 快照, grant 白名单 }`，存进新 DO `Escrow`
  （getByName(hostUid)，SQLite 后端），应用层 AES-GCM（worker secret `ESCROW_KEY`）
  再叠 Cloudflare 静态加密。
- **调用**：B `POST /px/v1/call`（Supabase JWT + hostUid/serverId/tool/args）。
  三道闸沿 ADR-0164 的顺序在云端复刻：**身份**（JWT 的 sub 就是 fromUid，比帧
  自报更硬）→ **关系**（worker 用 service role key 查 friendships=accepted，
  60s 缓存；删好友=代理死，云端同样成立）→ **白名单**（escrow 里的 grant）。
  过闸后 worker 以 A 的托管凭证向服务的真 MCP url 发 JSON-RPC，回结果。
- **token 生死**：A 在线时自己刷新 token 会重写 mcp-auth.json——凡有活着的托管，
  顺手 re-sync 上去；A 长期下线时 worker 兜底自刷（RFC8414 discovery 找
  token_endpoint + refresh_token + client_id）。两层都失效 = 该服务云端不可用，
  错误话术指回「让 A 上线重新授权」。
- **B 侧**：新的 cloudBorrow McpCapability（callTool = fetch /px/v1/call），
  经 **同一套 proxyNamespace 前缀机制** 合并进会话——B 看到的工具名与 live
  通道完全一致（`mcp__square_32c6716a__*`），share_grant_note 一字不用改。
  工具表来源：`GET /px/v1/grants`（escrow 里的 toolDefs 快照），A 下线也拿得到。
- **执行路径的优先级**：live 通道 ready 用通道（免费、快、A 可见 inflight），
  否则落云端。对 B 是同一把刀，路由在 capability 层。
- **审计**：DO 里 append（谁/何时/哪把刀/放行还是拒），A 上线 `GET /px/v1/audit`
  增量拉回并入本地台账——审计账本从「只在 A」变成「云端为准、A 侧镜像」。
- **撤销**：proxyRevoke 扩展为同时 `DELETE /px/v1/escrow`——凭证与授权即刻消失，
  B 的下一笔 403。A 重置密码/登出所有设备时应一并清（后续任务）。

### 分享流的语义

ShareGrantDialog 的勾选不变；勾了即托管（③ 是拍板的默认，不再叠一个「云端可用」
子开关——两档心智太碎）。卡片上那句「调用时 TA 得在线」删掉，换成「TA 不在线
也能用（凭证托管在 Mr Otto 云端）」——知情同意的对象从在线性换成托管本身。

## 切片（tracer bullet，各自独立 PR）

1. **T1 edge 执行面**：`services/edge/src/px.ts` 纯逻辑（闸序/escrow 编解码/审计）
   进根门禁；worker 挂路由 + DO；`checks/px.mjs` 打真 workerd。
2. **T2 A 侧托管**：分享/邀请流上传 escrow；token re-sync；撤销级联删除。
3. **T3 B 侧云借用**：cloudBorrow capability + grants 拉取 + 通道/云端路由。
4. **T4 审计回流 + UI**：A 拉审计并入台账；借出页标「云端可用」。

## 被否掉的路

- ①常驻守护进程 / ②OAuth 令牌委托：见 #794 正文，维护者否。
- 端到端加密托管（B 才能解）：执行方是云端不是 B，云端解不开就执行不了；
  假加密比明说更坏。
- 复用 relay DO 做执行：中继按 channel 分房、零知识；执行面按 hostUid 分、
  看明文——责任面不同，混在一个 DO 里迟早互相渗透。

## 推翻它的前提

运营方可读托管凭证这一点若不可接受（多租户商业化、合规要求），就得回到
①+② 或引入用户侧 KMS——那时本 ADR 整体重估。
