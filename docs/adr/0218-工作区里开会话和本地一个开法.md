# ADR-0218：工作区里开会话和本地一个开法——侧栏工作区长成工程组，云会话搬进主区

- 状态：已采纳
- 日期：2026-09-04
- 关联：issue #919；承接 ADR-0217（工作区刚搬进侧栏项目区）；改动 ADR-0198 切片 3
  的工作区面板与 ADR-0199 的云会话入口位置（协议、runtime、执行面一个字没动）

## 背景

ADR-0217 把工作区列表从页脚抽屉搬进侧栏「项目」栏之后，维护者在真机上看了一眼，
给了一句话：

> 工作区创建会话方式应该和用户本地会话一致

当时两条路差得很远：

| | 本地会话 | 工作区里的云会话 |
|---|---|---|
| 从哪儿开 | 侧栏工程组头一颗 ＋ | 侧栏那行 → 抽屉 → 「会话」tab →「新建云会话」 |
| 开的时候发生什么 | 主区出一张 composer，写完第一句、**发出去才建** | **立刻建一条空会话** |
| 会话列在哪儿 | 侧栏，组头下面一道竖脊上 | 抽屉里 |
| 点开在哪儿 | 主区 | 抽屉 |
| 怎么离开 | 点侧栏里别的一行 | 一颗返回键 |

五行里没有一行是一样的。

## 决定

### 1. 一个工作区 = 一个 SidebarGroup，骨架逐处对齐本地工程组

可折叠的组头（同一枚 `ChevronRight`、同一份 `SidebarGroupLabel`、收起时才报条数）
+ 组头右边的 `SidebarGroupAction` + 组内一列会话行挂在同一道竖脊上
（`border-l ... ml-[11px] pl-[6px]`，逐字照抄）。

**不是"长得像"，是同一套组件同一组类名**：像是会漂移的，共用一套骨架不会。

### 2. 组头两颗动作，本地只有一颗

- **＋** = `startCloudDraft(workspaceId)` —— **这一步不建任何东西**，只把主区换成
  开局卡。这是"一致"的核心：本地那颗 ＋ 也只是把主区换成 composer。
- **⚙** = 打开工作区详情（成员 / 连接器 / 已发布 / 已归档的云会话）。本地工程没有
  「管理」这回事，工作区有——它是一群人的东西，得有地方拉人和撤授权。

### 3. 开局卡（CloudWelcome）少三个控件，不是漏做

文件夹、型号、thinking 挡位在云会话里都不是「这一条会话」的属性，而是**工作区**
的属性（仓库由 owner 在 config 帧里配；模型 key 跟着工作区走，ADR-0202；云会话
本来就没有型号选单）。摆上来会得到三个点了不生效的控件——比少三个控件糟得多。
免审批开关同理：云端审批走 approvalRouter 路由到发起人/owner，不是本机 bypass 那套。

留下的是：位置（主区正中）、外壳（`ComposerBar`）、回车即发、空文本发不出去。

### 4. 第一句话要等 ready 才发得出去，所以先排队

主进程的 `say()` 要求 `status === "ready"`（`cloudSessionClient` 的 `requireReady`），
而"建会话 + 进房"结束时 runtime 的 `welcome` 还在路上。三条路都试过：

- **在 store 里 `useChat.subscribe` 等** —— 本仓渲染层至今没有用过这个 API，为一次
  等待引入一种新的状态订阅方式不划算。
- **轮询 `getState()`** —— 能用，但把一个天然的"状态到了就做"写成了定时器。
- **选中：排进 `cloudPendingFirstMessage`，由主区那块的 effect 在 ready 那一刻补发。**
  这是 React 里表达"等某个状态"的原生方式，不新增任何机制。

`takeCloudPendingFirstMessage()` **先摘后发**：effect 会因为状态变化重跑，清晚一步
就会发两遍。建/进房失败时把这句话一并清掉——不留一句吊在半空、下次进别的云会话
时突然自己发出去。

### 5. 云会话搬进主区，返回键跟着删掉

侧栏里列着它，就该和本地会话落在同一块地皮上。离开的方式也因此一致：
`newSession` / `resume` 各自先 `closeCloudSession()`，点侧栏里别的一行就走了。
`CloudSessionPage` 的 `onBack` 因此改成**可选**——省掉时画一个不可点的工作区名
（那一行回答的是「我在哪个工作区里」，而云会话的每一件事——谁看得见、扣谁的额度、
用哪把 key——都挂在它上面）。

主区那条分支排在 `phase === "welcome"` **之前**：进云会话时本地 `phase` 还停在上一条
会话或 welcome 上，按那个判会画错屏。

### 6. 归档的云会话不进侧栏，去工作区设置页底部

同本地：归档的会话在「已归档会话」那一屏，不在工程组里。抽屉里那节「云会话」
因此变成「已归档的云会话」，**去掉新建按钮**，一条都没有时整节不出。这不是把同一
份清单画两遍——活着的在侧栏、归档的在管理面，是两批不相交的东西。

## 否决的路

- **只把入口做一致（＋ 仍然立刻建空会话、会话仍在抽屉里开）**。那样"一致"只剩
  按钮的位置，而维护者那句话说的是「创建会话方式」。
- **给云会话也配上文件夹/型号/挡位选单**，好让两张 composer 长得一模一样。见决定 3：
  一致的是**方式**，不是控件的件数。
- **让 `say()` 在主进程排队**（改 `cloudSessionClient` 让未 ready 的帧攒着）。那会给
  一条协议客户端加一层隐式缓冲，影响的远不止这一处；等待是这一次交互的事，就留在
  这一次交互里。

## 代价

- 主区的分支链又长了两条。判据是两格互斥的 store 字段（`cloudDraftWorkspaceId` /
  `cloudSession`），但"谁排在谁前面"现在是四条规则而不是两条。
- 侧栏每多一个工作区就多一趟 `refreshCloudSessions`（无推送通道，同 workspaceGroups
  的待遇）。依赖钉在 id 拼成的串上，快照重拉不会连带重跑。
- 开局卡上写的第一句话如果卡在 `connecting` 上一直没 ready，它就停在
  `cloudPendingFirstMessage` 里不动，界面上只有云会话自己的连接状态在说话。没有为
  这一格单独做超时——超时该由连接那一层报，不该由一句待发的话报。
