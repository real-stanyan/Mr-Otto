## 背景

1a/1b/2/3（ADR-0219 / 0220 / 0221）之后，工作区里站着若干只 @ 得着的 agent，各有提示词、
型号白名单、连接器白名单，花的钱也分得出是谁烧的。**它们唯一没有的是记忆**——
`services/runtime/` 里所有叫 `Memory` 的东西都是容器内存限额（spec §6.1 原话「云 runtime
今天零记忆」）。症状有两个方向：

| 缺口 | 症状 |
|---|---|
| 每只 agent 攒不下自己的手感 | 同一只运营 agent 每条新会话都要被重新告知「销量表看哪一列」 |
| 工作区攒不下公共口径 | 「销量含不含退款」这种全员都要遵守的定义，只能靠人每次复述，或写进每只 agent 的提示词（改一次要改 N 处） |

本机那套记忆（四档 USER/MEMORY/PROJECT/TOPIC，ADR-0204 / 0207）不能直接搬：它的落点是
accountConfig 下的磁盘目录（`src/main/memoryFiles.ts`），而云会话跑在 VPS 上、读写方是
runtime；它的档位里 `user` / `memory` 两档在工作区里根本无解——群里「用户」是谁没有答案
（多人），云容器里也没有本机环境事实（PATH、CLI 登录态）。

## 决策

### 1. 一张表、一档一行；`agent_id = ''` 是共享档；成员在籍即可写

migration `supabase/migrations/0023_workspace_memories.sql`（幂等，同 0021/0022 的约定手动
执行一次）：主键 `(workspace_id, agent_id)`，`agent_id` 空串 = 工作区共享档，非空 = 那只
agent 的私有档。条目切分（`ENTRY_DELIMITER` / `parseEntries` / `formatEntries`）留在
`src/shared/memoryStore.ts` 的纯层，**DB 只存整份文本**——数据库不懂条目，就不会有第二套
切分规则。

字符上限沿用本机量级：**共享 2200**（接替 `project` 档的位置）、**私有 1100**
（`WORKSPACE_MEMORY_LIMITS`）。紧上限不是为了省 token，是为了逼出策展——`memoryStore.ts`
头注的同一条理由。

**RLS 是「成员可读 + 成员可写」，不是「只有 owner 或建的人能写」**：对称于连接器池
（ADR-0198 决策③）——记忆是这个群的公共财产，不是谁的私产。共享档尤其如此：一条被写错的
口径谁看见谁就该能改，要走 owner 审批的话它会一直错着。代价写在代价段（任何成员都能清空
共享档，没有版本历史）。

`user` / `memory` 两档**不出现在工作区里**，理由如背景段所述；这是本 ADR 与 ADR-0204 那套
四档的第一处分岔。

### 2. 快照事件 `workspace_memory_loaded`：缺席或变了才落，投影**最新一条胜出**

模型可见就必须先落盘（AGENTS.md 硬规则），所以记忆注入在这里也是一条事件而不是 runtime
现场拼的字符串。落的时机在 `services/runtime/src/sessionService.ts` 的 `runJob` 里，
`briefIfNeeded` 之后、`engineFor` 之前，判据是**两条缺一不可**（与 `briefIfNeeded` 同型）：

- 只判「有没有」→ 别人在本会话中途改了共享档，我下一 turn 看不见；
- 每 turn 都落 → 日志里堆满同一段文字，而且模型每轮被重新塞一遍同样的话（前缀缓存每轮打穿）。

于是**一条云会话里一只 agent 会有多条快照**，这是它与本机 `memory_loaded`（一会话一条）的
根本差别，原因只有一个：**共享档是多写者可变状态**，会在会话进行中被别的 agent 改。投影因此
必须是**最新一条胜出**——`deriveMessages` 不在 case 里直接 `+=`，而是记下 `renderWorkspaceMemoryPrompt(event)`
覆盖上一条，主循环跑完再拼一次进 system 尾部。直接 `+=` 的话两条快照就是两个 SHARED 块叠在
system 里，**模型读到新旧两套口径而不报任何错**。

拼在 system **尾部**（volatile tail）的理由同 `memory_loaded`：前缀缓存。

**两档都空时也落一条基线快照**（`shared === "" && own === ""` 在第一次也走 append）——事件
本身就是「这套装配有记忆」的凭据，同本机 `memory_loaded` 无条件渲染的那条理由。空快照的投影
是一段只有指引没有记忆块的文字（`renderWorkspaceMemoryPrompt` 里 `s || o` 为假时 `blocks` 是
空串），模型因此知道自己有 `memory` 工具、知道现在一条都还没有。

**压缩幸存**靠 `src/session/modelContextScan.ts` 的 `boundedContextEvents` 多捞一类
（`store.ofType(sessionId, "workspace_memory_loaded", { beforeSeq: cp.seq })`）：checkpoint
之前的快照要能被扫描窗口捞回来，否则压缩过一次的长会话里记忆块凭空消失。**全部捞、投影只
认最后一条**——`agentView` 的 `ofType` 已经按 `agentId` 过滤过，捞回来的都是我自己的。

事件带 `agentId` + `agentName`：前者让 `agentView.OTHER_AGENT_VERDICTS` 判 `drop`（别人的
记忆快照是它的上下文不是我的，同 ADR-0219 的纪律）；后者是快照那一刻的名字，只给 OWN 块的
标题用，**改名不回写历史**（同 ADR-0221 的 `agentNameOf` 一贯纪律）。

### 3. 云侧档位枚举是自己的一份，`applyEntryOps` 是抽出来的共同本体

`src/shared/workspaceMemory.ts` 有自己的 `WorkspaceMemoryTier = "shared" | "own"`，
**不动 `MemoryTarget`**（spec §6.1）：那个类型手机端也在用，收窄或扩宽它会把桌面四档一起
打红。两套档位于是共存，但**原子批量的语义只有一份**——`memoryStore.ts` 抽出与档位无关的
`applyEntryOps(entries, ops, { label, limit })`，`applyOps(target, …)` 退化成「先查这一批
是不是同一档，再交给它」的薄壳。理由是那段代码里住着 ADR-0116 那条「超限**且没变小**才拒」
的教训：两份实现意味着云侧迟早会漏掉它，然后在云上重演一次「存量超限的档静默锁死」。

抽取是纯重构：`tests/shared/memoryStore.test.ts` 与 `tests/tools/memory.test.ts` 一字不改
仍全绿，错误文案逐字节不变。**唯一的行为差别在混档批量的错误顺序**：`applyOps` 现在把「这
一批只能操作 X」的检查做成了 `applyEntryOps` 之前的前置扫描，于是一批里既有跨档操作又有内容
为空的操作时，先报的是跨档那句（原来按顺序走到哪句报哪句）。**唯一的生产调用方
`src/tools/memory.ts` 的 `parseOps` 给整批赋同一个 target，这条路走不到**——记在代价段。

`toOpList` / `inferAction`（宽容解析的边界）从 `src/tools/memory.ts` 导出给云侧复用：那段
宽容是踩出来的（模型给单个对象而不是数组、给 `new_text` 而不是 `content`），**边界只该有
一份**。

### 4. 共享档的写入者前缀由**写入路径**拼；桌面手改不拼

`withWriterPrefix(writer, content)`（spec §6.2）在
`services/runtime/src/workspaceMemoryTool.ts` 的写入路径上执行，不靠模型自觉——模型不写前缀
时提示词管不住它，而没有前缀的两条矛盾事实读起来像同一个权威说的两句话，人要修它得先知道
去问谁。已带同一前缀的不再叠加（模型照着旧条目的样子重写时常会自带）。

名字**现取不定死**：`createWorkspaceMemoryTool` 收的是 `agentName: () => string`，
`sessionService` 递的是 `specNames.get(agentId)`（`runJob` 每次刷新）。建刀那一刻的
`spec.name` 定死的话，改完名字要重开会话前缀才更新——ADR-0202「每次 `chat()` 现读」与
ADR-0219 `engineFor` 缓存那条教训的同一个形状。

**桌面设置页手改不拼前缀**：人写的不是 agent 写的，给人的字打上一只 agent 的名字是伪造署名。
代价是共享档里会有带前缀和不带前缀两种条目——那正是事实（一部分是 agent 写的、一部分是人写
的），比统一伪造一个前缀诚实。

### 5. 读失败不阻塞 turn；写互斥是**进程内**锁

`loadMemoryIfChanged` 的读失败只 `console.warn` 然后 `return`，**不抛、不停 turn**——记忆
副作用永不阻塞回复，同本机 memory 工具的纪律。代价是这一 turn 用的是上一条快照（或没有
快照）：记忆不是这条会话的正确性前提，而「表还没建好 / Supabase 抖了」变成「所有人都说不了
话」是不可接受的量级差。部署顺序因此也松：runtime 先升级而表还没建，每 turn 只 warn 一行。

写侧是 `read → apply → write` 整段持锁（issue #185 同款），锁键
`workspaceMemoryLockKey(workspaceId, rowAgentId)` = `ws-memory:<workspaceId>:<agentId>`，
用的是 `memoryStore.withMemoryFileLock` 这把**进程内**互斥。它挡住的是同一个 daemon 里两条
云会话同时写共享档（真实且常见：一个工作区里两只 agent 各跑各的 turn）。**它挡不住两个
daemon**——那是单 daemon 前提，写进「推翻它的前提」。

### 6. 桌面设置页：单块保存只 patch 那一行，「刷新」要先问一句

`WorkspaceMemoryTab` 一份档一块（`memoryDocs` 排：共享档第一 → 名单顺序 → 已删 agent 的残留
行标 stale）。**保存成功后只替换那一行**（`workspaceMemoryView.replaceRow`），归一化用的是与
主进程落库前**同一步纯函数**（`formatEntries(parseEntries(text))`），本地直接算，不必整份重拉
才知道存下去长什么样。

初稿是「保存成功 → `refresh()` 整份重拉」，评审时抓到：重拉会先卸载所有 `MemoryDocBlock` 再
重装，**用户在共享档打到一半的字会被另一只 agent 那块的保存悄悄冲掉，且不报警**。「刷新」
按钮仍然整份重拉，但任何一块有未保存草稿时先 `window.confirm` 问一句——那才是用户主动放弃
草稿的时刻，不该在别的块保存时顺带发生。

**已删 agent 的残留档画出来标「（已删除）」，不静默丢**：同 ADR-0221 决策 3 的 `staleSelections`、
同 #722「撒谎的勾」的一般形式——界面上看得见的状态必须是真实状态。

**手改不校验上限**：人手改自己的笔记不该被上限拦住（同本机 `applyUserEdit`）；归一化照做
（去空条目、保序去重），所以云端存的永远是归一化后的样子。

### 7. 桌面与云端共用工具名 `memory`，因为它们永不同台

云侧工具的 `name` 就是 `"memory"`，与 `src/tools/memory.ts` 那把同名。**两把刀从不挂在同一台
engine 上**：桌面那把只在 `src/main/agent.ts` 的本机装配里，云侧那把只在
`services/runtime/src/sessionService.ts` 的 `engineFor` 里。同名是刻意的——模型在两个世界里
学到的是同一个工具名、同一组 action、同一句超限文案，只有 `target` 的枚举不同。

### 8. 新事件类型的检查清单实际是**十一处**

AGENTS.md 那条索引写的是九处（`PRIVACY_VERDICTS` 那一条）。这次落 `workspace_memory_loaded`
时另有两处必须表态，都不在那份名单里：

- `src/renderer/src/lib/threadGroups.ts` 的 `isInvisible`——虽然 `groupThread` 在 `src/` 里
  零调用（ADR-0219 已经指出它是死代码），但 `tests/renderer/timelineLists.test.ts` 断言它与
  `Timeline.tsx` 的 `EventRow` 一致，漏一处就红。
- `tests/session/persistencePolicy.test.ts` 里手写的 `DURABLE` 数组——它靠
  `Exclude<SessionEvent["type"], (typeof DURABLE)[number]>` 做类型级穷举，漏一处 tsc 直接红。

这两处写进 AGENTS.md 新加的索引条目里（那是 L2 的索引改动），**不动既有那条的「九处」序号**
——序号会漂，那条自己已经说过不写死。

## 否决的备选

| 备选 | 为什么否 |
|---|---|
| 复用既有的 `memory_loaded` 事件 | 档位全错（它带 `user`/`project`/`topics` 三格，工作区一格都没有）、文案全错（提示词里写着 session_search、「下个会话才可见」，而共享档本会话中途就会变）、且它是一会话一条的语义。见决策 2 |
| 每 turn 都落一条快照 | 日志里堆满同一段文字，模型每轮被重新塞一遍同样的话，前缀缓存每轮打穿。见决策 2 |
| 只判「有没有落过」就跳过 | 别人在本会话中途改了共享档，我下一 turn 看不见——这正是共享档存在的意义。见决策 2 |
| 投影时把多条快照 `+=` 累加 | 两个 SHARED 块叠在 system 里，模型读到新旧两套口径，且**不报任何错**。见决策 2 |
| 两档都空时不落快照 | 事件本身就是「这套装配有记忆」的凭据；不落的话模型不知道自己有 `memory` 工具，而「一条都没有」与「这个世界没有记忆」是两件事。见决策 2 |
| 把 `shared`/`own` 塞进 `MemoryTarget` | 那个类型手机端也在用，收窄/扩宽它会把桌面四档一起打红。spec §6.1 明写 |
| 云侧自己再写一份 `applyOps` | ADR-0116 那条「超限且没变小才拒」的教训会在云上原样重演一次。见决策 3 |
| 复用 `src/main/memoryFiles.ts` 作落点 | 那是本机 accountConfig 的磁盘口（ADR-0207），云 runtime 的落点是 Supabase 表。spec §6.1 明写不复用 |
| 共享档前缀靠提示词让模型自己写 | 模型不写时没有任何机制补救，而缺前缀的两条矛盾事实读起来像同一个权威说的两句话。见决策 4 |
| 桌面手改也拼一个前缀 | 给人写的字打上一只 agent 的署名是伪造。见决策 4 |
| 记忆读失败就让 turn 失败 | 「表还没建 / Supabase 抖了」会变成「这个工作区所有人都说不了话」。见决策 5 |
| 单块保存后整份重拉刷新 | 会卸载所有块，把别的档里没保存的草稿悄悄冲掉且不报警（评审抓到）。见决策 6 |
| 现在就上 DB 级 `updated_at` 乐观锁 | 单 daemon 前提下进程内锁已经够，加一层版本冲突要多一条「你改的时候别人也改了」的用户可见错误路径。留在「推翻它的前提」 |

## 代价与天花板

| 面 | 结果 |
|---|---|
| **桌面手改不落审计事件** | 本机那套有 `memory_user_edit` 作证（ADR 的「记忆文件可从日志重建」凭据），云端没有：手改发生在设置页，**没有一条「当前会话」可以挂**这条事件（工作区是会话之上的容器）。唯一痕迹是 `workspace_memories.updated_at`，而它连「谁改的」都不记 |
| 工具成功行不带 memory-chips | 桌面那把 `memory` 返回值末尾会附 `formatMemoryResultLine(result)`，渲染层据此画「记住了 / 忘掉了」的 chip；云侧这把**不发**——那个函数的返回类型绑着 `MemoryTarget`，而云侧档位不是它。代价是云会话时间线上看不到记忆 chip，只有工具卡里那句「已更新 SHARED（1 处，123/2200 字符）」 |
| 写互斥只在进程内 | 两个 daemon 同时写同一个共享档会后写覆盖先写。单 daemon 前提，见「推翻它的前提」第一条 |
| `applyOps` 混档批量的报错顺序变了 | 前置扫描先报「这一批只能操作 X」，原来是按顺序走到哪句报哪句。**唯一的生产调用方 `parseOps` 给整批赋同一个 target，这条路走不到**；接受，见决策 3 |
| 共享档会分叉的那一半没修完 | 写入者前缀让矛盾**看得见**，不让它**不发生**（spec §11 已列）。真正的对账不在本切片 |
| 任何成员都能清空共享档 | RLS 是「在籍即可写」（决策 1），且没有版本历史——一次误清没有撤销路径。对称于连接器池的既有取舍 |
| 已删 agent 的残留档只能清空不能删行 | 设置页只有「保存」没有「删除这一档」：残留行标了 stale、内容能改成空串，但那一行仍在表里 |
| 手改不校验上限 | 人可以把共享档改到 5000 字符，下一 turn 照样整份注入；`memory` 工具此后会拒绝一切「没变小」的写入（ADR-0116 的既有行为），模型看得到那句错误文案 |
| **手工冒烟一次都没跑** | 前置条件是登录账号 + 有订阅的工作区 + VPS 上活着的 runtime daemon + 在生产 Supabase 手动执行过 0023。纯逻辑与投影有单测覆盖；设置页的渲染、快照的真实落盘时机、模型对两档判据的实际遵守全部 UNVERIFIED |
| migration 是外向副作用 | 0023 要维护者在 Supabase 手动跑一次（同 0021/0022 的约定）。跑之前 runtime 每 turn warn 一行、`memory` 工具报错，其余功能不受影响 |

## 推翻它的前提

- **若 runtime 从单 daemon 变成多实例**（水平扩容 / 蓝绿部署重叠窗口），决策 5 的进程内锁立刻
  不够：修法是 `workspace_memories` 上做 `updated_at` 的乐观锁——读时带回 `updated_at`，
  写时 `.eq("updated_at", 读到的那个)`，撞了就重读重放这一批操作。`applyEntryOps` 是纯函数，
  重放不花钱；要加的是一条「重试 N 次仍冲突」的用户可见错误路径。
- **若共享档的矛盾成规模**（决策 4 的天花板），前缀不够，要的是真正的对账：两条语义冲突的
  事实自动打架、或写入时提示「已有一条相反的口径，是 [运营] 写的」。那要一层语义比对，不是
  这份 ADR 的形状。
- **若「谁改了记忆」变成要追责的问题**（代价段第一条），要给工作区一条**不挂会话**的审计流
  ——今天所有事件都住在某条会话的日志里，工作区级的事实没有落点。届时 `workspace_memories`
  加一列 `updated_by` 是最小改法，完整审计要一张新表。
- **若两档不够**（比如要按项目/客户分桶，同本机 TOPIC 档 ADR-0204 走过的路），
  `WorkspaceMemoryTier` 扩一档即可，`applyEntryOps` 与表结构都不用改（`agent_id` 这一列本质
  是「档的键」）——决策 3 的「云侧自备枚举」正是为这条路留的门。
- **若本机会话也要接工作区记忆**（比如桌面直接进一个工作区的上下文），决策 7 的「永不同台」
  前提就没了，两把同名 `memory` 会撞：那时得给云侧那把改名，或把 target 枚举合并成一份带
  五档的表——后者要先解决「`user`/`memory` 两档在工作区里无解」那个问题。
- **若快照事件的体量成为问题**（一条长会话里共享档被改了几十次 ⇒ 几十条全量快照），投影侧
  「最新一条胜出」不变，落盘侧可以改成只落 diff——但那会让「投影可从日志推导」多绕一层重放，
  收益要先量出来再说。
