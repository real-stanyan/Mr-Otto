# ADR-0350：好友三档权限——每人一边、生效取最小值，两列落在 friendships，两道 runtime 闸

日期：2026-10-04 · issue #1494 · 维护者拍板：三档；每人一边、生效取两边的最小值；老好友默认第 2 档；新请求默认第 1 档

## 背景

#1461 让朋友私聊里能带自己的智能体（私密车道），#1441 让智能体替主人直接给朋友打电话（外联）。两件事都只问
「是不是已接受的好友」。维护者要三档：**仅聊天**（双方都不能在私聊里用智能体）、**部分开放**（可以带智能体进私聊）、
**全部开放**（对方的智能体可以直接发消息、打电话），加好友时选，之后在对方的资料页里能改。

## 决定

1. **每人一边，生效取两边的最小值。** 我给 TA 开到哪一档、TA 给我开到哪一档各管各的；关系上真正生效的是低的那一档。
   否决掉的是「一对人一个值、双方都能改」：那样对方把档位调到「全部开放」，我的智能体就能去找他、他的也能来找我，
   而我没点过头。代价是设置页多一行只读的「TA 给我的权限」，以及要向人解释「为什么我开了全开他的智能体还是不来」
   （选档的那张单子底下写了一句）。
2. **落在 `friendships` 的两列** `requester_tier` / `addressee_tier`（0054），不另开表：realtime 发布已经包含这张表，
   两端改完就同步；老客户端的 select 不带新列照常工作。哪一列是「我给 TA 的」看这一行里我是请求方还是被请求方
   （`tiersOf` / `myTierColumn`）。
3. **默认档：老行 `agents`，新请求的发起方默认选 `chat`。** 0054 之前已经是朋友的那些行按第 2 档——不打断已经在用
   私密车道 / 来电的人；老客户端插进来的新请求也落这一档（它不带这一列）。接受方接受时选自己那一边。
4. **自己只能定自己那一边**，三层钉：insert 策略要求 `addressee_tier` 是默认值（发起方不能替对方定）；已接受之后
   双方可 update 两列的列级 grant；触发器 `friendships_guard_tiers` 按 `auth.uid()` 拒掉改对方那一列的写（RLS 的
   with check 看不到旧行、列级 grant 分不出谁，所以是触发器）。service role 没有 `auth.uid()`，不受限。
5. **两道 runtime 闸读生效档**：带智能体进私聊 `pairCreateProblem`（≥ `agents`，缺 tiers 时照旧只看是不是朋友——
   老调用方 / 测试）；外联 `outreachHub.dispatch` 在 `resolveFriend` 之后、任何别的检查之前拒（= `full`），拒的话
   说给模型的是真话「他没开放」，不是「没这个朋友」。`pair_presence`（朋友那侧「对方带了几只」）也按档位走。
   **没跑 0054 时 runtime 退回按默认档算**（42703 → 不带两列再查一次），不炸。
6. **客户端藏入口只是体验**：私聊 ＋ 里「带上我的智能体」按生效档藏；真正的闸在服务端。

## 代价与没做

- **降档不追溯已有的车道**：私密车道已经建好之后把档位调回「仅聊天」，车道里的智能体继续听主人说话、继续读私聊内容
  （`updateChat` / pair `say` / `loadPairContextIfChanged` 都没补这一刀）。记在 #1494 的后续；先把入口与新建拦住。
- 第 1 档「仅聊天」**没有**顺带作废好友代理授权（ADR-0151 的 edge `isFriend`），也**没有**禁止把这位朋友拉进有我智能体的群
  （#1393）——两件事都不在维护者原话里，各自是一条独立决定。
- 桌面没有好友资料页，看不到也改不了档位（`src/main/supabaseFriendsApi.ts` 的 select 不带新列，照常工作）。
- 真机未验：0054 没在生产跑，手机那三处入口只有 tsc 与读源码的测试。
