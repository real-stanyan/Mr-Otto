# ADR-0015：Git Graph 主干钉 0 道，其余泳道照旧回收

日期：2026-08-18
状态：已采纳
关联：ADR-0013（Git Graph 只读可视化）、issue #27

## 背景

`assignLanes` 原来的分道规则是「谁先出现谁占最左空道 + 空道回收」。lane 0 归谁，取决于哪个
tip 在 `git log --topo-order` 里先出现。后果：站在 feature 分支上、feature 的 commit 最新时，
feature 占 0 道，主干被挤到 1 道；切个分支再看，主脊换了列。

图里最该稳的那根线反而最不稳。

## 决策

**默认分支（主脊）永久占 0 道，不参与回收；其余分支照旧回收空道。**

- `assignLanes(commits, spineBranch?)`：给了分支名且窗口里找得到它的 tip，就预留 0 道 ——
  主干 tip 强制落 0（哪怕别的线先等到它，也把它拽回主脊），其一父链自然续占；
  其余线分配空道时从 1 开始。
- 主脊分支怎么定（`pickSpineBranch`）：`git symbolic-ref --quiet --short refs/remotes/origin/HEAD`
  最准（纯本地读 ref，不联网）；拿不到就退 main / master / 当前 HEAD 分支；一个都认不出
  返回 null。
- null = 不预留，回到原行为 —— 免得为一根不存在的主干白留一列。

## 拒绝的方案：所有分支固定一列、永不回收

「主干在左，其余分支依次往右排」的完整版要求取消道回收，一个分支一列到底。拒绝原因：

1. **宽度会无界。** 面板是半屏 + `overflow-x-hidden`（Git Graph 打磨时刻意撤掉了横滚）。
   仓库里前后出现过 8 个分支就永远是 8 列，要么挤到看不清，要么把横滚加回来 —— 那是刚
   撤掉的东西。回收正是让宽度有界的机制。
2. **「依次」没有可靠的序。** 分支创建时间不在 log 里，能拿到的只有「在 topo 序里第一次
   出现」—— 现在的回收逻辑本来就近似这个。

## 代价

- 主干 tip 之前的几行，0 道空着（你站在 feature 上、主干落后时会看到左边一段空白）。
  这是「主干不在这几行」的事实，不是排版空洞，接受。
- 每次 `log()` 多一次 `symbolic-ref` 子进程调用（本地读 ref，无网络）。
