## 背景

用户想接一台 MCP server，原本只有两条路：设置页「新建 MCP server」对话框里手打 URL 或命令，或者在对话里跟水獭说「帮我接上 supabase」，让它查 `mcp_catalog`。两条路都要求用户**先知道有这么一台 server 存在**——没有一个「翻一翻有什么能接」的地方。

具体缺口三条：

- `MCP_CATALOG` 那 9 条只被 `src/tools/mcpCatalog.ts` 消费，renderer 里零引用——它是给水獭看的，不是给人看的
- `CatalogEntry` 没有图标字段，卡片网格画不出来
- 9 条手写清单撑不起一个搜索框

2026-08-28 对 `registry.modelcontextprotocol.io` 打真请求验过一批前提（完整列表见设计文档「三、验过的前提」），其中三条决定了整个设计的形状：

- **注册表是开放投稿的**：搜「notion」头两条是第三方包装（`ai.smithery/smithery-notion`、`com.mcparmory/notion`），不是官方那台
- **图标基本没有**：扫 100 条样本只有 7 条带 `icons`
- **全量拉不动**：循环翻页 `limit=100` 两分钟没到底；`world.http` 当时也只有 `postJson`，没有 GET

本 ADR 记录整个 6-task 功能背后的决定：从「分两层」这个总纲，到落到 `mcp_catalog` 工具与 `world.http.getJson` 接缝上的具体实现，以及实现过程中浮现、原设计没预料到的三处判据补充。

## 决定

### 一、分两层，信任边界画在层之间（4.1）

| | 精选层 | 长尾层 |
|---|---|---|
| 来源 | `src/shared/mcpCatalog.ts` 仓内常量 | `registry.modelcontextprotocol.io` |
| 何时出现 | 面板一打开，零网络 | 用户敲字才拉 |
| 核验 | 人工过目，进过 PR review | 无 |
| UI | 带「已核验」角标 | 分隔线以下，标「来自公开注册表，未经核验」 |

精选层从 9 条扩到 19 条（brief 原意「约 20 条」；为什么止步 19 见下方「落地时补充的三条判据」第 1 条）。

**理由**：注册表开放投稿，搜一个知名服务返回的头几条往往是中间商包装。把它直接当目录首屏，等于把「哪台是官方的」这个判断推给用户。首屏也用不了注册表自身的排序——它按字母序返回，第一条是 `ac.inference.sh`，没有任何排名信号。所以首屏只能是自己策展的那份，长尾只在用户明确搜索时才出现，并且明确标注未核验。

**被否掉的**：

- *只做精选层，不接注册表*：搜索框后面没东西，用户搜不到的一律回到「跟水獭说」，那就没解决问题。
- *只做注册表，废掉精选*：首屏无从排序，且把中间商条目摆在官方条目前面。
- *把注册表结果按某种启发式重排（名字像官方的排前）*：猜测发布者身份是一件会猜错的事，猜错的代价是用户装上一台假冒的 server。宁可不排，明说未核验。

**推翻它的前提**：如果注册表将来引入了可信的官方认证标记，且该标记可从 API 读到，那么「未经核验」这条分隔线可以改成按标记分组，精选层的存在意义随之下降。

### 二、搜索走 live query，不做本地全量同步（4.2）

**决定**：用户在搜索框敲字，主进程 debounce 250ms 后打 `GET /v0/servers?search=&limit=50`，结果直接画出来。不落盘、不做全量同步、不做过期刷新逻辑。

**理由**：全量同步在成本一侧已经被验掉了——翻页两分钟没到底。而它换来的两样好处都不成立：「离线可浏览」对一个装上也要联网才能用的东西没有价值；「搜索即时」的代价是引入一套「什么时候算陈旧、什么时候重抄」的逻辑，这是本设计里唯一会自己长出维护成本的部分。

**被否掉的**：

- *首次全量同步到本地*：见上。
- *构建期打快照塞进安装包*：内容冻结在发版那一刻，新 server 要等 Otto 下一次更新；且 2000+ 条进安装包。
- *渲染进程直连注册表*：违反 ShellBridge 硬规则，不予考虑。

**推翻它的前提**：如果注册表提供了增量接口（`?since=`）或者一个可直接下载的全量 dump，全量同步的成本项就消失了，届时值得重新评估。

**已知限制**：`ipcRenderer.invoke` 带不了 `AbortSignal`，`main/mcpRegistry.ts` 的取消参数在真实调用路径上是死的，只有 15s 超时可达。后果是竞态——先搜 notion 再搜 linear，慢的那条后到会盖掉新的；`McpDirectory.tsx` 必须自己按请求序号丢弃过期响应。这不是本节决定被推翻，是「live query、不落盘」这个选择的直接代价，转嫁给了 UI 调用方。

### 三、stdio 条目一键装要弹确认卡（4.3）

**决定**：从**长尾层**点 `+` 装一台 stdio server，落盘前弹一张确认卡，正文直说「这会从 npm/PyPI 下载 `<包名>` 并在你的电脑上运行它」，附发布者与仓库链接。精选层的 stdio 不弹（已人工核过）。

**理由**：`packages[]` 条目装上意味着 Otto 会 `npx <identifier>` / `uvx <identifier>`，从公共包仓库下载并在用户本机执行任意代码。注册表开放投稿，所以这等于一键运行一个陌生人发布的包。用户在「新建 MCP server」对话框里手打命令也是执行任意代码，但那是用户自己敲进去的——从搜索结果里点一下不是一回事，点击的人未必知道自己触发了什么。

这道确认与 ADR-0118 的审批门是**两回事**，各管一侧：审批门管的是水獭替用户做决定，这张确认卡管的是用户在信息不足时替自己做决定。

**被否掉的**：

- *只给 remote 条目一键装，stdio 只显示配置让用户自己粘*：最保守，但把 filesystem / playwright / git 这批最有用的本地 server 全挡在外面。
- *两种都装，不额外确认*：摩擦最小，但把「从陌生人的包里跑代码」降成了一次无语境点击。

**推翻它的前提**：如果 stdio server 一律跑进 bot 自己的容器（v2 Docker，ADR-0050 提到的方向），爆炸半径缩到容器内，这张确认卡可以降级为一行说明。

### 四、图标一律不外链（4.4）

**决定**：渲染进程不出现 `<img src="<远程 URL>">`，一张远程图片都不加载。**长尾层一律首字母色块**；**精选层用打进包的本地 SVG**（`src/renderer/src/assets/mcp/<key>.svg`），`CatalogEntry.icon` 存的是**资源键，不是 URL**。

**理由**：让渲染进程直接加载注册表条目里的任意 URL，等于每翻一次目录就把用户 IP 交给一批陌生服务器，且这批 URL 由投稿者自由填写。

**写计划时的细化**：spec 原方案是「有 `icons` 的由主进程代下」。写实现计划时改掉——100 条样本只有 7 条有图标，为这 7% 造一条下载 + 缓存 + 失败兜底的链路不划算，而首字母色块本来就要写（93% 的条目走的就是它）。改成长尾层一律色块、精选层图标打进包，零远程图片、零代理子系统，安全边界从「代理后可控」收紧成「压根不出网」。精选层只有约 20 条，图标打进包即可。

**被否掉的**：

- *直接 `<img src>`*：见上。
- *主进程代下远程图标*：见上，为 7% 造一个子系统。
- *完全不显示图标，全用色块*：更省事，但精选层那 19 条是有官方图标的，卡片认知效率差很多。

### 五、`world.http` 开一个 `getJson`（4.5）

**决定**：在 `src/world/executionWorld.ts:261` 的 `http` 接缝上加 **`getJson?(url, opts)`——可选字段**，`src/world/localWorld.ts` 实现，镜像 `postJson`；`withAbortSignal` 条件透传（`withExecOutput` 是整对象透传，不用改）。

**为什么可选（写计划时的细化）**：spec 4.5 原文没说必填与否，写实现计划时读代码读出来这条更省。仓里有 35 处测试假 world 写着 `http: { postJson: async () => ({}) }`，做成必填会让它们全红，而那些红跟网络能力毫无关系。仓内已有先例——`execDetached?` / `openTerminal?` / `browser?` / `simulator?` 都是可选，理由原文是「可选 = 向后兼容（假 world 零改动）」。照抄这个先例：缺席的语义是「这个世界不提供 GET」，调用方据此退回 web_search；v2 Docker 世界若要断网，不实现这个字段即可。

**理由**：4.6 让 `mcp_catalog` 工具查注册表，而工具只能依赖 `ExecutionWorld`（硬规则，`tests/architecture.test.ts` 第 1 条）。现有接缝只有 `postJson`，注册表是 GET。这是 ADR-0050「MCP 骑在 world 接缝上」的正常延伸——把新能力加到缝上，而不是在工具里绕过缝。

**被否掉的**：

- *在工具里直接 `fetch`*：违反硬规则，且 `src/tools/` 目前零处 `fetch(`，破例的成本是把这条干净的边界弄脏。
- *用 `postJson` 打 GET 接口*：注册表不接受 POST。

**实现中的一个坑**：按 brief 原文写的 `withAbortSignal` 用 `...(world.http.getJson ? { getJson: ... } : {})` 做条件展开——这是**急求值**，构造 wrapper 的那一刻就要去读 `world.http.getJson`，而仓里已经存在把假 world 写成 `{} as ExecutionWorld`（连 `http` 本身都没有）的测试（`tests/loop/engine.autoCompact.test.ts`）。改成 `world.http?.getJson` 探测存在性而不炸。这条纪律同样约束 4.6 的消费端，见下一节。

### 六、agent 侧回退到注册表，而不是回退到 web_search（4.6）

**决定**：`src/tools/mcpCatalog.ts` 的 `run()`：精选层没命中 → 打注册表 → 渲染成同样的文本块，尾巴加一句「来自公开注册表，未经核验，装之前跟用户确认发布者」。工具仍免审批（只读）；装依旧过 `mcp_configure` 的审批门。

**理由**：现在的回退话术是「查不到再用 web_search」，而 `src/shared/mcpCatalog.ts` 的文件头自己写了这个取舍的代价——web_search「每次多花几秒、还可能拿到错 URL」，且「让用户在审批卡上判断一个 URL 对不对，等于把认知负担又还给了用户」。注册表返回的是结构化配置，比从网页里读出来的 URL 准。这是对既有取舍的改进，不是新增一条路。

**被否掉的**：

- *不接，注册表只给 UI*：水獭发现不了面板之外的 server，「帮我接上 X」这句话的覆盖面不变。
- *单开一个 `mcp_registry_search` 工具*：工具表多一条，且水獭得自己选先调哪个——而正确顺序是固定的（精选优先），固定的顺序应该写在代码里而不是交给模型判断。

**消费 4.5 那个可选字段时的纪律**：`world.http.getJson === undefined` 时直接 `return []`——**不用 `!` 非空断言**，否则缺席时抛的是裸 `TypeError`，而不是设计承诺的人话回退。注册表本身连不上（DNS 失败、超时、返回形状不对）同样吞成空数组：这是一条回退路径，它自己失败不该让整个工具调用失败，调用方拿到空数组会退到 web_search 那句话，链条不断。

## 落地时补充的三条判据

设计文档写完之后、六个 task 实现过程中，评审与实现各自浮现了三处 spec 原文没有预料到的判据。这三条都是对既有决定的收紧或修补，理由和上面「被否掉的」一样，是这份 ADR 的价值所在，不能只留结论。

### 1. 精选层的门槛不只是「人工过目」，还要求鉴权链路在本应用里真的能走通

`src/main/mcpAuthStore.ts` 的 `clientInformation` 字段只由 `mcpClient.ts` 的 `saveClientInformation` 写入，那是 MCP SDK 的动态客户端注册（DCR）回调；全仓没有任何手填 `client_id` / `client_secret` 的入口。Slack、HubSpot、Vercel、Google Drive 的授权服务器都不提供 `registration_endpoint`，要求预先在服务商后台注册应用——这四家因此被从精选层候选里砍掉。同一次筛查里，已被上游标记 `DEPRECATED` 的 `@modelcontextprotocol/server-postgres` 换成了 Neon；`auth: "token"` 这个类目在仓里没有任何消费它的 UI/UX 接线，为免让 DigitalOcean 成为第一个在无人验证过的路径上裸奔的条目，连同 OAuth 元数据返回 `not_found`、证据不够干净的 Zapier 一并跳过。

**代价（若判错）**：用户截图里正是 Slack/HubSpot/Vercel/Google Drive 这四家，会觉得目录里少了东西。但错的方向是可逆的——补条目容易；反过来不可逆——用户装上发现永远授权不了，对精选层「人工核过」这条唯一的价值判断就没了。这是 Otto 目前真实的能力缺口（不支持手填 OAuth 客户端凭据），留给后续单开 issue 追踪，不在本功能范围内解决。

### 2. 未核验的条目装上，但不自动弹浏览器走 OAuth

4.3 为 stdio 条目论证的不对称——「从搜索结果里点一下不是一回事」——同样适用于长尾层的 remote/http 条目，只是危害的形状不同。原实现里，未核验的 http 条目一装完就自动触发 `authorizeMcpServer`，等于一次点击就用一台陌生服务器自己填写的 OAuth 元数据打开用户浏览器。4.3 给远程条目免确认卡的理由管的是**代码执行**（跑在对方机器上），管不住**浏览器跳转与钓鱼页**——这是两类不同的风险面，不能共用同一条豁免。

**决定**：未核验条目装上但不自动授权，改成提示用户到下面列表里自己点授权；精选层（已核过）照旧自动授权。**代价**：未核验条目装完之后多一步手动点击。

### 3. 请求头的名字和值模板必须同源产出，不能分两遍扫

注册表的 `remotes[].headers[]` 同时决定「该问用户什么」（`params`，问用户填值时显示的占位符名）和「答案怎么塞回请求头」（`headerTemplates`，形如 `Authorization: Bearer {smithery_api_key}` 的模板）。如果 `params` 和 `headerTemplates` 出自两次独立扫描，会出现「有 param 没 template」的漂移。这不是假设的风险，后果链是真实的：用户填了 key → 落盘成 `headers: { smithery_api_key: "<key>" }` → `mcpClient` 原样发出去 → 服务端永远 401，而 UI 只显示一句指向 OAuth 的错误，方向指错了，用户的密钥还躺在一个毫无意义的键下面，靠用户自己去编辑器里改键名也修不对（改成 `Authorization` 得到的是 `<key>` 而不是 `Bearer <key>`，模板本来就没在 UI 上出现过）。

**决定**：`CatalogEntry` 加一个可选字段 `headerTemplates`，`fromHeaders`（`src/shared/mcpRegistry.ts`）用同一次循环产出 `params` 和 `headerTemplates` 两样——同源产出，「有 param 没 template」这类不同步在构造上就不存在了。配置落盘时按模板渲染，而不是只拿占位符名字拼一个新键。**代价**：`CatalogEntry` 多一个可选字段；精选层的凭据要么走 OAuth、要么已经在 url 模板里，用不上这个字段，不受影响。

## 后果

- 首屏零网络，翻到搜索框才第一次联网；注册表活着与否只影响长尾层，精选层永远可用。
- `mcp_catalog` 工具的回退顺序固定写死在代码里：精选 → 注册表 → web_search，模型不用自己判断先查哪个、以什么顺序查。
- `world.http.getJson` 缺席时（v2 Docker 世界若要断网，不实现这个字段即可），UI 与工具两侧都退化成「这个能力用不了」的人话提示，而不是崩溃。
- 渲染进程里没有一条 `<img>` 指向远程 URL——安全边界是「压根不出网」，不是「代理后可控」。
- 精选层 19 条，比原来的 9 条扩容超过一倍，但 DCR 验证的门槛比预想更紧——四家知名厂商没能进来，这是本设计如实反映 Otto 现有能力边界的结果，不是遗漏（见上「落地时补充的三条判据」第 1 条）。
- 未核验来源的 server 永远不会替用户自动打开浏览器；只有人工核过的精选层会。

## 不做的

沿用设计文档「八、不做的」，实现过程中没有变化：

- 不做本地全量同步、不做离线目录（4.2）
- 不做「热门度 / 下载量」排序——注册表不提供这个信号，自己编一个等于猜
- 不做分类筛选——精选层条目不多，不需要筛；长尾层有搜索框
- 不碰已装 server 的管理界面，`McpServerRow` 原样保留
- 不做 Anthropic 官方 2232 条目录的抓取——没有公开接口
