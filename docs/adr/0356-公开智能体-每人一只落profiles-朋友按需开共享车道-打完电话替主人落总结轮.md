# ADR-0356：公开智能体——每人一只落在 profiles；朋友按需开共享车道（协议 26 onBehalf）；打完电话 runtime 替主人落一条总结轮

原为 ADR-0355（另一条 PR 先占了 0355；按项目 ADR-0074 改成 max + 1）。

日期：2026-10-04 · issue #1533（#1532 的一期）· 维护者原话：「在人与人之间的对话窗中，每个人可以设定一个自己的代理智能体，这个智能体属于公开智能体，
这样的话，我去给他拨打电话可以有两个选项：1：给本人打电话，2：给他的智能体打电话，智能体接到任务，他的智能体总结我的需求，在当前聊天窗中显示给对方。
@功能也可以@对方的公开智能体」

## 背景

#1523 的共享车道已经让「朋友在私聊里 @ 我带进来的智能体」成立：朋友以 ADR-0325 客人的身份进我主场里那条 facing = both 的车道。
缺三样：① 一个**每人一只**、朋友不用我先动手就能找到的智能体；② 车道能由朋友那一侧开出来（今天只有主场成员能 `create`）；
③ 朋友给它打完电话后，它把朋友的需求写成一段话给主人看。人与人之间的实时语音（选项 1）是另一个子系统（#1534），本条不碰。

只读核过的前提：客人进通话、`say`、被审批都走现成的客人机制；`call` 帧的在籍复查认客人；手机上「朋友那条车道」走第二条只读连接
（peerLane），没接语音——语音那一层只在 ChatScreen 上。

## 决定

1. **设定落在 `profiles.public_agent_id`**（0057），自己改自己那一行（`profiles_update_self`）。朋友读它走 **security definer RPC**
   `public_agent_of(p_uid)`：只给已接受、两边都不是「仅聊天」的好友（ADR-0350 的「两边取最小值」在 SQL 里就是两列都 ≠ chat），
   只回 `workspace_id / agent_id / name / description / avatar_slot`——提示词、型号、连接器一格不给（同 0043 的 `guest_chat_agents`）。
   没设 / 不给 / 读不到一律空，不泄露存在性。
2. **载体仍是共享车道，车道能由朋友开**：协议 25 → 26，`create` 的 pair 多 `onBehalf: true`。frameHandler 对这一种帧放行非成员
   （别的帧照旧只认成员 ∪ 客人），细判在 daemon：`onBehalfPairProblem`（发帧的就是配对的朋友、主人主场、主人设了那只且还在名单里、
   仍是好友、档位到「可带智能体」），朝向与名单**由 runtime 定**（both、[公开智能体]），帖子里的只是客户端的猜。行的 `publisher_uid`
   与房间的 `createdBy` 都记**主人**：creator 能改名单、能归档，这些不能因为是朋友开的口就落到朋友头上。已有车道就补：公开智能体进名单、
   朝向补成 both，改名单那一条事件记在主人名下。
3. **给它打电话 = 朋友把 ChatScreen 以 `kind: "guest"` 开在那条车道上、autoCall**：通话那一层（麦、TTS、CallKit）沿用，不给第二条连接
   再接一份语音。它要的客人快照（群主 + 我、车道里那几只）从 peerLane 拼（`peerLaneGuestChat`）——这条车道刻意不在 `teams.guests`
   里（#1523：它画在私聊页，不是一条群）。
4. **总结轮**：runtime 在 `setVoiceCall` 里记下「这场通话是谁开的」（从空到非空那一帧的发帧人）；车道里**客人开的**通话回到空名单时，
   替主人落一条 `greeting: "pair_call_summary"` 的开场白（fromUid 主人、点那只）让它用两三句话总结朋友的需求——与外联汇报轮
   （ADR-0337）同一种性质：正文是外人的话的转述，**那一轮受监督**（`openingTraits.report` 与 `tightenSupervision` 都认它）。
   总结落在车道里，两人都看得到——这就是「在当前聊天窗中显示给对方」。主人自己开的通话不落。
5. **@ 对方的公开智能体**：私聊页 @ 名单里列它，哪怕车道还没有；第一次 @ 时先 `ensurePeerLane`（开车道）再说。
6. **电话钮**：私聊页标题栏一颗电话，弹两项——「给本人打电话」灰着、写明是二期（#1534）；「给 TA 的智能体打电话」。

## 否决的

- **智能体的总结写进 `messages`（人与人的私聊表）**：要以主人身份代发、或加一个「智能体发的」标记列；车道已经把它画在同一条时间线上，
  不需要第二条路。
- **让 runtime 代朋友调 `create`（朋友先经 Supabase 写一行「请求」）**：多一张表、多一个轮询；一条带 onBehalf 的帧 + 放行一种非成员帖
  更直接，细判仍在 runtime。
- **朋友那条车道的第二条连接接语音**：语音那一层与 chatStore / CallKit 绕在一起，复制一份是两套；开一张 ChatScreen 更便宜。

## 代价与已知未做

- **人与人打电话**（#1534）：要新的媒体通道，等拍板。
- **总结不推给主人**（车道不推回复，ADR-0346 决定 5 照旧）：主人不在私聊页时要自己进来看。
- **朋友点起的轮的审批卡**（#1526）照旧没有：电话里让它动手的事会等 10 分钟自动拒；总结轮本身不动手。
- **协议 26 硬切**，部署顺序 0057 → runtime → 手机；runtime 升了之后协议 25 的客户端连不上云会话。
- `profiles.public_agent_id` 只存 id，不存主场 id：主场只有一个（kind = home），RPC 按它 join；哪天一人多主场再加列。
- 真机未验（Windows 上没有模拟器）。
