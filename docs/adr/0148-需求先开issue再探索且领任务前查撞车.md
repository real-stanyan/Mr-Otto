# ADR-0148：需求先开 issue 再探索，领任务前先查撞车（含 closed issue 与远程分支）

- 状态：已接受
- 日期：2026-08-28
- 关联：issue #616（本决策的协议缺口）、#611 / #612（撞车现场）、ADR-0147（活下来那套的架构补记）
- 相关 ADR（协议）：gearbox 0003（issue 的三种角色）、0005（Memory 活在 open issue 里）、0044（阻塞边）、0047（claim）、0048（并行 lane）
- 相关 ADR（本仓）：0134（「做不了」先验前提——同一类毛病：上一班的省略变成下一班的既定前提）

## 背景

「@好友分享会话」一个需求被两条 lane 各自从头做了一遍，架构还分叉了（#611 走 Storage + DM 信封并合并；#612 走新建表，只写完纯逻辑层就发现撞车）。现场详情在 #616。

关键在于：**这次没有人违反协议**。

- #611 那条 lane 随 PR 合并关掉 issue —— 合规（Task 的关闭条件就是「做完且门禁绿」）。
- 上一班在探索阶段被 app 强退 —— 不是违规，是非正常终止，协议对此没有规定。
- 下一班按 three start-of-shift steps 查 **open** issues —— 合规，但 #611 已经关了，看不见。

ADR-0048 的隔离前提是「claim 不相交」。这次两条 lane 的 claim 确实不相交（#611 和 #612 是两个不同的 issue 号）——**claim 机制防的是任务重叠，防不了需求重叠**。两个 issue 号可以指向同一件事，claim 一个字都拦不住。

## 决策

补两条规则，都落在 Working agreement（L1 变更，走 issue + ADR + PR + 维护者同意）。

### 1. Issue-first：需求一到手先开 Task issue，再开始探索

不是「做完/做到一半再补 issue」，是**动手之前**先开。issue 里此刻只需要一句需求原文 + 一句「正在探索」。

**为什么这条能治「打断不留痕」**：被强退的会话没有机会写任何东西——指望它临死前留痕，是在给一个已经死掉的进程派活。唯一可靠的痕迹是**在它还活着的时候就已经落进仓库的那份**。开在前面的 issue 正是这样一份痕迹：会话被杀之后，它仍然开着、无人 assign，下一班按第 2 步就会撞见。

代价：会多出一些「开了但没做成」的 issue。这是想要的——一个开着的空 issue 说的是「有人碰过这件事，没做完」，正是撞车时最缺的那句话。收工时按 On ending a shift 第 3 条照常处理（做完就关，没做完写进度）。

### 2. 领任务前查撞车：搜同主题的 issue（**含 closed**）与远程分支

开新 Task issue 之前、或从 frontier 领一个之前，先搜一遍：

```bash
gh issue list --state all --search "关键词"
git branch -a --list '*关键词*'
```

命中就先读再决定：已经做完 → 不重做，需要接着改就开一个引用它的新 issue；做了一半 → 顺着往下，别从头再来。

**为什么现有的第 1 步不够**：three start-of-shift steps 的第 1 步已经要求 `git log --oneline -10`。这次那三个 share commit 就在这十条里——但「开工时扫一眼最近十条」和「领某个具体任务前搜这个主题」是两件事，前者不蕴含后者。人（和 agent）扫 log 是在建立「最近发生了什么」的背景印象，不是在对某个还没成形的需求做检索。缺的是后者，就得单独写出来。

closed issue 必须进搜索范围：合规关闭的 issue 是这次的盲区本身。

## 为什么不选另外三种

| 候选 | 否决理由 |
|---|---|
| 要求关 issue 时同步开一个「已做过什么」的索引文件 | 又一份会腐烂的副本（gearbox ADR-0045：副本会腐烂，引用不会）；issue 本身已经是那个索引，缺的只是「搜的时候带上 closed」 |
| 靠 label / GitHub Projects 建需求台账 | 要 triage 权限、要人维护；ADR-0044 已经选过纯文本 + grep 的路子，这里没有理由反悔 |
| 强制串行（同一时刻只允许一条 lane） | 直接推翻 ADR-0048。撞的是需求不是任务，串行只是把两次重复做拉长到两班，治不了根 |

## 后果

- 接受：多出一批「开了没做完」的 issue，噪音换可见性。
- 接受：每次领任务多两条命令的成本。
- 不变：ADR-0048 的 lane 模型、ADR-0047 的 claim、ADR-0044 的阻塞边都不动——本 ADR 只在它们前面加了一道检索，没有改隔离机制本身。
- 这两条治不了「两条 lane 同时从零开始做同一个需求、双方 issue 都在同一分钟开出来」的正面对撞。那种情况下第 2 步搜不到东西。接受：它需要真正的串行化才能防，代价大于收益。
