# ADR-0306 决策模型：中断的那一发照样计费——超时是延迟止损，不是钱的闸

> 原为 ADR-0304，再为 ADR-0305 —— 合并前两次 re-fetch 各撞一次（#1290 拿走 0304、#1304 拿走 0305），
> 按项目 ADR-0074 改号。提交信息与 PR 正文改不了，所以这一行留着让旧引用还找得回来。

- 日期：2026-09-21
- 状态：已接受
- 相关：#1303（本条）/ #1281 与 ADR-0299（决策模型接入）/ ADR-0301（#1300 量完的结论）/ #1304（网关跨 colo 慢）/ ADR-0203 决定 17（中断 ≠ 没花钱）

## 背景

`serveDecision` 里那一段读起来像「客户端断开 = 这一发免费」：

```ts
res = await doFetch(…, { signal: req.signal });
…
} catch {
  await deps.quota.release(caller.uid, requestId);
```

#1303 真机量出来的却是：客户端在 300ms 中断的 5 发，额度照样掉了 192 micro（一发完整调用 41）。
意图与事实对不上，而两种可能该做的事正相反：

1. **Cloudflare 在客户端断开时掐掉了 Worker**，`catch` 压根没跑 —— 那么 hold 既没 release 也没
   settle，是**挂着**的；
2. **上游那一发照跑完、`settle` 正常执行** —— 那么钱是真花了，`release` 那行是死代码，留着会让
   下一个人以为超时免费。

## 怎么分辨的

**① 真 workerd（`wrangler dev`，与生产同一个 `compatibility_date`）**。一个自带假上游的最小复现：
客户端 120ms 断开、上游 1.5s 才回。结果是三件事一起成立 —— 断开之后 `req.signal.aborted`
**仍然是 false**、abort 事件**一次没派**、上游那一发**照样跑完**，于是走的是 settle 那条路。
也就是说，`signal: req.signal` 这条线在这个形状下（非流式、响应还没开始发）根本不响。

**② 生产上的观测对得上，而且是 #1303 正文里现成的数**：连发 5 发中断之后紧接着那一发
**没有**被 `too_many_inflight` 拒，它照常 200 + `cost=41`。而 `MAX_INFLIGHT` 是 **4**、
`HOLD_TTL_MS` 是 **10 分钟** —— 真有 4 笔挂着的 hold 时，那一发必然被拒。所以那 5 笔 hold
不是挂着的，它们结算了。

两条证据指向同一个答案：**② 成立**。钱是真花的，答案被客户端扔了。

## 决策

1. **决策这条路不再把 `req.signal` 递给上游。** 删而不是修好它：这一发是一次前向、没有流式
   输出，中断它省不下上游那笔；而它一旦真生效，行为就翻成「中断 = 免费」，那正是 ADR-0203
   决定 17 堵上的白嫖洞（连发再中断，一分钱不付）。留着一行够不着、又恰好会在某个
   `compatibility_date` 之后突然生效的代码，比没有它更坏。
2. **整段交给 `ctx.waitUntil`。** 本地 workerd 是跑完的，但 Cloudflare 留着「客户端断开时取消
   请求上下文」这条路；真取消的话，结算与释放都跑不完，那笔 hold 挂到 TTL —— 而
   `MAX_INFLIGHT = 4` 意味着 **4 发中断就能把这个账号的整扇网关堵十分钟**（聊天、出图、语音
   一起堵）。这是这条链路上最坏的结局，而保险很便宜：流式那条路本来就靠 `waitUntil` 活过
   响应。改完之后，两种运行时行为下结局都是确定的：要么结算、要么释放，不会挂着。
3. **把话写在读者会看见的地方**：`DecisionDeps.timeoutMs` 那一格上现在写着「它是延迟止损，
   不是钱的止损闸」。调短超时省不下钱，只会更频繁地白买。

## 否决了

- **改成「中断 = 免费」**（把 signal 修好 + 在 abort 分支 release）：白嫖洞，见决策 1。
- **加一个常驻的 `checks/` 脚本盯 workerd 的断开语义**（ADR-0129 那套「运行时那一层打真
  workerd 验」的先例）：它验的是 Cloudflare 不是我们，而决策 2 之后我们的结局在两种语义下
  **都**成立 —— 没有需要保鲜的假设，就不该养一个会在别人改行为时翻红的脚本。复现方法记在
  这条 ADR 里，要再验时现搭一个最小 worker 就够。
- **顺手把 `chat/completions` 那两条也改了**：流式那条已经有 `waitUntil` + 「转发过字节就
  结算」的规矩（ADR-0203 决定 17），非流式那条形状与决策这条相同、同样的保险也适用，但它
  不在 #1303 的射程里，改它要另一条 issue 和另一份真机对照。

## 代价与已知未做

- **超时 = 全价买一个扔掉的答案**，这是事实不是缓解措施。#1300 量出派活那条路在 VPS 上
  3.8–15s、对着 1200ms 是 100% 超时 —— 所以 ADR-0301「runtime 的决策接线先别部署」原样成立，
  这条 ADR 只是把它的原因说准：不是「白等一会儿」，是每一次都付钱。
- **客户端断在 hold 那一趟里**时，DO 可能已经记下这笔 hold 而回执没回到我们手上 —— 那一段在
  `waitUntil` 之前，只能等 10 分钟 TTL。
- **本地 workerd 不是生产边缘**：①是在 `wrangler dev --local` 上验的。它与生产共用一个运行时
  与同一个 `compatibility_date`，且与②的生产观测一致，但两者不是同一台机器。
- **没去查 `usage_event` 落没落那 5 行**（那是最直接的第三条证据）：本机自动模式拦住生产库与
  生产 API 的动作。要补的话，查 #1303 那次探针时间窗里这个 uid 的行数即可。
- 单测钉的是**我们自己那一半**（上游收到的 init 里没有 signal、那段活交给了 waitUntil）。
  「客户端断开后 `req.signal` 不响」钉不进单测 —— undici 的 Request 会老老实实 abort，而那
  正是生产上不会发生的事。
