## 1. 传输层重试的边界：首 token 前可重试，首 token 后一律不

adapter（openaiCompatible）从裸 fetch 升级为：429/5xx/网络错/响应头超时/首字节前
静默 → 指数退避重试（默认 3 次尝试，0.5s/2s）；SSE 静默 90s、响应头 30s 超时掐断。

**为什么以"首 token"划线**：流式路径上碎片边到边直播给 UI（onAssistantDelta），
首 token 之后重试等于把已播出的内容重放一遍，而且半条消息在 OpenAI 方言里续不上。
宁可把"说了一半断线"留给用户重发（barrenTurns/ADR-0042 会把空跑挤出投影），
也不做"聪明"的续写。

**为什么用户 abort 优先于一切**（退避窗口里也立即醒）：停止是意志不是故障（ADR-0006）。

**推翻条件**：若将来 adapter 支持断点续流（provider 侧支持），首 token 后的边界可以重划。

**副作用收口**：vision-bridge 自带给免费视觉档调的五段退避（总窗 ~35s），叠上
adapter 内建重试会把等待乘起来——那条路径 `timing: { maxAttempts: 1 }` 关掉内层，
重试权威唯一。cheapAdapter（helper 通道）保留内建重试：30s 预算内多试一次是纯收益。

## 2. 工具并发的 seam 放在 Tool.parallelSafe，屏障语义保守

模型同一步的连续 parallelSafe（且免审批）调用并发执行；其余工具是屏障，前后严格串行。
结果仍按**原调用序**落盘——投影按 toolCallId 配对本不吃顺序，但日志顺序的确定性
对重放和测试是白捡的，不丢。

**为什么是白名单（默认串行）而不是黑名单**：贴错"可并发"的代价是执行序 bug
（先写后跑被打乱），贴漏的代价只是慢——不对称，所以宁漏勿错。首批只贴四把纯读工具
（read_file/web_search/web_extract/session_search）；browser_read 共享同一浏览器实例的
当前页、MCP 工具是第三方代码，都不贴。

**推翻条件**：MCP 协议若引入 readOnlyHint 之类的能力声明，可据它自动贴标。

## 3. 同 turn 二次自动压缩：布尔锁换增长闸

原 `compactedThisTurn` 一压锁整 turn，防的是"摘要本身仍超阈值时原地重压烧钱"；
代价是超长工具密集 turn 压缩后又胀回去时只能顶着窗口上限跑死。换成增长闸：
距上次压缩尝试占用再涨 ≥ 20k 估算 token（`REAUTO_MIN_GROWTH_TOKENS`）才允许再压。

两个场景都覆盖：摘要胖 → 占用不动 → 永远够不着闸（原保护不丢）；真有新料 →
第二刀值得挨。失败也记地板：同一水位不再撞墙（失败原因多半还在），涨够一档再试。
20k 是拍的：约为最小可感知的"新增了一整段工具往返"的量级，太小会频繁压、
太大等于回到布尔锁。

## 4. 长 turn 软告警：通知，不设上限

不数步数收口是 DSH 式的明确决定（失控兜底是用户停止键，ADR-0006），本轮不推翻。
但灵动岛场景用户不在屏幕前，空转烧钱无感知——单 turn 模型步数踩 30
（`LONG_TURN_ROUNDS`）时发一次系统通知（窗口聚焦时不发，通知是打断不是日志，
同 friendNotifier 的纪律）。只喊一次：反复喊就成了骚扰，而第 30 步之后的局面
用户点开窗口自己看得到。

**刻意不做**：按 token/花费告警（估算口径会随型号漂）、可配置阈值（等真有人抱怨再说）。
