# ADR-0023：桶余额与桌上筹码是两个容器，不是两套账

- 状态：已接受
- 日期：2026-08-18
- 相关：#57，ADR-0022（德州钱规则）、ADR-0021（按型号分桶）

## 背景

#48 定了一条硬约束：「结算走已有账本，不新开一套余额 —— 两套账一定会漂移」。
但 ADR-0022 决定三又要求桌注制：单手最大损失 = 带上桌的那份筹码。
桌注制必然需要一个"桌上有多少筹码"的数，而那个数不是桶余额。

表面看这两条冲突。

## 决定

不冲突，因为 `poker_stacks` 不是第二套账，是**第二个容器**：

- 同一个 token 任一时刻只在一个容器里 —— 要么在桶里（能买推理），
  要么在桌上（能下注）。两个数字永远不描述同一笔钱，所以没有"哪个是准的"这种问题。
- 容器之间只有两个入口：`poker_buyin`（桶 → 桌）和 `poker_cashout`（桌 → 桶）。
  两者都是单个 plpgsql 函数，也就是单个事务，同时改两边。
- 桶的每一分变动仍然只有 `token_ledger` 一个来源 —— 买入/离桌在账本里各留一行。
  #48 那条硬约束说的正是这件事，它成立。

手牌之间的输赢**不进 token_ledger**：那些 token 从没离开牌桌。它们的
append-only 记录是 `poker_hands`，投影是 `poker_stacks`，
再加一张 `poker_transfers` 记两个入口的进出。栈可以从这两张表重算
（`rebuild_stack`），与「事件日志 → 投影」是同一条法理，也是同一套对账手段。

## 为什么不把每手牌都记进 token_ledger

试过在脑子里推一遍，三个问题：

1. 一晚上几百手，账本会被牌局淹掉，而账本是**钱**的账本 —— 想查"这个月
   API 用掉多少"要先把德州的噪音滤掉。
2. 桌注制要求下注只能动桌上那份。如果输赢直接改桶余额，就得在每次下注前
   再查一次"他桌上还剩多少"，那个数还是得存 —— 绕一圈回到原点，只是多了一层。
3. 幂等键会变成 `poker:<hand>:<user>`，一手牌 N 个人 N 行，而结算本身
   是一个原子动作。用一行（`poker_hands`）当幂等单位，重放判定是 `on conflict (id)`，
   不需要"N 行里有几行成功了"这种半截状态。

## 代价

- 一个用户的"总资产"要看两处（桶 + 各张桌上的栈）。UI 要显示总额时必须两边相加，
  漏一边就是少报。
- `poker_stacks` 现在没有指向牌桌表的外键（牌桌在 #58 才建），
  桌被删而栈还在的孤儿行要靠 #58 的建表 migration 补外键收口。

## 什么情况下该推翻

如果哪天取消桌注制（改成直接押桶余额、输光为止），第二个容器就没有存在理由，
`poker_stacks` 该删，结算直接落 `token_ledger`。反过来说：只要"最多输掉带上桌的那份"
还是规则，这个容器就删不掉。
