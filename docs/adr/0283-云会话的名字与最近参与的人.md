# ADR-0283：云会话的名字与最近参与的人

- 状态：已采纳（2026-09-10）
- Issue：#1213
- 维护者拍板三条：会话由**模型**自动命名，话题漂了就重命名（不是一条会话只命名一次）；
  会话行右边画出最近有过对话的那个 5 小时窗里参与过的**人类成员**，头像叠罗汉封顶 3 个；
  窗口是**固定窗**（`floor(ts / 5h)` 的不重叠桶），当前窗没人说话就一直保留最后一个有过
  对话的窗——一旦有过对话，这一格永远不会变空

## 背景

真机形态：团队「mandy's bubble tea」侧栏五条云会话全叫「新会话」。两条独立的病，共用
一个挂载点和一张表。

**① 标题从来没有被写过。** 建云会话时 `workspace_sessions.title` 写死空串，此后没有任何
一处更新它。本机那条路有 `session_autotitled`（`src/main/index.ts`，搭便宜模型的合并调用），
云端一条都没有。侧栏那五行是 `displaySessionTitle` 的兜底在说话（#925），不是命名失败——
命名这件事在云端压根不存在。

**② 「最近谁在这条会话里说过话」没有任何数据源。** 权威日志在 VPS 上，桌面够不着（要先
开一条那个团队的会话房才读得到 backlog），而侧栏那行必须在一条会话都没开的时候就画得出来。
这与 #1064（被点名的提醒角标）是同一个形状，结论也同一条：只能是 runtime 往 Supabase 写
一份日志的投影。

拍板第 3 条（窗口是固定窗、只保留最后一个有过对话的那个）化简掉了一个维度：既然永远显示
"最近一个有对话的窗"，就不需要存历史窗口，也不需要定时器让它到点过期——只有一个当前值。
两件事因此可以共用**一个挂载点**（runtime 的 `say()` 落盘之后）和**一张表**
（`workspace_sessions`：标题用已有的 `title` 列，参与者加两列），协议不进位、不新增事件
类型。落地是三个模块：`src/shared/sessionParticipants.ts`（纯投影，谁算人类发言、窗口
怎么切）、`services/runtime/src/sessionTitler.ts`（标题：提示词/解析/一次网关调用）、
`services/runtime/src/cloudSessionMeta.ts`（`workspace_sessions` 那三格的写入口），加
migration `0035_cloud_session_participants.sql`。

## 决策

### 1. 标题挂在人类发言落盘之后，不挂在 turn 收口上

团队会话是群聊，人可以只跟人说话——`resolveTargets` 解出空名单时只落一条 `chat_message`，
一个 turn 都不起（ADR-0270）。本机那条路把命名挂在 `outcome === "completed"` 上是对的，
因为本机会话必然有 agent 应答；云端如果照抄同一个挂法，"人在群里聊了很久但没人点名任何
agent"的会话会一直停在"新会话"——不是命名滞后，是**永远不会被命名**，因为它压根不产生
挂载点要求的那个事件。改成挂在人类发言落盘之后，回答的是"这条会话有没有发生过对话"，
而不是"这条会话有没有起过 turn"，这两件事在团队场景里不是同一件事。

### 2. 首行兜底为什么存在——不是"模型没命名之前就是空"

第 1 条人类发言不打网关，直接把发言首行截 40 字写进 `title`。两条理由：

- **与本机那条标题投影同一口径。** 本机的标题不是数据库列，是从日志现推的一个投影
  （`events.ts` 对 `session_autotitled` 注释里写的优先级：手动改名 `session_renamed`
  （最后一条胜出）> 本事件（最后一条胜出）> 第一条 `user_message` 首行）——`session_autotitled`
  缺席时，本机侧栏从来不会显示"新会话"，会自己退到第一条消息的首行。云端 `title` 是
  Supabase 一个字面列，没有这层投影机制，"缺席时退到首行"这件事不会自动发生，必须在
  第 1 条发言落盘那一刻**显式写一次**，云端才能在"模型还没命名之前显示什么"这件事上
  给出与本机相同的答案。
- **它同时是模型那条路的降级出口。** 网关挂了、所有者没订阅、解析不出，标题不会卡在
  空字符串上等 `displaySessionTitle` 兜底成"新会话"——它已经有一句人话可看了。

真正让模型命名的第一次排在第 2 条人类发言，不是第 1 条：只有一句"你能听到吗"时，模型
手上的信息量和首行兜底一样少，只会起一个同样烂的名字，还多花一次网关调用。

### 3. 重判把当前标题一起给模型

第 2 条发言起每 5 条人类发言重判一次（`TITLE_EVERY`），提示词把"当前标题 + 最近几句"
一起递给模型，模型回 `KEEP` 或一个新标题。这是"话题漂了就重命名"不至于让侧栏那行字
天天乱变的**全部原因**：多数轮回 `KEEP`，那一行就不动。

被否掉的做法是每次重判都让模型从零起一个新标题、不告诉它当前叫什么。这样同样能满足
"重命名"这个要求，但代价是同一段对话会因为**措辞抖动**被反复改名——模型对同一件事的
复述天然带随机性，两次转述用词不同不代表话题真的换了。而"用户在侧栏里找不到刚才还在
的那条会话了"是比"标题稍微有点旧"贵得多的代价：前者是一次真实的迷失，后者只是一行字
没跟上。

### 4. 参与者是 `workspace_sessions` 的两列，不是新表

`participants`（uid 数组，jsonb）与 `participants_window`（`floor(ts / 5h)`，bigint）加
在既有表上。三条理由，任一条单独成立：

- 这份东西**只有一个当前值**——拍板第 3 条已经把历史维度化简掉了（固定窗、永远显示
  最后一个有过对话的窗），新建一张表会凭空长出一个没有任何消费方的历史维度；
- 会话列表的查询（`listCloudSessions`）已经在查这张表，加两格 `select` 是**零额外往返**；
  新表则是侧栏每次刷新多一次查询；
- RLS 也已经有（`wss_select_member`，在籍即可读）；新表要另写一遍完全相同的策略。

对照 #1064 的 `workspace_mentions`（同一个 feature 集群里，同样是"日志的投影写进
Supabase"）为什么反而选了新表：那份是**一人一行的收件箱**——主键 `(uid, session_id, seq)`、
要按人查、要标已读，形状是一个集合。这份是**会话的一个属性**（"此刻是谁"），形状是一个
标量。两个选择并不矛盾，是同一条"表的形状要匹配数据的形状"给出的两个不同答案。

写方只有 runtime（service key，绕过 RLS）：**不新增任何 `update` 策略**——给在籍成员写
权限，就是让任何一个成员都能伪造"某某参与过"。

### 5. 排除 `relay` 与 `greeting` 开场白

判定"这是不是一条人类发言"时，带 `relay`（agent 互相 @ 接力，ADR-0223 §4.2）或
`greeting`（拉进语音通话的招呼，#1174）标记的 `user_message` 一律不算——即使它们的
`fromUid` 字段填的确实是一个真实的人。

这两种开场白的 `fromUid` 记的是**点火的那个人**，不是此刻在场的人：接力链可能在原始
点火者早已离线几个小时之后还在往下传好几棒；语音通话的招呼开场白记的是拉人进通话的
那个人，不是被拉进来的新成员自己。如果照单全收，一条几小时前的接力链会在点火者早就
离开的那个窗口里，**替他重新"参与"一次**——他会出现在一个自己根本不知道存在的时间段里。

这条判据不是新想出来的：它与 `hiddenFromCloudTimeline` 第 ①⑦ 条问的是**逐字相同的
问题**——"这条 `user_message` 是不是真的有人此刻打出来的"。前者用来决定要不要在时间线
上画出来，这里用来决定要不要算作参与，问题相同，答案也必须相同，分别实现只会走向分裂。
`dispatch: "auto"`（不 @ 任何人时分类器代挑收件人，#1153）的那条**照常算**：它的 `fromUid`
就是真人此刻打出来的这句话本身，只是收件人换了个决定方式，与 `relay`/`greeting` 是完全
不同的情况。

### 6. `session_autotitled.model` 必须是真正产生这个标题的模型

实现期间（Task 4）最初的写法给这一格填了一个写死的常量（形如 `"cloud-titler"`），而
`events.ts` 对这个字段的定义是"标题出自哪个模型（溯源）"。事件日志 append-only，这个
字段一旦写错永远改不回来——写一个编出来的常量进去，就是在一份声称可追溯的日志里，埋
一句永远也无法更正的假话。

裁定是把 `requestTitle` / `requestTitleAsOwner` 的返回类型从 `string | null` 改成
`{ title, model } | null`，`model` 取真正调用的那一款（这条路目前恒等于 `me.models[0]`，
即 ADR-0237 定义下"最便宜的那一款"，但字段记录的是**调用当时的事实**，不是这条选型
规则本身——哪天挑选逻辑换了，这个字段的写法不用跟着改）。代价是多一个字段要在标题
模块、`sessionService` 接线、daemon 装配三处首尾一致地串起来；串错的话 tsc 会在编译期
就挡住，不会安静地流到运行时才被发现。

同一次实现里评估过、判定不改的一处，记在这里免得被当成漏做：`session_autotitled` 不填
`route`（这笔钱走 hosted 还是自带 key）。那一格只对挂了 `usage` 的事件有意义（#1091），
而命名调用**故意不挂 `usage`**——钱的唯一事实在网关自己的 `usage_event` 里，
`session_autotitled` 再挂一份就是给同一笔钱开了第二本账。

## 明确不做

- **手动重命名**：维护者选的是"话题漂了就重命名"这一档，没要手改。`session_renamed`
  压过 `session_autotitled` 的优先级规矩已经在本机那条路上了（决策 2 引用的同一条），
  将来要加手动重命名是纯增量，不需要改动这次的任何决策。
- **agent 头像不画进参与者**：要回答的问题是"最近有哪些人类成员在场"，混进 agent 会让
  "谁在场"这个问题多出一个歧义的答案。
- **参与者历史窗口不留**：只存当前那一份，决策 4 已经把这个维度化简掉了。
- **realtime 不接**：`workspace_sessions` 不加进 Supabase realtime publication——那样
  会让这张表每一次 `updated_at` 变动都推给每个团队成员，而参与者这一格没有那么急；刷新
  走窗口重新聚焦（`focus` 事件），复用 #1064 立下的纪律：会看到它的那一刻必然是人回到
  这扇窗前。
- **参与者为空时不退回显示创建者**："没人说过话"和"某人说过话"是两件不同的事，用创建者
  顶上就是编一个没有发生过的参与。

## 已知代价

1. 固定窗按 epoch 切，边界落在 UTC 00/05/10/15/20（悉尼时区落在 11:00/16:00/21:00/
   02:00/07:00），跟谁的作息都不对齐。因为显示的永远是"最近一个有对话的窗"，相位本身
   基本无感——但一条会话可能在 10:59 和 11:01 各有一个人说话，画出来只有后者，前者那
   个人此刻看着好像没说过话。
2. 每 5 条人类发言重判一次，是忙碌团队里的常态开销（每次约 $0.00005，算在所有者的
   额度上）——这是决策 3 换来"话题漂了就重命名"的代价，不是意外。
3. 参与者只在桌面回到前台时刷新，一个一直开着不切走的窗口里，那排头像会陈旧到下一次
   聚焦。
4. 只做了桌面——手机端还没有云会话客户端，谈不上要不要跟进。
5. 要跑 migration `0035_cloud_session_participants.sql` + 重新部署 `services/runtime`
   才生效（#791）；两件事任一没做，行为都退回改动前的样子。**读、写两侧各自独立
   容错，缺一不可**：写库那一侧，`createSupabaseCloudSessionMeta` 拿到 PostgREST 的
   42703（列不存在）只记一行日志、不抛，不把一句已经发出去的话翻成失败；读那一侧，
   `listCloudSessions` 把 `participants` 拆成单独一条查询（`fetchCloudParticipants`，
   同 `fetchSandboxApproval` 的教训，#977）——**这条查询若拼进主 select，0035 落地前
   PostgREST 会对整条查询回 42703，`unwrap` 抛出，这个团队所有云会话一条都读不出来，
   侧栏与设置页一起挂一条红色错误**（复审 Critical 1 抓到的正是这个：实现期间一度
   真的拼进了主 select）；拆开之后它出错只让参与者那一列回 `[]`，其余字段与整份
   列表照常返回。文件编号原为 0034，合并 origin/main 时与另一条 lane（#1140）的
   `workspace_wiki_journal` migration 撞号；那份已在生产 Supabase 上执行过（先到
   先得），这份从没跑过，改成 0035（project ADR-0074，见
   `tests/docs/migrationNumbers.test.ts`）。
6. 首行兜底写的是发言原文的首行，可能很难看（比如一句"在吗"）。第 2 条人类发言那次
   模型判定会覆盖它，但那两句发言之间的时间里，侧栏上就是那句原文。

## 推翻前提

- 固定窗的边界如果被真实抱怨"跟自己的作息完全对不上"（而不是已知代价 1 描述的
  "基本无感"），再考虑按团队所在时区偏移窗口边界——今天故意选了最简单的 epoch 切法，
  没有为"按时区对齐"预留任何接口。
- 如果 5 条一判的频率在真实团队里显得太频繁或太滞后，`TITLE_EVERY` 是唯一要改的常量，
  不涉及决策 3 本身的判据。
