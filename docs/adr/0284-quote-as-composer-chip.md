# ADR-0284：划词引用改成输入框上方的一张 chip

- 状态：已采纳（2026-09-10）
- Issue：#881
- 维护者拍板三条：引用块拼在**正文之前**；引用**可叠加**（一次能带好几条）；
  **切会话清掉**（引用是指向那条会话里某段话的指针）

## 背景

划词引用（`SelectionQuote`）从上线起就是 `injectComposer(toBlockquote(选中的文字), true)`——
把 `> …` 直接贴进输入框。用户反馈（2026-09-03）：贴进去之后「哪些是引来的、哪些是自己写的」
分不出来了。这不是排版问题：输入框是一块纯文本，引用一旦落进去就和用户敲的字同质，
想删掉重引只能手工挑行。

顺带暴露的第二件事：`injectComposer` 是**追加**（这条不变量本身是对的，F2 / #158 的
`composeInjectedText`），于是引用落在用户已经打了的半句话**后面**——引用回复的通行读法
是先摆出在说哪一段、再说要求。那个顺序不是有人选的，是通道的副作用。

## 决策

### 1. 引用另开一格 `store.quotes`，不并进 `staged`

`staged` 那一排会 travel 回主进程变成 `OutgoingAttachment`（图片 ref / 文本文件全文），
再变成 `user_message.attachments` 落进事件日志。引用不是那种东西——它是这条消息**正文**
的一部分，发送那一刻折回引用块，一个字节都不出渲染层。

并进 `staged` 的代价是让「附件」这个词同时指两种东西，而 `OutgoingAttachment`、
主进程 intake、事件 schema、`resendPayload` 四条路都得跟着加一档——为了一个不出渲染层的
东西改事件 schema，还要背上「旧日志必须永远可重放」那条硬规则。

代价（明写）：**发出去之后，引用和用户自己打的字在日志里重新混在一起**。分层只发生在
输入框这一侧。要让它在时间线上也分层，就得动事件 schema，而那是另一条 issue 的成本。

### 2. 折回引用块发生在 `dispatch()` 里，不在调用点、也不在 `store.send()`

`ChatComposer.dispatch` 是「给模型的话」唯一的出口（`send` 与 `enqueue` 的分岔点）。
折在这里，**每一条**给模型的话带上引用是由构造保证的；折在各个 `dispatch(...)` 调用点上，
漏一处就是引用被悄悄吞掉——chip 清了、话没带上，而那种失败在界面上一个字都不说。

也不折在 `store.send()` 里：排队走的是 `enqueue`（队列只存文字，#1048），在 `send` 里折
意味着 turn 跑着时排的那条把引用留在暂存区、贴到**下一条**消息上。折在 `dispatch` 的
好处正是排队路径免费拿到——引用在入队那一刻已经是文字了。

`$skill` / `@好友` / `/指令` 三条路的判定仍然读**原文**：它们认的是用户敲的头一个 token，
前面糊上一段引用块会让它们一个都认不出来。其中 `/指令` 与 `@好友` 走的是别的出口，
**不消费引用**（它们不是给模型的话），chip 留在原地——这一条是对的，不是漏做。

### 3. 引用在正文之前

引用回复的通行读法：先摆出在说哪一段，再说要求。改动前的顺序（引用在后）是
`injectComposer` 追加语义的副作用，没人选过它。

一排 chips 的读序与发出去的读序因此也一致：引用 chips 排在附件 chips 前面
（`tests/renderer/StagedChips.test.tsx` 钉住 DOM 顺序）。

### 4. 可叠加

「这两个函数一起改」是真实动作。一次只留一条的话，第二次划词会让第一条凭空消失，
而界面上没有任何地方解释它去哪了。id 用 `crypto.randomUUID()`：逐字相同的两段可以引两遍，
文字不是身份（同 `QueuedTask` 的规矩）。

### 5. 换会话清掉——与 `staged` 图片刻意不一致

引用指的是**那条会话里**的某段话；带进另一条会话，这条消息就在说一件没发生过的事。
`staged` 图片今天跨会话留着，两者不一致是**故意的**：图片是用户从磁盘挑的内容，换个会话
照样是它；引用是一个指向别处的指针。

落点是 `enterChat`（chat→chat）加三处回欢迎页的 `set`（`newSession` / 删当前 / 归档当前）——
判据co-located 在「清掉 `events` 的地方」。漏清的那天，Welcome 的 `launch` 里那行
`composeQuotedMessage` 让它退化成「引用被多带了一次」而不是「引用被悄悄吞了」：后者在
界面上什么都不说，而 chip 明明还画着。

### 6. 全空白不收，闸在 `store.addQuote` 而不是浮钮上

一条引用存在 ⇒ 折出来的正文必然非空。composer 的「有东西可发」（`canSend` / `submit`
的两条早退）因此可以直接数 `quotes.length`，不必每次现折一遍。闸放在 store 这一层是因为
第二个调用方那天不会有人记得浮钮上还有一道。

### 7. chip 复用 `ComposerAttachmentChip`，`elements/composer.tsx` 一行不改

图标位走现成的 `thumbnail` 口子塞 `Quote`——不塞的话那张 chip 会按名字猜文件类型图标
（`fileIconName`），一段以 `foo.ts` 开头的引用会被画成用户贴了个 `.ts` 文件进来。
名字 = 第一行**有字的**（刷选常从行尾开始，首行是空的时候画一张空名字的 chip 等于让人
认不出自己引了哪一段），副行 = 「引用 · N 行」，全文挂 `title`（名字那行是截断的，
这是全文唯一的出口）。

## 代价与已知未做

- 发出去之后引用与正文在日志里混在一起（决策 1 已述）——时间线上不分层。
- `title` 是唯一的全文出口：触屏/键盘用户看不到被截断的部分。
- 引用只在本机主会话里做得出来（`SelectionQuote` 只挂在 `App.tsx` 的时间线宿主上）；
  云会话、SideChat、DM 都没有划词引用，本条一个字都不涉及。
- 引用 chip 与附件 chip 长得一样。它们在同一行、回答同一个问题（「这条消息还带着什么」），
  但走两条完全不同的路——想区分只能靠图标位那枚 `Quote`。
- **真机一次没跑过**：本条落在渲染层，`npm run e2e` 里没有划词引用的用例。
