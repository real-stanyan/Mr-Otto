# ADR-0101：撤掉工作区信任门禁——选了工作区并开口说话即授权

- 状态：已接受
- 日期：2026-08-25
- 相关：issue #353（门禁的来处）、issue #425（本次撤销）

## 背景

issue #353 给项目指令注入加了一道 fail-closed 的信任门禁：工作区不在
`userData/trustedWorkspaces.json` 里，`AGENTS.md` / `CLAUDE.md` 一个字节都不进
上下文；UI 在输入框上方挂一条横幅，给「信任并加载」和「本次忽略」两个出口。
威胁模型是 prompt injection —— 陌生仓库里的指令文件是现成的载体。

跑了一段时间之后，这道门禁的实际形态是：

1. **问的时机是错的**。会话在渲染层只是草稿，`startSession` 发生在用户敲下
   第一条消息的那一刻（`App.tsx` 的 `launch()`）。所以横幅总是和会话同时诞生，
   看起来像「发消息才跳信任框」。
2. **它没挡住任何东西，只是让第一轮变瞎**。`launch()` 里 `startSession` 之后
   紧接着就 `void send(t)`，不等信任决定。于是第一个 turn 在零项目指令的状态下
   跑完，横幅还挂在那儿问；点了信任，`project_instructions` 才追加，第二轮才生效。
   而第一条消息通常正是带任务的那条。
3. **信任的 key 是工作区路径原文**，每个 git worktree 都算一个新工作区。本仓的
   工作方式是一个任务开一个 worktree（见 CLAUDE.md 的 worktree 约定），于是同一个
   仓库被反复问。

## 决定

撤掉门禁。**用户选定工作区并在其中开口说话，本身就是授权**——找到指令文件就注入，
不再单独问一次。删除 `src/main/workspaceTrust.ts`、`trustedWorkspaces.json` 落点、
`instructionsNotice` 推送通道、`trustWorkspace` IPC 与 `InstructionsNoticeBanner`。

保留的部分一个字没动：注入仍然只发生在会话开场（记忆之后、第一条 `user_message`
之前），仍然以 `project_instructions` 事件落盘（model-visible means logged），
每段仍带来源路径（provenance）。**「这一刻注入了哪几份」照旧由日志自解释，可审计性
没有损失**——丢掉的只是「事前逐次点头」这一步。

顺带修好了上面第 2 条：门禁没了之后，注入在 agent 装配期完成，首个 turn 就看得到
项目指令，不再存在「第一轮跑在无指令状态」的窗口。

## 代价（明写出来）

clone 一个陌生仓库、在里面开会话，那份 `AGENTS.md` 会直接进上下文，没人再问一句。
这是接受的代价：门禁挡的从来不是「你自己的仓库」，而是「你没读过的仓库」，而它换来的
每日摩擦（每个 worktree 问一次、第一轮变瞎）超过了它在那个低频场景里的收益。

推翻本决定的前提：Otto 开始被用于**批量打开非自有仓库**的场景（比如代跑 OSS
issue、审外部 PR）。那时正确的做法不是把这道横幅原样加回来，而是在**选目录那一步**
做判断——决定属于开工之前，不属于第一条消息之后。
