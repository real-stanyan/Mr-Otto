# ADR-0213：流式光标只归「正在长的那一段」，且由构造保证只有一个

- 状态：已采纳
- 日期：2026-09-03
- 关联：#894、#538（浮窗流式渲染的来处）、#516（浮窗与主聊天共用一份 markdown 配置）

## 背景

用户报：

> 现在的文本输出时会出现多行光标一起输出，应该始终只有一个光标在输出文字

光标是 streamdown 画的（`content: var(--streamdown-caret)`，字形 `" ▋"`）。
它的两个条件不一样：class 只要 `caret` prop，**变量还要 `isAnimating`**。
所以「屏幕上有几个光标」= 有几个 `<Streamdown>` 同时 `caret && isAnimating`。

排查结果分两半：

- **主聊天没有这个毛病**。投影层（`aui/toThreadMessages.ts`）把一个 turn 里的所有
  `assistant_message` 合并成**一条** UI 消息（status 是 `requires-action` / `complete`），
  只有 live 缓冲那条是 `running`；而 `StreamdownTextPrimitive` 的 `isAnimating` 取的是
  **part 自己**的状态。e2e 实测整段流式过程中恒为 1（`tests/e2e/streamingCaret.e2e.ts`）。
- **浮窗（SideChat）有**。它不走 aui，自己手写了两个 `<Streamdown>`：一个画
  `messages` 里的最后一条，一个画正在流的缓冲，**两个都传了 `caret="block"`**，
  而 `isAnimating` 在「上一条已落盘 + 这一条正在流」那段窗口里同时为真 → 两个光标。

顺带排掉一条**假根因**：`app.css` 的 `.streaming > :last-child::after`。
上一只水獭（轨迹 `s-20260903012849-797611f1`）判定它与 streamdown 的 caret 冲突，
然后在这个错误结论上原地循环了两小时（#891）。事实是这个类**从没被任何组件挂上过** ——
`grep -rn 'className.*streaming' src/renderer/src --include=*.tsx` 零匹配。死 CSS，画不出任何东西。

## 决定

### 一、光标只属于「此刻还在长字的那一段」

`messages` 里的每一条都是**已落盘的完整事件**——它不会再变了。给它画光标是在撒谎：
读者据此以为字还在往外冒，实际那段早就定稿了。

### 二、浮窗里只有一个 `<Streamdown>` 拿得到 `caret`

修法不是「把两处的条件对齐」，是**让「同时只有一个」由构造保证**：整个浮窗只有
流式缓冲那一个实例传 `caret`。条件对齐是要靠人每次改动都重新对一遍的东西；
「只有一处传得到」不需要任何人记得。

**逐字出场（`animated` / `MD_ANIMATED`）留在原处不动**：那是「刚落下的这条」的入场动效，
和「还在长」不是一回事，把两者绑在同一个条件上正是这个 bug 的来处。

代价：turn 在跑但缓冲是空的那一小段（模型在想 / 工具在跑），浮窗里一个光标都没有。
这是对的——那一刻确实没有任何字在长，「还在跑」有运行指示条负责说。

### 三、删掉 `.streaming` 那条死 CSS 与它的 `caret-blink`

留着一段谁都没挂、却看起来像在管光标的样式，下一个人还会再被它骗一次
（这次已经骗掉了两小时）。

### 四、两层断言，各钉各的

- `tests/renderer/sideChatCaret.test.tsx`：mock 掉 `Streamdown`，数**有几个实例拿到了
  `caret`**。这是那个 bug 的定义本身；断言 `=== 1` 而不是 `>= 1`——后者全程绿。
- `tests/e2e/streamingCaret.e2e.ts`：主聊天那条路在真 Electron 里数 DOM。
  jsdom 没有样式解析，`getComputedStyle(el, "::after")` 恒空，这一层只能在真浏览器里验。
  采样跑在**页面内**（`setInterval` + 峰值变量），不从测试端一次次 `evaluate`——
  每次 evaluate 过一趟 IPC，采样空档比流式窗口还长，峰值落进空档就是假绿（第一版踩过）。
  判据取「wrapper 上有没有内联的 `--streamdown-caret`」而不是遍历整棵树量 `::after`：
  后者 40ms 一轮能把渲染进程拖到流式都跑不完（第二版踩过）。两者等价——
  变量有值 ⇒ class 一定在 ⇒ 那个 `::after` 一定画得出来。

## 后果

- 浮窗第二轮及以后的对话不再出现两个光标。
- **主聊天这条路本来就是对的，本 ADR 没有改动它**——e2e 是给它上的保鲜期，不是修复。
  如果用户在主聊天里仍然看得到多个光标，那是本次没能复现的第三条路径，
  需要知道「是哪个界面、当时屏幕上有几条消息」才能继续（见 #894 的备注）。
- 已知未收口：用户同一条消息里报的问题 2「输出时输入框无法切换模型」不在本 ADR 范围。
