# ADR-0292：会话目录换成每轮一格的会话地图，撤掉分区分类员

- 日期：2026-09-11
- 状态：已接受
- Task issue：#1259
- 关系：推翻 ADR-0034「会话目录由分区事件驱动」的界面那半（事件类型本身留着）；ADR-0080 的合并调用少一个任务

## 背景

维护者原话：「https://www.assistant-ui.com/elements/conversation-map 我们之前实现过这个滑块看会话不同
state 的功能，但是实际应用场景上并没有显示出来。查一下什么问题，顺便改用这个 UI 来实现」。

之前那一版是分区轨 SectionRail（#109）：每个 turn 收口后便宜模型判「话题换了没」，落 `section_classified`；
`deriveSections` 投影出分区；时间线左侧留白里一小撮刻度，**至少两个分区才画**。

诊断（本机真库，生产账号的 sessions.db 拷出来查的）：≥4 轮的 15 条会话里只有 2 条（08-18 / 08-21 两条
7–9 轮的短会话）拿到过 ≥2 个带标题的分区；52 轮那条 7 次分类 1 个标题，35 轮那条 19 次分类 1 个标题。
三层原因：

1. **粒度**：一段会话一个话题是常态，模型几乎总回「延续」。门槛（一条目录是噪音）本身没错，错的是拿
   「话题切换」当目录的粒度。
2. **无声失效**：一个分区都还没有时模型回 `newSection:false` → `parseSectionReply` 判解析失败、不落事件
   → 下一轮照旧 → 会话永远 0 个分区。21 轮那条：同一次合并调用里建议那半成了 9 次，分区那半 0 次。
   「失败了下一轮自愈」的前提是偶发失败，这里是每次都失败。
3. **覆盖面**：云会话压根没有（runtime 不跑分类员，CloudSessionPage 没挂轨）；窗口窄于 1024px 不画
   （`hidden lg:block`）。

## 决定

1. **一轮一格，纯投影。** 换成 assistant-ui registry 的 conversation-map（`conversation-map` +
   `elements-conversation-map`，取回于 2026-09-11）：一句人话 + 回它的那几条 = 一轮，标题取那句话的首行、
   预览取第一条有字的回答，当前正在读的那格加粗。不打模型、不落事件，两轮就画得出来（`MIN_TURNS = 2`
   留着——一格的地图没有「别处」可去）。
2. **本地与云会话同一个组件，浮层挂在滚动区外面。** 纯逻辑在 `lib/conversationMap.ts`（上游写在
   `.aui.tsx` 组件里的切轮 / 取名 / 量位置，外加本仓的云会话条目），浮层与量位置在
   `components/ConversationMapRail.tsx`，元件在 `components/elements/conversation-map.tsx`。
   本地的条目取 assistant-ui runtime 的消息，记号是 MessagePrimitive.Root 自带的 `data-message-id`；
   云会话的头是人说的话（`UserMessageRow` / `ChatMessageRow`）+ 通话卡，渲染循环**按条目的 id** 给头行打
   `data-turn-id`——条目与记号出自同一份结果，不会出现「点了找不到」的格子。上游把地图挂在 assistant-ui
   的 Viewport **里面**（靠 `useThreadViewport`），本仓挂在宿主（relative）上的 `absolute inset-y-0`：
   云会话的时间线不是 assistant-ui，没有那个 store。
3. **分区分类员删掉。** 地图不读分区之后它只剩开销——每轮把最多 4000 字的跨度塞进便宜模型的提示词
   （合并调用里最贵的一块），产出又几乎没有。`sectionClassifier.ts` / `deriveSections.ts` /
   `SectionRail.tsx` / thread.tsx 的 MessageAnchor 槽 / App 那套 IntersectionObserver scrollspy 一起删；
   合并调用剩三个任务，重新编号（跟进建议 / 会话标题 / 会话主题 = 任务一 / 二 / 三）。
   **`section_classified` 事件类型留着**：旧日志要永远可重放（硬规则），投影照旧丢弃它、旧账照旧计进
   `deriveUsage`，隐私闸与笔闸的表态不动。
4. **预览卡用 Radix HoverCard，不引 base-ui。** 上游用 `@base-ui/react` 的 PreviewCard（detached trigger +
   handle：一张卡跟着指针在刻度间走，不是每格各开各关）。base-ui 在 node_modules 里只是 @lobehub/ui 的传递
   依赖，直接 import 是偷用；加依赖是 Tech stack 那一级的事（ADR-0264 为弹簧不引库是同一个先例）。
   Radix 没有 handle，改成整摞刻度当同一个 Trigger、按所指那格算 `alignOffset`：扫过刻度时卡片原地换内容、
   瞬时换位置，进退场只在第一次出现与最后一次收起时演。进退场走 keyframes（Radix Presence 只等 animation
   不等 transition），与 shadcn Popover 共用同一对。
5. **尺寸缩进 16px 的左内边距。** 上游的时间线 44rem 居中，刻度住在宽阔的留白里；本仓的正文撑满宽度，
   留白只有 `px-4`。命中带与它等宽（一格都不越到正文上），静止的刻度 10px、从 6px 起画；悬停时照上游
   三档伸长——瞬时的，允许探进正文（原分区轨同一个取舍）。
6. **reveal 桥的键换成消息 id，住进 OttoThread。** 格子的 id 就是那一轮第一条消息的 id（`String(e.seq)`），
   与 `messageIds` 同一把尺子，`buildSectionAnchors` 那张对照表删掉。原来跳转请求住在 App、要自带
   sessionId 防它串进新会话的那一帧（passive effect 子先于父）；现在挂起的跳转住在 OttoThread 自己的
   state 里，切会话时与窗口在同一次渲染里归零，那一帧不存在了。
7. **滚动不用 scrollIntoView**（它会把每一层可滚动的祖先都对齐一遍）；减动效时显式 `behavior: "instant"`
   ——本地视口挂着 `scroll-smooth`，`auto` 会被那条 CSS 接管成平滑。
8. **跳走就关掉贴底跟随**（真机上撞出来的，jsdom 里一条都看不见）。本地视口是 `turnAnchor="bottom"`：
   assistant-ui 的 autoScroll 内容一长高就 `scrollToBottom`，直到它自己的 scroll 回调认出一次「用户往上滚」
   （`isUserScrollUp`：相邻两次回调之间 scrollTop 变小**且** scrollHeight 没变）才松手——程序滚动天然凑不齐这
   两条，reveal 桥刚补挂几百条消息时紧跟着的那次尺寸回调就把跳转整个取消（真机时间线：跳转 75ms、被拽回底部
   77ms）。上游没这个问题：registry 那份 thread 是 `turnAnchor="top"`（autoScroll 默认关），也没有窗口挂载。
   修法用 `ThreadPrimitive.Viewport` **公开的** `autoScroll` prop：OttoThread 持一格 `following`，跳走那一刻关，
   人自己滚回底部（落稳之后）/ 新的一轮开跑 / 切会话再开，重新打开时补派一次 scroll 让它按实际位置重读。
   否决了「同步喂它两次合成 scroll 骗过 isUserScrollUp」：试过，真机上仍被拽回，而且赌的是一个升级时不会报错
   的内部判据。云会话的滚动区没有 autoScroll，跳走时把它自己的「贴底」标记清掉即可。
9. **落地后按住目标一小会儿。** 本地消息是 `content-visibility: auto`（`contain-intrinsic-size: auto 200px`），
   没渲染过的按 200px 估、滚到附近才换成真高：平滑滚动瞄的是出发时算的绝对位置，一路上经过的消息纷纷换成
   真高，真机上落在了前一轮；落地后目标**上方**那条也还会长高，而浏览器的滚动锚定未必锚在目标上（真机上
   目标被顶下去 225px）。所以落地后逐帧量，偏了瞬时补回，连续 8 帧不动（或已经挪不动——最后一屏的轮次到不了
   顶）就收手，最多按 1 秒；用户在这期间滚轮 / 按下 / 键盘 / 触摸任何一样都立刻放手。

## 否决的路

- **修分类员、保留分区轨**：修掉 `newSection:false` 那个无声失效只解决第 2 层；第 1 层（话题粒度太粗）是
  这条路的本质，修不掉。而且每一轮都要为它付一次大提示词。
- **每轮一格 + 分区标题叠在卡上**：真库里一场会话的分区标题通常只有 1 个（基本等于会话标题），叠上去
  信息量接近零，却要让分类员继续跑。
- **直接依赖 base-ui**：见决定 4。

## 代价 / 已知未做

- 窄窗口也画了（原来 `lg:` 以下不画）：刻度住在 16px 留白里，不再需要宽度；悬停伸长会探进正文。
- 悬停伸长动的是 `width` 不是 transform（上游原样；2px 高的条，重排范围只有它自己那个按钮）。
- 云会话的「一轮」只认人说的话与通话卡：agent 自己接力、没有人话打头的那一段并进前一轮；时间线上第一句
  人话之前的内容不属于任何一格。
- 本地会话窗口上沿以上的轮次，量位置时只看得见挂着的消息：视口停在窗口顶时，「当前」兜底取窗口里第一条
  所属的那一轮。
- 已经写进旧日志的 `section_classified` 永远在那（append-only），不再有任何界面消费方。
- 贴底跟随靠一格 `following` 管，打开的时机是三条启发式（回到底部 / 新一轮开跑 / 切会话）：跳走之后又来一轮
  后台回注（没有人按发送、状态照样变 running）也会把人拉回底部——与上游 `scrollToBottomOnRunStart` 同一个取舍。
- 按住目标那一秒里界面可能瞬时校正一两次（真机上一次：64px）；用户一动就停。
- 窗口补挂那道补偿（thread.tsx，ADR-0285）在视口不在窗口顶时会与原生滚动锚定叠加、把视口推到底部夹住
  （锚点在插入点下方时原生已经挪过一次）。reveal 桥这条路上看不见——同一个任务里紧接着就跳走了；哨兵那条路
  锚点是哨兵自己，不叠加。单开了 #1262，没顺手改那道补偿：它是 ADR-0285 的判据。
- 云会话一侧没在真机上跑过：它要一个真登录 + 活着的云会话，而本机 dev profile 被正在跑的实例占着。
  替身是 `tests/renderer/cloudConversationMap.test.tsx`（真渲染 CloudSessionPage：刻度与带 `data-turn-id`
  的行一一对上、点一格滚的是那一行）；滚到位这件事只在本地那侧真机上验过（真库里 52 轮的会话：48 格、
  悬停卡、快慢两条跳转路都落在目标上）。
- 手机端没有这个组件（手机本来也没有分区轨）。
