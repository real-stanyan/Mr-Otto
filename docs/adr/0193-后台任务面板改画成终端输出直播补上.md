# ADR-0193：后台任务面板改画成终端，输出直播随之补上

- 状态：已接受
- 日期：2026-08-30
- 相关：issue #772、ADR-0109（后台任务面板 = 日志的投影）、ADR-0139（面板搬进右侧槽位）、
  ADR-0144（vendored assistant-ui element 的本仓改动怎么记）、issue #389 / #395（后台任务本体）

## 背景

后台任务面板从 ADR-0109 起画的是一行一个任务：一个图标、命令原文、一个走秒的计时。
这一行回答得了「有几个在跑」，回答不了用户唯一真正想问的那个问题——**它卡住了没有**。

而后台任务的典型形态恰恰让这个问题变得尖锐：它们的主要来源不是用户点单，是**前台命令跑满
30 秒被自动转过去的**（`AUTO_BACKGROUND_AFTER_MS`，issue #395）——全量测试、整包构建、
`npm install`。这些命令要么跑三十秒要么跑三十分钟，而「◜ npm run build · 12:04」这一行
在两种情况下长得一模一样。

雪上加霜的是：转后台那一刻，工具行底下那条直播尾巴（`ToolLiveTail`）会**当场消失**——
`bash` 立刻返回「已转入后台任务 bg-7」，`tool_result` 落地，渲染层按既有规矩清掉
`toolOutputByCall[toolCallId]`。于是同一个进程，转后台之前看得见输出，转后台之后一片空白。

本仓早就有画这件事的组件：`components/elements/terminal-block`（assistant-ui element，
`ToolLiveTail` 用的就是它）。缺的不是画笔，是**内容**——`execDetached` 的注释写着
「不接直播」，`background_task_completed` 事件只带 `taskId / cmd / exitCode`。

## 决定

**面板每一行改画成一台终端，后台任务的输出直播随之接上。**

### 一、直播接到哪一层：`execDetached` 加可选 `onOutput`

```ts
export type DetachedOptions = Pick<ExecOptions, "onOutput">;
execDetached?(cmd: string, opts?: DetachedOptions): Promise<ExecResult>;
```

刻意只有 `onOutput` 这一格：`signal` 不能有（躲开 turn 信号正是 `execDetached` 独立成方法的
理由，见 ADR-0006 的 `withAbortSignal`），`timeoutMs` 也不给（30 分钟那个上限是 world 的承诺，
不是调用方的旋钮）。两个装饰器（`withAbortSignal` / `withExecOutput`）改成透传 `opts`——
**但都不往里塞自己的 sink**：`withExecOutput` 那份是按 `toolCallId` 挂到工具卡上的，
而后台任务的输出该挂在 `taskId` 上。

### 二、两条起点各有各的接法，漏掉任一条都是一片空白

- **显式 `run_in_background=true`**：`background.start(cmd, (onOutput) => world.execDetached!(cmd, { onOutput }))`。
  `BackgroundStarter.start` 的 `run` 参数因此从 `() => Promise` 变成 `(onOutput) => Promise`。
- **前台跑满 30 秒自动转后台**：进程已经在跑了，回调加不进去。所以 `bash` 在**命令起跑那一刻**
  就挂一份自己的 tee（`world.exec(cmd, { timeoutMs, onOutput })`）：交接前攒着（超 4000 字丢头部，
  尾巴才是「最新进展」），交接那一刻整段补给面板，之后直通。为此
  `withExecOutput` 的 `exec` 从「顶掉调用方的 `onOutput`」改成「**两个都喂**」——
  一条输出流，两个接收方（工具卡 + 后台面板），顶掉任何一边都会让一个瞎掉。
  代价：命令在 30 秒内跑完的那条路白攒一次，有界的几 KB。

### 三、这不违反「投影必须可从日志推导」，判据与前台直播同一条

硬规则要的是**事实**可从日志推导。直播碎片从来就不是事实——`ExecOptions.onOutput` 的注释
（issue #278 之前就写好了）已经把这条边界立过一次：「直播是 UI 增强，不是事实——完整输出仍由
`ExecResult` 一次性返回并落盘，和 assistantDelta 同款边界：碎片永不进日志，日志只收凝固后的整体」。
后台任务的完整输出照旧随**完成回注那条 `user_message`** 进日志（`formatCompletion`），
一个字都没少。面板上「哪几行该出现」仍然 100% 是日志的投影（`projectBackgroundRuns`），
新加的只是那几行**里面**画什么。

同一条判据也解释了为什么**不**把输出塞进 `background_task_completed` 事件：那条事件是审计注记
（`ignorable`，模型不消费），而完整输出几秒后就会以模型可见的形式进日志——写两遍是把同一份
字节记两次，不是让它更可推导。

### 四、尾巴在主进程留一份，因为「推送只覆盖此刻在场的人」

`BackgroundTasks` 每个任务留最后 4000 字（`TAIL_CHARS`），最多 32 个任务（`TAIL_TASKS`）。
留这一份的理由不是「再存一遍」，是**补得回来**：一个跑三十分钟、十分钟不吭声的构建，
重开面板 / 重载渲染层的人错过那几帧就是永远空白。`liveBackgroundTasks` 这趟本来就每 5 秒跑一次
（ADR-0109 的「谁还真的活着」），顺路把尾巴带回来，一趟 IPC 干两件事。

淘汰**跳过还活着的任务**：宁可暂时超额，也不清一个正在写字的终端；超额的上界是「同时活着的
后台任务数」，那个数本来就很小。淘汰在两个时机跑——有新输出、和**有任务死掉**：
只挂前者的话，一批任务全跑完之后没人再写字，超额就永远收不回来。

### 五、渲染层：尾巴**按会话分格**

`bgOutputBySession: Record<sessionId, Record<taskId, string>>`。不是洁癖——`taskId` 是 `bg-N`，
计数器每个会话各数各的（`BackgroundTasks` 的 `this.n`），平铺一层的话 A 会话的 `bg-1` 会把
B 会话 `bg-1` 的输出画出来，而两者都叫 `bg-1`，**看不出错**。

`setLiveBg` 的语义：名单整份替换，**尾巴只合并不替换**。那趟 5 秒的轮询问的是「谁还活着」，
跑完了但结果还没贴回对话的任务不在答案里——可它的卡片还画在面板上，照名单整份替换会让那张卡
每 5 秒被清一次屏。

推送走既有的合帧器（`deltaCoalescer`，issue #278）新增的第三条通道 `bgOutput`，不直发：
后台任务多半是构建/全量测试，刷屏速度和前台 bash 一模一样。走合帧器还顺带继承了那条顺序纪律
（任何非 delta 推送前先 flush）。

## 后果

- **`BackgroundRun` 多一个 `completedAt`**（取自 `background_task_completed` 的 `ts`）。
  少了它，「跑了多久」只能拿此刻的钟算，于是一个早就跑完的任务会在面板上一直往上走秒。
  纯投影字段，旧日志天然有 `ts`，不需要迁移。
- **`terminal-block` 多两处本仓改动**（记法同 ADR-0144）：`exitCode`（上游把 `exit 0` 写死在
  完成态里——它画的是文档里那个永远成功的示例，本仓这块要画真跑过的任务，失败是常态）、
  `footer`（卡片底部状态条：已跑多久 / 结果还没贴回对话。这些字说的是**这个任务在会话里的处境**，
  不是命令吐出来的东西——混进输出区就是在伪造终端输出）。外加命令行截断（槽位能被拖到很窄）。
- **`aria-live` 从输出区挪到了头上那句计数**。输出区现在是逐帧刷新的终端，把 live 区圈在它外面
  等于让读屏软件念完整个构建日志；「2 个在跑 → 1 个在跑」才是值得被念出来的那句话。
- **已知留白**：app 重启后，「跑完了但还没贴回对话」的那些行会显示成没有输出的空终端——
  主进程那份尾巴在内存里，重启就没了。不补，因为完整输出几秒后就会以回注消息的形式出现在时间线上，
  为这个几秒的窗口把碎片落盘不划算。
- **`bash` 的 tee 只覆盖 `world.exec` 这条路**。`bash` 里的 `&` 后台进程、`nohup` 出去的东西
  照旧看不见——那本来就不是后台任务，`BackgroundTasks` 里没有它们的登记。
