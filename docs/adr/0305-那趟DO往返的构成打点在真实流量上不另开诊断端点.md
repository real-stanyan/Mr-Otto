# ADR-0305：那趟 DO 往返的构成——打点打在真实流量上，不另开诊断端点

> 原为 ADR-0304 —— 合并前 re-fetch 撞上 #1290 那条（项目 ADR-0074）。提交信息改不了，这行让旧引用还查得到。

- 日期：2026-09-21
- 状态：已接受
- 关联：#1304（承接 ADR-0303 / #1300 / #1303），`services/edge/src/quotaTiming.ts`、`services/edge/src/worker.ts` 的 `Quota` 与 `handler.fetch`

## 背景

`QUOTA` 是一户一个 Durable Object 实例（`getByName(uid)`），落点由它第一次被创建时的 colo
决定、之后不动。于是**一趟 DO 往返的代价取决于请求从哪个 colo 进来**，而云会话跑在
HEL 那台 VPS 上、每一轮 chat 都在付这笔。

ADR-0303 砍掉了三趟里纯问答的那一趟（成功 3 → 2，被拒 2 → 1），部署后量到的数写在 #1304 的
第二条评论里，两件事：

1. **地板真降了**：`/me` 走 `view`（**一趟** DO、不碰上游，ADR-0303 没碰它，正好当对照组）
   各打 15 发，Mac（SYD）中位 0.176s / 区间 0.156–0.247，VPS（HEL）中位 1.34s /
   区间 0.829–4.90。对上不碰 DO 的 400 那条（两边都 0.1–0.2s）⇒ **一趟 DO 往返在 HEL 约
   0.7s、在 SYD 约 0**，那些实例就在悉尼附近。
2. **但这 0.7s 在真机上被方差盖住了**：改动前后各四发 decision 在噪声里分不开，而对照组
   自己在 0.83s 与 4.90s 之间跳——Mac 那侧 15 发一次 excursion 都没有。

所以剩下的问题不是「远」而是「远 + 抖」，而那 1.34s 里至少有三样东西混在一起，
**它们各自对应一个完全不同的修法**：

| 分格 | 修法 |
|---|---|
| ① 纯往返（客户端 colo → DO 落点 → 回来） | 只有放置策略治得了 |
| ② DO 里 `plan()` 那两条 Supabase 查询 | `planCache` 落 storage 就治好了（它现在是**实例内存**、60s，实例被回收就没了） |
| ③ DO 冷启动 `pageAll` 翻 `usage_event` 重建 `state` | 又是另一件事 |

不知道构成之前任何一个修法都是猜——**Smart Placement 尤其不能盲开**：现在已知这些 DO
都在悉尼附近，开了很可能把欧洲用户的「一趟慢往返」换成「整个请求都慢」。

本条决定**只造尺子，不动任何行为**：额度怎么算、谁被拒、拒了说什么，一个字没变。

## 决定

### 1. 打在真实流量上，不另开诊断端点

#1304 的原话是「从 `/healthz` 或一个带鉴权的诊断端点回出来即可」。两条都否了：

- `/healthz` **根本不碰 DO**，量不到要量的东西。
- 独立诊断端点量到的**永远是一个热 DO**（`planCache` 命中、`state` 已在 storage 里）——
  而要分辨的那 0.83–4.90s 的抖只出现在真实流量里偶发的那几发上。一把系统性地测不到
  病灶的尺子，比没有尺子更坏：它会给出一个「看，很快啊」的结论。

落法：DO 的**每一条回执**都带一格 `timing`，Worker 侧把这一次请求打过的每一趟汇成一个
响应头 `x-otto-quota-timing`。于是量到的就是真实的那一发，包括偶发的慢发。

### 2. 头永远挂，不给开关

开关的代价是：**看到慢的那一刻，它已经过去了**。慢发是偶发的，而一个要先打开才生效的
开关意味着永远只能量到打开之后的那些。代价是每条碰过 DO 的响应多约 60 字节，且关掉它
要重新部署——接受。

### 3. 两侧各量各的时长再相减，不比对两边的时间戳

DO 与 Worker 是两台机器、时钟对不齐。「Worker 观测到这趟 fetch 花了多久」减去「DO 自报
在里面花了多久」是两个**各自成立的时长**之差，天然没有时钟偏移；而「DO 报它几点收到、
Worker 减一下」会把两台机器的钟差直接读成往返。

### 4. 往返不预先减好，由读的人自己减

`outer - in` 这个减法**不在代码里做**。Workers 的 `Date.now()` 只在 I/O 之后推进（时序
攻击缓解），两侧的推进边界不同，差值可以为负；而一个负的「往返」是测量噪声不是事实，
夹成 0 则会把噪声伪装成「往返可以忽略」——那恰好是这次要判的那件事的一个方向。
头里给原始的 `outer=` 与 `in=`，减法留给人。

### 5. `parseTiming` 五格缺一不可，缺了回 null，不拿 0 / false 冒充

同 `parseRemaining` 那条（ADR-0303）。一个假的 `in=0` 会把这一趟的**全部时间记到纯往返
头上**，而「往返还是 DO 内部」正是要分辨的东西——冒出来的答案比没有答案更坏。
没有内层数据时头里**整段 `in=` 缺席**，所以「没有数据」与「内层确实是 0」长得不一样。

### 6. 账本不做实例字段

DO 单线程只保证「一次 fetch 里的读改写没人插队」，`await` 之间照样会切出去——两个并发
请求进同一个 DO 时，一个实例字段会把两笔账混成一笔。账本由 `fetch` 现造、一路递给
`plan()` / `state()`。

### 7. 两个记号各自置在该置的地方

- `planCold` 置在**查之前**：查炸了（→ 503）那条路也报得出「它是冷的」，而最慢的那几发
  恰恰是这一条。
- `rebuilt` 置在 `blockConcurrencyWhile` 里 `if (again) return again;` 这道闸**之后**：
  排在重建后面的那个请求什么都没重建，置在前面就会让它也报「这一发做了冷启动重建」。
- `state` 的耗时用 `try/finally` 而不是在三条 return 上各记一次：**重建失败那条（→ 503）
  是最该量到的一发**。

### 8. `me:db` 单独量

`/billing/v1/me` 不止一趟 DO——它还在 **Worker 侧**打 Supabase 拿 `routes` 与 `plans`
（前者有 isolate 级 60s 缓存所以常常约等于 0，后者每次都真查）。不单量这一段，它会藏在
「客户端总时长 − DO 那趟」的残差里被读成往返的一部分。

### 9. 挂头那个函数收结构类型，不收 `Response`

`{ headers: { set(k, v): void } }`。理由是这个文件要进根门禁，而
`@cloudflare/workers-types` 只能待在 `services/edge/tsconfig.json`（见那份文件头注：塞进
根 tsconfig 会和 Electron 主进程的全局声明打架）。收结构类型之后，「空样本不碰」与
「只读头抛了就算了」这两道闸进得了 vitest。

两道闸各有一个具体的坏结局挡在后面：中继那条 **101 升级响应**连 `new Response` 都构造
不出来（它本来就不碰 DO，所以空样本这条闸由构造保证）；上游那份 Response 的头是只读的，
`set` 会抛——**一个诊断头不值得把一次正常响应变成 500**。

### 10. 接线断言落在源码上

`worker.ts` 进不了 vitest（一 import 就要 `cloudflare:workers`）。而这套东西的失败模式
全是静默的：DO 少回一格 `timing`，头上就只剩 `outer=`，读的人把整趟记成纯往返。
判据因此读 `worker.ts` 的源码，同 `tests/runtime/sandbox.test.ts` 的 `freeKib` 接线断言。
其中「DO 产出的字段集」与「`parseTiming` 要的字段集」是**对拍**不是各抄一份——
哪天 `QuotaTiming` 多一格而 DO 没跟上，这条当场红。

## 代价与已知未做

1. **流式 chat 的 `settle` 进不了这个头**：它跑在 `waitUntil` 里、在响应发出之后。
   流式那条只看得到 `hold`（形状与 `settle` 那趟一样，所以不影响结论）。
2. **`total − plan − state` 那点残差（storage put + CPU）没单独分格**，要的时候相减得出。
3. **每条碰过 DO 的响应多约 60 字节**，且没有开关（决定 2 的代价）。
4. **DO 的 `timing` 进了内部线上格式**：今天没有第二个消费方，哪天有人给 DO 回执加严格
   校验要知道这一格在。
5. **这条什么都没修好**。它是一把尺子；#1304 仍然开着，下一步是拿它量、再据构成选修法。
6. **一次真机都没量过**——要 `npm run edge:deploy` 才在线上生效。

## 部署后量到的（2026-09-21，edge 指纹 `fdd929981211`）

同一个账号（dev，`sub=2819d0bb`）、同一份请求，从 Mac（SYD）与 VPS（HEL）交叉打，读
`x-otto-quota-timing`。**注意用的不是本 issue 前两轮那个 max 账号**（主 profile 的 token
过期、app 没开着）—— DO 一户一个，所以下面的绝对值不与前两轮的基线直接可比；但要回答的是
「这一趟由什么构成」，而构成是在**同一个账号的两个 colo 之间**比出来的，那一步成立。

`/billing/v1/me`（一趟 DO + Worker 侧一次 Supabase），26 发：

| | Mac（SYD） | VPS（HEL） |
|---|---|---|
| `view` 往返（`outer − in`，热） | **8–10ms** | **323–367ms**（中位 ~344） |
| `view` 内层（`in`，热） | **0** | **0** |
| `plan()` 冷那一发 | 659ms | 139 / 337ms |
| `state` / 冷启动重建 | 全程 `state=0 reb=0` | 全程 `state=0 reb=0` |
| `me:db`（Worker 侧 `plansQuery`） | 115–353ms | **290–326ms**（冷 isolate 上 830–912ms） |

`/llm/v1/chat/completions`（两趟 DO：hold + settle），各 3 发：`hold` 往返 SYD 20ms /
HEL 379–402ms，`settle` 往返 SYD 20–21ms / HEL 338–358ms，冷那一发的 `plan()` 1163ms。
⇒ **云会话每一轮在 HEL 付约 700–760ms 的纯 DO 往返**，同一件事在 SYD 是 40ms。

三条读法，其中两条**推翻了背景里的怀疑**：

1. **远端的代价几乎全是纯往返。** 热的时候 `in=0` —— 问题不在 DO 里干了什么，在「话说到
   那儿再说回来」。
2. **怀疑 ③（冷启动 `pageAll` 重建）一次都没触发**（32 发全 `reb=0`）。它不是原因。
3. **怀疑 ②（`plan()` 的两条 Supabase 查询）确实贵（139–1163ms），但只在 `planCache`
   过期那一发付**，每 60 秒一次；而且那一发的开销是从 **DO 所在地**发出的，与客户端 colo
   无关。它是一个周期性尖峰，不是地板。

**一条本来不在任何假设里的发现**：`me:db` —— Worker 侧那条 `plansQuery()` —— **没有任何
缓存**，每次 `/me` 都真查一次库，在 HEL 上稳定 290–326ms，**比一趟跨洲 DO 往返还贵**；
隔壁同一行 `Promise.all` 里的 `routesOf(env)` 有 isolate 级 60s 缓存，它没有。修法是一行，
另开 #1322。

**顺带修正 ADR-0303 补记里的一个数**：那里写「一趟 DO 往返在 HEL 约 0.7s」是**按减法估的**
（`/me` 总时长减去不碰 DO 的 400），而它把 `me:db` 那 300ms 一起算进了往返。直接量出来是
**~344ms**。这正是本条决定 8（`me:db` 单独量）要挡的那件事 —— 第一次用就挡到了，也是这把
尺子存在的全部理由：**按减法推出来的分格会把没量的东西算进量了的那一格**。

**没复现出那个 0.83–4.90s 的抖**：26 发 `/me` 全落在 0.66–1.51s，最慢那发是 `plan()` 冷。
上一轮的抖是在 max 账号上量的（另一个 DO 实例），换账号之后没看见 —— 要用同一个账号重量
才说得准，这一格仍然欠着。
