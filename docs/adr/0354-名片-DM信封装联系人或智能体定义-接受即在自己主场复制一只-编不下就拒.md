# ADR-0354：名片——DM 信封装一位联系人或一只智能体的定义；接受 = 在自己主场复制出一只；编不下就拒

日期：2026-10-04 · issue #1524 · 维护者原话：「增加 CONTACT CARD 功能，和微信一样可以分享联系人名片，也可以分享对方的智能体，点击接受智能体后，该 AGENT 保存在接受者智能体库中。」

## 背景

朋友私聊是 `messages` 表（0001），body 是 4000 字以内的文本；此前唯一的「结构化消息」先例是分享会话的信封
（`sessionPackageCodec.ts`：整段 body 是一段 JSON，接收方认出就画成卡，老客户端看到 JSON）。智能体的定义住在 `workspace_agents`
（名字 / 职责 / 提示词 / 脸 / 声音 / 型号 / 连接器白名单），每只属于一个工作区、由主人的云电脑跑、花主人的额度。

## 决定

1. **名片是 DM 里的又一种整段 JSON 信封**（`otto: "otto.contact-card"`, `v: 1`），不发明夹在正文里的记号、不加表、不加列：
   与分享会话那张卡同一条代价（老客户端看到 JSON），同一条判定口径（整段占用，没有「正文里出现同样 JSON」的歧义）。
2. **两种卡**：联系人（uid + 名字 / 头像 / 邮箱**快照**）、智能体（名字 / 职责 / 提示词 / 脸 / 声音 + 谁的）。
   卡上带快照是为了**免读就能画**：接收方不必对 profiles / 别人的 workspace_agents 有读路径（后者本来就没有）。
3. **接受智能体 = 在接受者自己的主场复制出一只**（新 id、接受者的电脑跑、接受者的额度），走与「建一只」同一条闸
   （`createAgentChecked`：校验 / 威胁扫描 / 同名拒）。**不是共享同一只**——共享是 #1461 的车道；也不记来源、不与原主人同步。
   不带的东西：记忆（主人电脑上的事实）、连接器白名单（主人借出去的授权）、型号（接受者的路由自己定）。
4. **解是严格的**：卡是别人发来的字，要拿去建智能体 / 发好友请求，一格不对整张不认（uid / agentId 形状、名字非空、from 齐全、
   各字段上限与 `createAgentDraft` 同一套数）。
5. **编不下就拒**：提示词本身可到 4000 字（`AGENT_INSTRUCTIONS_MAX`）而 body 的 CHECK 也是 4000，装不下时说「提示词太长，名片装不下」，
   **不截断**——截掉一半的提示词是另一只智能体。
6. **推别人的联系人不问被推的人**（微信同款）；收到的人「加为朋友」走现成的好友请求并照旧选档位（#1494）。
7. **只写名字的三处**：聊天列表第二行（`dmPreview`）、车道信封（`pairChat.oneLine`：不把一只智能体的整段提示词塞进另一只的上下文）、
   桌面（先不画卡，写「[名片] 名字 · 在手机上查看」）。
8. **入口只在朋友私聊的 ＋ 里**（「名片」→ 挑我的智能体 / 别的朋友，复用 PickAgentsDialog 的两段），每挑一张发一条。

## 否决的

- **卡只放引用、接受时去读原件**：接收方对别人主场的 `workspace_agents` 没有读路径，开一个 RPC 等于把一只智能体的提示词对任何拿到 uid 的人公开。
- **大提示词走 Storage、卡里放路径**（同分享会话的做法）：要新 bucket / 策略 / 清理；今天先拒，真有人撞上再做。
- **接受后与原件保持同步 / 记来源**：那是另一种产品（订阅别人的智能体），不在这次范围。

## 代价与已知未做

- 老客户端（桌面旧版、没升的手机）看到的是一坨 JSON（提示词明文在里面）——与分享会话那张卡同一条代价；发之前没有办法知道对方是不是老版本。
- 「接受过」只记本机这一次会话：刷新再按会按同名被拒（`createAgentChecked` 的同名闸），不会建出两只。
- 群聊 / 智能体聊天里不能发名片；资料页上没有「推荐给朋友」入口（只在私聊 ＋ 里）。
- 真机未验（Windows 上没有模拟器）。
