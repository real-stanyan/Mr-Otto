# ADR-0303 额度快照随 hold / settle 回来：砍掉那趟纯问答的 DO 往返

> 原为 ADR-0302。PR #1309 与 #1308 并行，#1308 先落地占了 0302（`0302-聊天身份三态-名单从日志推导.md`），
> 本条按项目 ADR-0074 改成 `max + 1`。提交消息与 PR #1309 正文里写的是 0302，改不了，这行就是那些引用的解析器。

- 日期：2026-09-21
- 状态：已接受
- 相关：#1304（本条修的是它的一半）/ #1300 与 ADR-0301（量出这件事的那条）/ ADR-0203（订阅制计费落地）

## 背景

2026-09-21 量出来（ADR-0301）：同一个账号、同一份请求，只差从哪台机器发 ——

| 路径 | Mac（`cf-ray` 尾 SYD） | VPS（`cf-ray` 尾 HEL） |
|---|---|---|
| `/llm/v1/decision` 回 400（认证之后、`quota.hold` 之前，**不碰 DO 不碰上游**） | 0.18–0.23s | 0.04–0.34s |
| Supabase REST 直连（`model_route?limit=1`） | 0.15–0.36s | 0.34–0.46s |
| **`/billing/v1/me`（碰 DO + DB、不碰上游）** | **0.35s** | **3.65s** |
| `/llm/v1/chat/completions` | 1.4–2.5s | 4.7–15.6s |

Worker 自己两边一样快，Supabase 两边也只差 0.1–0.2s。**差在 Durable Object 那一趟**：`QUOTA` 是一户一个实例（`getByName(uid)`），落点由它第一次被创建时的 colo 决定，之后不动。于是「一趟 DO 往返」的代价取决于**请求从哪个 colo 进来**，而云会话跑在那台 VPS 上（HEL），桌面用户则遍布各地。

数了一下每次调用打几趟：

```
hold        → 上游 → settle → remaining
 ①                      ②        ③
```

**② 和 ③ 之间什么都没发生**。`settle` 那一刻 DO 手里就是刚落盘的 `r.state` 和 `plan`，而 ③ 回头去问同一个 DO 手里同一份状态，只为了拼那三个响应头。被拒的那条路同理：`hold` 回 `quota_exhausted` 的那一刻它也知道还剩多少，`holdRejected` 却又问了一趟。

## 决定

**`hold` 与 `settle` 的回执顺带带上额度快照；`remaining()` 退成兜底。**

- 成功路径 3 趟 → **2 趟**；hold 被拒路径 2 趟 → **1 趟**。
- chat 那扇门的额度头本来就取在 settle **之前**（流式的 settle 发生在流末尾），所以它用 `hold` 带回来的那份 —— 与改动前单独问那一趟问到的是**同一时刻同一份状态**，数一个不差。
- tts / decision 两扇门的头取在 settle 之后，用 `settle` 带回来的那份。
- `settle` 撞上 `no_hold`（幂等重入 / 已释放）时**没有快照可言**，回 `null`，调用方这才单独问一趟。

`QuotaRemaining` 在 `HoldOutcome` 上是**可选字段**：桩件与任何还没带它的实现照旧工作，只是多走一趟。这不是为了兼容某个旧部署（网关与 DO 同一次部署），是为了让「少打一趟」这件事**由数据在不在手上决定**，而不是由一个必须每处都记得传的约定决定。

## 判据与细节

1. **`parseRemaining` 住在 `llmGateway.ts` 不住在 `worker.ts`**：后者进不了 vitest（一 import 就要 DO 运行时），留在那边等于「缺一格该回 null 还是回 0」这个判断零执行覆盖 —— 同 `usageAttribution.ts` 那次的教训。
2. **三个数缺一不可，缺了回 `null` 不拿 0 冒充**。0 会被客户端读成「额度用完了」，而那是这条链路上最响的一句假话：`quotaAlert` 的 `exhausted` 判据、`ContextRingTrigger` 那枚点、`PlanQuotaSection` 两扇窗全都据它画。回 `null` 只是多一趟往返。
3. **用例钉的是 `remaining()` 被调了几次，不是响应头长什么样**。两条路给的数一样，钉头钉不住「有没有多走一趟」—— 而这条 ADR 的全部内容就是那一趟。
4. **`hold` 被拒时的快照取 `before`**（hold 没成功，状态没变），成功时取 `r.state`。

## 没有做的

- **没开 Smart Placement**。它把 Worker 挪到靠近依赖的地方跑，看起来正对这个形状；但 `QUOTA` 是**一户一个** DO、落点各不相同，一个 Worker 级的放置策略不可能同时靠近所有人的 DO。开之前要先知道这些 DO 实际落在哪，否则可能把今天快的那一侧弄慢。留在 #1304。
- **没动 DO 的落点**。`locationHint` 只在创建时有效，存量 DO 挪不了。
- **`hold` 与 `settle` 合不了**：它们一前一后夹着上游调用，中间隔着真正要花的时间。
- **这条只把 3 趟压成 2 趟，没有消除位置带来的差距**。HEL 那侧剩下的 2 趟仍然贵。#1304 仍然开着。

## 已知代价

- **`settle` 的返回值从 `void` 变成 `QuotaRemaining | null`**，八处桩件跟着改（机械改动，tsc 全指出来了）。
- **快照是「这一趟回来那一刻」的**，与改动前那趟单独问到的值在时间上可能差几毫秒（那趟本来也在 settle 之后）。没有消费方依赖这点差别。
- **真机没验**：要部署 worker 才量得到效果，而部署本身要维护者点头。预期是 HEL 那侧每次调用少约 1/3 的 DO 开销。
