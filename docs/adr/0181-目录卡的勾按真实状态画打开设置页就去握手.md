# ADR-0181：连接器目录卡的勾按真实状态画；打开设置页就去握手

- 状态：已采纳
- 日期：2026-08-29
- 关联：issue #722、ADR-0171（连接器目录分两层）、ADR-0121（MCP 的 OAuth）

## 背景

在连接器目录里点 `+` 装 Canva，系统浏览器弹出 Canva 登录页；**没登录直接关掉**。
回到连接器页，Canva 那张卡是绿色 ✓「已经装上了」。

配置确实落了盘（`~/.mr-otto/mcp.json` 里有 canva），但它没授权成
（`mcp-auth.json` 里有 `clientInformation` + `codeVerifier`，**没有 `tokens`**）。
后端分得清——`McpServerStatus.status` 有 `needs-auth` 这一档，页面下半那份 server
清单会显示「需要授权」并给一个「授权」按钮。

撒谎的是上半的目录卡：`McpDirectory` 拿到的只有 `installedIds`，那个 ✓ 的判据是
**「配置里有没有一个叫这名字的」**，从来不看状态。于是「连上了」「要授权」「连不上」
三种情况长得一模一样。

还有第二个窗口：`install()` 里 `saveMcpServer` 一成功 `installedIds` 就更新，卡片
立刻切到 ✓ 那个分支，而该分支完全不看 `busy`。此时 `authorizeMcpServer` 还挂在
`waitForCode(AUTH_TIMEOUT_MS)` 上——**五分钟**。浏览器一关，用户看着一个绿勾，
背后是五分钟静默等待。

## 决策

### 一、卡片右边那一格按真实状态画

`DirectoryItem.installed` 从 `boolean` 变成 `McpDisplayStatus | null`，画什么由纯函数
`installSlot(item, busy)` 决定（`lib/mcpDirectory.ts`）：

| 状态 | 画什么 |
|---|---|
| busy（**最高优先**） | 转圈 —— 盖住的正是上面那个五分钟窗口 |
| 没装 | `+` |
| `connected` | ✓ |
| `needs-auth` | 一颗**能点的**「授权」 |
| `failed` / `connecting` / `disabled` | 一句安静的说明，动作留给下面那份清单 |

`needs-auth` 给的是动作不是标签：用户此刻就在这一格，不该为了走完流程先弄明白
「上面这张卡和下面那一行是同一台 server」。

**不回滚 save。** `install()` 里原有的注释是对的：授权失败 ≠ 装失败——配置留着才能
再点一次「授权」，DCR 注册下来的 `clientInformation` 也该留着复用。要修的是那个 ✓
在撒谎，不是它存了东西。

### 二、打开设置页就触发 `mcpHub.ready()`（不 await）

上面那张表只有在 `status` 是真的时候才成立，而查下去发现它常常不是：**连接只由
`ready()` 发起**（会话开始时），在那之前每台的 `status` 都停在 `connecting`——而这个
`connecting` 的意思是「还没试过」，不是「正在连」（`mcpHub.ts` `syncFromDisk` 的注释
写着这个复用）。于是重启后第一次进设置页，一台连得好好的 server 和一台需要授权的
长得一模一样，**页面上下两半都在说同一句没有信息量的话**。

所以 `listMcpServers` 的 handler 里加一句 `void mcpHub.ready()`。

- **不 await**：`ready()` 最长等 10 秒（`READY_TIMEOUT_MS`），而每连上一台 hub 都会
  `emit()`，顺着 `mcpChanged` 推给渲染层。页面立刻拿当前快照画出来，状态随后自己
  填进去——不用让用户对着空页面等握手。
- **触发面确实只有设置页**：`listMcpServers` 在渲染层只有两个调用点，`settingsSection
  === "mcp"` 和 `refreshMcp()`，都是「用户打开了连接器页」。不是开机路径，所以这不等于
  把所有 stdio server 提到 app 启动时 spawn。

## 后果

- 目录卡与下面那份清单从此说同一句话（`mcpDisplayStatus` 是同一把尺子）。
- 打开连接器页会真的去握手：stdio 的会 spawn 子进程、http 的会发请求。这是自愿的
  ——这一页的用途正是「看看它们现在行不行」，而在此之前这页什么也不知道。
- 代价：`ready()` 每次调用会重试上次 `failed` 的那些，所以反复进出设置页会反复重连
  失败的 server。可接受（用户可能刚把网连回来），且 `readying` 保证并发只连一次。
- e2e 加了一条走完整链路的用例（打开设置页 → `ready()` → 401 → `needs-auth` → 卡片画
  「授权」）。401 用本地起的一台服务，不打真 `mcp.canva.com`——不让本仓的门禁依赖第三方
  在线。

## 被否掉的

- **`await mcpHub.ready()`。** 状态最准，代价是打开设置页要卡最多 10 秒。既然
  `mcpChanged` 这条推送通道本来就在，等它没有意义。
- **授权失败就把配置删掉。** 见上：那会连 DCR 注册一起丢掉，下次授权还得重注册一次
  （#471 踩过 redirect_uri 不匹配那个坑）。而且用户下次点「授权」时这台就该在列表里。
- **`connecting` 也画 ✓（"先当它是好的"）。** 这正是原来那个 bug 的一般形式——
  把「不知道」渲染成「没问题」。
