# ADR-0119：LoopEngine 的工具表按 turn 重算，turn 内冻结

> 原为 ADR-0114。合并前 origin/main 上另一条车道先落了 0114 这个号，按项目 ADR-0074 在本 PR 内顺延改号；照旧号来的引用按这行解析。

日期：2026-08-26
状态：已接受
相关：设计文档 `docs/superpowers/specs/2026-08-26-mcp-oauth-agent-config-design.md`（§3.4）、ADR-0121（OAuth 授权）、ADR-0118（agent 自助配置的权限边界）、ADR-0050（MCP 双 ID / 撞名分配）

## 背景

`engine.ts` 把 `toolsByName` 折在**构造那一刻**，`createMcpTools` 也是装配时快照（`agent.ts`）。

所以 agent 配完一台 MCP server、连上了，**本会话它自己用不了那批新工具**——这正好毁掉「在聊天里配」（ADR-0118）想要的那种顺畅：配好了，但要重开会话才能用。

## 决定

`LoopEngineOptions.tools` 从 `Tool[]` 放宽成 `Tool[] | (() => Tool[])`，**每个 turn 开始时重算一次（`rebuildTools()`），turn 内冻结**。传数组的老调用方行为基本不变（内部包成 `() => opts.tools`）。#474 订正：严格说不是「完全不变」——provider 每 turn 惰性重读同一个数组引用，调用方原地 push 会在下个 turn 生效，撞名 warn 从整场一次变成每 turn 一次；生产代码唯一的调用方走函数模式，数组模式只有测试在用，所以没有实际影响面。

### 关键取舍：turn 内必须冻结

**模型看到的声明表和 dispatch 时查的 `toolsByName` 必须是同一份。**

若 turn 中途换表，模型按旧表发出的调用会在新表里查不到，收到「未知工具」——这是 `mcpTool.ts` 顶部注释已经明确要避免的那类失败。工具名还牵扯 `assignMcpToolNames` 的整桌统一分配（撞名 salt 取决于先来后到，ADR-0050），中途换表连名字本身都可能变。

所以粒度定在 turn 边界：**够新**（配完下一轮就能用）且**够稳**（一轮之内模型的世界不变）。

### 被否掉的路

- **告诉用户下个会话生效**：改动最小，但把「配好了」和「能用了」拆成两步，用户得自己记住去重开会话。这正是本次功能要消灭的那种断点。
- **逐会话重装配 engine**：不动 engine 内部，但「什么时候重装配」（turn 中途？）和状态交接是新的一类 bug 源，比改 engine 内部更难测。把难题从「engine 内部的一处重算」搬到「装配层的时序」，没变简单，只是换了个地方藏。

### 推翻它的前提

出现一类必须在 turn 中途改变工具可见性的需求，且它比「模型收到未知工具错误」更重要。眼下没有——`tool_search` 的 deferred 暴露（`deferredExposed`）是在**已注册**的工具里改可见性，`toolsByName` 始终有它，不产生「未知工具」，所以它不构成反例。

## 顺带修好的存量缺陷

**会话中途 MCP server 重连或新增，当前会话一直看不见。**

这不是新功能的副产品，是**现在就存在的缺陷**：用户手动在设置页重连一台掉线的 server，正在进行的会话仍然拿的是装配时的快照。工具表按 turn 重算之后，这个洞一起没了。

## 后果

- 每 turn 多一次工具表重算（去重、撞名判定、暴露度过滤）。工具数是几十量级，成本可忽略。
- `rebuildTools()` 必须在 turn 的 `try` 之内：provider 抛错（比如 hub 正在重连时读到半截状态）也要能正常收口，不能把整个 turn 崩在收口之前。
- `deferredExposed` 集合跨轮存活——重算的是「有哪些工具」，不是「模型搜到过哪些」。搜到过的工具不该因为换了一轮就重新隐身。
- 测试钉住四件事（`tests/loop/engine.test.ts`）：turn 之间工具表会变；turn 之内不变；`deferredExposed` 跨轮存活；传数组的老调用方行为不变。
