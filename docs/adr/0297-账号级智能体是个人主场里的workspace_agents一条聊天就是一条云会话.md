# ADR-0297：账号级智能体 = 个人主场里的 `workspace_agents`，一条聊天 = 一条云会话

- 日期：2026-09-20
- 状态：已接受
- 相关：#1280、#928、ADR-0199、ADR-0219、ADR-0271、ADR-0283

## 背景

侧栏第三栏要从「团队」改成「我的智能体」：每只智能体是一个一等实体，有自己一条永久私聊；
群聊降级成「自己拉 2～6 只进去」的可选房间（借鉴 Grok Bot）。

挡在前面的是一条结构性事实：**全系统没有「这条会话里有哪几只智能体」这回事**。runtime 每
turn 按 `workspace_id` 拉整份 `workspace_agents`，@ 解析 / 派活 / 接力 / brief / 通话选人约
40 处下游全从 `CloudSessionOpts.agents` 这**一个口**读（`sessionService.ts`）。唯一的「会话内
子名单」先例是语音通话——`voice_call_changed` 是一条日志事实，`callRoster` 在 `say()` 里按它
收窄（ADR-0271）。

另一条事实是分母：容器 / 卷（`otto-ws-<workspaceId>`）、EventStore（`<workspaceId>.db`）、wiki、
连接器托管箱、计费的 `x-otto-on-behalf-of`、Pro/Max 闸，**全部按 workspace 分**。

## 决定

**① 个人主场（home）不另起租户。** 每个账号一个隐藏的 `workspaces.kind='home'`，上面那一整套
原样复用；`kind` 由触发器钉成不可变。智能体就是这个 workspace 里的 `workspace_agents` 行，
团队（`kind='team'`）一个字不变。

**② 一条聊天就是一条 `kind='cloud'` 的 `workspace_sessions`。** 多两列 `chat_kind`（`dm`/`group`）
与 `agent_ids`；私聊一条唯一索引保证「每只智能体至多一条私聊」。**这两列是投影不是事实**，
存在的唯一理由是桌面在没开着那条会话时也要画得出「群里有谁」（同 0035 的 `participants`）。

**③ 名单是日志事实：`chat_roster_changed`。** 最新一条胜出，投影在 `src/shared/chatRoster.ts`；
`null`（一条都没有）= 这条会话没有名单这回事 = 团队会话 / 存量日志 = **不收窄**。runtime 在
**`rosterNow` 这一个口**把团队名单 ∩ 聊天名单，此后 `sessionService.ts` 里不许再出现裸的
`opts.agents(`——40 处下游一次全对，少改一处就是那一处还站着整个团队。**团队名单 degraded
时不收窄**：降级记号一旦被名单滤掉，下游那几句「名单读不出来」的实话就再也说不出口，症状
变成「这条聊天里没有智能体」。

**④ cs 协议 19 → 20，七处一次进位。** `create.chat`、`create_failed`、`chat_update`、
`chat_update_result`、`welcome.chat`、`backlog.tail`、`backlog.hasMore`。握手是精确相等，进两次
位就是发两次版，所以分页那半的实现晚几个 PR、帧形状现在就定。`create_failed` 是新开的一条：
控制房的 `create` 原先只认 `created` / `denied`，抛错就是让桌面白等满超时、把「群聊至少要两只」
报成「云端无响应」（方向指向 VPS 宕机）。

## 否掉的备选

- **聊天实体单独一张表（`workspace_chats`）+ 多条话题**：本次对话的第一版。维护者看过 demo
  后否掉话题——「智能体应该自动管理上下文，用户就像在微信里和人聊天」。没有话题，聊天与
  会话就是一对一，那张表只剩下抄一遍 `workspace_sessions` 的列。
- **真·账号级 `agents` 表，runtime 按账号重键**：概念最干净；容器命名、wiki、用量归因、px
  授权、`admin` 的 8 处特判、RLS 全部重做，团队还得发明「借来的智能体」。收益个人主场都拿到了。
- **团队仍是第一层，点进去才看到智能体**：改动最小，但第一层还是「团队」，不是维护者要的形状。

## 代价

- **常驻房间随用户数线性增长**：daemon 启动时给每条未归档云会话各开一个房间（错峰 1.5 秒一条），
  而一个人有几只智能体就有几条私聊。出路是房间按需开、闲置关，不在这条里。
- **`title` 一列两种来历**：团队会话里是自动标题，聊天里存群名（私聊恒空），靠 `chat_kind` 区分。
  聊天因此不过标题器——`maintainTitle` 第一行就 return。
- **删一只智能体是三步、不原子**：摘出所有群 → 删私聊 → 删那一行。顺序倒着排，断在半路留下的
  是「智能体还在、聊天没了」，比反过来好收拾。
- **群的身份就是一条会话 id**：解散 = 聊天记录一起没了，没有「退群留记录」。
- **聊天不能归档，只能删**：私聊那条唯一索引不带 `archived`，归档一条私聊 = 那只智能体从此再也
  开不出私聊。所以归档帧对聊天回一句说清出路的话，不是静默失败。
- **我的智能体进不了多人团队**：同一只要在团队里再建一遍。

## 推翻它的前提

- **若用户反复要「这件事单独聊」**：加一条「清空上下文」（落一条压缩事件，线不断），不是把话题
  请回来。
- **若房间数让 daemon 启动超过几分钟**：房间按需开。届时定时/触发任务（#1283）也要跟着想——
  没有房间的会话怎么自己起 turn。
- **若多人团队里反复有人要用自己的智能体**：先做「复制一份进团队」（拷贝，断链），不做跨租户。
