# ADR-0077 性能一轮:热路径上的三笔权衡

日期:2026-08-24
状态:已接受
关联:issue #275

## 背景

首轮系统性性能盘点(两路静态勘察 + 合成库基准)找到的热路径:

1. **每条事件都全表扫描**:`pushFleet`(灵动岛投影)跟着每条事件跑一次
   `store.sessions()`——标题/归档两个子查询都是全表扫描,合成库(8 万事件/200 会话)
   实测 31ms/次,工具密集的 turn 一秒好几次,全在主线程上同步付。
2. **每条事件一次 fsync**:WAL + 默认 `synchronous=FULL`,`append()` 每条事件
   独立事务,每笔提交都 fsync。
3. **渲染进程整店订阅 + O(n²) 流式估算**:`App()` 在树根无选择器订阅整个
   Zustand store,每个流式 token 重渲染整棵树;`TurnMeta` 每个 token 对全量
   已累积文本跑一遍逐字符 token 估算。

多数修复(二级索引、prepared statement 复用、逐字段选择器、memo、Context 分发
投影)是无语义变化的实现优化,不需要决策记录。有三笔是真权衡,记在这里。

## 决策

### 1. `synchronous = NORMAL`(store.ts)

WAL 的文档推荐搭配:只在 checkpoint 时 fsync。**代价**:操作系统级断电/内核崩溃
时可能丢最后几笔提交(进程崩溃不丢——WAL 写还在页缓存里由 OS 保证)。
**为什么可接受**:事件日志本来就设计了断尾自愈(deriveMessages 的 dangling
工具调用修复);丢的是"最后一秒的几条事件",不是库损坏。
**推翻前提**:若出现真实用户断电后日志不一致且自愈不了的案例,退回 FULL 并改为
批量事务摊薄 fsync。

### 2. 岛的会话表 1 秒记忆化(index.ts `fleetSessions`)

`sessions()` 结果缓存 1s;改变会话表形状的路径(建会话/改名/归档经 `feedIsland`,
purge/rename 的 IPC 手动清)当场失效。**代价**:岛上按 lastTs 的排序最多晚 1 秒
重排。**为什么可接受**:排序漂移只在多会话并行时发生,1s 无感;真正可见的
变化(标题/增删行)不吃延迟。同文件 30s 的 `islandUsageCache` 是既有先例。
**推翻前提**:岛改成显示逐事件跳动的字段(事件数/相对时间实时刷)时,缓存
策略要跟着重审。

### 3. 流式 token 估算跟 1 秒钟走,不跟 token 流走(OttoThread `TurnMeta`)

`estimateTokens(全量已吐文本)` 从每 token 一次改为每秒一次(useMemo 挂在
1s 定时 tick 上)。**代价**:orb 旁那行"↑N tokens"最多滞后 1 秒。
**为什么可接受**:那行数字本来就是 1 秒一跳的估算值(±30%),更高的刷新率
只是把 O(回答长度²) 的计算白付一遍。
**推翻前提**:若估算改成增量维护(按 CJK/其余计数增量累加),可以恢复逐 token
更新且没有二次方成本——届时删掉这个节流。

## 后续(本轮刻意没做,已开单)

架构级的三刀留给后续 shift,已各自开 Task issue:

- #277 引擎每个模型步全量重读+重投影会话日志(O(事件数×步数))——改为进程内
  增量维护,`load({afterSeq})` 已有。
- #278 流式 delta 每个 SSE chunk 一条 IPC——主进程按 ~16ms 合帧。
- #279 turn 收口的四个钩子(分类/建议/nudge/微压缩)各自全量 load——加
  `lastSeqOf` 下推成尾段读取。
