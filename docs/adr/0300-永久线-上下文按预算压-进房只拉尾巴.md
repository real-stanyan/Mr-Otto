# ADR-0300：永久线 —— 上下文按预算压、进房只拉尾巴

**日期**：2026-09-20
**Issue**：#1280（A6）
**Spec**：`docs/superpowers/specs/2026-09-20-agents-roster-design.md` §6.5 / §5.3
**状态**：已落地（真机未跑）

## 背景

ADR-0297 把第三栏改成智能体花名册之后，一只智能体一条**永久私聊**：不换线、不分话题、
不归档。维护者看过话题（topics）的 demo 之后把它砍掉了，原话是「智能体应该自动管理上下文，
用户就像在微信里和人聊天」。

这句话把三笔代价推到了这一片头上，而它们都是**随时间单调变坏**的那种：

1. **进房**：`welcome` 之后一律 `backlog(afterSeq: -1)`，一次全量。聊半年的线就是几千条事件
   跨中继下发一遍，人点一下等十几秒。
2. **渲染**：云会话页把整份 `events` 一次挂满。本机那边早就为此开了窗口（ADR-0285，#1190 实测
   2555 条事件的会话首渲 400–500ms，大头是首挂载的 markdown 解析），云这边没有。
3. **钱**：自动压缩按**窗口比例**判（ADR-0062）。1M 窗口的型号要攒到 50 万 token 才压一次，
   而永久线上每一句话都背着全部上下文——那是一整天的钱，且没有任何自愈路径。

## 决定

### 一、预算闸与窗口比例**取小的那个**

`AutoCompactSettings` 加一格可选的 `maxTokens`；`shouldAutoCompact` 取
`Math.min(窗口 × 阈值, maxTokens ?? +∞)`。聊天用 `CHAT_CONTEXT_BUDGET_TOKENS = 60_000`，
团队会话与本机会话照旧（`maxTokens` 缺席 = 行为逐字不变）。

两条都是上限，先到的那条说了算：小窗口的型号上仍然是比例先到（32K 窗口 × 0.75 = 2.4 万），
大窗口上是预算先到。**未知窗口照旧不触发**——宁可不压，也别按猜的数字烧一次全量。

### 二、闲置压缩：只判第一圈，按**这只自己**上一轮的收口时刻算

隔了 `CHAT_IDLE_COMPACT_MS`（6 小时）再开口、**且**上下文超过
`CHAT_IDLE_COMPACT_MIN_TOKENS`（1.6 万），这一轮先压再答。

理由是钱：厂商的前缀缓存早过期了，旧上下文是原价重读一遍；而隔了半天再开口，多半也换了
话题——压掉的那部分本来也用不上。

三条判据各挡一个失败：

- **只在一轮的第一圈判**。turn 中途再判，会在工具密集的一轮中间凭空多压一次，而「隔了多久」
  说的是这一轮**开口之前**的事。
- **按这只自己的上一轮算**，不按整条会话。群里别人刚说过话不算这一只「没闲着」——它自己的
  上下文照样是六小时前的那一份。`turn_ended` 带 `agentId`（ADR-0219），按 id 分开记。
- **`lastTurnEndedTs` 由装配方给**，不让 engine 自己去猜。engine 手上的 store 可能是
  `agentView` 分过视野的、也可能不是，「这只上一轮什么时候收口」该由知道的人说。
  回 `null` = 这只还没跑过一轮 = **「读不到」不是「隔了很久」**，不压。

### 三、尾巴分页：第一页的起点盖住「没收口的 turn」与「进行中的通话」

`backlogTail(beforeSeq, limit)`：`beforeSeq` 缺席 = 第一页（末尾 `limit` 条），给了 = 往前翻。
`hasMore` 说清这一页之前还有没有，**只挂在最后一片（`done: true`）上**——中间分片不知道
「这一页之前还有没有」，也不该说。

第一页的下界取 `min(排队中的开场白 seq, 在跑的那一轮的开场白 seq, 通话第一条事件的 seq)`。
少了它，「正在回复」那枚指示器和通话卡会因为那几条落在尾巴外面而**画不出来，且不报错**——
界面上的样子是「它在跑，但这一屏什么都没说」。

`TAIL_FLOOR_MAX_EXTRA = 2000`：下界离得太远就不盖了。一场开了三天的通话不该让进房变回
全量拉——那时候少一格是**能看见、会自愈**的偏差，而进房要等十几秒是**每一次**都发生的事。
两个失败方向不对称，所以这条闸往「少带」那一侧倒。往前翻的那几页不盖下界：那只是第一页的事。

末条 seq **现查库**，不取 `lastSeqSeen`：后者由 `notify` 维护，而 `daemon.ts` 往同一个 store
直接 append 了四类事件全都绕开 `notify`（那个函数自己的注释就写着这件事）。拿它当尾巴的末端，
这一页会安静地少掉最后几条。

### 四、只对聊天生效，团队会话照旧全量

判据是 `session_created.cloud.chat`（建会话时记进日志的事实，一生不变）与 `welcome.chat`。

团队那边的上下文环（`cloudContext.ts`）与通话折卡（`voiceCallCards`）都靠「把整份日志读一遍」，
尾巴分页会让它们**静默算错**。那两样在聊天里本来就不画（ADR-0297 摘掉了上下文环）。

### 五、渲染层：窗口上沿**按 seq 钉**，先补挂再拉网络

窗口的尺子从 `lib/messageWindow.ts` 借（首窗 60 / 步进 60 / 只增不缩），不另拍一套数——
两处各拍一个数的那天，两条时间线会在同一台机器上表现不同。

- **窗口数的是「会真的画出来的行」不是事件数**：渲染循环里一路 `return null`
  （hidden / 通话卡 / 压缩事件三道），拿 `events.length` 去算会把被藏起来的也算进名额。
  这份可见行列表与「一条都画不出来」的计数同源。
- **上沿按 seq 钉，不按「隐藏了几条」记**（与本机那份不同）。往前翻的那一页落在列表**前面**，
  按条数记就得每次把「新来了多少条」补进 `hidden`，而那笔账在 StrictMode 的双渲染下很难记对。
  按 seq 钉的话 `indexOf` 每次现算，前插与追加都自动对；钉不到时退回全挂，是一个看得见、
  会自愈的退化，不是空屏。
- **先把内存里的补挂完再打网络**（`nextOlderAction`）：那一页已经付过网络的钱了，而补挂是纯渲染。
  反过来的话，人往上滚两屏就打一次网络，而屏幕上早就有可以画的东西。
- **失败是一颗要人点的钮**，哨兵不自己重试：一条连不上的线会在人往上滚的时候反复打网络。
  上一页的内容**留在原地，不清屏**。
- **往前翻一页会让 `eventCount` 变大，跟底那条 effect 要让路**——不让路就是人正在往上读、
  被一把拽回底部。滚动补偿量的是「那条旧节点位移了多少」，不是 `scrollHeight` 的差
  （同一次提交里流式消息可能还在往底部长）。

## 否掉的

- **「清空上下文」那颗钮**。它是把话题从后门请回来——按一下就是一条新线的开始，而这一片
  存在的全部理由是「一只一条线，不换」。维护者砍掉话题时砍的正是这个心智。
- **按窗口比例调低阈值**（把 0.5 调到 0.1 之类）。`effectiveThreshold` 夹在 0.3 以上，
  1M 窗口仍然要 30 万；而放开那个夹子会让小窗口的型号每两句话压一次。**预算是绝对量，
  阈值是相对量，用相对量表达绝对约束只会两头不靠。**
- **给尾巴分页也做「缺口」对账**。没加载的那一段不是缺口，是还没翻到。`missingCount` 的
  下界因此跟着已加载的最小 seq 走——不收这个下界的话，每条长聊天一进房就顶着一句
  「这条会话有 3000 条历史事件没能下发」，而那三千条好好地躺在服务端。

## 代价（接受）

- **压缩质量随时间衰减的那一半没修**（spec §13 第 1 条）：长期记忆全押在 wiki 上。
  一只聊了一年的智能体，它记得的是摘要的摘要的摘要。
- **会话地图只有已加载那几页的刻度**，跳不到半年前（`conversationMap.ts` 头注已补这条）。
  不兜底：兜底就意味着为了画一列刻度把整份日志拉回来，而那正是尾巴分页要省掉的。
- **私聊里没有额度告警**：那枚点挂在上下文环上（ADR-0255），而聊天页摘掉了环。
- **三个常量都是拍的**（60K / 6h / 16K），上线后按真机数据调。界面一个字不提上下文——
  这两条规则就是全部内容，用户该感觉到的只是「聊半年也不慢、不贵」。
- **滚动补偿与哨兵命中没有断言**：jsdom 没有布局、没有 `IntersectionObserver`，写出来只钉得住
  「调了这个函数」，而真正会坏的是时序（同 ADR-0236 第 1 条 / ADR-0285 的取舍）。
  保鲜期在紧挨代码的注释里。
- **真机一次没跑过**：要先在生产 Supabase 跑 `0037`、再部署 VPS runtime（#791）、再发桌面版。

## 推翻它的前提

- **若预算闸让「它忘事」的抱怨多过「烧得快」的抱怨**：调 `CHAT_CONTEXT_BUDGET_TOKENS`，
  或按档位给不同预算；**不是撤掉闸**（spec §14 第 5 条）。
- **若用户反复要「这件事单独聊」**：加一条「清空上下文」（落一条压缩事件，线不断），
  不是把话题请回来（spec §14 第 1 条）。
- **若首页 200 条仍然太慢**：先量是下发慢还是挂载慢——前者调 `BACKLOG_TAIL_DEFAULT`，
  后者调 `INITIAL_WINDOW`，两个数管的不是同一件事。
