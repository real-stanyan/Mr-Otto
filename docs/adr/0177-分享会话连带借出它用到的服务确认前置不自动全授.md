# ADR-0177：分享会话连带借出它用到的服务——确认前置，不自动全授

- 状态：已接受
- 日期：2026-08-29
- 相关：issue #694（本决策）、#612（会话分享）、#622（好友代理伞状需求）、ADR-0151（代理三防线）、ADR-0162（一次性 secret 不落盘）、ADR-0166（借来的服务加前缀合并）、ADR-0170（邀请失效那个死锁）

## 背景

「A 把会话分享给 B，让 B 帮他改 Shopify」这件事，在这之前要走两趟，且第二趟没有入口：

1. **会话分享**（#612）：一次性快照、过隐私闸、DM 里一个信封，B 点卡片导入后在自己机器上 fork。
   包里**不带任何凭证**——B 那边调 `shopify` 必然失败，因为他机器上根本没接那台 server。
2. **好友代理**（#622）：A 打开好友抽屉圈白名单 → 生成 `otto-proxy:` 邀请码 → **带外发给 B** →
   B 打开同一个弹窗的「接受邀请」页**手动粘贴** → 握手 → 借来的服务按好友短标签加前缀
   合并进他的会话（ADR-0166）。

第二趟全靠 DM 里口头指挥：邀请码在私信里是一段纯文本，**没有卡片**（分享信封有
`SessionShareCard` 认领，邀请码没有对应物）。用户的原话是「分享了就该能帮我干活」——
两趟里的第二趟，在他的心智模型里根本不存在。

## 决策

**把授权并进分享那一趟，但保留 A 的一次显式确认。**

具体四条：

1. **范围 = 这个会话实际调用过的、此刻还连着的服务**，不是 A 接通的全部。
   反查在 `src/shared/shareGrant.ts` 的 `serversUsedInSession`。
2. **分享前就地确认**（`ShareGrantDialog`）：列出那几台，**默认全勾、可减**。
3. 确认后生成一枚绑定这次分享的代理邀请（白名单走 `shareAllow` = 整服务放行），
   塞进 DM 信封的新字段 `invite` / `grantServers`。
4. B 那张分享卡上多一个「导入并接上 TA 的服务」，一键握手 —— **B 全程不碰邀请码**。

用户要的那句「不需要 B 再去拿授权」拿到了；A 那一次确认留着，理由见下。

## 为什么不是「分享即全量自动授权」

这是提出需求时的字面口径，被否掉的是**自动**那半，不是**默认**那半（默认仍然全勾）。

**知情同意会消失，而这一步没有第二次机会。** 白名单内**没有逐次审批**（ADR-0151：
圈的是「工具」不是「一次调用」）。「分享会话」今天的心智是「给你看我干了啥」——只读、
一次性、剥过隐私；连带授权之后，同一个动作的实际后果是「你可以用我的身份下单、改价、
删商品」。这两件事差得太远，不能靠一个隐式默认糊过去。确认框的全部意义就是把这句话
摆在按钮上方，并在按钮上写清这次到底借了几项。

代价是 A 多按一次。这个代价只在**真有服务可借**时付：没用到 MCP 的会话不弹这个框，
纯对话分享一步都没多——为一个不存在的授权去点一次确认，只会训练人闭眼点确认。

## 为什么随分享发的邀请活 24 小时（而 secret 仍然不落盘）

手动那条路上 A 生成、B 当场粘，10 分钟绰绰有余。分享包是**异步**的：它躺在 DM 里
等对方哪天点开，10 分钟意味着「几乎一定过期」，功能等于不存在。

放宽到 24 小时（`PROXY_SHARE_INVITE_TTL_MS`）不是把闸门拆了，因为 **secret 从来不是
唯一那道闸**：兑换还要求 A 的房间开着，而 secret 只活在内存里（ADR-0162），
**A 一重启这张码就作废，与 TTL 无关**。真实窗口 = min(A 这次运行时长, 24h)，
通常由前者封顶——也就是 ADR-0170 已经命名过的那个死锁，解法同样是「让 TA 重发一次」。
确认框把这句话原样告诉用户，而不是留给他自己撞。

两条被否掉的实现路：

- **把 TTL 写进邀请码**——否决。线上格式是固定七段（`encodeProxyInvite`），
  加字段会让旧客户端把整张码判成非法。改成两端共用一个常量即可，
  且 **A 侧那次判定才是权威**（`verifyWith`），B 侧那次只是提前给人话。
- **为了让隔天也能兑换而落盘 secret**——否决，理由与 ADR-0162 一字不改。

## 为什么 DM 里放 secret 不是新的暴露面

手动那条路本来也是「A 复制 → DM/当面发给 B」，ADR-0151 说的「带外渠道」就是这个。
信道没变，变的只是**谁来复制粘贴**。信封 `v` 保持 1：涨版本会让旧客户端把整条私信
判成不认识（`decodeEnvelope` 的 `v !== 1` 直接返回 null），一个可选字段不值得那个后果。

## 后果

| 面 | 结果 |
|---|---|
| 没用 MCP 的会话 | 行为与上线前逐字节一致：不弹框、信封里没有新字段 |
| A | 多一次确认；授权照旧进「好友代理 → 已授权」，可看审计、可一键撤销 |
| B | 不再需要邀请码；卡片上两个按钮，**接不上服务时不会顺手把对话导进去**再报错 |
| 旧版本客户端 | 照常渲染分享卡（认不得新字段），只是没有「接上服务」那个按钮 |
| 链式转借 | 不可能：候选只来自渲染层的本地 server 快照，借来的那些不在里面 |

## 天花板（没做的）

- **B 用服务时 A 必须在线**：代理是同步的，分享是异步的。A 关机 = 报错且不回落本地
  （ADR-0166）。确认框和卡片把在线状态说出来，仅此而已。
- **反查是尽力而为**：日志里只有模型可见名，反查靠 `assignMcpToolNames` 重算——
  而名字分配依赖当时整桌的顺序。昨天那次调用发生时的桌面可能与此刻不同。
  这没问题：产物是给 A 看的一张勾选表，不是自动授权。
- **只到「服务」这一层**：想圈到单个工具，仍然走好友代理弹窗那张表。
- **上传失败时那张授权会留下**：邀请必须先于信封生成（顺序反了就是「码还没有就已经许诺了」），
  所以打包/上传/发 DM 任一步失败时，A 侧台账里已经多了一条 grant、房间也开着了。
  不算漏洞——没有 secret 谁也连不上，而且它在「已授权」里看得见、可一键撤销，
  状态就是 ADR-0170 命名过的 `pairing`「等待中」那一档。不做自动回滚是因为
  `proxyCreateInvite` 会覆盖该好友原有的授权，失败即撤销会把原来那条一起抹掉，
  代价比这个 wart 大。
