# ADR-0044：key 的遮罩可以过桥，key 本体不行

- 日期：2026-08-20
- 状态：已接受

## 背景

原来的规矩是：`keyStatus` 只过**布尔**，"渲染层能知道的关于 key 的全部信息就是配没配"
（`main/index.ts` 的 keyStatus handler、`providerCatalog.ts` 的注释）。

这条规矩在设置页只有一个输入框的年代够用。收进弹窗之后，那一行常驻显示的是
env 变量名 `DEEPSEEK_API_KEY` —— 它回答的是"这一格是干什么的"，
而用户站在这一行前面真正会问的是**贴进去的是哪一把**：多账号、轮换过一次、
或者怀疑把 GLM 的 key 贴进了 DeepSeek 那一格的时候，布尔一个字都答不上来。

## 决定

`keyStatus` 的载荷从 `Record<string, boolean>` 改成 `Record<string, string>`：
值是 key 的**遮罩形态**（`sk-31cf5*****828c`），空串 = 没配。

- **遮罩在主进程算完再过桥**（`shared/keyMask.ts`，只在 main 调用）。
  过桥的是一个推不回原文的派生物，不是秘密本身 —— 原来那条"桥上只走结论、
  不走凭据"的规矩没有松动，松动的是"结论"能有多细。
- 露前 8 + 后 4，中间**固定五颗星**、不按长度伸缩：星星的个数本身也是信息
  （key 有多长），没必要白送。
- 短 key 少露（8–15 位露前 3 后 2，8 位以下一点不露）：
  一把 10 位的 key 露前 8 等于没遮。
- "配没配"照旧从同一个字段推：空串是假值，`!== ""` 就是原来的布尔。
  两个字段各存一半才会出现"配了但没有遮罩"这种拧巴状态。

## 后果

- 渲染层现在知道 key 的 12 个字符。这是各家控制台的通行做法（Stripe、OpenAI
  都这么显示），且这台机器上本来就存着 `keys.json` 明文 —— 遮罩不构成新的暴露面，
  它只是把"用户自己已经能 `cat` 到的东西"换成一个不用离开界面就能核对的形态。
- 渲染层仍然**无法**用它去调任何 API：这是遮罩和 key 的分界线，也是这条决定成立的全部理由。
- 日志、IPC 之外的其他通路一概不变：key 依旧不进事件日志、不进 IPC 的其他消息。
