# ADR-0145：会话视角贴着最新输出，人一上滑就松手

- 状态：已接受
- 日期：2026-08-27
- 关联：issue #599；ADR-0010（shadcn/registry 是抄进来的起点，不是上游依赖）

## 背景

一轮回答里，正文、思考、工具行是一段段往下长出来的。长出来的东西在视口下面，人看不到——要看最新那一段，得自己一路往下滚，边滚边追。

原因在 `src/renderer/src/components/assistant-ui/thread.tsx` 的一个 prop：`turnAnchor="top"`。它是从 assistant-ui 的 shadcn registry 抄进来的（ADR-0010 的那次装配），语义是「新一轮把用户那条消息钉在视口顶端」——ChatGPT 式的读法：你的问题在上面，答案往下铺，视线整轮不动。

这个默认值背后还藏着一条本仓当时没读到的：上游 `autoScroll` 的**默认值是 `turnAnchor !== "top"`**（`useThreadViewportAutoScroll`）。也就是说 top 锚顺带把跟随一起关掉了。

## 决策

换成 `turnAnchor="bottom"`（上游默认），跟随随之默认打开。

行为：内容长高就贴着底；人往上滑一下就松手（上游 `handleScroll` 里的 `isUserScrollUp`：滚动位置变小且 `scrollHeight` 没变 = 是人在滑，不是内容在长）；滑回底部又自动接上。

**为什么不是「留着 top 锚 + 显式 `autoScroll`」**：不够。内容变高那一段还有一道 `!(isRunning && hasActiveTopAnchor())` 挡着——一轮跑起来、顶锚还在，就是不跟。要跟随就得放弃顶锚，两者在上游是一件事的两面。

**代价（接受）**：失去「你的问题钉在顶端」那种读法。取舍的依据是这两种视线服务的对象不同：Mr Otto 一轮里下面长出来的是工具在动、文件在改、思考在走——是**进行中的过程**，人要盯的就是最新那一行；纯问答场景下面长出来的只是同一段答案的后半截，钉着顶端读更稳。本仓是前者。

**什么前提会推翻它**：如果一轮的输出变短（比如工具行折进一行摘要、思考默认不展开到正文流里），"下面长出来的东西值得盯"这个前提就弱了，顶锚会重新变得更好读。

## 验证

`tests/e2e/followOutput.e2e.ts`，真 Electron 里量视口离底还有多远——jsdom 没有布局，`scrollHeight` 恒为 0，这件事在单测层面量不到。

一条用例量的是**一对**行为：直播时贴底（①）+ 人上滑后不被拽回去（②）。只验前者的话，把跟随焊死也能全绿，而那是比不跟随更糟的界面：用户想回头看上面那段，视线被一次次抢走。

反向验过：把 prop 改回 `turnAnchor="top"` 重新打包，这条用例在 ① 上红（「正文在长,视口却没跟着贴到底」）。两向都不动的用例等于没有。

顺手修的：`tests/e2e/harness.ts` 的 `startSession` 从 #559 起就点不到工作区选择器了——欢迎页默认落在「任务」档，那一档整行文件夹 UI 都不出现。所有走 `startSession` 的 e2e 都卡在同一处（e2e 不在门禁里，ADR-0138，所以一直没红给谁看）。修法是先切「项目」档；不修的话本条用例根本跑不起来。
