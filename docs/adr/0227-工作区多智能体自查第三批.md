# ADR-0227：工作区多智能体自查第三批——协议进位 5→6，停止 + 三条回执帧

- 状态：已采纳
- 日期：2026-09-06
- 关联：issue #957（第三批）；先例 ADR-0225（第一批，PR-1 runtime/服务端）、ADR-0226（第二批，PR-2 桌面 + 共用校验）；关闭 issue #964（say 无回执）；#927（approve 无回执根因，本批同族修法）；不解决 #959（A-7 冻结，仍在）；#965（正文可伪造说话人行，不在本批范围）

## 背景

ADR-0226 决策 5/6 在桌面侧各打了一块本地补丁——审批按钮的"迟到拒绝"两层兜底（订阅 `workspaceGroupsError` + 15 秒定时器）、开局卡发送失败改种草稿——但两处的收尾段落都写明了同一句话：根治要协议进位，加 `say_result`/审批确认回执，与 stop 帧一起排进下一轮。本批就是那一轮。

三件事绑在一次进位里，不是因为它们本身耦合，而是因为**协议版本号是精确相等判据**（`frameHandler.ts` 的 `version_mismatch`），同一个仓库两端一起发版，加一个字段与加三个字段的升级成本相同——凑够一批要改的东西再进位，比每加一个字段就跳一次版本更省事，也更少给旧桌面制造"连不上"的窗口。

## 决策

### 1. 一次进位带三样：stop 帧 + 三条回执，不是三次进位（否决：分批进位）

`CS_PROTOCOL_VERSION` 从 5 提到 6（`src/shared/remote/cloudSession.ts:31`）。`CsUp` 加 `{ t: "stop" }`（`cloudSession.ts:216`）；`CsDown` 加三条：`{ t: "say_result"; ok: boolean; message?: string }`（`cloudSession.ts:261`）、`{ t: "approve_result"; callId: string; ok: boolean; message?: string }`（`cloudSession.ts:264`）、`{ t: "stop_result"; ok: boolean; message?: string }`（`cloudSession.ts:265-267`）。`encodeCs`/`decodeCsUp`/`decodeCsDown` 各补一个分支（`cloudSession.ts:457-458`、`518-544`），`tests/shared/cloudSessionFrames.test.ts` 逐帧往返（含 `approve_result.callId` 形状不对时 `decodeCsDown` 回 null 的边界用例）。

**否决双版本兼容**：不做"新 runtime 认旧桌面、旧桌面凑合用"这种过渡层。旧 runtime × 新桌面、新 runtime × 旧桌面两个方向都走既有 `version_mismatch`（`frameHandler.ts:191`，文案已经存在于 `cloudSessionClient.ts:103`）——握手在 hello 那一步就把话说清楚，好过让一条读不懂新帧的旧客户端在协议层面猜。**代价**：本批 PR 部署之后、桌面发版之前的窗口里，跑着旧桌面的用户看到的是"版本不匹配"而不是新功能——这是已知代价，不是缺陷。

### 2. 回执不复用 `error`（照 `config_result` 先例）

三条回执各自是独立的帧类型，不搭在 `error` 上。理由与 ADR-0199/ADR-0226 里 `config_result` 的先例逐字一致：`error` 帧还承载 backlog 跳过（`BACKLOG_SKIP_MARKER`）、hello 之外的杂项拒绝，`await` 一次 `say()`/`approve()`/`stop()` 时如果监听的是 `error`，会被一条完全不相干的 error 提前唤醒，结算出一个牛头不对马嘴的结果。三条回执统一形状 `{ ok: boolean; message?: string }`（`approve_result` 多一个 `callId` 用来配对），`ok=false` 时 `message` 说明原因，文案沿用第二批已经写好的那几句，只是换了帧承载——不是重新措辞。

### 3. 谁能停：与 approve 逐字同一条判据，而"有没有得停"另有一格判据

`CloudSession.stop(byUid, byLabel): "ok" | "idle" | "not_allowed"`（`services/runtime/src/sessionService.ts:353`，实现 `:1211`）。判据顺序固定：先看有没有得停（`runningNow()` 是 null → `"idle"`），再看有没有资格停（`router.canDecide(byUid)`，与审批的"发起人或 owner"是**同一个函数**，不是两处各写一遍）。顺序不能反——反过来会把"没什么好停的"说成"你没权限"，用户分不清两次点击之间发生了什么区别。

**"有没有得停"与"打不打得动"是两格状态，不是一格**（终审 Important I1 之后定稿的形状，`sessionService.ts:381 / :391 / :399` 三个闭包变量）：

| 变量 | 何时置 / 何时清 | 回答的问题 |
|---|---|---|
| `currentJob` | `runJob` **一进门**就置（`:873`），`finally` 清 | "这条会话欠着一轮吗" —— `runningNow()`（`:673`，**私有，不上接口**，见 M2）唯一的判据 |
| `currentEngine` | `runLoggedTurn` 的**前一行**置（`:1013`，中间不许有 await），`runLoggedTurn` **一返回就清**（`:1028`），`finally` 再兜一次（`:1051`） | "此刻 `abortTurn()` 打得动谁" |
| `stopRequested` | `abortCurrent` 在没有 engine 可打时置（`:691`），`finally` 清（作用域是一个 job，不是一条会话） | "已经按过停止，但那一刻没有 engine 可打" |

三格分开的理由是同一件事的三段窗口，每一段的正确动作都不同：

- **起跑前那一段**（验籍 / `agents()` / brief / 取记忆 / `hostUids()` + 每个成员一次 edge 往返，都是真网络调用）：`currentJob` 已经在、`currentEngine` 还没有。此时 `abortTurn()` 是 `undefined?.abort()` 一次静默无操作 —— 回执说"停了"、群里也写了"停止了"，而这一轮照跑到底、照样记在 owner 账上。所以这一段记 `stopRequested`，由 `runJob` 起跑前自查（`:998`）**当场落一条真收口的 `turn_ended{aborted}`**。为什么必须是真收口而不是静默 return：开场白早在 `say()` 那一刻就落盘了（#932 坑 ②），没有 `turn_ended` 的话 `openTurns` 把它**永远**算作"排队中" —— 界面上那行转到天荒地老，daemon 每次重启还会把它重新排上跑一遍（每遍都花 owner 的钱）。**"真收口 vs 永远排队中"就是这一格存在的全部理由。**
- **turn 在飞那一段**：`currentEngine` 在，翻它的信号，收口事件由 engine 自己的 catch 落（既有路径）。
- **收口之后、`finally` 之前那一段**（终审 Important I1 补上的第三段）：`runLoggedTurn` 已经返回、`engine.turnAbort` 早已 null，而下面还有一整段 `relayAfterTurn` —— 里面是**两次真 Supabase 往返**（`agents()` `:740`、`relayMaxDepth()`）。原来 `currentEngine` 要到 `finally` 才清，于是这个窗口里的 stop 走"翻信号"那条路：翻的是一个已经结束的 turn 的信号，一次无操作，而回执说 ok、群里写了"停止了"，接力紧接着照点火 —— **人按下停止之后，屏幕上冒出下一只 agent 开始回复**。修法是 `runLoggedTurn` 一返回就 `currentEngine = null`（`:1028`），让这个窗口自动落进 `stopRequested` 那条路，再由 `relayAfterTurn` 自己查两次：`if (archived || stopRequested) return`，一次在函数开头（`:730`）、一次在 `relayMaxDepth()` 那次 await 之后（`:796`）—— 与 `archived` 逐字同一个位置、同一个理由（那两处 await 期间人随时可能按下停止或归档）。回归用例：`tests/runtime/sessionService.test.ts` 的「收口之后、接力取名单那个窗口里按停止」。

`frameHandler.ts` 的 `case "stop"`（`frameHandler.ts:483`）不复制这条判断，只转译三态为 `stop_result`：`"ok"` → `{ok:true}`；`"idle"` → `{ok:false, message:"此刻没有正在跑的 turn"}`；`"not_allowed"` → `{ok:false, message:"只有发起人或 owner 能停"}` 并 `deps.log` 一行（拒绝是这一层唯一的失败出口，同 ADR-0201 对 `rateLimit` 的纪律——不记的话"谁按的、为什么没停下来"没有第二个地方能答）。

**`CloudSession.running()` 不上接口（终审 M2）**：初版把 `runningNow()` 也开成了接口的一格，而生产代码零调用——`stop()`/`archive()` 都在同一个闭包里自己用它，frameHandler 拿到的是 `stop()` 的三态回执，不需要先问一遍"有没有在跑"。多一格接口就多两份假件要写（`checks/smokeAssembly.ts`、`tests/runtime/frameHandler.test.ts` 的桩），而它对外的全部信息都能从 `"idle"` 读出来，所以撤掉、只留私有函数。

**停止键也有桶**：`STOP_BUCKET = { capacity: 5, refillPerMin: 10 }`（`services/runtime/src/rateLimit.ts:37`，`ThrottleKind` 从三档变四档 `:88`），扣在**在籍复查之后**（被踢的人该拿到"你不在这了"，不是"慢一点"）。理由不是模型调用的钱——停止不起模型调用，看着是免费的——而是**每一次成功的 stop 都往日志里落一条系统发言**，而日志是这条会话唯一的事实来源：按住不放能把它刷成一屏"某某停止了"。容量取 5、每分钟补 10：一个人手动按停止的合理频率，不是压测出来的数字（同另外三档的取值依据）。

**`say` 的内部异常不把原文交给客户端（终审 M4）**：`frameHandler` 那条 `catch` 罩着的是内部异常（Supabase 抖了、`agents()` 抛了、`store.append` 挂了），措辞是说给维护者听的——照搬给用户就是一句他既看不懂、也没有任何下一步动作的信息，还可能带上表名/uid 这类不该出门的东西。原文只进 `deps.log`，客户端拿到的是固定的一句「发送失败，请重试」（同 `humanizeMcpError`/`humanizeBillingError` 的纪律：只翻认得出的，认不出的不硬翻）。限速/不在籍那两条**不在**此列——它们是判据明确的业务拒绝，文案照旧精确。

### 4. 停的语义：停这一轮，不清队列（否决：连排队的一起清）

`abortCurrent()`（`sessionService.ts:691`）**不判权限**——两个调用点各自判过（`stop()` 判 `router.canDecide`，`archive()` 的权限 frameHandler 收帧时就判过），没有 job 在手时是无操作、回 false。已经落盘但还没跑到的 job 照旧留在队列里。**否决**把停止扩大成"清空这个 agent 接下来所有排队的开场白"——那是另一个功能（用户可能只是想打断这一轮跑飞的输出，不代表想撤回后面已经 @ 出去的话），本批不做，真有这个需求再另开一轮（见"推翻它的前提"）。

`abortTurn()` 本身只翻一个信号，真正的收口事件 `turn_ended{outcome:"aborted", agentId}` 由 engine 在它自己的 catch 里落——这是既有路径（`turnLedger`/`openTurns` 已经认识这个 outcome），本批不新增事件类型。它**晚于** `abortCurrent` 落的那条系统发言、也晚于归档那两条事件，daemon 的收房因此改成等 `settled()`（决策 5）。

**停掉的 turn 不接力**，两条路各有各的挡法（终审 I1 之后才齐）：turn 在飞时被停 → `outcome === "aborted"`，`runJob` 那行 `if (outcome === "completed") await relayAfterTurn(...)` 天然挡住（那行原本是走不到的死防御，本批之后它是活的）；**收口之后被停** → `outcome` 已经是 `"completed"`，`relayAfterTurn` 照样进得去，靠里面那两处 `stopRequested` 判据挡（决策 3 第三段窗口）。少了后者，"停止"这颗按钮在真实时序里有一整段窗口是假的。

群里落一条 `chat_message{fromUid:"system", label:"系统"}` 说明"谁停了哪只 agent 的这一轮"（`abortCurrent` 里那句，名字现取 `specNames`，查不到退回 agentId），与归档那句系统发言走同一条路（`daemon` 的 `notifyWorkspace`）。说出口是硬要求，同 ADR-0168「撤销要说出口」那条纪律：只翻信号的话，"有人按了停止"和"模型这一轮碰巧没话说"在群里长得一模一样，而这两件事该做的动作相反。

### 5. 归档顺带停，daemon 收房等 `settled()` 封顶 10 秒（否决：让 archive 等 turn 自然跑完）

`archive(byLabel)`（`sessionService.ts:1224`）先 `abortCurrent(byLabel)` 再翻 `archived = true`、落两条事件——不判权限，因为归档权限已经在 `frameHandler` 收帧那一刻判过（owner 或建会话的人），这里再判一次会误用 stop 的判据（发起人或 owner）去否决一个本来有权归档、但恰好不是发起人/owner 的人。**否决**反过来做——归档时不动正在跑的 turn、等它自然跑完——因为 daemon 原来固定 2 秒后就把房间收了（`cidTransport.delete` → `globalSend` 静默丢帧），于是一条已经归档的会话里，turn 继续跑、继续花 owner 的钱，产出的每一条事件（含它辛苦跑出来的回复）都发给了没人（A-8：意图与实际行为相反）。

daemon 的 `closeRoom` 延时因此从固定 2 秒改成"先等 `settled()`（`sessionService.ts:1185`）或封顶 `ARCHIVE_SETTLE_MAX_WAIT_MS = 10_000`（`daemon.ts:62`），再延一拍收摊"：`Promise.race([active.session.settled(), 10 秒计时器])`（`daemon.ts:764-767`），无论排空还是超时都落到 `.then(close, close)`（`daemon.ts:770-773`）——`settled()` 抛了也照样收房，收不掉才是真的漏。**封顶那颗定时器要 `clearTimeout`**（终审 M5，`daemon.ts:763/767`）：`Promise.race` 只是不再理输的那一边，并不取消它；排空先到时那颗 10 秒计时器还挂在事件循环上，让进程平白多活最长 10 秒（`unref` 不行——一次真的超时收房要靠它把 `close` 叫醒）。两段等待各答不同的问题：`settled()` 等的是"这条 turn 不再产出事件"（inflight 排空），随后 `setTimeout(close, 2_000)` 等的是"已经交给 socket 的那些字节写出去"（既有的延一拍收摊逻辑，本批只是把它接在排空/超时之后，不是取消它）。跑完的回复不再发给没人，也不会因为一条卡住的 turn 让归档操作无限期悬挂。

### 6. 桌面等回执：`pendingSay` 单一挂起，`pendingApprove` 按 `callId` 分 Map（偏离"单一挂起"，理由是 `approve_result` 天然带 callId）

`cloudSessionClient.ts` 的 `ActiveSession` 新增三个字段：`pendingSay: CsPending | null`（`cloudSessionClient.ts:285`）、`pendingApprove: Map<string, CsPending>`（`cloudSessionClient.ts:286-289`）、`pendingStop: CsPending | null`（`cloudSessionClient.ts:291`）。`say()`/`stop()` 各自只有一个挂起态，形状照 `pendingConfig` 的先例；`approve()` 是唯一的偏离——同一时刻可能有两张不同的审批卡各自在等各自的回执（两只 agent 各请求一次危险操作），若也做成单一挂起，后一次 `approve()` 会因为"上一条还没回执"被拒，而那一条根本是另一张卡。`approve_result` 帧本身带 `callId`（`cloudSession.ts:264`），桌面用它精确对号，`Map` 是这份"天然可寻址"的直接映射，不是过度设计。

15 秒超时（`ACK_TIMEOUT_MS`，`cloudSessionClient.ts:336`）三条共用，超时文案 `ACK_TIMEOUT_MESSAGE = "没有收到回执，不确定有没有生效——看时间线"`（`cloudSessionClient.ts:337`）。**15 秒本身是"不知道"，不是"大概率成功"或"大概率失败"**：这个数字不是压测出来的延迟分布，是"给正常网络留够余量，同时不让用户等太久"的一个工程判断——超时之后界面唯一诚实的立场是承认自己不确定,建议用户去看时间线上有没有真的发生（同 ADR-0226 决策 5 对"15 秒定时器"本身的立场，此处只是把本地兜底换成协议层的真回执，数字延续，不是巧合)。断线（`markGone`）/拒绝（`markDenied`）/主动关闭（teardown）三处终态路径统一走 `settleWaiters()`（`cloudSessionClient.ts:415-419`）把 say/approve/stop 三类挂起态一并结掉——与 `settleConfig` 严格并列，注释里明写"漏哪条就是那条路径上的'发送中…/审批中…'永远转下去（#834 在 config 上踩过一模一样的坑）"。`pendingSay`/`pendingStop` 已有挂起时不排队，直接回 `{ok:false, message:"上一句还没有回执，稍等"}`（`cloudSessionClient.ts:865`）/`"上一次停止还没有回执，稍等"`（`cloudSessionClient.ts:910`）——**否决**给 say 做排队：say 不是一个可以攒起来批量发的操作，用户此刻就该知道上一句到底发没发出去，排队会把"回执"这个新加的确定性又还给用户去猜。

### 7. 渲染层：停止按钮门槛与审批卡同源

`canStopTurn(turn, selfUid, cs)`（`src/renderer/src/lib/cloudTimeline.ts:164`）是按钮画不画的判据：`cs.state === "ready"` 且 `turn.state === "running"` 且 `selfUid` 是发起人或 owner——不重判权限，服务端的 `stop_result` 才是唯一事实，这个函数只决定按钮该不该出现在界面上。`ShellBridge` 新增 `workspaceCloudStop(): Promise<FriendsResult<null>>`（`src/preload/index.ts:263` 经 `CHANNELS.workspaceCloudStop`，`src/main/index.ts:3345` 接到 `cloudClient.stop()`），store 里 `cloudStop()`（`src/renderer/src/store.ts:971`、`:2412`）调用它。`PendingTurnLines`（`CloudSessionPage.tsx:1124`）里 `canStopTurn(t, selfUid, cs)` 为真时渲染 `<StopTurnButton />`（`CloudSessionPage.tsx:1151`、`:1166`）：点击后 `disabled` 到 `stop_result` 回来为止，`ok:false` 时把服务端给的精确文案画在按钮旁。**`cloudStop()` 回 `{ok, message}` 而不是 boolean，且一个字都不写 `workspaceGroupsError`**（终审 M3）：那一格是页脚共享的错误带，停止失败的原因（"此刻没有正在跑的 turn" / "只有发起人或 owner 能停"）画在按钮旁边才读得懂——两处一起显示就是同一件事在屏幕上说两遍，页脚那条还会赖着不走（它归下一次别的操作清）；文案随返回值走，归属天然确定，不必像 `ApprovalRow` 那样去共享格里捞一句归不了属的话。这里**没有**审批卡那种"迟到拒绝"两层兜底（ADR-0226 决策 5）——`stop` 没有第二条会与 await 解耦的确认路径，15 秒超时兜底已经在 `cloudSessionClient` 的 `pendingStop` 里做过一次（决策 6），`store.cloudStop()` 直接转发那个结果，UI 侧不用再叠一层。

## 已知代价（本批接受，留给下一轮）

- **旧桌面在发版前看到 `version_mismatch`**：决策 1 的直接后果，不做双版本兼容换来的窗口期体验代价。
- **`pendingSay` 不排队**：决策 6——用户在上一句还没回执时再发一句，界面直接拒绝并要求"稍等"，不是排队攒着自动补发。
- **A-7 冻结仍在（#959）**：本批解决的是 A-2（stop）与 A-8（归档收房）两项，A-7（工作区群聊某个方向的冻结场景）不在本批范围，仍待后续一批处理。
- **没有清队列**：决策 4 的直接后果——停止只停当前这一轮，不清空已经 @ 出去、还在排队的开场白；真要撤回后面排队的话，用户目前没有别的手段。
- **第二批的通知/定时器兜底原样保留**：ADR-0226 决策 5 里审批按钮"订阅 `workspaceGroupsError` + 15 秒定时器"的两层本地兜底，和决策 6 里 `cloudDraftSeed` 草稿种子机制，本批**不撤掉**——`approve_result`/`say_result` 是根治的协议回执，但两条本地兜底作为"协议层万一也失灵"（比如帧本身在传输中丢了）的双保险继续留着，属于 belt-and-braces，不是冗余待清理。
- **归档只停"当前这一轮"，已排队的 @ 照跑（终审 M7）**：`archive()` 走的是 `abortCurrent()` 同一条路（决策 4/5），它只动手上这一个 job；同一句话 @ 了两只、或接力已经排下去的那几条开场白，归档之后照样被 `drain` 取出来跑（`drain` 的 while 循环本身不看 `archived`，ADR-0201 的既有分工）。挡它的是 `runJob` 里那道 `if (archived && openingDepth > 0)` ——**只挡接力棒**，人自己一次 @ 出去的多只 agent 挡不住。后果是归档之后房间还得等它们，可能顶到 `ARCHIVE_SETTLE_MAX_WAIT_MS` 那 10 秒上限才收房（超时之后那几条 turn 的产出就发给没人了，回到 A-8 的形状，只是窗口小了很多）。要根治得先有"清队列"这个能力（见"推翻它的前提"第一条），本批不做。
- **`docker exec` 没有 kill 原语，停止有物理天花板**：`abortTurn()` 翻的是 engine 那一层的信号，它能让 loop 不再发下一次模型调用、让 `chat()` 的 fetch 被 abort；但一条已经在容器里跑着的 `bash` 工具停不下来 —— `src/world/dockerWorld.ts` 的既有天花板（`docker exec` 无 kill 原语，运行中中断只能 reject，靠包在命令外层的 `timeout(1)` 自然到期兜底收口）。所以"按下停止"到"容器那头真的安静"之间可以隔着一整个工具超时，`settled()` 也得等它——这不是本批漏做，是 ADR-0199 那条天花板在停止这条路上的投影。
- **`stop` 没有第二条兜底路径**：决策 7——审批卡的"迟到拒绝"两层兜底（ADR-0226 决策 5）在 stop 按钮上没有对应物，`stop_result` 到不了时唯一的救济是 `pendingStop` 的 15 秒超时；这是本批判断"回执帧已经根治了这个问题"之后的取舍，不是遗漏。

## 推翻它的前提

- 若"停止只停这一轮、不清队列"在真实使用中反复被吐槽——用户点了停止之后发现排队里还有好几条 @ 在等着跑，体验上更接近"没停干净"——那时应该重新评估要不要加一个显式的"清空队列"操作，而不是把 stop 的语义悄悄扩大。
- 若旧桌面与新 runtime 长期共存的窗口比预期长（比如手机端或某个渠道的桌面客户端更新滞后），"不做双版本兼容"的代价会从"发版前几小时的窗口期"变成"持续数周的可用性问题"——那时才值得考虑给协议加一层双版本兼容，而不是现在就为一个理论上的场景预先设计。
- 若 `stop` 按钮没有审批卡那种本地兜底在真机上暴露出问题（比如 15 秒对着一颗卡死的按钮体验很差），那时应该把 ADR-0226 决策 5 的两层兜底模式搬到 `StopTurnButton` 上，而不是继续认为"回执帧已经够了"。
