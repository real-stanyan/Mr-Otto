# ADR-0199：云执行面与群聊会话——工作区二期六个架构决策

日期：2026-08-31
状态：已接受（设计对话已定，T1–T14 tracer bullet 已实现并合并；本 ADR 是收尾的架构记录）
关联：ADR-0197（好友代理云端执行器凭证托管——px 三道闸在 edge 复刻的先例，本期连接器路由直接复用，不新造执行面）、
ADR-0198（工作区一期：连接器池 = escrow 群组化，发布制会话 = 包机制群组化；本 ADR 是它的二期延伸）、
issue #816（二期设计对话）、issue #811（总路线）、
`docs/superpowers/specs/2026-08-31-workspace-phase2-design.md`（本 ADR 的决策来源，下称「spec」）

## 背景

工作区一期（ADR-0198）做完了「成员名单 + 连接器授权池 + 会话列表」，但会话本身还是本机
单 agent 会话发布出去的静态包——没有「一群人共享一个正在跑的 agent」这件事。二期一次
覆盖全部三块（用户选择「一个 spec 全包」，不做单人竖切分期）：云 runtime、每工作区 Docker
沙箱、群聊 turn 协议。

已定前提（#816，不重议）：群聊 Agent 云端执行；ExecutionWorld 接每工作区一个 Docker 沙箱
（持久卷 + git clone）；spike 已验通 agent 核心（loop/session/model/tools/world）零 Electron
耦合，纯 Node + VPS Docker 完整 turn 跑通，better-sqlite3 prebuilt 可用；基础设施是 VPS
（ssh -p 2222，docker 29 + node 24）、edge Worker（relay + Escrow DO）、Supabase Cloud；
已知缺件是云端 Approver 路由（审批闸 fail-closed 已有，缺「请求送到人面前」那半）。

## 六个架构决策

| # | 决策 | 结论 |
|---|---|---|
| 1 | 权威 event log | VPS SQLite（EventStore 原样复用）+ relay 直播 |
| 2 | 沙箱编排 | dockerode 直管；loop 在宿主 daemon，容器只执行工具 |
| 3 | 群聊 turn 协议 | @提及显式触发 + 中途发言在模型调用边界注入本 turn |
| 4 | 审批归属 | 发起人审批 + owner 可代批；超时 deny；谁批的进日志 |
| 5 | 部署通道 | 单仓 esbuild bundle + 脚本部署 + 协议版本握手 |
| 6 | 过渡期模型 key | 维护者 key 配 VPS env；本期埋计量，额度强制执行留三期 |

### ① 权威 event log：VPS SQLite（EventStore 原样复用）+ relay 直播

**理由**：Hard rule「append-only 事件日志是唯一事实来源；先落盘再喂模型」不因 loop 挪到
VPS 而失效——它只规定「先落盘再喂模型」这个顺序，不规定盘在哪台机器。EventStore
（better-sqlite3）原样复用意味着 `SessionEvent` schema、`deriveMessages`、`invariants.ts`、
auto-compact 判据这些既有投影全部免改——不用为云会话另起一套并行实现（spike 已验证
better-sqlite3 prebuilt 在 VPS 上可用）。直播复用 `src/shared/remote/wsTransport.ts` 与
`wire.ts`（三方共用一份变四方共用），也是同一条「不新造」的路。

**推翻条件**：如果工作区需要真正的多 runtime 实例横向扩展（不是单 VPS 单进程），单文件
SQLite 的单写入者模型就会变成瓶颈——那时候需要挪到具备多写入者协调能力的存储，本决策要
整体重估，而不是加个读副本就能糊过去。或者如果部署形态从「持久盘的常驻 VPS」换成无持久盘
的容器化/serverless 部署，「本地文件系统持久化」这个前提本身就不成立。

### ② 沙箱编排：dockerode 直管；loop 在宿主 daemon，容器只执行工具

**理由**：模型 key 与 MCP 凭据永不进容器是安全不变量，不是实现偏好——loop 留在宿主进程，
容器里只有 `docker exec` 送进去的一次性命令（`src/world/dockerWorld.ts` 的文件头注释：
「只有 http 走宿主侧 fetch，能出网的是 loop 进程，不是容器」）。`DockerWorld` 严格实现
`ExecutionWorld` 接口，是 `LocalWorld` 的平行替身而非分叉——Hard rule「工具实现只依赖
ExecutionWorld 接口」原样成立，engine 半个字都不用改。dockerode 直连单个 docker daemon
（不引入 k8s/nomad 这类编排层）匹配单 VPS 的真实承载规模，spike 已验证过这条路径整
turn 跑通。

**推翻条件**：如果需要跨多台宿主机做容器编排（超出单 VPS 承载能力），dockerode 直连单个
daemon 的模型不再成立，需要引入真正的编排层，容器归属/网络/卷迁移都要重新设计。或者如果
多租户/合规要求提升到需要网络出口白名单、seccomp 细化（本期「容器里没有任何凭据可漏，
所以网络白名单不做」的前提是运营方=维护者本人的单租户场景），这条 YAGNI 判断要重新评估
（spec §9 已把这条列进「明确不做」，但前提是当前信任模型）。

### ③ 群聊 turn 协议：@提及显式触发 + 中途发言在模型调用边界注入本 turn

**理由**：与 ADR-0179「@好友不发给模型」同一条原则——发送侧动作信号必须显式化，不做文本
猜测。`mention` 在 `cs_say` 帧里是独立的布尔字段（`src/shared/remote/cloudSession.ts` 的
`CsUp` 的 `say` 变体），不从正文解析「有没有 @ 到我」，避免误触发/漏触发。单 turn 全局互斥
+ 无隐形队列（`turnCoordinator.ts` 的 `idle/claimed/running` 三态机）让语义保持简单：跑着时
新的 @Agent 只降级为 `logged_only` 注入，不排队生成新 turn——「排队」交给用户自己再 @ 一次。
event-sourced 投影天然支持中途注入：`chat_message` 落盘后不用碰 engine 半个字，engine 每轮
从 store 重新投影天然看到它（`sessionService.ts` 文件头注释）。

**推翻条件**：如果产品需要「定向回复某人」的语义（不是全员广播式的单一聊天区），或者需要
多个成员各自触发独立并发 turn（不是全局单 turn 互斥），`turnCoordinator` 这个纯粹的全局
状态机就要重新设计——它目前没有「按目标」或「按发起人」分道的概念。

### ④ 审批归属：发起人审批 + owner 可代批；超时 deny；谁批的进日志

**理由**：把审批权限收紧到「turn 发起人 + workspace owner」两类人（`ApprovalRouter.canDecide`），
而不是「任何在场成员都能点」，是因为审批的问责语义需要锚定到具体的人——发起人对自己触发
的 turn 负责，owner 对整个工作区负责、可以代批不在场的发起人。超时 10 分钟自动 deny 保持
fail-closed 不变（发起人/owner 都不在线时 turn 卡在闸上直到超时，不会因为无人应答就放行）。
`decidedBy` 走显式参数而不是旁路状态是本期实现中定下、spec 未写的关键细节，见下节。

**推翻条件**：如果工作区场景证明「发起人经常离线、owner 又不是天天在」导致大量 turn 长期
卡在审批闸上（10 分钟超时后果是 turn 直接 denied，不是等待），这条严格的二人名单可能需要
放宽（比如允许指定审批代理人）——但那会削弱「谁批的」这一列的问责语义，需要配套重新设计
审计记录方式，不是简单加个人进白名单。

### ⑤ 部署通道：单仓 esbuild bundle + 脚本部署 + 协议版本握手

**理由**：匹配现有的脚本驱动部署惯例（本仓没有 CI/CD 流水线做自动化部署），单 VPS 目标不
需要镜像仓库/滚动发布这类基础设施。esbuild 把 `better-sqlite3`/`dockerode` 两个原生绑定
external 出去（本机 arm64 打出来的二进制在 VPS x86_64 上跑不了），`deploy-package.json`
的依赖版本现读根 `package.json`（不在部署脚本里手抄第二份，见 `scripts/runtime-deploy.mjs`
的注释）。`cs_hello` 带 `protocolVersion` 整数、破坏性变更 +1，版本不匹配时客户端提示升级、
runtime 拒帧不崩——避免协议不兼容时的静默数据损坏。

**推翻条件**：如果 runtime 需要多实例部署（不是单 VPS 单 systemd 服务），rsync + `sudo
systemctl restart` 这套单机部署脚本就不够用了，需要真正的编排（镜像仓库 + 滚动部署），
「`RUNTIME_SSH=user@host npm run runtime:deploy`」这个部署心智模型要整个换掉。

### ⑥ 过渡期模型 key：维护者 key 配 VPS env；本期埋计量，额度强制执行留三期

**理由**：匹配项目明确的非目标（spec §9：「额度强制执行、Stripe 接入、平台 key（三期）」
不在本期）——本期用户 = 维护者本人 + 受邀成员，没有独立计费主体，所以维护者一份 key 配
进 VPS env（`services/runtime/src/config.ts` 的 `REQUIRED_KEYS`：`MODEL_BASE_URL` /
`MODEL_API_KEY` / `MODEL_ID`）已经够用。但本期仍然埋计量：`model_usage` 事件进权威
event log（uid = turn 发起人），异步镜像写 Supabase `usage_ledger`，写失败不阻塞 turn——
「先把账记在权威日志里，云端镜像失败可以靠日志重放补账」，为三期的额度强制执行预留数据
基础，不是完全不管计费这件事。

**推翻条件**：如果这个云 runtime 要接纳付费或非维护者信任范围之外的用户（多租户计费场景），
维护者一个人的 key 配置模式立即不成立——这正是 spec §6 三期要解决的问题（`plans` +
`subscriptions`，计量单位归一化 credits，起 turn 前查额度）。本决策的前提是「本期使用者
都在维护者的信任边界内，无需按用户扣费」。

## 实现期间浮现的关键结论（spec 未写，代码现状核实）

以下五条是 T1–T14 实现过程中定下、spec 正文没有写但对理解系统行为至关重要的判据，均已
对照当前代码核实：

- **触发 turn 的消息一律走 `user_message`（`[label]: ` 前缀），`chat_message` 只承载
  非触发/中途插话**——`sessionService.ts` 的 `say()`：`decision === "start_turn"` 时调
  `engine.runTurn(`[${label}]: ${text}`)`，而 `LoopEngine.runTurn`
  （`src/loop/engine.ts:543`）落盘的事件类型是 `type: "user_message"`；`decision ===
  "logged_only"` 时 `sessionService.ts:111-119` 直接 `store.append` 一条
  `type: "chat_message"`。这个区分不是随手选的事件名——`src/session/deriveMessages.ts`
  的 auto-compact 兜底判据（第 383–385 行：「最后一条非空跑 `user_message` 的下标…
  compact 之后还没有新 `user_message`（= 被折的就是当前请求）时投影兜底重注原文」）
  依赖「`user_message` = 真正开启一个 turn 的消息」这个不变量。如果群聊里的中途闲聊也
  落成 `user_message`，compact 兜底会把「当前请求」的边界算错。
- **踢人「关门」= 写路径与读路径都关**（`say`/`approve`/`config`/`backlog` 均复查在籍
  + `dropCid` 摘广播席位），只关写等于留了无限期只读订阅——`frameHandler.ts` 的
  `requireStillMember()` 在这四种帧类型的处理分支里逐一调用（第 202/207/214/223 行），
  命中「已不在籍」时做两件事：① 把 cid 清出验籍表（等效 `onGone`，之后任何帧都落进「未过
  hello」分支）；② 调 `deps.dropCid`，让 daemon 把同一个 cid 从 daemon.ts 的
  `roomRosters` 广播名单里一并摘掉。第②步是必须的补丁——`frameHandler` 自己的验籍表
  只管「这个 cid 还能不能发帧」，daemon 侧另有一张独立的实时广播表，只堵写路径的话，
  被踢的成员发不出消息，但仍会继续收到该会话后续每一条 `onEvent` 广播，等于留了一个
  无限期的只读订阅。
- **事件保序：直播先于 backlog 到达时要缓冲，`done:true` 才合并 flush**——
  `cloudSessionClient.ts` 的 `handleSessionFrame`：welcome 之后到 backlog 落定这段窗口
  期，直播 `event` 帧可能先到（文件头注释记录了实测复现：
  `welcome(lastSeq=7)→直播event(seq=5)→backlog([0..7])`，即发即转会产出
  `[5,0,1,2,3,4,6,7]` 这种非 seq 升序的顺序，而渲染层是纯 append，乱序会让工具调用与
  对话先后错位）。做法是：未 ready 前收到的直播事件先进 `liveBuffer`，backlog **只在
  最后一片（`done:true`）** 时与 `liveBuffer` 合并、按 seq 排序后统一走 `deliverEvent`
  （去重表防止同一条转发两次）——不是每个分片都合并一次，因为服务端总是一次
  `done:true` 下发全量，中间分片提前合并 `liveBuffer` 反而会把还没轮到的直播事件提前
  放出去。
- **云会话要合成一条虚拟 `SessionSummary` 才进得了 fleet/手机**（`pushFleet` 以本地
  `store.sessions()` 为遍历主体）——云会话从不 `store.append`（本地 EventStore），天生
  不在 `index.ts` 的 `fleetSessions()`（`store.sessions()` 的投影）里；
  `src/main/islandProjection.ts` 的 `flattenFleet` 只遍历传给它的 `sessions` 参数，不会
  反向遍历 `islandStates` 的 key。`index.ts:934`：
  `const sessions = cloud ? [...fleetSessions(), cloud] : fleetSessions()`——本地会话数组
  是主体，`cloudSessionFleetRow`（`cloudSessionClient.ts`）合成的虚拟行只是追加在后面。
  不补这一行的后果是静默的：`approval_request` 命中 self 可批时算出的 `IslandState`
  （含 `pendingApproval`）永远不可达原生岛/手机 fleet，审批横幅永远不出现，且没有任何
  报错。
- **`decidedBy` 走显式参数不走旁路 Map（TOCTOU）**——`approvalRouter.ts` 的 `resolve()`
  签名把 `decidedBy?: {uid,label}` 当参数直接传入，随 `settle()` 一起落进 `outcome`。
  文件注释（第 26–34 行）记录了被推翻的早期方案：调用方在 `resolve()` 之前把
  `{uid,label}` 存进一个按 `callId` 键控的旁路 Map、`resolve()` 内部再回读；这在「同
  `callId` 背靠背两次 `approve`、中间不 await」时有 TOCTOU 窗口——第二次调用可能先覆盖
  Map 里的条目，又因为 `resolve()` 失败（pending 已被第一次消化）把整个 key 删掉，等
  第一次 `resolve` 触发的 `decide()` 续体去读时 Map 已空，`decidedBy` 静默丢失（decision
  本身仍对，但审计「谁批的」这一列空了）。改成参数直传后，同一个 `callId` 的 pending
  只能被消化一次（`pending.delete` 发生在 `settle` 里），第二次调用连 entry 都查不到，
  早早短路返回 `false`——不存在「读到别人刚写的值」的窗口，因为压根没有共享的旁路状态
  可读。

## 明确不做（YAGNI，抄 spec §9）

- 网络出口白名单 / seccomp 细化（容器无凭据，先不做）。
- 多 Agent 编排（AGENTS.md 明确不做）。
- 额度强制执行、Stripe 接入、平台 key（三期）。
- 云会话导出成 session package / 与一期发布制互转（后续按需）。
- turn 队列（显式再 @ 一次即可）。
