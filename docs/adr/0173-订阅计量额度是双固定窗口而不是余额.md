# ADR-0173：订阅计量 —— credit 是成本锚定的整数，额度是双固定窗口而不是余额

- 状态：已接受（stanyan 会话指示，issue #696）
- 日期：2026-08-29
- 推翻：ADR-0085（官方停止供 token）—— 它自己写明「若因商业化重新成立，第 1、2 条失效」
- 复活：ADR-0019（官方 key 藏在网关后）、ADR-0021（token 计价桶）的机制层
- 相关：ADR-0020（自带 key 优先，见 ADR-0175）、ADR-0045（赠额是明路 —— 赠额形态本身不复活）

## 背景

产品上四档订阅（Lite \$19 / Pro \$59 / Max5 \$149 / Max20 \$299），30% 毛利、70% 折成
用户可用的量，官方统一供 token。这需要一套服务端计量。

`0002_token_wallets.sql` 里已经有一套：append-only 账本 + 余额投影 + 原子扣费，
单位 micro-USD 整数，带幂等键。它是 #45 那一版网关留下的，代码被 #517 删了、
表还在真库里（68 行账本、4 个用户持有非零余额 —— 这也是 #520 停手的原因）。

所以这不是从零建，是**复活并改造**。改造的核心是一个问题：**额度是"余额"还是
"速率"**。

## 决定

### 1. credit = micro-USD，成本锚定，整数

沿用 `0002` 的单位与整数约定（`bigint`，不用浮点 —— `0.1 + 0.2 != 0.3` 不能发生在钱上）。

**不卖 token，卖 credit。** 同样 \$13.30 的成本预算，不同模型能买的 token 差 10 倍以上
（deepseek-v4-flash 有效混合价 \$0.104/M，Qwen 3.7 Max \$2.54/M）；档位若承诺
token 数，换个模型这个承诺就是假的。credit 锚定成本，因此：

- 图片、视频、LLM 三类计价单位（`per_token` / `per_unit` / `per_second`）能装进同一个池
- 用便宜模型额度掉得慢，**成本压力自然转给用户**，不需要偷偷降级
- 记账、成本核算、对账全在一个单位上，不做二次换算

### 2. 额度是**双固定窗口**，不是余额扣减

```
1 周窗口：周额度 W = 月成本预算 ÷ 4
5 小时窗口：0.2 W
```

准入 = 对 `usage_event` 的两次滚动聚合，两个都不超才放行。

**为什么不是余额**：余额模型允许一次性烧穿（一个 24/7 的 agent loop 能在一天里
花掉一个月的钱），而窗口把峰值削平 —— 5h 上限是周额度的 20%，意味着**烧完周额度
至少要跨 5 个窗口、25 小时**。这一条同时保护三样东西：你的现金流、上游一方站的
TPM/RPM 配额、以及用户自己（不会一天用完然后觉得被骗）。

**为什么周额度是月预算 ÷ 4 而不是 ÷ 4.33**：一个月有 4.33 周，按 ÷4.33 发且不滚存，
用户忙的那周不够、闲的那周浪费，实际拿到手 < 月额度。那 8% 是对"不滚存"的补偿。
（更慷慨的 ÷3.5 也算得过来 —— 周粒度不滚存会把 breakage 推到 50% 以上，
但先取保守值，等真实用量数据出来再调。）

### 3. 窗口是**固定**的，不是滑动的

第一次请求开窗，5h 后整窗清零；周窗按订阅锚定日重置。

滑动窗口更公平，但"什么时候能再用"是个连续函数，说不清楚。固定窗能给用户一个
倒计时（「3:47 后恢复」）。**可预测性 > 公平性** —— 用户对限流的愤怒主要来自
不知道什么时候恢复，不是来自被限。

### 4. 不滚存

窗口过期即清零。滚存会累积成预付负债（用户攒几个月然后一次性烧掉，那个月现金流
为负），且退订时未用额度在某些司法辖区触发无人认领财产法。

### 5. 加购：算 credit，**不进时间窗**，12 个月有效期，垫底消耗

- **不进窗口**：算进去的话，用户付了钱还是卡在 5h 窗口里 —— 加购形同虚设，是最
  愤怒的一种体验。代价是加购额度可以无视限速，第一版靠单用户并发上限 + 上游
  rate limit 兜底，出问题再给加购单独加一条速率上限。
- **12 个月有效期**：无限期 = 预付卡 = 长期负债 + escheatment 风险。
- **消耗顺序：套餐额度优先，加购垫底。** 套餐额度周末就过期了，先花它才不浪费。
  反过来会让加购额度永远排在前面被烧掉，用户会算出来。
- **加购不跨能力门禁**：Lite 加购也做不了图，想做图升 Pro。能力门禁是唯一的升级
  阶梯，用加购绕过等于取消它；而且做图需求应该导向 MRR，不是一次性收入。

### 6. 视频走**独立的额度秒池**，图片吃 credit

数量级说话（境内一方站价）：

```
一次对话 turn（30K token, deepseek-v4-pro）≈ $0.0092
一张 Seedream 4.0 图                        = $0.028   （≈ 3 个 turn）
一个 5 秒标准档视频                          = $0.12    （≈ 13 个 turn）
一个 5 秒高清档视频                          = $0.70    （≈ 76 个 turn）
```

图和一个 turn 同量级，塞进 credit 池天经地义，用户心智也简单。视频差一到两个
量级，必须单独一格 —— 否则「我做了几个视频，对话额度没了」。

额度秒按档位倍率扣（标准 1× / 中档 4× / 高清 6×），倍率由成本比推出。这与 credit
是同构的设计（都是成本锚定的抽象单位），只是单独一个池。

### 7. `usage_event` 是唯一事实，窗口计数器是投影

照抄仓库的硬规则（`0002` 的头注已经写过一遍）。两个窗口计数器用 Durable Object
per user 的环形桶实现（5 分钟 × 60 格 = 5h；1 小时 × 168 格 = 1w），O(1) 读写、
DO 单线程天然无竞态、崩了从 `usage_event` 重建。**不要每次请求扫表 sum。**

### 8. 单次预算闸

单个请求预估成本 > 5h 窗口的 25% 时，先问一次（「这个视频约占你 5 小时额度的
40%，继续？」）。把「一个请求打爆窗口」从事故变成一次明确的用户选择。复用现有
的危险操作审批 UI。

### 9. 流式是先花后扣，所以要 hold

LLM 的 token 数在末 chunk 的 usage 里，必须**请求前按 `max_tokens` × 输出价预扣、
结算时退差额**。没有 hold，并发请求能把余额打成负数。

视频是异步 job，**提交时全额预扣**（GPU 跑起来没法中途取消），失败走 refund；
且**按提交时刻计费** —— 否则用户能卡在窗口边界提交、完成时落进新窗口，白嫖一个窗口。

## 被本 ADR 调整的既有决定

- **ADR-0085 第 1、2 条失效**。它写的「会被推翻的前提」是「官方不供 token 若因
  商业化（付费充值等）重新成立」—— 正是本 ADR。第 3 条（德州）不受影响，德州已
  按 ADR-0143 整层删除，不随之恢复。
- **ADR-0019 / 0021 的机制层复活**，形态换成订阅制。
- **ADR-0045（赠额是一条明路）不复活**：赠额模式正是 ADR-0085 砍掉的东西
  （注册口子敞开 × 人人有赠额 = 持续漏钱，见 issue #122）。订阅制下入账由
  Stripe webhook 触发，不由注册触发。
- **issue #520（删 token 钱包三张表）应当作废**。它自己写明删的前提是「这条业务线
  整层下线、历史没有服务对象」——业务线要复活，前提不成立。那 68 行账本和 4 个
  用户的余额留着。

## 会被推翻的前提

- **「一个 turn ≈ 30K token、cache 命中率 70%」是拍的**，上面所有 turn/天 的数字都
  压在这两个假设上。仓库已有真实数据（`usageStats.ts` 吃的就是事件日志里的
  `promptTokens/completionTokens/cachedTokens`），跑一次全量聚合就能算出真实分布。
  **在定死档位数字之前应当先跑这个。**
- **「DeepSeek V4 Pro 境内 cache 价 ¥0.025」是二手资料**，属于全球开源旗舰里最低的
  一档，是异常值。整个成本模型压在它上面，必须开控制台核实。
- 若 breakage 实测远低于 50%（用户比预期用得满），周额度的 ÷4 要退回 ÷4.33，
  甚至要重定价。
