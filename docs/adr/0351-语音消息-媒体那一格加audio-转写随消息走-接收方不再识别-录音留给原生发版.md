# ADR-0351：语音消息——媒体那一格加 `audio`、转写随消息走、接收方不再识别、录音那一刀留给原生发版

日期：2026-10-04 · issue #1492 · 维护者拍板：按住说话默认发语音、对方收到也是语音、底下能转文字；**发给智能体的语音只给转写文字**

## 背景

今天输入栏左边那颗「按住说话」是听写：`otto-speech` 的 tap 只喂 `SFSpeechRecognizer`，松手把文字发出去，不落音频文件。
维护者要微信式语音消息。#1443 P1 给朋友私聊铺好了媒体管线（`messages.media` + `dm-media` bucket），只差一种 kind。

## 决定

1. **媒体那一格加 `kind:"audio"`**（`audio/mp4`，m4a 里的 AAC；≤ 60 秒、≤ 5MB、`width`/`height` 为 0、没有封面），
   不另开表也不另开列。老客户端的 `parseItem` 认不出这个 kind → 整份丢、画占位正文「[语音]」，说的仍是实话
   （P1 立的降级规矩在这里兑现了一次）。
2. **转写随消息走**（`transcript`，≤ 2000 字，可缺席）。发送方录的时候听写本来就在出字（`voiceStore` 的 finals），
   发消息时带上；接收方的「转文字」展开的是这一份，**不在本机再识别一遍**——省掉 `SFSpeechURLRecognitionRequest`，
   也让两边看到的字一样。没听清就没有字，气泡里说「这条语音没有文字」。
3. **发给智能体的语音只给转写文字**（维护者拍板）：那正是今天 `stopDictation → sendText` 的路，智能体那一侧一个字不改；
   云会话的引用（`ChatMediaRef`）这一期不收 `audio`，`sendCloudMedia` 遇到直接拒。
4. **放音走 expo-video 的无头播放器**（AVPlayer 放 m4a 没问题），不碰 `otto-speech` 的音频会话——那边管的是通话。
   同一时刻只放一条；组件卸载即停。代价：通话进行中按语音条会和通话抢扬声器，先不管。
5. **录音那一刀不在这一期**：`otto-speech` 没有任何地方把音频写成文件，加录音 = 动 `mobile/modules/` = 必须出新原生包
   （`publish-ota` 对 `NATIVE_PATHS` 的闸）。这一期只合**能热更新的那一半**（数据、气泡、bucket 放行），录音的 Swift 与
   JS 另开一条 PR、**不合进 main**，等下一次 TestFlight 一起上——合了就把所有热更新堵死。
6. **0055**：两个 bucket 的 `allowed_mime_types` 加 `audio/mp4`。先跑它再发热更新；反过来上传被 mime 白名单拒、
   `storageError` 翻成「这个格式传不上去」。

## 代价

- 这一期合进去之后，**没有人能发语音**（录音还没有）：用户看到的只是「别人发来的语音能放、能看字」的那一半，
  而别人也发不了。价值在下一次原生发版那天兑现；现在合是为了热更新那条路不被原生改动堵住。
- 语音条用 ▶ / ■ 两个字符当钮，没加新图标（图标表是生成的 JS，加也能热更新，先不动）。
- 真机未验：m4a 的签名地址在 expo-video 里能不能直接放、`playToEnd` 在无 VideoView 时会不会发，要等第一条真语音。
