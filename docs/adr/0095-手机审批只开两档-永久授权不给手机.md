# ADR-0095: 手机审批只开「本次同意」和「拒绝」两档

日期：2026-08-25
状态：已接受
关联：spec `docs/superpowers/specs/2026-08-25-mobile-remote-control-design.md` 第二节「命令面」；ADR-0093（手机命令面五个词）；`src/main/uiApprover.ts` 的 `availableDecisionsFor`、`src/main/permissionStore.ts`

## 背景

桌面的审批卡实际有四档（`availableDecisionsFor`）：`deny` / `abort` /
`approve_session` / `approve_always`。手机端要做审批，最省事的做法是把同一组按钮
照搬过去——毕竟命令面已经是白名单，多两个词也不多。

## 决定

**手机端只有「本次同意」和「拒绝」。** `approve_session` 不开，`approve_always` 更不开。
`UpFrame` 里 `approve` **没有 grant 字段**，且解码器用的是"认得的键集合之外还有别的键
= 整条丢弃"，所以 `{"type":"approve","grant":"always"}` 这种形状不会被剥掉多余字段后放行，
而是整条掉地上。

这一条有两条**具名**测试守着（`带 grant 的 approve 整条丢弃且不回调`），
具名是刻意的——将来有人想"顺手开一下"时，红的那一行得能自己说清楚为什么。

## 后果

- 手机上误触的最坏代价，是跑了一条本来不该跑的命令，且只跑这一次。
- 想给某类命令永久授权，必须坐到电脑前。这会让重度用户偶尔觉得手机端"少了一步"——
  接受，这正是想要的摩擦。
- `abort`（拒绝并中止整个 turn）也不在手机上。它不是安全取舍，是形状取舍：
  手机上没有"turn"这个视图概念，一个能远程掐掉整轮的按钮在只看得见一行状态时太钝。

## 为什么这不是过度谨慎

两档误触的代价不在一个量级：

- 误触「本次同意」→ 跑一条命令。可观测、可回滚、下一次还会问。
- 误触 `approve_always` → 往 `permissionStore` 写一条**永久**授权。从此那类命令
  再也不问了，而"再也不问"这件事没有任何后续提示会告诉你它发生过。

而手机恰恰是判断质量最低的终端：走路时、锁屏刚解时、通知栏顺手点时。
「最容易误触的地方」和「误触代价最大的档位」放在一起，是这条决定唯一要拆开的组合。
永久档留给坐在电脑前、看得见完整命令全文和工作区路径的那个人。

## 会推翻它的前提

- **若手机端将来能显示与桌面等价的审批上下文**（完整命令、完整路径、diff 预览、
  以及"这条永久授权将来会覆盖哪些命令"的说明），那么"判断质量最低"这个前提就弱了，
  `approve_session` 可以重议。`approve_always` 仍不建议——它的代价不在判断质量，
  在于那条授权是**静默**长期生效的。
- **若 `permissionStore` 将来给永久授权加上到期、可审计、可一键撤销的形状**，
  误触的代价就从"不可见的永久"降成"可见的一段时间"，那时这条决定的整个论证要重来。
- **若审批档位在桌面侧被重构**（例如 `abort` 合并进 `deny`），本条要跟着对齐 ——
  它引用的是 `availableDecisionsFor` 当下的那四档。
