## 背景

1a/1b/2/3/4（ADR-0219 / 0220 / 0221 / 0222）之后，一个工作区里站着若干只 @ 得着的 agent：
各有提示词、型号白名单、连接器白名单、记忆，钱也分得出是谁烧的。**唯一还缺的是它们之间
说不上话**——「运营」把报表跑出来之后，得有个人（真人）看见、再手打一句 `@广告 按这个投`。
用户原话（#928）里「这些智能体也可以互相 @ 来协同工作」说的就是这一段。

技术上缺的东西很小：`parseMentions`（ADR-0219 / spec §4.6）早就是服务端也能跑的纯逻辑，
`say()` 的排队与去重（ADR-0220）也早就在了。真正要点头的是**边界**：AGENTS.md 开篇
写着「明确不做：多 agent 编排」，而这条链子一旦打开，一只 agent 的输出就会**自己**点起
下一条 turn——这是本仓第一条不经人手就长出新 turn 的路径。所以这份 ADR 一半在讲机制，
一半在讲**为什么这不是把那句话作废，以及打开之后怎么刹住**。

## 决策

### 1. 收窄「明确不做多 agent 编排」，而不是删掉它；ADR-0047 决定 5 原样成立

AGENTS.md 开篇那句改成：

> 明确不做：通用多 agent 编排框架——工作区群聊里 agent 互相 @ 接力是唯一例外（带周期护栏
> 与棒数上限，ADR-0223；本机子 agent 仍不能再派子 agent，ADR-0047）、插件系统（…）

被否掉的仍然是**通用编排框架**：没有 DAG、没有角色调度器、没有「主 agent 拆任务派给从
agent」的那套。打开的只有一条形状极窄的路——**群聊里的接力**：一只 agent 在**自己那条给
人看的回复里** @ 了另一只，服务端替它把这句 @ 当成一次点名。心智模型和人 @ 人完全一样
（spec 决策 1 的「群聊参与者模型，不是派活模型」），区别只在于点名的那一位这次不是人。

**ADR-0047 决定 5「子 agent 不能再派子 agent」不动一个字**，`task` 那两个把守点原样保留。
两条路径不同在三处，缺一条就该重新想：

| | 本机子 agent（ADR-0047） | 工作区接力（本 ADR） |
|---|---|---|
| 谁看得见 | 子会话是**私有分区**，人要点开才看得到；派活方把返回值当结果吃掉 | 全落**同一份群日志**、画在同一条时间线上，群里每个人和每只 agent 都看得见每一棒 |
| 谁在跑 | 本机，人的机器上，人就在屏幕前 | VPS 上的 runtime，**可能没人看着** |
| 天花板 | 无——所以只能靠「不许再派」这条硬闸挡住指数展开 | 有——`depth` 落盘、到顶硬停（决策 4） |

第二行正是 ADR-0212 那条「只注话不停」在这里不够用的原因，第三行是本 ADR 有资格开这条口
的原因：**接力的每一棒都是日志里的一条事实，因此可以被数、被停**。子 agent 那条路上没有
这样一个可以数的量（返回值吃掉之后什么都不剩），所以那边的答案仍然只能是「不许」。

### 2. 载体是两条事件，不是一条：`agent_relay`（群事实）+ 带 `relay` 的 `user_message`（起 turn 的载体）

```ts
{ type: "agent_relay"; fromAgentId; toAgentId; depth; ignorable: true }   // 群事实
{ type: "user_message"; content: 接力开场白; fromUid; mentions: [to]; relay: { fromAgentId; depth } }
```

两条各回答一个问题，硬揉成一条就会有一个问题没人回答：

- `agent_relay` 回答**「发生了什么」**：谁把棒传给了谁、这是第几棒。时间线上那条接力线是
  它的投影（决策 6），周期护栏与棒数上限的判据（`relayChain` / `decideRelay`）也从它重放
  ——**必须落盘**，只活在内存里的话 daemon 一重启护栏就形同虚设（spec §4.4 原话）。
- 带 `relay` 的 `user_message` 回答**「谁来接」**：它就是普通的点名消息，唯一的不同是多了
  一个 `relay` 字段说明「这条不是人打的」。

选它当起 turn 的载体不是为了省事，是因为 ADR-0220 已经把「一条点名的 `user_message` 落盘
→ `openTurns` 认领 → 协调器排队 → engine 起 turn」整条路铺完了，而且铺得比接力需要的更
稳：`openTurns` 的重启补跑、`unseenUserTail` 对带 `mentions` 的消息不重采样（「答两次」堵
在不变量上）、渲染层的「排队中 / 正在回复」——**全部免费拿到，一行都不用为接力再写**。
造第二种起 turn 的机制才是贵的：那意味着上面每一条不变量都要有第二份实现。

`AgentRelayEvent` 因此表态 **`ignorable: true`**：它是**模型不可见**的注记，模型可见的那
一面是配对的那条 `user_message`（`deriveMessages` 里 `agent_relay` 走 `break` 不投影）。
喂给模型等于让它读一句关于自己身份的元话。旧版本客户端跳过这条事件只少一条时间线上的
接力线，不会复活一个残缺会话——同 `model_usage` 的表态口径。

新事件类型的检查清单（ADR-0222 决策 8 的**十一处**）这次走完了，但**只有八处真的写了一笔**
——那份清单是「逐处去看」，不是「逐处都得加行代码」：

- 写了的八处：`events.ts` 的 union + `KNOWN_EVENT_TYPES_MAP`、`persistencePolicy`
  （必须持久，判据要能重放）、`deriveMessages`（显式 `break`，不投影）、
  `Timeline.tsx` 的 `EventRow`（`return null`）、`threadGroups.isInvisible`、
  `PRIVACY_VERDICTS`（`keep`——谁 @ 了谁是这段对话里发生的事，不是发送方那台机器的私事）、
  `agentView` 的 `OTHER_AGENT_VERDICTS`（`keep`——没有 `agentId` 的群事件本来就走早退路径，
  但穷举 `Record` 里「反正放行了」不构成不写的理由）、`tests/session/persistencePolicy.test.ts`
  的 `DURABLE` 数组。前两类与后两类是**穷举表**，漏了 tsc 直接红；中间那几处不是。
- 落进 `default` 分支的四处：`deriveSections` / `deriveUsage` / `toThreadMessages.isAuditEvent`
  / `contextEstimate.pendingAfter`。前三处的默认答案就是对的（不成段、不计用量、不是审计行
  ——`EventRow` 已经 `return null`，三份名单由 `tests/renderer/timelineLists.test.ts` 互相对表）。
  **第四处是一个已知的、隐式的 0**：`agent_relay` 根本不进模型上下文，所以 0 是正确答案，但它
  今天是「没写所以是 0」不是「写了 0」——ADR-0222 的 review finding 3 说的正是这个区别。
  记在代价段。

### 3. 接力开场白的 `fromUid` 是**点火的那个人**，不是 agent

`relayAfterTurn` 落的开场白带的是 `job.fromUid`——这一条链最初那句人话是谁说的，整条链就
一直是谁。理由直接来自 spec §4.2：uid 是 `auth.users(id)`，编一个伪 uid 塞进去会让三处同时
开始撒谎（审批链的 `initiatorUid` / `byUid`、代理执行的身份闸、`usage_event.user_id`）。

**代价明说**：B 在接力里动手时，走的是**点火者的**代理授权（ADR-0164 第一道闸按人查），
不是「B 自己的」——B 根本没有「自己的」授权，它不是一个 uid。所以「@ 一只 agent」在授权
意义上等于「让它以我的名义去做」，与 ADR-0151 好友代理那条「B 用的是 A 的凭证」是同一个
形状，只是这里的 B 是一只水獭。接受：另一条路（给每只 agent 发伪 uid）要先解决「这个 uid
在 `auth.users` 里不存在」这个更贵的问题。

### 4. 两层刹车：周期护栏注话不停（护栏参数 3/2）、棒数上限硬停并向人汇报（默认 6，1–20 可配，现查）

判据全在纯层 `src/shared/agentRelay.ts` 的 `decideRelay`，落盘在 `relayAfterTurn`：

- **第一层 · 周期护栏**：判据抄 `toolLoopGuard.detectToolLoop` 的形状——**周期重复**不是
  「连续相同」（ADR-0212：A→B→A→B 相邻两棒从来不相等，只认 `last === prev` 的护栏会全程
  沉默）。命中往群里注一条话，**不停**。
- **第二层 · 棒数上限**：`depth` 到顶就不再落这一棒，群里说一句「接力到上限了…交回给人」。

**护栏参数取 `RELAY_GUARD = { maxPeriod: 3, minRepeats: 2 }`，不是 `toolLoopGuard` 默认的
24/3**：上限默认才 6 棒，24/3 的护栏在 6 棒之内**永远赶不上**——一条参数配错的护栏和没有
护栏在观测上一模一样（这正是 ADR-0212 抓到的那类失败）。3/2 的含义是「同一组 ≤3 棒来回
两遍就喊一次」，A↔B 在第 4 棒命中。

**为什么非要第二层**：ADR-0212 那条「只注话不停」成立的前提是**用户就在屏幕前**，注了话
之后人可以自己按停止。云会话这个前提不成立——链子跑在 VPS 上，群里可能没人看着（决策 1
表格第二行）。

**上限落在 `workspaces.relay_max_depth`**（migration `0024_workspace_relay_max_depth.sql`，
默认 6，DB `check` 限 1–20，幂等，同 0021/0022/0023 的约定手动执行一次；`workspaces` 此前
没有 update 策略，顺带补一条 `ws_update_owner`）。**每一条会接力的 turn 现查一次**、不缓存
——同 ADR-0202「每次 `chat()` 现读」的教训：会话房是长命的，定死意味着 owner 改完要重启
daemon。查询失败在 daemon 侧回落成默认值（`sessionService` 里再兜一层 try/catch，防的是
daemon 之外的调用方）。范围校验有两道且只有两道：表单 `validateRelayMaxDepth` 与 DB 的
`check`，**`workspaceManager.setRelayMaxDepth` 不再重复校验一遍**——第三份同样的范围常量
只会多一个漂移点，落地判断由 RLS 做（非 owner 撞「无权修改」）。

**到顶与打转两句话都走 `chat_message`（`fromUid: "system"`）**，不是只写给某一只 agent：
群里所有人看得见，且 `chat_message` 在 `agentView` 里是 `keep`，所以**每只 agent 的上下文
里也有这句话**——正在打转的那两只读得到「你们在打转」。到顶那句话末尾附一段
`lastWords`：这只 agent **最后一条** `assistant_message` 的**前 200 字**。取最后一条而不是
把这一轮的话拼起来（拼起来取头 200 字读着像「最先说」，和「最后说：」的文案对不上）；
取前 200 字而不是后 200 字（这是给人看的引用摘要，从头读起更容易看懂它在说什么）。

**人话点火重置 `depth`**：`relayChain` 只算**最近一条人点名**（带 `mentions` 且没有 `relay`）
之后的 `agent_relay`。人每说一句就是一次新的授权（spec §8）。

### 5. 只有 `completed` 才接力；归档之后一律不接力

`relayAfterTurn` 挂在 `engine.runLoggedTurn` 的返回值上，且只在 `outcome === "completed"`
时调用。`aborted` 是人按了停止——替它再点起另一只，等于按了停止之后事情反而更多了；
`error` 那条路根本走不到这里（抛进了 catch）。

**归档就地返回**（`if (archived) return`）。这一条不是顺手加的：接力是 turn 收口后**唯一**
会自己长出新 turn 的路径（中途插话靠 engine 下一轮重新投影天然生效，不额外起 turn），而
`drain` 本身**不看** `archived`（ADR-0201：归档只翻标志 + 落一条 `session_archived`，收房
延一拍）。刹车只能加在这儿——否则人在归档之后，这条链还在后台往下传、烧一间已经关掉的
房间的钱。

### 6. 扫描窗口按**这一轮起跑前的日志尾**划界，不是开场白的 `seq`

`relayAfterTurn` 要回答「这只 agent **这一轮**说了什么」。第一版按 `afterSeq: job.opening.seq`
划界，复审时判定为错（Critical ①）：**同一只 agent 排队排两个 job 时**——第二句点名在第一
个 turn 还没跑完时就落了盘、进了队列（`tests/runtime/sessionService.test.ts` 那个「去重与排队
混在同一条调用里」的既有夹具已经在踩这个形状）——第二个 job 的开场白 `seq` **早于**第一个
job 产出的 `assistant_message`。于是第二个 job 的扫描窗口会把第一个 job 那句早就被它自己
处理过的话**重新扫进来**：同一次 @ 落两条 `agent_relay`，而且多出来的这一跳还会把周期护栏
诓成「打转」，群里冒出一句没人看得懂的提醒。

改法是在 `runLoggedTurn` **之前**捕获 `scanFrom`：

```ts
const scanFrom = store.load(sessionId, { afterSeq: job.opening.seq }).at(-1)?.seq ?? job.opening.seq;
```

它与 `engine.ts` 的 `readUpToSeq`（ADR-0220）是**同一个量**——「这只 agent 这一轮开跑前
日志已经到哪儿」。回归用例钉在 `tests/runtime/sessionService.test.ts` 的「同一只 agent 排队
排两个 job 时不重复接力、也不误报打转」。

### 7. 时间线上画的是接力线，不是那条开场白

云会话页（`CloudSessionPage.tsx`）对 `agent_relay` 画一行斜体旁白「运营 → 广告 · 接力第 N 棒」
（`relayLineText`，名字**现查** `agentNameOf`——被删的 agent 回 id，同 spec §11 的既有取舍），
配对的那条带 `relay` 的 `user_message` **不画**（`hiddenFromCloudTimeline`）。那条开场白的正文
是写给模型看的「[系统]「运营」在上一条发言里 @ 了你…」，人看接力线就够——两条都画是同一件
事说两遍。本机时间线不画它：`Timeline.tsx` 的 `EventRow` 对 `agent_relay` `return null`、
`threadGroups.isInvisible` 判 `true`（路标不是对话内容，云页自己画）。

## 否决的备选

| 备选 | 为什么否 |
|---|---|
| 只用一条事件（把 `relay` 塞进 `user_message` 就够了，不要 `agent_relay`） | 那样「谁传给了谁」只能从开场白正文反解，而正文是给模型看的自然语言；护栏与上限的判据要的是结构化的 `(from, to, depth)`。见决策 2 |
| 只用一条事件（只落 `agent_relay`，让 runtime 直接起 turn） | 要造第二种起 turn 的机制，ADR-0220 的 `openTurns` 重启补跑 / `unseenUserTail` 不重采样 / 渲染层状态行全部要有第二份实现。见决策 2 |
| `depth` 只活在内存里 | daemon 一重启接力链的历史就丢了，护栏与上限形同虚设——而重启恰恰是长链最可能撞上的事件。spec §4.4 明写 |
| 接力开场白复述 A 的原话 | B 的上下文里本来就有 A 那条 `assistant_message`（`agentView` 对别人的发言是 `keep`，只剥 `toolCalls`）——复述一遍就是同一段话在 B 的上下文里出现两次，白烧 token 还可能让模型以为收到了两条指令。所以开场白是**短提示**不是**转述** |
| 在 `LoopEngine` 内部做接力 | engine 不该认识 roster：它今天只知道自己的 `agentId`，接力要的是「群里还有谁、名字怎么匹配」，那是装配层（`sessionService`）的知识。放进 engine 等于让本机那台 engine 也扛上一套它永远用不到的概念 |
| 给每只 agent 发一个伪 uid，让接力开场白「像人一样」 | 审批链 / 代理身份闸 / 用量归因三处同时开始撒谎，spec §4.2 明写。见决策 3 |
| 护栏用 `toolLoopGuard` 的默认 24/3 | 默认上限才 6 棒，24/3 永远赶不上——一条永远不触发的护栏与没有护栏在观测上一模一样。见决策 4 |
| 打转时直接停 | ADR-0212 的判据是启发式，会误判；误停一条正常的往复讨论比多喊一句贵。硬停交给上限那层（一个不会误判的计数），护栏只负责喊话 |
| 到顶 / 打转的话只发给相关的那两只 agent | 群聊里所有人都该看见链子为什么停了——而且这句话恰恰是要说给「不在屏幕前的人」听的。见决策 4 |
| `aborted` 也接力 | 人按了停止之后事情反而更多。见决策 5 |
| 归档只靠 `drain` 自己收口 | `drain` 不看 `archived`（ADR-0201 的既有分工），接力是唯一自己长新 turn 的路径，不加这道就会在关掉的房间里继续烧钱。见决策 5 |
| 扫描窗口用 `job.opening.seq` | 同一只 agent 排两个 job 时会重复接力 + 误报打转。见决策 6，回归用例已钉 |
| `workspaceManager.setRelayMaxDepth` 里再校验一次范围 | 第三份同样的范围常量只多一个漂移点；表单 + DB `check` 已经是两道。见决策 4 |
| 时间线上把接力开场白也画出来 | 同一件事说两遍，而且那条正文是写给模型的措辞。见决策 7 |

## 代价与天花板

| 面 | 结果 |
|---|---|
| **hop 与开场白是两次 append，不原子** | 两条之间崩溃会在日志里留下一个孤儿 `agent_relay`（有棒、没人接）。后果只有一个：它会被后续的 `relayChain` 数进去，把周期护栏往「更容易喊」的方向偏一格。不影响正确性，也不会让任何 turn 跑错——所以没有为它引入事务或补偿路径 |
| **护栏一旦命中就会在这条链后续每一棒继续命中** | `detectToolLoop` 判的是「历史里有周期重复」，A↔B 到第 4 棒命中之后，第 5、6 棒的历史里那个周期只会更长。默认上限 6 时最多多喊 3 句（`chat_message`，群里可见、进每只 agent 的上下文）。做成「一条链只喊一次」要多一份状态，收益不抵 |
| **`depth` 封的是一条**分支**，不是总工作量** | 一条 turn 里 @ 了 N 只，就分叉出 N 条各自独立计数的链（`decideRelay` 按 `openingDepth + 1` 算，同一轮里第二只看得见第一跳只是为了护栏判据）。最坏情况是 `N^maxDepth` 条 turn——默认 6 棒、每轮 @ 两只就是 64 条。真实模型很少这么写，但这是**已知的、没有闸**的一面：要封总量得再加一层「一条链累计多少 turn」的计数，本切片不做 |
| **`contextEstimate.pendingAfter` 对 `agent_relay` 是隐式 0** | 结果正确（这条事件不进模型上下文），但它落在 `default` 分支——与「显式写一个 0」在维护意图上是两回事（ADR-0222 review finding 3 的同一条）。云会话页今天不画本机圆环，所以走不到；哪天要画，这里得跟 `deriveMessages` 的「不投影」对齐着显式表态 |
| **接力开场白在本机 `Timeline.tsx` 会画成一条匿名 user 气泡** | 本机时间线不认 `relay` 字段（#936 那一族「`origin` 全仓没换皮」的同一个形状）。今天走不到——本机会话永远不会有云会话的日志；哪天桌面要直接渲染云日志（或分享一条云会话），这里要跟着 `hiddenFromCloudTimeline` 一起处理 |
| **每条会接力的 turn 查一次 `relay_max_depth`** | 一条 30 棒的链就是 30 次单行查询。这是「owner 改了下一棒生效」的直接代价（决策 4），单行主键查询，接受 |
| **串行接力慢** | @ 了两只会排队跑完（spec §11 的既有代价）。事件 schema 没为并行留字段，但 `agent_relay` 已经带 `depth` 与两端 id，改并行时日志格式不用改 |
| **改了名字之后，历史那条接力线要现查** | `agent_relay` 存的是 `agentId`；渲染时 `agentNameOf` 现查名单，被删的 agent 只剩 id。同 ADR-0047 对「史前会话退回 sessionId」的同一条取舍（spec §11 已列） |
| **接力仍然烧 owner 的钱** | ADR-0217 不动：工作区的 turn 一律记在 owner 头上。一条失控的链看得见是哪只在烧（ADR-0221 的用量表，spec §10 把切片 3 排在 5 前面正是为此），但不会自己停在额度那一侧——停它的是本 ADR 的两层刹车 |
| **migration 0024 是外向副作用** | 要维护者在 Supabase 手动跑一次（同 0021/0022/0023 的约定）。跑之前 `relay_max_depth` 查询失败 → 每次接力 warn 一行、回落默认 6，接力照常工作；`ws_update_owner` 策略没建之前设置页那格保存会撞 RLS |
| **手工冒烟一次都没跑** | 前置条件是登录账号 + 有订阅的工作区 + VPS 上活着的 runtime daemon + 生产库跑过 0024。纯逻辑（`agentRelay.ts`）、runtime 编排（含两条复审回归用例）、时间线文案都有单测；真机上模型是否真的会在回复里 @ 别人、护栏文案对模型的实际效果，全部 UNVERIFIED |

## 推翻它的前提

- **若模型学不会在回复里 @ 人**（真机上接力几乎从不发生），那问题不在这套机制而在
  `agent_briefed` 的 roster 呈现方式——要在提示词里明说「群里还有谁、需要谁就 @ 谁」，
  而不是给接力加一条「你应该 @ 某某了」的自动推断。自动推断就真的成了编排框架。
- **若分支展开成为真实的账单问题**（代价段第三条），要加的是「一条链累计 turn 数」这一层
  计数，判据仍然从 `agent_relay` 重放——`depth` 那一列不用改，加的是聚合方式。
- **若串行队列成为主要抱怨**（@ 三只等三倍时间），并行是下一步，日志格式已经为它留好了
  （spec §12）。届时要重新想的是并发审批卡与中断传播，不是事件 schema。
- **若「点火者的授权」被证明太粗**（决策 3 的代价：@ 一只 agent 等于让它以我的名义动手），
  下一步不是给 agent 发伪 uid，而是给接力开场白加一条**降权**语义——比如接力起的 turn
  一律不许过审批门、只能读不能写。那要先有一套 per-turn 的能力裁剪，本仓今天没有。
- **若周期护栏被证明会误伤正常的往复讨论**（两只 agent 你一言我一语地对齐口径本来就该来回
  几轮），先调的是 `RELAY_GUARD` 的 `minRepeats`，不是把护栏摘掉——摘掉就退回 ADR-0212
  抓到的那个「零信号」失败模式。
- **若本机子 agent 也开始需要互相接力**，决策 1 那张表的三行要重新逐行验：私有分区那行不
  成立（看不见就数不清），所以那时该做的是先把子会话搬到同一份可见的日志上，而不是直接
  把这套机制搬过去。
