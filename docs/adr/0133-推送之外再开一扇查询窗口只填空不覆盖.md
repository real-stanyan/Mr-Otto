# ADR-0133：推送之外再开一扇查询窗口，补状态只填空、不覆盖

日期：2026-08-26
状态：已接受
Issue：#548

## 背景

主进程 → 渲染进程的运行时状态一直是**纯推送**：`turnStatus` 在 turn 开头/结尾各推一次，
`approvalRequest` / `askUserRequest` 在卡片弹出的那一刻推一次。

纯推送有一个前提：**接收方从头听到尾**。渲染进程重载（开发时的 reload、崩溃恢复、
未来的多窗口）之后这个前提就不成立了——那些推送早已过去，store 里查无此会话，
运行指示条整个不渲染，一直空到这一轮结束。用户看到的是"跑着，但界面上什么都没有"。

事实一直在主进程手里（`runningSessions`），只是没有出口。灵动岛早就有同一件东西
（`islandSnapshot`，ADR-0061），因为它天然是"中途接进来的观众"；主窗当年被默认成
"从头听到尾的那个"，于是没给。

## 决定

**推送管变化，查询管补课。** 加一条 `sessionRuntime(sessionId)`：turn 状态、turnId、
压缩标记、挂起的审批/问卷，一次问清。渲染进程进聊天时（boot 命中 / resume）问一次。

补课的规则只有一条：**只填空，不覆盖**（`lib/runtimeHydration.ts` 的 `runtimePatch`）。

快照是"我问的那一刻"的事实，在 IPC 上飞的这几十毫秒里真相可能已经变了；推送永远是最新的。
所以 store 里已经有这个会话的记录 = 推送这一路是通的，快照无权改写；查无此会话 = 我
确实错过了，才落位。两种到达顺序下结果都对：

- 推送先到 → 键已存在 → 快照被忽略
- 快照先到 → 键落位 → 随后的推送照常覆盖

这条规则让「补课」不需要时序保证，也就不需要版本号、序列号或者一把锁。

## 取舍

- **挂起的审批存成"已经拼好的载荷"**，而不是事后从 `approver` 里重算。卡上的 preview
  是异步现算的（`buildApprovalPreview`），事后重算等于交出一张和推送时不一样的卡——
  "中途切进来看到的卡"和"刚推来的卡"说的是同一件事，不该长得不一样（#175 I1）。
  代价是主进程多存一份 Map，turn 收口时清。
- **压缩标记只在 running 时补**。它是 running 灯的一个子档，`idle + compacting` 是自相
  矛盾的快照；补错的代价是指示条永远停在"压缩中…"，没人会再来纠正。
  同理，`onTurnStatus` 的 idle 分支现在也顺手清 `compactingBySession`——补进来的那份
  没有对应的 `finally` 负责清它（发起 compact 的调用不在这个窗口里）。
- **不做通用的"状态重放"**。只补这一屏需要的四样东西。事件日志本来就能重放
  （resumeSession 已经交出全量事件），这里缺的只是"日志之外的运行时状态"那一小撮。
- 查不到的会话不报错，一律答"闲着、什么都没挂"：这是一次补状态的查询，不是一个操作。

## 为什么 e2e 必须等到正文开始流才 reload

第一版用例是**假绿**的：running 推送分两拍（turn 锁一上先推一次不带 turnId 的，
engine 落下开场 user_message 后再推一次带上），而 reload 恰好落在两拍之间——
第二拍顺手把状态补回去了，把修复删掉用例照样绿。

真实场景是人在 turn 跑到一半时重载，那时两拍早就过去。所以用例先等正文流出来再 reload
（`tests/e2e/runIndicatorReload.e2e.ts` 里那段注释）。删掉修复必须变红，这条用例才有意义。
