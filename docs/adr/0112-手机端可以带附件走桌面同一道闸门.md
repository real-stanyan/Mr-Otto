# ADR-0112：手机端可以带附件，走桌面同一道闸门

> 原为 ADR-0106：与 main 上先合入的「输入框指令的判定只有一份」 ADR 撞号，按 ADR-0074 在合并前改号。

## 状态

已接受（2026-08-26）

## 背景

ADR-0094 把手机端的范围写成「看 + 审批 + 回一条消息」，并明确排除附件。实际用起来，手机上最常出现的一句话就是「看看这张图」——截图、拍一张照片、转发一个 PDF。没有附件的那条消息只能靠文字描述一个手机上现成的东西，这是把范围里最自然的一个用法挡在外面。

三个约束决定了实现形状：

1. **中继单帧卡 256 KiB**（`services/gateway/src/gateway.ts` 的 `MAX_UPLINK_BYTES`，超了回 413 `frame_too_large`），而随手一张照片是几 MB。
2. **桌面已经有一道完整的准入闸门**：`src/main/attachmentIntake.ts` 的 `intakeFile(path, data, store)` 是纯逻辑、字节由调用方喂，四路出口（图片入库 / 文档转 Markdown / 文本带内容 / 拒收带理由）。
3. **手机端加原生模块要重新装机**，一个还没做完的功能不该把已经能用的那些一起带走。

## 决定

**一、分片，不压缩协议。** 新增上行帧 `upload{uploadId, seq, total, name, data}`，明文分片 128 KiB（过 base64 涨 4/3 ≈ 175 KiB 线上，离 256 KiB 有余量）。重组在 `src/shared/remote/uploads.ts`，纯层，跟着根门禁跑。

顺序和防重放**不在重组器里**：密封流（`sealedStream.ts`）的严格递增计数器已经保证帧不乱序、不重放，所以重组器只断言「正好是下一片」，不自己做接收窗口——多一套顺序逻辑就多一处能和密封流打架的地方。

三条上限（单文件 4MB / 一批 12MB / 同时 6 个）是内存性质不是礼貌：字节来自公网上一台已认证但仍可能有 bug 或被控的手机，没有上限的话一条 `total` 撒谎的帧就能把主进程撑爆。

**二、准入策略只有一套。** 手机只管把字节发上来，分类全部由桌面的 `intakeFile` 做。手机端**不做**第二套判断（除了「选的时候就知道超 4MB」这种能省掉几十秒白等的预筛）。两套准入策略迟早会不一样，而不一样的那天没人会发现。

**三、附件先传完，最后那条 `send` 才带上它们的 id。** `send` 增加可选字段 `uploads: string[]`。少一个 id 就**整条不发**并回话——消息正文很可能是「看看这张图」，把文字单独发过去等于让模型对着一句没有指代对象的话开工。

**四、新增下行帧 `notice{text}`，专门用来说「这个附件没收下」。** 静默丢弃在手机上和「传成功了」长得一模一样。刻意不去重：两次同样的拒收是两件事。

**五、上行 POST 必须串行。** 这一条是被附件逼出来的，但修的是一个早就存在的洞：密封流按严格递增计数器收帧，计数器在 `seal` 那一刻就定了，而并发 POST 的到达顺序由 HTTP 栈说了算——后 seal 的先到，先 seal 的那条就成了「迟到帧」被**永久丢弃**。单帧的时候看不见（一条一条发，中间隔着人的操作），附件一分片就是连着几十帧，当场撞上。两端的传输层（`mobile/src/transport.ts` / `src/main/remoteTransport.ts`）各加一条上行队列。

**六、原生模块懒加载。** `expo-image-picker` 和 `expo-file-system` 在 `mobile/src/attach.ts` 里用 `require` 现要并 try/catch，拿不到就是这一个按钮报「要重新装机」。写成顶层 `import` 的话，一台还没重 build 的机器上整个 app 一打开就白屏。

不装 `expo-document-picker`：`expo-file-system` 从 SDK 57 起自带 `File.pickFileAsync`，多一个原生模块就多一次装机成本。

**七、图片在发之前统一过一道 `expo-image-manipulator`。** 这一条解决两件事，而它们的修法是同一个：

- **iPhone 默认拍 HEIC，而桌面不认它**。签名表（`src/shared/images.ts`）只有 png/jpeg/gif/webp，HEIC 原样传上去会被 `intakeFile` 当成「图片和文档之外的二进制」拒收——也就是说这个功能最常见的那条路本来是走不通的。
- **一张原图可能顶到 4MB 上限**。4032px 的照片有一多半字节花在模型不会看的细节上。

做法：转成 JPEG，同时按阶梯（2048/0.8 → 1600/0.7 → 1280/0.6 → 1024/0.5）降到能过为止。**每一级都量真实字节数**，不从像素尺寸去猜——同样 2048px，纯色图几十 KB，树叶几 MB，猜错的代价是用户白等一次上传。只缩不放：比目标还小的图硬拉到 2048 只会更大更糊。

两条例外，都是为了不白丢画质：

- **桌面认得的格式 + 尺寸够小 = 原样走。** 手机上发的截图多半是报错信息，是 PNG，转 JPEG 会让小字糊掉。
- **相册那一步不设 `quality`。** 压缩只在阶梯里做一次；两处各压一遍等于画质白丢一道。

不是图片的（pdf/docx/txt）没有这条路可走：超了就在选的时候当场说清楚，别让人等完一次上传再被拒。

**八、`detectImageType` 从 `src/session/attachments.ts` 搬到 `src/shared/images.ts`。** 手机端在发之前判「这张图桌面收不收」的那一刻，必须和桌面判的是同一套签名。两份表迟早会不一样，而不一样的那天表现是「传上去了然后被拒」，最难查。老 import 路径靠 re-export 保持不变。

## 后果

- 手机端的范围从「看 + 审批 + 回一条」变成「看 + 审批 + 回一条（可带附件）」。**没有变的**：不建会话、不切模型、不改设置、不管 MCP。
- 图片一律不在选的时候按大小拒——它有缩放这条路可走，在那儿按原图大小拒掉等于把一张能传的照片说成传不了。真正传不了的（压到 1024/0.5 还超 4MB）在发送时报，带上实际大小。
- 代价：一张 HEIC 照片从选中到开始上传会有一两秒的转码，进度条先显示「处理附件…」。同一张图不缓存转码结果——重发一次就重转一次，换来的是不用管临时文件的生命周期。
- 附件功能要重新 build 装机才有；在那之前 ＋ 按钮会明说这件事，而不是静默失败。
- 中继依然什么都不知道：`upload` 帧和别的帧一样是密封流里的密文，文件名和内容一个字节都不过它的手。
