## 背景

工作区云会话（ADR-0199）今天只有**一台 engine**：一条会话 = 一只水獭。用户要的是
「群里站着好几只，各管一块业务，@ 谁谁答，agent 之间也能互相 @」（issue #928 原话）。
设计稿把这件事切成 6 片，**1a 是服务端骨架**：`workspace_agents` 表 + 抽 `EventLog`
接口 + `agentView` + `CloudSession` 从一台 engine 换成 N 台 + 串行队列 + 事件加
`agentId` + `cs_say` 加 `mentions`。验收标准写在设计稿 §10：**跑得起来，桌面界面上
还看不见任何变化**——1b 才点亮 UI。

十三个实现任务全部完成，其中一个（Task 11：daemon 接线）在协调者的账本里一度被跳过、
终审时才补做——这件事本身被记进了执行账本，不在本 ADR 复述。本 ADR 只记那些会长期
影响后续切片、影响这仓库怎么读这份代码的决定；账本里逐任务的审阅细节、被否掉的实现
草稿、已推迟的 minor 项，都留在账本里，不搬进来。

## 决策

### 1. 上下文隔离靠构造，不靠每处补过滤

一只 agent 的心智模型是**「群里我听得见你说话，看不见你在你电脑上敲了什么」**。
engine 里 model-facing 的读有三处（`snapshot()` 首圈 / 增量圈、`compactInner()`
全量）——按 ADR-0047 否掉「子 agent 事件写进父日志」时的同一条教训，逐处补过滤
漏一处就会安静地把别人的上下文灌进模型。

所以隔离**抽成一个窄读接口**（`src/session/eventLog.ts` 的 `EventLog`：`append` /
`load` / `forkOrigin` / `lastOfType` / `ofType`，五个方法是从 `engine.ts`（只碰
`append`/`load`）和 `boundedContextEvents`（另外三个）实测出来的，不是照抄
`EventStore` 的公开面），`src/session/agentView.ts` 的 `agentView(store, agentId)`
是第二个实现。`LoopEngine` 和 `boundedContextEvents` 的 `store` 参数类型跟着从
`EventStore` 收窄成 `EventLog`——这是一次真实的类型收紧（`EventStore` 是带
`private` 成员的 `class`，结构类型检查过不了一个裸包一层的对象，必须先有共同接口），
不是免费的重构。装配点（`services/runtime/src/sessionService.ts` 的 `engineFor`）
在**新建每台 engine 那一刻**把 `agentView(store, spec.agentId)` 递给它，engine 内部
那三处读点一个字都不改。`tests/architecture.test.ts:220` 钉死这条装配关系（判据是
"`new LoopEngine` 那段里 `store:` 后面跟的是什么"，不是全文搜 `agentView` 字符串）。

**这是变换，不是过滤**——`agentView.ts` 头注把这句话标成全篇最要紧的一句。别人的
`assistant_message` 不能整条丢弃：要剥掉 `toolCalls` / `reasoning` / `usage`，只留
`content`（剥完为空就整条丢，纯工具调用的那一轮它没「说话」）。剥 `toolCalls` 不是
顺手：留着它又丢掉配对的 `tool_result`，`deriveMessages` 的悬空工具调用自愈
（ADR-0005 的保命层，`deriveMessages.ts:351`）会替它**造一条「没执行」的 tool 消息**
塞进我的上下文——别人明明跑成功了，我的模型读到的是它没执行。这不是崩溃，是一句
凭空捏造的事实，比 400 更难查。

同一条理由推到 `context_compacted`：`agentView` 的 `lastOfType`/`ofType` 对它按
`agentId` 过滤，不是无条件转发（原设计稿第一版写反了，见决策 2）。压缩摘要是**按
视角生成的**（ADR-0003），运营那只压缩一次留下的检查点如果被广告那只的
`boundedContextEvents` 捡到，广告会把运营视角的摘要当成自己的历史——上下文串台，
且这件事不崩、不报错、界面无痕。

### 2. 裁决表是穷举 `Record`，不是名单

`agentView.ts` 的 `OTHER_AGENT_VERDICTS: Record<SessionEvent["type"], OtherAgentVerdict>`
（`keep` / `drop` / `spoken`）现在穷举了 `SessionEvent` 联合类型此刻的全部成员（读
今天的代码是 44 条判决）。这不是风格选择：**这张表的第一版是一个 `Set`（丢弃名单），
而它漏掉了 `context_compacted`**。`deriveMessages.ts` 对 `context_compacted` 的处理
是 `messages.length = 0`——清场重来，把摘要注入成「你对这段历史的全部记忆」。名单
漏一个事件类型 = 别人压缩一次，我的整段真实历史被抹掉换成别人视角的摘要，触发条件
只是「群里任何一只压缩过一次」，不是边缘场景。名单漏一个是静默灾难；换成 `Record`
之后，加一个新 `SessionEvent` 类型不来这里表态，`tsc` 直接报 `TS2741`（`Property
'context_compacted' is missing in type ... but required in type Record<...>`——这条
在实现审阅时被临时删掉一行验证过是真的编译错误，不是 `Partial` 装样子）。形状照抄
`src/shared/sessionPackage.ts` 的 `PRIVACY_VERDICTS`（AGENTS.md 记着它是「新事件类型
检查清单」的一处，本仓已经用它救过一次场）。

**这张表里的 44 条不是全部同等地"已验证"**：今天真正会被查到、走进 `owner !==
agentId` 分支的只有那 9 个带 `agentId` 的事件类型（`assistant_message` /
`tool_result` / `tool_execution_started` / `approval_request` / `approval_decision` /
`request_envelope` / `turn_ended` / `tool_hook` / `context_compacted`）；其余 30 多条
今天不带 `agentId`，被 `projectForAgent` 里 `owner === undefined` 的早退分支接住，
判决暂时是「先想清楚，还没到验证的时候」的声明，不是已验证的结论——`memory_loaded:
"keep"` 就是这样一条**今天碰巧对、明天可能错**的声明：切片 4 要给每只 agent 一份
私有记忆档，一旦 `memory_loaded` 带上 `agentId`，`"keep"` 就意味着广告那只读得到
运营的私有记忆。同类需要在切片 4 重判的还有 `route_changed` / `model_changed`
（今天判 `keep`，但它们说的是某一只的调用管路）与 `checkpoint_created` /
`branch_checked_out` / `workspace_restored`（今天判 `drop`，但它们是工作区级事实，
同一个容器里别的 agent 理应知道——ADR-0161 的协作记录就是为这个存在的）。

### 3. turn 互斥换成串行队列

`services/runtime/src/turnCoordinator.ts` 把 ADR-0199 那把「一会话一把互斥锁」换成
一条队列（`enqueue` / `nextJob` / `isRunning`）。@ 谁就塞一个 `TurnJob`，真正的不变量
是**「拿到 `start_turn` 的那一方，负责把队列排空到 `null` 为止」**——不是"这一批
job 跑完就够了"。串行不并行：并行审批卡、并行直播、中断传播要重新想一遍，同 ADR-0047
否掉并行派活的理由一样，而决策 4 的接力形状本来就是一棒接一棒。

这条不变量在实现期间被踩穿过两次，都是真实复现（不是理论推演）：

- **① `finally` 少排一次 → `running` 永久钉 `true`。** `sessionService.ts` 早期版本
  在 `finally` 里只调一次 `nextJob()`，假设队列此刻已经空了。真实探针：
  `say#1 enqueue → start_turn` → `say#2 enqueue → queued`（并发，可达——frameHandler
  的 `serialize` 是按 cid 串行，两个成员 = 两个 cid = 两条独立链，并发 `say()` 到
  同一条会话是常态不是边缘）→ `say#1 finally nextJob → job`，**`isRunning` 仍为
  `true`** → 此后任何 `enqueue()` 都只能拿到 `queued`，这条云会话再也起不了 turn，
  直到 daemon 重启。修法是 `finally` 里 `while (job !== null)` 循环排空（commit
  `3b470032`）。复审把修复回滚重跑，精确红在 `tests/runtime/sessionService.test.ts:272`
  的 `isRunning` 断言（应 `false` 收到 `true`），其余七条不受影响。
- **② 去重回 `logged_only` 的 job 压根没入队，调用方对非 `start_turn` 一律不落盘。**
  `turnCoordinator.ts` 的 `enqueue` 在同一只 agent 已经排着队时直接返回 `"logged_only"`
  **不 push 任何东西**（连点三下 @运营 不该跑三遍）。`sessionService.ts` 的 `say()`
  最初假设"非 `start_turn` 就返回"总是安全的，因为 `queued` 的 job 迟早会被别人的
  排空循环跑到、落一条 `user_message`——但这条假设对 `logged_only` 不成立：探针
  显示"第 1 条 enqueue → `start_turn`；第 2、3 条 → `logged_only`"，第 2、3 条**没有
  任何 `runJob` 会替它们落 `user_message`**，`finally` 的补偿排空也捞不到（它们压根
  不在队列里）。main 上每次 `say()` 恰好落一条事件，这条路径落零条——直接踩
  「append-only 事件日志是唯一事实来源」这条硬规则。这是**跨任务破口**：写去重时的
  前提成立，另一个任务的修复轮把"非 `start_turn` 返回"那段改掉时只想到了 `queued`，
  单任务审阅看不见这种组合。修法（commit `169a035d`）：一批 `enqueue` 结果**全是**
  `logged_only`（一个都没入队）才补一条 `chat_message`；混着 `queued` 就不补（那个
  `queued` 的 job 自己会落 `user_message`）。验证：拿掉 `decisions.every(d => d ===
  "logged_only")` 这行判据 → 1 failed；还原 → 17/17 绿。

### 4. 一句话一条事件

事件类型说明它的下场：**`user_message` = 它得到了自己的一轮**（模型会看见、会回应）；
**`chat_message` = 它没有**（纯观察性发言，中途插话靠 engine 每轮从日志重新投影天然
生效，不碰 engine 半个字）。`deriveMessages` 把 `chat_message` 投影成
`{role:"user", content:"[label]: content"}`，与 `user_message` 走到 `runTurn` 之后
投影出来的形状**完全相同**——如果一句话同时落了 `chat_message` 又落了 `user_message`，
不是日志变胖，是**模型把同一句指令读两遍**，1b 的时间线上也会显示两遍。

这条规则逼出了一个**代价必须如实写的**取舍：`queued` 的消息不再立刻落
`chat_message`（它一定会被别人的排空循环跑到，届时由 `runTurn` 落 `user_message`，
与 `start_turn` 路径对称）。也就是说，一条被 `enqueue()` 判为 `"queued"` 的消息，
在它真正轮到执行之前，**日志里不存在任何一条事件记着它**——`turnCoordinator.ts`
的队列是一个纯内存数组（`const queue: TurnJob[] = [];`，`createTurnCoordinator()`
随 `createCloudSession()` 在 daemon 装配会话房那一刻创建），不落盘、不持久化。
**daemon 重启会让排队中的消息无声消失**：frameHandler 收到 `cs_say` 帧后
`await session.say(...)` 一旦不抛错就 `return`（`frameHandler.ts:355-368`），
客户端并不知道自己的消息此刻是"已经跑完"还是"正排在一个纯内存队列里"——如果
daemon 在它被排空之前重启，这条消息连一个字节都不会进日志，而客户端已经认为
它发出去了。**`say()` 不再保证「收下了 = 记下了」**，这半条不能省。

### 5. agent 身份走新事件 `agent_briefed`，投影成 user 消息

一只 agent 在这条会话里的自我介绍——它管哪块业务（`instructions`）、群里还有谁
（`roster`，@ 得着谁靠这份名单）——落一条新事件 `AgentBriefedEvent`
（`src/session/events.ts`），**不复用 `subagent_briefed`**。理由钉在 `events.ts`
的注释里：`subagent_briefed` 投影出来的文案是「你是 subagent「X」，以下是你的指令，
请在完成任务时遵循」——它把模型的最终一段文本定义成**返回值**（ADR-0047 的
`DEFAULT_PREAMBLE`）。群聊里这是一句假话：agent 说的话是说给群里的人听的，不是
交回给谁的返回值，复用等于给模型灌一句关于自己身份的假话，而这句假话会稳定地
改变它怎么说话。

投影成 **user 消息不是 system**（手法同 `subagent_briefed` / `skill_invoked`——中途
插 system 消息各家方言兼容性参差，ADR-0047 决定 1 的原话）。落盘时机的判据两条，
**且是 `&&` 不是 `||`**：这只没被介绍过，**或**介绍时的指令和现在不一样，两样都没有
（没提示词、没同伴）才不落——写成 `||` 的话，「有提示词但暂时没同伴」这种完全正常
的单 agent 工作区会被一起挡掉。终审曾经因为这个守卫写错方向，弄红了
`runtime:smoke` 的事件序列断言、并给每条既有云会话塞一条永久的空洞事件（打断一次
前缀缓存，ADR-0073），已在合并前修回 `&&`（commit `0768f928`）。别人的
`agent_briefed` **不进我的上下文**（决策 2 的裁决表判它 `drop`）：我需要知道群里有
「广告」这个人——那来自我自己 briefing 里的 `roster`——不需要读它的提示词。

## 三处已知偏差（如实记，不美化）

### a. 服务端解析压过了 `mention: false`

`resolveTargets`（`services/runtime/src/sessionService.ts:67-81`）三级判定：①客户端
算好的 `mentions` → ②服务端用 `parseMentions` 从正文里认 → ③都没有时按 `mention`
布尔唤醒名单第一只。**②不受 `mention` 布尔影响**——只要 `parsed.length` 非空就直接
返回，根本不看 `mention` 是 `true` 还是 `false`。于是一条 `mention: false` 但正文里
含 `@管理员` 的消息，在这条分支上会**起 turn**；而 `main` 上（单 agent、无 `②` 这一级）
`mention: false` 永远只落 `chat_message`。这比设计稿 §4.5「`mentions` 缺席时按老语义」
走宽了一步——「老语义」原本是纯布尔闸门，`mention: false` 无论正文写什么都不会触发
任何东西；现在多出的这一级中间判定，会在 `mention: false` 时也可能触发。1b 若要收紧，
落点是让②只在 `mentions` **完全未定义**（不是"缺席等价于假"）时才尝试正文解析，
或者干脆让 `mention: false` 提前短路、跳过②。

### b. `engineFor` 命中缓存就返回，adapter 在首次创建那一刻定死

`engineFor(spec)`（`services/runtime/src/sessionService.ts:192-210`）按 `agentId`
惰性建 `LoopEngine` 并永久缓存在 `engines: Map<string, LoopEngine>` 里；命中缓存
直接 `return hit`，`opts.adapterFor(spec)` **只在这只 agent 第一次开口时被调用一次**。
`daemon.ts:259` 的注释写着「sessionService 的设计就是要「这一刻的名单」，建/改 agent
下一 turn 生效」——这句话对**改提示词**成立（`briefIfNeeded` 每次都现查、指令变了
就补一条新 `agent_briefed`），对**改型号**不成立：`daemon.ts` 的 `adapterFor` 闭包
在构造时把 `agent.models[0]` 存进去决定选哪个逻辑型号，而 `engineFor` 缓存住的是
**用那一次 `agent.models[0]` 构造出来的 adapter 对象本身**，之后 `opts.agents()`
即使查到新的 `models` 白名单，也不会让缓存住的 engine 换用新 adapter——直到 daemon
重启，这只 agent 都还在用旧型号，且**没有任何信号**：不报错、不落日志、界面上
（1a 还没有界面）什么都不会说。这与 ADR-0202「每次 `chat()` 现读，因为会话房是
长命的」是同一条教训，在"每只 agent 一台 engine"这个新粒度上又踩了一遍——1a 里
这条路径今天走不到（`daemon.ts` 的 `adapterFor` 现在按 `models[0]` 固定取，`workspace_agents`
的 CRUD 还没有界面能改 `models`），**1b 一旦让用户能改 agent 的型号白名单，必须修**：
要么 `engineFor` 在 `spec.models` 变化时重建 engine（连带要想清楚"半途换 adapter"
对进行中 turn 的影响），要么把"选哪个型号"从 adapter 构造时下沉到每次 `chat()`
内部现读。

### c. `workspace_agents` 表至今没有在真库执行过

`supabase/migrations/0021_workspace_agents.sql` 与 0015 系列同一约定：打到生产
Supabase 的副作用留给维护者手动在 SQL editor 里执行一次，**这次合并不执行它**。
这是刻意的，不是遗漏——`daemon.ts` 的 `queryAgents` 因此设计成 fail-fast（查询失败
直接 throw，不在函数内部回落），装配点 `agents: () => queryAgents(workspaceId)
.catch(...)` 捕获失败后回落到 `DEFAULT_WORKSPACE_AGENT`（单条"管理员"占位，
`agentId` 与 migration 里 `seed_workspace_admin_agent` 触发器种下的默认行同构）
并 `console.error` 留痕（不是 `warn`——这不是预期内的抖动，是"多智能体这半条链路
还没打通"，运维应该看得见）。也就是说，**这次合并之后到维护者手动执行 0021 之前**，
所有工作区云会话实际上仍然是单 agent 行为，`resolveTargets`/`agentView`/串行队列
这一整套机制虽然装好了，但 `queryAgents` 会一直命中"表不存在"这类 PostgREST 错误、
一直走回落路径。

## 后果

| 面 | 结果 |
|---|---|
| 类型收紧 | `LoopEngine`/`boundedContextEvents` 的 `store` 参数从 `EventStore` 收窄成 `EventLog`；新增 44 项穷举 `Record` 裁决表，将来每加一个 `SessionEvent` 类型都要在这张表补一行，`tsc` 强制 |
| 并发行为 | 同一条云会话里两个成员各自 @ 不同 agent 时，第二只要等第一只的 turn 跑完——`agent_relay.depth` 之类的并行留白已经在 schema 里，但 1a 没有并行执行 |
| 消息可见性 | `queued` 的消息在真正轮到之前，日志里没有任何痕迹；`say()` 对客户端"不抛错"不再等价于"已经落盘"——见偏差 a 之外，这是本切片对协议语义最大的一次收紧 |
| 用户可见行为 | 设计上是零变化（`agentId`/`mentions` 缺席都退回旧语义），但偏差 a 说明"零变化"这句话在服务端解析层已经有一个例外 |
| 运行态 | 合并即生效，但因为偏差 c，`workspace_agents` 查询在维护者手动跑完 0021 migration 之前恒回落到单 agent 占位——多智能体功能"装好了但还没打开" |
| 测试 | `tests/architecture.test.ts` 新增一条云会话装配断言；`turnCoordinator`/`agentView`/`agentMention`/`sessionService` 各有专门测试文件，`runtime:smoke` 的事件序列断言覆盖了 `agent_briefed` 空守卫这条回归 |

## 推翻它的前提

- **若「一只 agent 看不见别人的工具输出」被证明太窄**（用户反复要求"让广告直接读
  运营刚跑出来的表"），决策 1 该退回带一把 `read_transcript(agent, since)` 工具的
  形态，而不是直接把裁决表里那些 `drop` 改成 `keep`——那样做等于把决策 1 的隔离
  边界整个拆掉，而不是开一道可控的口子。
- **切片 4（agent 私有记忆）给 `memory_loaded` 之类的事件带上 `agentId` 的那一刻**，
  决策 2 里标成"今天碰巧对"的那几条裁决（`memory_loaded`/`route_changed`/
  `model_changed`/`checkpoint_created`/`branch_checked_out`/`workspace_restored`）
  必须逐条重新验证，不能假设它们还对——这不是"可能要改"，是账本里已经点名"必须
  重判"的待办。
- **若串行队列成为主要抱怨**（@ 三只要顺序等三倍时间），并行是下一步；`agent_relay`
  已经带 `depth` 与收发双方 id，日志 schema 不用改，但需要重新设计的是并发审批卡
  与中断传播，不是事件形状。
- **若偏差 a（服务端解析压过 `mention:false`）在 1b 真机上造成"我明明没 @ 人，
  agent 却答话了"的真实困惑**，决策 3（串行队列）不受影响，但 `resolveTargets`
  的三级判定顺序需要重新排——让 `mention:false` 提前短路，而不是任由正文解析
  抢在布尔判断之前生效。
- **若排队消息在 daemon 重启时静默丢失被证明不可接受**（工作区里同时有好几只
  agent 排队是常态、而 daemon 重启不是罕见事件），决策 4 的"纯内存队列"需要换成
  某种持久化表示（比如把"排队中"当成一条会落盘的事件，而不是只活在
  `TurnCoordinator` 的内存数组里）——但那时"一句话一条事件"的判据要重新设计，
  因为"排队中"本身也是一句话的一种状态，不只是"没起 turn"和"起了 turn"两态。
