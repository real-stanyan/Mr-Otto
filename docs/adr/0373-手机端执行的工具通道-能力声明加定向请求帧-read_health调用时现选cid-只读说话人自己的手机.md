# 0373 手机端执行的工具通道：能力声明 + 定向请求帧，read_health 调用时现选 cid，只读说话人自己的手机

原为 ADR-0372（合并时 #1655 先占了 0372，按 ADR-0074 改号；#1656 分支上的提交信息里写的 0372 指的是这一篇）。

日期：2026-10-05 · 状态：已采纳 · issue #1656 · spec：docs/superpowers/specs/2026-10-05-apple-health-design.md

## 背景

维护者要智能体能读手机的 Apple 健康数据，选了「按需拉取、工具在手机上跑」与「只读说话人自己的手机」。此前没有任何在手机上执行的工具：
手机只是云 runtime 的 guest 连接（ADR-0317），跨设备工具只有借来工具 px（ADR-0151 / ADR-0197），都不在手机上跑。

## 决定

1. **能力声明 + 定向请求帧**（协议 29）：手机 welcome 后发 `caps{health}`，开关变动再发；runtime 的 healthBroker 记「哪条 cid 能读」，
   `read_health` 调用时按这一轮的发起人现选该 uid 最近声明的那条 cid，单发 `health_query`，只认那条 cid 回的 `health_result`。
   30 秒超时、cid 断开、turn 中断都收成 ok:false 抛给模型。客户端只在**已收到 welcome 的连接**上发 `caps` / `health_result`，
   且 `health_result` 只回到问它的那条 host cid（hello 之前先发帧会让这次会话被拒）。
   能力表是 daemon 全局的（按 uid，不按会话）：说话人用别的设备 / 别的会话开口，也是他那台手机来答；
   而那一行灰字落在发问的那条会话里，手机自己的聊天里只有当那恰好是这条会话时才看得到。
2. **cid 调用时现选**：手机切后台即断 WS、回前台换新 cid，turn 开始时那条可能已经没了。
3. **挂载判据** `healthTurnEligible`：
   - 这一轮覆盖的每一条开场白都是同一个人亲口打的（无开场白代发、无接力，即 `soleSpeaker`），且不是定时 / 汇报 / 补跑的那一轮；
   - 主场（approveAll）里只认主人；团队会话里任一成员（读他自己的）；
   - 发起人此刻有能力连接才亮；
   - 若这一轮中途另一个人插话，一次只针对健康的收紧（`tightenHealth`）会把这面旗关掉，`read_health` 在调用时拒绝（`allowed: () => healthTurn`），
     因为引擎的工具表在一轮之内只增不减，没法把已挂上的工具摘掉。
4. **结果照常落盘**：作为普通 `tool_result` 进事件日志（Hard rule「先落盘再喂模型」），只回按天汇总减少落盘量。
5. 不弹审批；手机聊天流对这一把工具例外地画一行灰字，让人看得见读了什么。

## 否掉的

- **事件日志驱动（仿审批卡）**：请求广播全房、桌面也收到、要客户端过滤；而发问的人此刻必在前台，重连补答价值低。
- **复用 px 通道**：那是 MCP server + 凭据托管的形状，手机两样都不是。
- **手机定期同步到云端**：健康数据长期存服务端，维护者没选。
- **手动附带**：智能体不能主动看，维护者没选。

## 后果

- 健康数据会留在云端会话库（随会话删除而删除）；隐私政策与 App Review 备注要写明（维护者操作）。
- 睡眠按「一夜」归并（相邻样本间隔 ≤ 2 小时合成一夜），归到醒来那一天，而不是按样本开始时间切成两天。
- 这是第一条「runtime → 指定设备 → runtime」的工具通道；以后再加设备端工具（定位、日历…）照这个形状加能力位与请求帧，不另起炉灶。
- 推翻前提：若要在手机锁屏 / 后台时也能读（例如定时任务汇报健康），需要静默推送唤醒 + 新的授权模型，另立 ADR。
