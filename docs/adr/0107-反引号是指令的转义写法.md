# ADR-0107：反引号是指令的转义写法

- 状态：已接受
- 日期：2026-08-25
- 关联：issue #441；订正 ADR-0106

## 背景

ADR-0106 把 `$skill` 的判定改成扫全串（句中也算指令头），并在「理由」里写了一句：

> 正文里真要提到 skill 名，本来就该写引号而不是 `$`。

**这句话当时是假的。** 加引号没用 —— 实测：

```
"`$apple-design` 是什么"            => 命中，正文变成 "`` 是什么"
"https://x.com/$apple-design 看这个"  => 命中，正文变成 "https://x.com/ 看这个"
```

第一条最难受：用户只是想**问这个 skill 是什么**，结果 skill 白注入一次、名字被摘走，模型收到的正文只剩一对空反引号。两条都是 0106 改出来的新伤 —— 改之前它们不在行首，压根进不了指令分支。

## 决定

**sigil 的前一个字符是 `` ` `` 或 `/` 时，不算指令。**

- **反引号 = 正式的转义写法**。想提名字就写 `` `$apple-design` ``，跟 markdown 里引用代码是同一个手势，不用另学一套。0106 那句话由此**成真**，不再是一句好听的空话
- **斜杠 = URL 和路径**。`https://x.com/$foo`、`./$foo` 不是指令

判定放在 `escapedAt()`，`makeFormatter.parse` 和 `findSkillDirective` 共用 —— 这正是 ADR-0106 立的规矩（判定只有一份）在第一次修改时的兑现方式：两头一起认、一起不认，锁步测试保证它。`/命令` 走同一个 `makeFormatter`，一并适用。

## 理由

反方案是把 0106 里那句话划掉，承认「没有转义写法，提到 skill 名就是会误伤」。没选：**一门有 sigil 的语法必须有办法说出 sigil 本身**，否则用户没法讨论自己的工具 —— 而「问这个 skill 是什么」恰恰是新用户最常做的动作之一。

选反引号而不是发明 `\$` 或 `$$`：用户已经会它，而且输入框本来就渲染 markdown；发明的写法要教，教了还会忘。

## 后果

- 只看**贴身的前一个字符**，不解析成对的代码段或围栏。三反引号代码块里 `$名字` 顶在行首（前一个字符是换行）的照旧算指令。真解析 markdown 结构是另一个量级的事，输入框里贴多行代码块本来就少见 —— 有人撞上再说，测试里钉了这条已知代价，改行为会红。
- `$$apple-design` 照旧命中（前一个字符是 `$`）。shell 的 `$$` 是 PID，理论上会误伤，没人在聊天框里打它。
- 代价是多了一条要记的规则。但它只在**想提到而不想调用**时才需要知道，而那个场景下用户本来就会去打反引号。
