# ADR-0144：工具产出的图片落附件库、日志只记 ref，卡上显示的是真图

- 状态：已接受
- 日期：2026-08-27
- 关联：issue #594；ADR-0009（附件库 / 视觉桥）、ADR-0140（工具组折叠头底下挂结果）、ADR-0141（写盘行数账落进日志而不是渲染层现算）

## 背景

会话里出现图片时，界面上什么都没有。

MCP server 返回的 `kind: "image"` content 在 `renderMcpContent`（`src/shared/mcp.ts`）里被折成一行字「(server 返回了一张 image/png 图片，本版不展开)」，字节当场丢弃。kling 的 `text_to_image`、blender 的 viewport 截图这类 server 已经在用户环境里，它们每次出图，Mr Otto 都只显示这一行字。

除 MCP 外，将来经会话调用的图片生成 API（Midjourney 之类）没有任何可落地的出口——不是"还没接"，是**没有地方可接**：`Tool.run` 的返回类型只有 `string | { output, concludesTurn }`，一个工具想交出一张图，类型上就交不出来。

## 决策

### 一、图片进附件库，日志只记 ref

`ToolResultEvent` 加可选字段 `images?: UserAttachmentRef[]`，图片本体进现成的 `AttachmentStore`（`src/session/attachments.ts`，内容寻址）。

**为什么不是 base64 直接进日志**：一张 1024×1024 的 PNG base64 约 1-2MB。日志是 append-only 的，撑爆了删不掉，而且每次重放、每次压缩扫描都要驮着它走。附件库是内容寻址的，同一张图重复产出天然去重；用户附件已经走这条路（ADR-0009），图片显示的 IPC 通道（`attachmentDataUrl`）也已经在。

**为什么复用 `UserAttachmentRef`**：名字里的 `User` 是历史（它出生时只有用户附件一种来源），形状是通用的——`{ id, mediaType, bytes, name? }` 里没有一个字段是"用户"专属的。为一个字段名另起一个逐字段相同的类型，代价是两处要同步改，收益只有名字好看。

代价（接受）：附件库文件丢了，日志重放出来的这条 `tool_result` 就指向一张不存在的图。这与 ADR-0009 对用户附件的取舍是同一条——UI 退成一张"图片文件已丢失"的空框，不炸时间线。

### 二、落库由中间件做，不由工具做

`Tool.run` 的对象返回形态加 `images?: readonly ToolImage[]`（原始字节）；`src/main/imageIntake.ts` 是一个中间件，跑在洋葱最外层，把字节存进附件库、换成 ref 挂在 `ToolOutcome.imageRefs` 上，由 engine 落进事件。

**为什么是中间件**：硬规则「工具实现只依赖 `ExecutionWorld` 接口，禁止直接 import fs」。附件库是 app 级资源（`EventStore` 同级），工具够不着也不该够得着。这条缝与 turnDiff 中间件填 `diffStat` 是同一条（ADR-0141）。

**为什么是两个字段（`images` 装字节、`imageRefs` 装 ref）而不是一个**：一个字段先装字节后装 ref，读的人没法从类型上分辨手里这份到底落没落盘。"以为落了盘其实没落"正是让日志说谎的那类错，而日志是唯一事实来源。

**没装中间件时静默降级**：裸装配和单测里图就地丢弃，工具调用照常成功，`tool_result` 的形状与从前逐字节一致（`"images" in result === false`）。一个展示层能力不该让工具调用整个失败。

### 三、base64 解码放在工具层，不放 shared

`imagesOf` 在 `src/tools/mcpTool.ts` 里用 `Buffer.from(data, "base64")`。不放进 `src/shared/mcp.ts`：那一层手机端（Expo/RN）会 import 同一份源码，而 `Buffer` 在 RN 上不存在——`tests/architecture.test.ts` 的第 5 条守的就是这条线。

### 四、元件显示的是真图，不是上游那坨渐变

vendor `elements-image-generation` 到 `src/renderer/src/components/elements/image-generation.tsx`。

上游那张卡**从头到尾没有 `<img>`**：generating 时画 8×8 点阵，完成态画一坨写死的 oklch 渐变。它是官网上的视觉演示，不是一个能显示图的元件。本仓拿它装的是工具真产出的图，所以：

- **收 `src`，完成态是图本身**；那坨渐变的位置降级成"ref 有了、data URL 还没读回来"的占位。
- **尺寸标签用 `naturalWidth × naturalHeight`**，读不到就不显示。上游写死 `1024 × 1024`——生成出来的图不一定是这个尺寸，而这行字的全部价值就是可信。
- **去掉 `aspect-square`**：出图不一定是方的。
- **去掉 Regenerate 按钮，改成点卡就地看大图**。本仓接不上"重新生成"——工具调用是模型发起的，那颗按钮点了没有东西可接，摆一颗点不动的按钮比没有按钮更糟。就地摊开的交互语义同 message-attachment / artifact-card 的本仓改动。
- **展开/收起不做动效**，只有图自己的 blur→sharp 淡入（上游 1000ms 收到 500ms）。时间线是刻意静止的界面；而且展开改的是尺寸 = 布局动画，既不便宜也不好看。

`generating` 这一档在本仓的语义是**"还没读回来"，不是"还在生成"**。刻意如此：工具跑起来的那一刻，谁也不知道它会不会产出图（工具名不是契约，`text_to_image` 这种命名只是碰巧），所以没有诚实的办法在结果回来之前画一个"正在出图"的占位。曾经考虑按工具名白名单猜——否掉了：猜错时界面上会凭空出现一个永远不会变成图的方框，那比没有占位更糟。

### 五、卡挂在工具组折叠头底下，与文件树平级

那棵树答"这一组动了哪些文件"（ADR-0140），这一排答"这一组产出了哪些图"。两者都是**结果**而不是过程，所以都常驻在折叠区外面——出图这件事的价值全在那张图上，藏进折叠区里等于没做。

抠图逻辑（`generatedImagesOf`）进 `src/renderer/src/aui/toolArtifacts.ts`，纯函数：那个文件的定位就是"一次工具调用到底产出了什么给人看"。

卡下面那行说明取参数里的 `prompt`，**只认这一个名字、只认字符串**。往下猜 `description`/`query`/`text` 会把"某次调用碰巧有个同名参数"也印到图上——那时候说明文字和图没有关系，比没有说明更糟。取不到就退回 ref 的名字（`imageIntake` 存的是 `<工具名>.<ext>`，至少说得出出处）。

## 范围外

- **模型看不看得到这张图**：视觉桥（`createVisionBridge`）是另一条路（ADR-0009）。模型收到的仍然只有 `output` 那段文字——但那句话改成了"已显示给用户，你自己看不到内容"，模型据此才知道自己可以就这张图和人对话，而不是以为这次调用什么都没产出。
- 正文 markdown 里的 `![](url)`。
- 手机端远程投影。

## 后果

- 任何工具想在时间线上出图，只需在返回值里挂 `images`，不需要碰 fs、不需要碰日志、不需要动渲染层。
- `src/renderer/src/lib/useAttachmentUrls.ts` 从 `UserAttachments.tsx` 里提出来：用户附件和工具产出的图走同一个附件库，内容寻址意味着同一张图在两处就是同一个 id，缓存本该共享。
- 旧日志没有 `images` 字段，照常重放（schema 向后兼容硬规则）。
