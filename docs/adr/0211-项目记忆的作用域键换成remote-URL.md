# ADR-0211：项目记忆的作用域键从「本机路径」换成「remote URL」

> 原为 ADR-0210（合并前撞号，ADR-0074）。提交信息里的旧号改不了，这一行是它的解析入口。

日期：2026-09-03
状态：已接受
关联：#886（Task）、ADR-0116（三档记忆 / 作用域键的第一版）、ADR-0207（记忆跟账号走，这条天花板出自它的「已知天花板」第二条）

## 背景

ADR-0207 把记忆搬上云之后，USER / MEMORY / TOPIC 三档真的跟着账号走了，**项目档没有**。
病根在键：项目档住在 `memories/projects/<sha16(项目根绝对路径)>/`。同一个仓库在甲机是
`/Users/a/Mr_Otto`、在乙机是 `/Users/b/code/Mr_Otto`，哈希出来是两个目录；云端老老实实
把两份都同步给两台机器，而每台机器的 `resolveProjectRoot` 只解析得到自己那把键，
另一把在设置页里显示成一个此机不存在的路径，永远读不到、也永远合不起来。

也就是说：项目档不是「同步得不好」，是**从来没有跨过机器**。

## 决定

**作用域键 = `origin` 的 remote URL 归一化后的 `host/path`；没有 remote 的仓退回项目根绝对路径。**

```
github.com/real-stanyan/Mr-Otto   ← 有 remote：所有机器上都是这一个字符串
/Users/a/scratch                  ← 没有 remote：退回路径，等于保持改动前的行为
```

`root.txt` 装的从此是**作用域键**而不是路径（`PROJECT_ROOT_FILE` 的注释里写着这一句）；
目录名仍是 `sha16(键)`，所以「目录名 = sha16(root.txt)」这条不变量对新旧目录都成立。

### 归一化的四条，各自对应一种「同一个仓在两台机器上写出两把键」的真实写法

| 做什么 | 为什么 |
|---|---|
| `https://` / `ssh://` / scp 短语法 三种写法折成一种 | `git@github.com:a/b.git` 与 `https://github.com/a/b` 是同一个仓 |
| 去掉 userinfo | `https://x-access-token:<token>@github.com/a/b` 里那段凭据每台机器都不同；顺带也不会把 token 哈希进目录名 |
| 去掉端口 | `ssh://git@host:22/a/b` 与 `git@host:a/b` 是同一个仓 |
| host 小写、**路径原样** | DNS 不区分大小写，所以 host 必须小写；路径不小写是保守选择——大小写敏感的自建 host 上 `/a/Repo` 与 `/a/repo` 可能真是两个仓，**合并两个不同仓的记忆（注入错内容）比拆开同一个仓（退回今天的行为）更糟** |

`file://` 与本地路径 remote（`git clone /srv/git/repo`）→ 认成「没有跨机身份」，退回路径。

### remote 现读 `.git/config`，不起 `git` 子进程

同 `branchFromWorktreeGitdir` 的理由（岛的每条事件都会重推一次 fleet，一个 `git` 子进程
在那个频率上付不起）。副作用是 submodule（`.git` 是文件）读不到 config → 退回路径，
与 `rootFromGitdir`「子模块不折叠」是同一个取舍。

### 旧目录：合并，不是覆盖；留墓碑，不是删除

`src/main/projectMemoryMigrate.ts`，开机跑一次 + **每次云端对账之后再跑一次**
（对账会把别的机器的旧目录也拉下来，只在开机跑就永远轮不到它们）。三条判断：

1. **只搬本机能解析出 remote 的旧目录。** 别的机器的旧目录（`root.txt` 里那条路径在本机
   不存在，读不到它的 `.git/config`）留在原地——它的归属只有那台机器说得清，猜不出来。
   代价写明：那台机器不升级，它那份就一直以旧键留在清单里，和今天一样。
2. **搬 = 两边条目取并集。** 两台机器会先后写同一把新键，覆盖就意味着后到的那台把先到的
   那台的项目记忆抹掉。并集靠 `parseEntries`（自带 trim / 去空 / 保序去重）。
3. **搬完在旧目录放一块墓碑（`merged.txt`），不删目录。** 这是全篇最反直觉的一条：
   云同步没有墓碑机制（`planReconcile` 里「本地有、云端没有」一律推上去），所以任何一台
   还揣着旧副本的机器都会把删掉的目录原样推回来，变成删了又回、回了又删的无限来回。
   加一个文件是幂等的，两边都收敛。**而且它同时解决另一个问题**：跑第二遍时墓碑让整个
   目录被跳过，用户在设置页手动删掉的条目才不会在下次开机被重新合回来。
   代价是旧内容在盘上和云端各留一份——换来的是上面这两条，值。

删项目时（`deleteProject`）连墓碑目录一起清：确认弹窗说的是「不可恢复」，就得真的不可恢复。

### 键与本机路径分开带，不是二选一

`{ id, root, dir }` 三件套一起传（`createMemoryTool` / `readTiers` / `memory_loaded`）：

- `id` = 作用域键 → 写盘、目录哈希、设置页那份清单的身份
- `root` = 本机项目根绝对路径 → 提示词里的「当前项目（…）」、`projectMentionInGlobal`
  的点名检测。模型写进记忆里的是它工作的那条路径，拿 `github.com/a/b` 去做子串匹配会漏
- `dir` = `memories/projects/<sha16(id)>`

`memory_loaded` / `memory_user_edit` 各加一个**可选** `projectScope` 字段（旧日志没有它照旧
重放，硬规则要的向后兼容成立）。**旧日志里 `projectRoot` 那个值就是它当时的键**——所以
主进程拿到一个「看起来像绝对路径」的键时会按今天的规则重解析一次（`isPathScopeId`），
否则恢复出来的老会话点「忘掉」会写回一个已经被并走的旧目录。

## 被否掉的路

- **root.txt 写成「remote + 本机路径」两行**（#886 正文里的建议）。否决理由：路径那一行
  每台机器都不同，而这份文件是同步的——甲机写一次、乙机改回去，两台机器互相把对方的
  行覆盖掉，白白在云端来回推。本机路径本来就现查得到（`resolveProjectRoot`），不必存。
- **迁移时删掉旧目录。** 否决理由见上面第 3 条：删除会被没升级的机器推回来，形成无限来回；
  而且用户手删的条目会在下次开机被重新合回来。
- **把路径也小写。** 否决理由见归一化那张表最后一行。

## 已知天花板

- **同一个仓换了 remote 地址**（改名、换 host、从 GitHub 搬到自建）= 换了一把键，项目记忆
  跟着断。没做重定向：判据不存在（新旧地址之间没有任何本地证据能把它们连起来）。
- **没升级的机器上的旧目录**不会被本机搬走（第 1 条），它会一直以旧键留在设置页清单里。
- **旧内容留在盘上和云端各一份**（第 3 条），不会自动清理。真要清，走设置页删项目。
- **开机那次迁移不挡会话装配**（`void migrateProjectScopes()`）。理论上存在一个窗口：迁移还没跑完就建了会话，
  那个会话的 `memory_loaded` 快照里项目档是空的。实际上会话只能由渲染层的 IPC 发起，而渲染层启动要几百毫秒、
  迁移是几次小文件读写——所以窗口存在但赢不了。没为它把整段 `whenReady` 改成串行 await：代价是每次开机都变慢，
  而这次迁移一辈子只跑一次。真被撞上的后果也只是那一个会话的提示词里少一份项目档，不丢数据。
