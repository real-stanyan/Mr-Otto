# ADR-0033：会话 id 是时间戳 + 随机段，随机段才是承重的那一半

日期：2026-08-19
状态：已接受

## 背景

会话 id 在 `src/main/agent.ts` 一直是秒级时间戳：

```
s-${new Date().toISOString().replace(/[-:TZ.]/g, "").slice(0, 14)}   // s-YYYYMMDDHHMMSS
```

同一秒内建两个会话就撞 id。后果不是「两个会话看起来一样」——
id 是 append-only 事件日志的分区键（`events.session_id`），撞车意味着
**第二个会话的事件 append 进第一个会话的日志**。日志不可编辑，事后没法干净地拆开。

发现于 PR #110 的终审（#111）：那个 PR 新加的「幽灵会话防护」用
`agents.has(sessionId)` 判存活，id 撞车是唯一能绕过它的路径。
但问题本身是既有的，跟那个 PR 无关。

## 决策

格式改为 `s-<14 位时间戳>-<8 位十六进制>`，随机段取 `randomBytes(4)`。

时间戳留着，但它的职责降级为「给人读」：日志文件名、issue 里贴 id、
列表大致按时间排。唯一性完全由随机段承担。

## 后果

- **旧日志不受影响**。全仓没有任何一处解析这个形状：`sessions()` 按 `lastTs DESC`
  排序而不是按 id，`resumeSessionId` 原样透传，测试里的 id 是 `s-x` / `s-old`
  这种任意字符串。旧 `s-<14 位>` 继续可读可重放（AGENTS.md 硬规则）。
  回归护栏钉在 `tests/main/agent.test.ts`「旧格式 id 照旧能恢复」。
- 32 位随机在「同一秒内」这个窗口上足够：撞车要求两个会话同秒创建**且**
  4 字节相同。会话由人手动新建，量级与生日悖论相去甚远。
- id 变长 9 字符。没有长度约束的消费方（SQLite TEXT 列，无上限）。

## 备选方案

**直接换 UUID。** 唯一性更强，但 id 从此不可读——排查线上问题时
「这条日志是什么时候的会话」要多查一次库。撞车的实际风险（同秒 + 同随机段）
用 32 位已经压到可忽略，为此放弃可读性不划算。否决。

**建之前查库确认 id 未被占用，撞了就重试。** 能给出确定性保证，但要给
`EventStore` 加一个只为这件事存在的 `exists()` 接口，并把「创建会话」
从纯函数变成一次 IO。收益（把可忽略概率压到零）配不上这个接缝。否决。
