# ADR-0256：被 @ 的人类成员真的收到提醒——一张收件箱表，三条送达路

- 状态：已接受
- 日期：2026-09-08
- 关联：issue #1064（ADR-0252「代价」第一条开的那一条，本条落地后那条已划掉）；协议 12→13；migration 0030；realtime 那条腿沿用 ADR-0027 的通知判定层与 supabaseFriendsApi 的订阅生命周期

## 背景

ADR-0252 让云会话的 @ 选人弹层认得人类成员。但 @ 一个人**只有一件事发生：名字进正文**。不起 turn，也没有任何提醒——被 @ 的人下次自己进来读到才知道。

维护者在 #1059 的问答里选的就是「要真通知（先只开 issue 不做）」，所以这条是那半个承诺。

不能顺手做的理由写在 #1064 的正文里：工作区**一条往成员那边推的通道都没有**。runtime 的广播只到此刻连在这条会话房里的 cid；桌面侧没有工作区级的未读概念；手机端的私信走的是另一套。

不过 #1064 那段判断里有一条前提是错的，而验前提这件事（ADR-0134）恰恰是本条最省力的一步：**realtime 这条腿早就在**。`supabaseFriendsApi.subscribe` 已经用 `postgres_changes` 订着 friendships / messages 两张表，`friendNotifier` 是一整套「通知是打断不是日志」的判定层（只在窗口没聚焦时发、点它落到哪个面板），`pendingAttention` 是 dock 角标。私信那条路的形状与这件事**逐字同构**：一张表、一条 INSERT 订阅、一条通知、一个未读数。

## 决策

### 1. 落在哪：一张新表，且它是日志的投影

`workspace_mentions`（migration 0030），一行 = 一次点名，主键 `(uid, session_id, seq)`。

**为什么不复用事件日志**：云会话的权威日志在 VPS 上，桌面够不着——要先开一条那个工作区的会话房才读得到 backlog。而「你不在的时候有人喊你」这件事，**恰恰只发生在你没开着它的时候**。角标必须在一条会话都没开的时候就画得出来，所以数据得落在桌面直连得到的那一侧，也就是 Supabase。

这不违反「append-only 事件日志是唯一事实来源」：这张表是 `user_message{fromUid}` + 那一刻这句话点到的成员的一份**投影**，整表丢掉、重放日志能重新算出来。

**主键取三元组不另造 id**：daemon 重启补跑、写入重试都可能把同一条开场白再写一次，主键天然幂等（`upsert` 而不是 `insert`——23505 走 throw 那条路的话，一次完全正常的重放会被记成告警）。

**写方只有 runtime（service key），表上不给 authenticated 的 insert / delete**：给 insert 就是让任何在籍成员替别人伪造一条「有人 @ 了你」；给 delete 则让「读过了」与「从没发生过」变成同一件事。能改的只有 `read_at`，且只能改自己那行。

**读要在籍**：`wsmn_select_self` 的判据是 `uid = auth.uid() **and** is_ws_member(...)`。退了群的人不该继续读得到群里的正文摘要，与「踢人 = 关门」（ADR-0199 的 `requireStillMember`）是同一条。行本身留着不删——重新拉回来的人该看见那段历史。

**`from_label` / `excerpt` 是写入那一刻的快照**，不现查 profiles。回头看「那天是谁喊我、喊的什么」不该被后来的改名改写。这与 `usage_event.agent_id` 记 id 不记名（ADR-0221）方向相反而理由对称：那边要的是「改名不断账」，这边要的是「当时的措辞不被改写」。

### 2. 谁写：runtime 的 `say()`，且 `resolveTargets` 一个字不改

`resolveTargets` 回答的是「起几条 turn」——那是花钱的那一格，人类 uid 在那儿一直是被静默过滤掉的，也应该继续是。@ 一个人**不起 turn、不花钱**。

所以协议 12→13：`say` 帧多一格 `memberMentions`（uid 数组），与 `mentions`（agent id）**分开带**。合成一格再让服务端去分，等于要求服务端认得出哪个 id 是人——它手上只有 agent 名单。

**为什么服务端不自己从正文里认**：认得出人类名字要先有一份成员**显示名**的名单（`profiles.name`，一次 Supabase 往返），于是「@小红算不算点到小红」就有了第二份判据——而客户端那份是用户**看得见**的（弹层里那一行、chip 行）。两份迟早分家，界面说点到了、服务端说没有。同 ADR-0220 坑 ④。

**客户端不是权威**，服务端两道闸：`hostUids()` 复核在籍（挡「@ 一个不在这个群里的人」），`uid !== fromUid` 挡 @ 自己。最坏情形下一个恶意客户端能做的，只是给他本来就能发消息的那几个人多推一条提醒，而 say 令牌那道粗闸（ADR-0230 #968）照旧按帧扣。

**收件箱写入排在入队之后、`startDrain` 之前**：turn 起跑不等这次网络往返，而 `say` 的回执等它——写完再回 ok，测试与真机才不用去猜那一行落没落（fire-and-forget 那版在进程收摊时还会丢）。**写失败只记一行日志**：权威那份已经落盘，把一句已经发出去的话翻成失败更糟。

`mentionInbox` 是**必需**的 dep（同 memory / agentWriter / isMember 的纪律）：忘接线该编译不过，而不是安静地跑一条「@ 了人但谁都没收到提醒」的会话——那正是这条 issue 要拆掉的东西，而它的失败模式本来就是无声的。

### 3. 撞名归 agent 的判据是**位置**，不是名字前缀

ADR-0252 定的规则是 agent 与成员撞名时归 agent 接（成员显示名来自 `profiles.name`，从没过 `agentNameConflict` 那套前缀检查），弹层上那格灰字「@ 会点到智能体「X」」就是这句话的界面版。

要在发送侧复现同一条规则，直觉写法是拿 `memberShadowedBy`（成员名以 agent 名开头）去过滤。**它只覆盖一个方向**：反过来——agent「小红助手」+ 成员「小红」，正文 `@小红助手`——成员那一遍照样在同一个 `@` 上匹配到「小红」，而「小红」不以「小红助手」开头，于是小红被通知了一次她根本没被点到的名。

所以 `parseMentions` 补一个带位置的孪生函数 `parseMentionSpans`，`parseMemberMentions` 的判据换成**同一个 `@` 的位置归谁**。两个方向一起对，且不引入第二套切词——它与 `parseMentions` 是同一次扫描的两半（同 ADR-0252 拒绝拿 `mentionTokens` 比字符串的理由）。

`memberShadowedBy` 留在原处不动：它答的是另一个问题——「如果你点这一行，那个 @ 会落到哪」，是一个静态的、只看名字的预测，画在列表上。

### 4. 怎么送到人：三条路，且 realtime 不是唯一的一条

- **推**：`workspace-mentions-<uid>` 一条 `postgres_changes` INSERT 订阅，filter `uid=eq.<我>`，挂在 `supabaseFriendsApi.subscribe` 里当第四条通道。**住在那套订阅里不是因为它跟好友有关**——它跟好友一点关系都没有；住在那里是因为「登录 → 建订阅 → 断线重连 → 登出拆掉」这套生命周期只有一份，另起一套就要把它抄一遍，而抄错的那次失败是无声的。
- **拉**：开机一次 + **每次窗口重新聚焦**一次。**不做定时轮询**——会看到角标的那一刻必然是人回到这扇窗前，`focus` 就是那个信号（同 pxAuditSync 不做定时轮询的取舍）。
- **通知**：`workspaceMentionNotification` 走 ADR-0027 那套聚焦判定与点击落点，`NotificationTarget` 加一档 `workspaceMention`（点它打开那条云会话，两格 id 都要——`openCloudSession` 按 (workspaceId, sessionId) 进房）。**带提示音**（Ping）：被点名是「有人在等你」，跟一条群里的闲聊不是一回事。

**这条订阅的状态故意不并进好友那份健康度**：那一格画在好友面板上、名字叫「好友实时连接」，而这张表是工作区的；更要紧的是 0030 还没在真库跑过的那段时间里这条通道会一直报错（表不在 publication 里），并进去等于让一次没跑的 migration 表现成「好友功能连不上」——ADR-0223 部署顺序那条教训。代价是它挂了这一层不说话，兜住它的是上面那条拉取。

### 5. 角标画两处，dock 那个也算

侧栏工作区**组头** + **会话行**各一枚。两处都要：组头收起来的时候会话行根本不在屏幕上，只有组头那一格能说话；展开之后又必须指出是**哪一条**会话，否则人得一条条点开找。

**组头那枚收不收起来都画**——旁边那个条数（`rows.length`）只在收起时报，因为展开就数得出来；未读数展开也数不出来，它不是这份列表的函数。

颜色取 `--brand` 不取 `--warn`：被 @ 不是「出事了」，而本仓 warn 这个语义是留给出事的（ADR-0240 那笔账已经让 Max 徽章借走一次形，不能再借第二次）。**不做入场动效**：它是个挂着的状态记号不是一次事件（同 ADR-0255）。

`pendingAttention`（dock 角标）把未读点名加进去——它问的是同一个问题「有人在等你吗」，而被点名比一条私信更明确地在等一个人。

`unreadMentionCounts` 在 section 那一层算一次往下传，**不在每个组里各 select 一次**：它每次都造新对象，写进 zustand 的 selector 就是一个真的死循环（`useSyncExternalStore` → Maximum update depth exceeded，测试里复现过）。

### 6. 进了那间房 = 看见了，且 @ 自己不算

`openCloudSession` 里本地先灭角标再发出去（乐观），失败时下一次拉取会把它变回来；反过来（等回执再灭）在断网时会让一条已经读过的会话永远顶着角标。这一步排在 `join` **之前**：它只碰收件箱、不依赖房间连没连上，而连接失败时人确实已经点开过它了。

`markMentionsRead` 那道 `is("read_at", null)` 条件不是优化：没有它，重开一条早就读过的会话会把当初的 `read_at` 改写成此刻，而那一列记的是「什么时候看见的」。

**@ 自己不落行**。选人名单里仍然有自己（ADR-0252 决策 1）——那份答的是「认不认得这个名字」，这里答的是「要不要惊动他」。两个问题，两个答案。

### 7. 开局卡那一句也算

那一屏（`CloudWelcome` → `CloudSessionMain` 的补发）没有选人弹层，但正文里的 `@小红` 与 composer 里那一句是同一件事。只在 composer 那条路上通知，就是同一个动作按入口不同给两种结果。判据用同一份 `parseMemberMentions`。

## 代价 / 已知天花板

- **只做桌面**。手机端读得到这张表（RLS 对它一视同仁），但没有推送凭据那一层，所以手机上今天什么都不会发生。
- **agent 写的 @ 不通知人**。`relayAfterTurn` 那条路不解析成员名字——一只 agent 在正文里写 `@小红` 今天没有任何效果。这是一个独立的能力（「agent 求助于人」），不是本条的漏做；#1055 已经定过一条相关的纪律（模型写的 @ 与人写的 @ 是两件事）。
- **`markMentionsRead` 是整条会话一起标已读**，不是逐条读回执。开一条 200 条消息的会话、@ 在第 5 条上，滚到底看到的是最新那几条——标准聊天语义，代价接受。
- **收件箱拉取失败静默降级成「没有未读」**。不落 `workspaceGroupsError`：那一格是整页共用的，一次角标查询失败盖掉别处一条真正需要人看的错误更糟。兜住它的是 realtime 与下一次聚焦重拉。
- **excerpt 把一段正文摘要复制进了 Supabase**。今天工作区的会话正文只在 VPS 上，这是第一次有一小段进 Supabase。只有被 @ 的本人（且在籍）读得到，没有扩大可见范围；但「那张表能读到什么」这条线从此不再是纯元数据。
- **0030 要手动执行**（同 0021 / 0023 / 0026 的约定），且**没跑之前 realtime 那条通道会一直报错**——已经把它挡在健康度之外，但控制台会有一行 warn。
- **真机没验**：要部署 runtime（协议 13）+ 在真库跑 0030 + 两个账号各起一台 app 才看得到全链路。本条落地的断言是纯逻辑 + sessionService 的服务端复核 + 侧栏角标的 jsdom 渲染，realtime 那一跳与系统通知那一跳一次都没在真机上跑过（跑法见记忆里那条 `cloud-ui-smoke-needs-runtime-deploy`；另需 #791 的 VPS 重新部署）。
