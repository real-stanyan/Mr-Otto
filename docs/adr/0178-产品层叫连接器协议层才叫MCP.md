# ADR-0178：产品层叫「连接器」，协议层才叫 MCP

- 状态：已接受
- 日期：2026-08-29
- 关联：issue #706；起因是 #661 / ADR-0171 把目录做进了「MCP」栏目；反例出处 ADR-0166（好友代理借来的服务）；词条落在 `CONTEXT.md` 产品/技术术语一节（ADR-0070）

## 背景

#661 把连接器目录做进了设置页的「MCP」栏目。做完之后那个栏目是这样的：

```
设置 → 「MCP」                    ← 栏目名 = 协议名
   ├ mcp.json 解析报错            ← 真·协议层
   ├ 连接器目录（精选 + 长尾）    ← 产品层
   └ 已装的服务列表               ← 产品层
   右上「新建 MCP server」        ← 真·协议层（手打 URL / 命令）
```

三块里两块是产品层，而用户看到的第一个词是协议名。同时 `McpDirectory.tsx` 的用户可见文案已经在说「搜索连接器」——两个词在同一屏上并存，谁也没定义过。

`CONTEXT.md` 里有 MCP、MCP server、transport 的词条，**没有「连接器」**——#661 引进了这个词、写进了用户可见文案，没人加进词表（ADR-0070 要求产品概念也进词表）。

## 决定

**分界线：能发现、能点、能装的那一面叫连接器；要你懂传输方式的那一面才叫 MCP。**

落地三处：

1. `CONTEXT.md` 补「连接器（Connector）」词条，并写明它与 MCP 的关系
2. 设置页栏目 `label` 从 `"MCP"` 改成 `"连接器"`（`settingsShell.tsx`）。**内部 id 仍是 `mcp`**——它是 store 的键，不是给人看的
3. 协议名保留在真正指协议的地方，**不动**：「新建 MCP server」对话框（它问的是 stdio 还是 streamable-http、命令还是 URL，这里出现协议名是准确的）、`mcp.json` 解析报错、审批卡上标工具来源（`MCP · <server>`）

## 连接器 ≠ MCP，尽管今天重合

- **MCP 是协议**：stdio / streamable-http、tools / resources / prompts，Otto 只做 client 那一半（ADR-0049 / 0050）
- **连接器是产品层的名字**：一台你可以接进来的外部服务。目录卖的是 *Notion / GitHub / Figma* 这些名字

今天在本仓两者外延恰好重合。**那是实现的偶然，不是定义**，两个方向都掰得开：

- **是连接器但不是你自己配的 MCP server**：ADR-0166，好友代理借来的服务按好友短标签加前缀合并进会话。用户眼里那就是「接进来的东西」，但它不是你机器上的一条 `mcp.json` 记录
- **是 MCP server 但不是连接器**：右上「新建」手打 URL 建的那台。它没进目录、不在策展层里；目录卖的是可发现、有名字的条目

以后接一个不走 MCP 的内置集成（直连某个 REST API），它在用户眼里照样是连接器——那天两个词就真的分开，而这份 ADR 已经把位置留好了。

## 被否掉的

- **拆成「连接器」和「MCP」两个栏目**：会把「Notion 装好了」和「Notion 这台的传输方式 / 授权状态」放进两个地方，用户找一台服务要去两处翻。目录和已装清单是同一件事的两半——目录页本身就是那个空状态，上一版的空状态块因此被删掉（`McpSettings.tsx` 里那处注释）。拆开是**把词汇问题当导航问题解**，代价比病重。
- **什么都不做，只补词条**：词表修好了，用户看到的第一个词还是协议名。词条是给写代码的人看的，栏目名是给用户看的，前者救不了后者。
- **连「新建 MCP server」一起改成「新建连接器」**：那个对话框逐字段问的就是协议细节（stdio / streamable-http、command / url）。把协议名从那里拿掉，用户面对 `command` 和 `url` 两个字段时反而没有词可以挂——协议名在这里是准确的，不是泄漏。

## 后果

- 用户可见文案里，「MCP」从此只出现在他确实需要理解协议的地方。发现与安装这条主路径上一个协议名都没有
- 栏目 `label` 是 e2e 的选择器（`openSettings(win, "连接器")`），改名会让 `tests/e2e/mcpDirectory.e2e.ts` 红——**这是好事**：说明那一层真的在盯用户可见文案，而不是在盯内部 id
- `id` 与 `label` 从此可以不同名。`settingsShell.tsx` 那处注释写明了原因，避免下一个人"顺手对齐"
- **推翻它的前提**：如果 Otto 决定不再有非 MCP 的接入方式、且把协议本身当成对用户的卖点（像开发者工具那样），那么用协议名当栏目名重新变得合理。今天的判断建立在「以后会有不走 MCP 的连接器」这个预期上
