# ADR-0285：时间线窗口挂载

- 状态：已采纳（2026-09-10）
- Issue：#1190
- 原为 ADR-0284：分支期撞号——#881（划词引用 chip）先合入拿了 0284，本文件按
  项目 ADR-0074 改号 0285；提交信息里的「ADR-0284」字样改不了，以本行为准

## 背景

真机实测（#1190）：2555 条事件的会话（投影出 624 条 UI 消息）首渲 400–500ms。
渲染管线是 store `enterChat` 全量塞 events → `buildOttoAdapter` 每帧
`toThreadMessages(events, live)` 全量投影 → assistant-ui `ThreadPrimitive.Messages`
**按 index 作 key 全量挂载**，每条 assistant 消息的 text part 过 Streamdown
（remark/rehype 全量解析）。首渲大头 = 624 条消息的首挂载解析；
`content-visibility:auto` 已经在消息根上，它只省布局/绘制，**JS 解析照付**。

流式期间还有一层放大：`toThreadMessages` 每次返回全新对象引用，assistant-ui 的
`ThreadMessageConverter`（WeakMap，按输入对象身份缓存）每 token 全 miss，
每 token O(n) 全量转换。

调查时核对过的「全量挂载」消费方只有三处：① SectionRail 的 scrollspy 与跳转
（锚点是挂在消息上的零高度 `data-section` div）；② 跟随流式输出
（`turnAnchor="bottom"`，只依赖 scrollHeight 不依赖锚点）；③ 划词引用
（只能选已挂载的内容）。没有 find-in-page、没有滚动位置记忆、没有未读 pill。

## 决策

### 1. 窗口活在渲染层，不进 store、不进投影

`store.events`、`enterChat`、`toThreadMessages` 的输出语义一个字不动——assistant-ui
的 runtime 里仍然是**全量**消息（`thread.messages` 一条不少），只有 thread.tsx 的
DOM 挂载切成后缀窗口。判据是这件事的性质：「此刻渲染到哪」是视图状态不是会话事实，
而窗口只要碰 store/投影，所有读 `events`/`messages` 的既有消费方（deriveSections、
usage、enterChat 的整份测试面）就都要重判一次「它看到的是全量还是窗口」。放在渲染层，
存量测试一行不改。

### 2. 后缀窗口：只增不缩 + 顶部哨兵 + 手动滚动补偿

`src/renderer/src/lib/messageWindow.ts`（纯函数）：首窗 `INITIAL_WINDOW = 60` 条
（624 条的首渲 400–500ms，60 条把首渲压回几十 ms 量级，同时仍是好几屏）、
哨兵一次补挂 `GROW_STEP = 60`、总数 ≤ 90 的小列表完全不启用窗口（行为与开窗前
逐字相同，连哨兵都不画）。

- **只增不缩**：滚上去补挂了的，滚下来不卸。卸载重挂等于把那条消息的 Streamdown
  解析钱再付一遍（解析才是大头，挂载不是），且挂载/卸载都动 scrollHeight，
  人正在读的位置会跳。代价：长会话翻到顶之后整个前缀都挂着——那是用户已经把
  解析钱付过了的状态，留着不亏。
- **哨兵**：消息组顶部一个「显示更早的消息（还有 N 条）」行，IntersectionObserver
  （root = 视口，向上提前 200px）可见即补挂一档；IO 缺席（jsdom）或失效时，
  那一行本身就是可点的按钮——两种环境都有一条走得通的路。
- **手动补偿**：prepend 会把视口里的内容往下顶。`useLayoutEffect` 在 paint 前量
  「补挂前第一条已挂载节点」的 `offsetTop` 位移（key 是消息 id，prepend 前后是
  同一个 DOM 节点），`scrollTop` 瞬时补上。**不量 scrollHeight 的差**：同一次提交里
  流式消息可能还在往底部长，会被一起算进来。视口上有 `scroll-smooth`，直接赋
  scrollTop 会被动画化（补偿变成一次看得见的漂移），必须 `behavior: "instant"`。
  只叠一层：Chromium 原生 scroll anchoring（`overflow-anchor` 默认开，assistant-ui
  与本仓 CSS 都没关它）管的是 `content-visibility` 消息的**延迟尺寸修正**；这里管
  prepend 这个**结构性**变化，两者量的对象不同，不冲突。

### 3. 分区跳转拆两条路：快路径不动，慢路径走 reveal 桥

`jumpToSection`：锚点已在 DOM → 原地 `scrollIntoView`（与窗口化之前逐字相同）；
不在 → App 置 `revealRequest = { section, nonce, sessionId }` 传给 OttoThread，
OttoThread 反查 `buildSectionAnchors` 建好的 `anchorsByMessageId`（第一个挂着这个
分区的消息 = 目标；**对齐判据只有 buildSectionAnchors 那一份**，reveal 是低频动作，
O(消息数) 扫一次无所谓，不另写一份 startSeq 比较——两份并存，漂移那天不会报错）
调 `revealHidden` 把窗口上沿抬到包含它，下一份 effect（依赖 hiddenCount）发现目标
已进窗口后 querySelector + scrollIntoView + 收口。smooth / reduced-motion 分支与
快路径同一条。

`sessionId` 那一格是复审抓出来的真 bug：清理残留请求的一道 effect 放在 App，而
React 的 passive effect **子先于父**跑——切会话那一帧，OttoThread 的 reveal effect
会先于 App 的清理 effect 看到旧会话留下的请求，拿旧分区号去解新会话的 sections。
所以请求自带发起时的 sessionId、OttoThread 消费前核对（判据是自己算得出的事实），
App 那道清理降级为纯卫生。判定抽成 `messageWindow.ts` 的 `planReveal` 纯函数，
OttoThread 的 effect 只执行它的计划（stale / settle / grow / scroll 四选一）。

scrollspy 在窗口截断下有一个新边界：首个**已挂载**锚点仍在判定线下方时，说明视口
停在窗口上沿那段——那段内容属于第一个已挂载锚点的**前一个**分区（分区是连续
划分的，锚点之前归上一区），`active` 兜底成它；`first === 0` 时维持 null
（与窗口化之前「还没进任何分区」同义）。另外补挂会把新锚点挂进 DOM，scrollspy
effect 靠 OttoThread 的 `onWindowChange` 回调重新收集——否则新锚点不在
IntersectionObserver 的观察名单里，补挂出来的那段分区永远不会高亮。

### 4. 身份保持：append-only 前缀复用，复用边界画在 turn 边界上

`toThreadMessages` 加模块级缓存（事件日志 append-only 是硬规则，两次调用之间
events 要么原样、要么尾部追加、要么整份换掉）：

- 同一份 events 引用 → 投影原样复用（连同**数组引用**——运行时对
  `oldStore.messages === store.messages` 有整段短路）；
- 尾部追加 → 只从最后一个「无未收口 turn」的 ResumePoint 起重放，已收口前缀
  **复用原对象引用**。同一 turn 的多条 assistant_message 合并成一条 UI 消息，
  turn 进行中新事件还会续进它，所以未收口 turn 的合并消息永远重投，边界画在
  turn 边界上。ResumePoint 带当时的 `turnAgg`/`turnStartTs` **原值**——
  `turn_ended` 不清账，崩溃日志里 assistant_message 可以紧跟在 turn_ended 后面，
  全量投影会拿着上一个 turn 的账继续累，续投必须给出逐字相同的答案；
- 防御分支：追加段里的 `tool_result` 若属于一条**已收口**的消息（「结果与调用
  同 turn 落盘」这条引擎不变量破了），不搞局部重投，直接全量重来，慢而不错；
- live 缓冲不在日志里，只影响尾部 `id:"live"` 那条，与事件投影分两层缓存——
  所以 OttoThread 的 `buildSectionAnchors`（调 `toThreadMessages(events)` 不带
  live）与 adapter 共享同一份事件投影，第二次调用近似零成本。

配套的一个不显然的硬约束：`ottoAdapter` 的 `convertMessage` 必须是**模块级常量**。
运行时（`external-store-thread-runtime-core`）发现 `convertMessage` 换引用就把
ThreadMessageConverter 整个丢掉重建——内联闭包每次 `buildOttoAdapter` 都是新引用，
身份保持会被它当场作废。

正确性靠对拍钉住：`tests/renderer/toThreadMessages.test.ts` 里 200 份伪随机日志
逐步 append-only 增长，每步与全量重投逐字段深相等（覆盖度断言按住「turn 中追加」
与「迟到结果」两条岔路，同 `tests/shared/turnLedger.test.ts` 的纪律）。

### 5. 用 assistant-ui 的 unstable 接缝，不自造、不引库

渲染缝用的是 `unstable_useThreadMessageIds` + `ThreadPrimitive.Unstable_MessageById`
（key = 消息 id，前缀补挂时既有消息一行都不重挂）。两个 API 标了
@deprecated（unstable/experimental，随时可能变）——thread.tsx 的头注写明：升级
assistant-ui 时先核对他们还在不在，不在了就把窗口退回 `ThreadPrimitive.Messages`，
功能先撤，不带病升级。

否掉的另外两条：

- **自己造 index-key 窗口**（继续用 `Messages` 但只喂后缀）：prepend 会让所有
  index 移位，既有消息全部重挂 + 重解析——补挂一次付一次全量的钱，正是要修的
  病本身；
- **引 react-virtuoso 等真虚拟化库**：加依赖 = Tech stack 改动（L1）；且变高行
  （工具组折叠/展开、图片懒取、content-visibility 延迟尺寸）要靠占位估算撑高，
  估算失真会让贴底跟随抖动，`followOutput.e2e.ts` 的「跟随/松手」语义会碎。

## 否掉的方案

- **真虚拟化（只挂视口 ± 余量）**：上面第 5 条已述——变高行 + 跟随语义 +
  撑高估算三者合不来。窗口方案把「挂载过就留下」当特性而不是浪费。
- **`content-visibility` 了事**：它已经在消息根上，实测首渲仍是 400–500ms——
  它省布局/绘制，**不省 JS 解析**（Streamdown 的 remark/rehype 在挂载时照跑）。
- **窗口进 store / 投影层**：见决定 1，那会把「读到的是不是全量」这个问题
  摊给每一个消费方。

## 已知代价

1. **SelectionQuote 选不到未挂载的内容**——视口外的消息不在 DOM 里，划词引用
   只能划窗口内的。收窄是接受的：引用本来用于「指着屏幕上这段话」。
2. **跳到很老的分区那一刻才付那段的解析钱**（reveal 桥抬窗口 → 一次性补挂
   中间所有消息）。首渲省下的钱没有消失，是推迟到「真要看」的那一刻；
   哨兵提前 200px 触发缓和了滚动上去的体感，跳转没有提前量。
3. **scrollspy 兜底是近似**：首个已挂载锚点仍在判定线下方时，active 取它前一个
   分区——窗口上沿以上若跨了多个分区，分不出具体哪一个（都显示为紧挨窗口的那
   个的前一区）。
4. **首挂载（scrollTop 还是 0、跟随滚动还没落地）那一帧哨兵在视口内，可能多补
   挂一档**（60 条，一次）：补完哨兵就远在视口外，不会连锁。把「刚挂载」这个
   状态从 IO 的视角里抠出去要引入第二条判据，不值为这一次 60 条。
5. **窗口挂上后的长会话形态没有真机/e2e 验收**：窗口缝本身有 jsdom 集成测试
   （`tests/renderer/threadWindow.test.tsx`——只挂后缀、哨兵计数、按钮兜底），
   `followOutput.e2e.ts`（跟随/松手）与 `streamingCaret.e2e.ts` 在真 Electron 里
   过了，但那些会话都很短、窗口不启用；长会话的补挂、滚动补偿、reveal 桥只在
   纯逻辑层与人工推理下验过。真机验收点：开一条几百条消息的会话 → 首渲应明显
   变快、初始贴底；滚到顶 → 自动补挂且阅读位置不跳；分区轨跳到窗口外的分区 →
   应滚到位且高亮跟上。
6. turn 边界与上一事件之间若夹着审计事件（model_changed 等），它们在每次续投里
   跟着尾部重投、对象身份每次换——内容不变，只是这几行会多过一遍转换器。量级
   是一行两行，不换实现复杂度。
