# ADR-0027：好友系统的推送兜底与牌局邀请

日期：2026-08-19
状态：已接受

## 背景

好友系统（ADR-0071，原 0014）把三件事都挂在 Supabase Realtime 一条链路上：关系链变更、私信、在线状态。
线上这条链路是**断的**——`/realtime/v1/websocket` 经 Kong 返 503（issue #77），
而且这个故障在客户端表现为"好像没人给我发消息"，不是一个报错。
好友列表全灰、私信要手动刷新才看得见，用户只会得出"这软件时灵时不灵"的结论。

同时缺一个功能：约好友上牌桌。牌桌只有 accepted 好友能同桌（ADR-0022 决定四），
但"叫人"这一步一直没有产品动作——两个人得在别的地方约好了再各自点进来。

## 决定

### 一、推送有两条腿，Realtime 只是快的那条

主进程的 `FriendsManager` 持有一个健康度状态机 `connecting | live | degraded`：

- 四条 Realtime 通道（friendships / messages / game_invites / presence）**全部** `SUBSCRIBED` 才算 `live`；
  任一条报错、超时或关闭，整体判 `degraded`。
  理由：只有 messages 哑掉时，好友列表照刷、聊天却静悄悄——那是最难察觉的坏。
  宁可多轮询，也不要"看着正常但其实哑了"。
- `degraded` 时起 5 秒轮询：关系链全量快照 + 收件箱增量（`id > 水位`）+ 邀请列表。
  收件箱水位在 `start()` 时定为当前最大 id，所以轮询只补此刻之后到达的消息，不会把历史当新消息推一遍。
- `degraded` 时每 60 秒重建一次订阅：Realtime 修好了要能自己爬回 `live`，而不是等用户重新登录。
- 健康度推给渲染层，好友区如实显示"实时推送不通，已切轮询兜底 · 消息会慢几秒"。
  能力不足是事实，藏起来只会变成用户对整个产品的不信任。

### 二、在线状态取并集：presence ∪ 心跳窗口

新增 `profiles.last_seen_at`（migration 0006）。客户端每 30 秒写自己一行，
读好友那一批；`now - last_seen <= 90s` 判在线。最终在线集 = Realtime presence ∪ 心跳窗口。

理由：presence 依赖 websocket，心跳只需要 REST。websocket 那条路断了（#77 的现状）时，
在线点仍然是准的。窗口取心跳间隔的 3 倍，漏一两拍不判下线。
`degraded` 时主动清空 presence 那一半——连不上的通道报不出谁下线了，
留着它只会留下一屋子假在线。

### 三、邀请是持久化的行，不是瞬时广播

新增 `game_invites` 表（inviter / invitee / table_id / table_name 快照 / status / expires_at）。

- 不用 Realtime broadcast：broadcast 是瞬时的，对端 app 没开就永远收不到；
  而"约你打牌"必须能落盘等人回来看。何况链路本身就不可靠（决定一）。
- `table_name` 冗余存快照：被邀请人不一定看得见那张桌的行（`poker_tables` 的 RLS 只放行
  自己建的 / 坐着的 / 好友建的），但邀请卡上得写清楚是哪张桌。
- 过期是**投影不是状态**：`expires_at` 到点了 UI 自己不显示，不需要定时任务去改 status。
- RLS：仅当事双方可见；只能以自己名义邀且必须已是 accepted 好友；
  被邀请人 `pending → accepted/declined`，邀请人 `pending → cancelled`；
  列级 grant 只放行 `status`（否则被邀请人能把 `table_id` 改成任意一张桌）。

### 四、接受邀请**不代付买入**

点"去牌桌"只做两件事：切到 game 档、订阅那张桌。买入仍然要用户在牌桌页自己按。

理由：买入花的是真 token（ADR-0021），一个通知上的按钮不该是花钱的按钮。
邀请卡上明写"买入在桌上再确认"。

### 五、系统通知只在窗口没聚焦时发，且只发新增

主进程 `friendNotifier` 判定：窗口聚焦 = 不打断（UI 里的角标已经说明问题）。
好友请求/邀请是**全量快照式推送**，不做差集会把同一条反复弹成通知，
所以按 id 取相邻两次快照的差集；第一份快照视为"补课"，一条都不弹。
登录态变化时把差集基线清零，换号后不会把一屏历史请求当成新事件。

dock 角标数由渲染层算（只有它知道哪个面板开着 = 哪些已读），经 `setBadgeCount` 报给主进程。

## 后果

- 好友系统不再依赖 Realtime 可用。#77 修好之前，功能是慢的（5 秒级），不是坏的。
- 代价：`degraded` 时每 5 秒三个查询、每 30 秒两个心跳查询。自托管实例、好友量级在两位数，
  这个量可以接受；真要长起来，第一步是把轮询间隔按空闲时长退避。
- `messages` 的 insert 改为 `.select().single()` 回真行，渲染层因此能做乐观气泡
  （回车即上屏，落库后换成实条，失败标红留在原地）。少一次"发完再拉一整页"的往返。
- migration 0006 需要手动执行（`supabase/README.md`），执行前邀请功能会报表不存在。
