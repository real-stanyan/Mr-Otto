## 一、`MAX_CONNS_PER_USER` 数的是房间不是人（#824）

**事实**：DO 的 `fetch()` 里那句 `existing.length >= MAX_CONNS_PER_USER`，数的是**一个房间
里的连接总数**。自远程的房间键就是 userId（`edge.ts` 的 `roomKey`），两者碰巧相等，所以
这个名字撒了三个版本的谎都没露馅；好友代理房间只有两个人，也照样成立。`cs-ctl` 是全平台
**一个固定房**（`csCtlChannel()`），于是这个上限的实际含义变成「全平台同时最多 16 条人类
连接进控制房」——一个人握住 16 条 socket，所有人都建不了云会话，而且失败长成 503，
不长成「谁在搞事」。

**否决了 issue 自己提的方向**（把控制房拆成 `cs-ctl-<uid>`）：relay 只在双方 attach 时各写
一条 `:peer`，**不排队**——runtime 必须在客户端连上来之前就已经在那个房里，而它没有任何
信号知道该去谁的房间开连接。拆房于是只剩两条路：给每个用户常驻一条 WebSocket（数量随
用户数线性增长），或者给 VPS 开一条入站 HTTP 面（二期从头到尾避开的东西）。两条都比这个
bug 大。

**采用**：让 DO 按人分桶数数，分桶键由 `edge.ts` 算好递下去。**不递 uid**——好友代理房间的
设计前提正是「中继不懂参与者是谁」（ADR-0151，鉴权在握手层），把 uid 递进 DO 等于顺手
拆了它。递的是 `sha256(roomKey + " " + uid)` 的前 64 bit：同一个人在同一个房间里稳定相同，
跨房间对不上号，DO 拿它只能做一件事——数数。第三个 tag 是**运行时行为**（`acceptWebSocket`
的休眠语义 + `getTags` 的位置约定），单测里那个照着 worker.ts 写的假 DO 覆盖不到，所以这
一条是打真 workerd 验的（`wrangler dev --local` + `checks/relay.mjs`，28 条全绿）。

**什么前提失效会推翻它**：relay 长出「有人在敲 X 房间的门」这类通知，或者 runtime 有了
入站面——那时按 uid 拆房就成立了，比共用一个 DO 更好（现在全平台的 create 都排在一个
Durable Object 上，这是个已知的吞吐天花板，不是安全问题）。

## 二、限流的三档与「拒绝要看得见」（#819）

过渡期烧的是**维护者的模型 key**（ADR-0199 spec §6，额度强制执行留三期）。在此之前三条路
一道闸都没有：无限刷 @Agent 烧 key、无限追加事件撑大 VPS 的 SQLite、无限建会话（每条 =
一行 Supabase + 一个常驻房间 + 一份 EventStore）。

形状照 ADR-0167 那道现成先例（好友代理执行器的并发 + 令牌桶）：

- **桶按 uid 分，不按 cid**：按 cid 分等于「多开几条连接就能多刷几次」，那不是限流是计数器。
- **一帧只记一个桶**：`@Agent` 走 turn 桶（每条都可能起一次真花钱的模型调用），普通发言走
  say 桶。不双记——双记会让「补一句上下文」这种正常形态莫名其妙地更早撞墙。
- **被限流的一个时段只记一笔**：日志本身不该成为第二个能被刷爆的东西（同 ADR-0167）。
- `rateLimit` 在 `FrameHandlerDeps` 里是**必需**不是可选：一个「忘了接线」的默认值等于把
  闸门悄悄拆了，这种东西该靠编译错误、不该靠记性。

**拒绝要看得见，而且两个房间用的回执不一样**：控制房的 create 回 `denied: rate_limited`
（新码，协议进位 v3）——`create()` 只认 created/denied 两种回执，回 error 等于让它白等满
超时；会话房**不能**回 denied——客户端把 denied 当终态（`markDenied` 直接断掉连接），而
限速是「待会儿再来」，两者语义相反，所以会话房回 `error` 帧。

顺带补上 error 帧的最后一公里：它原来**只进主进程日志**，用户那边彻底静默（消息凭空消失，
和「网断了」长得一模一样，而这两件事该做的动作相反）。现在随状态推送捎一个一次性的
`notice` 给渲染层，落进 CloudSessionPage 已有的那格人话里。

**什么前提失效会推翻它**：三期的计费落地之后，这三个桶应该退化成「防脚本」那一层，真正的
额度由账本说了算（跨进程、跨重启）；现在这套是进程内、重启即忘的，它拦的是脚本不是节俭。

## 三、归档：谁能按，以及「广播本身就是回执」（#822）

spec §2 生命周期的第 4 步一直是空的：`archive` 分支是**显式 no-op**，`workspace_sessions.archived`
这一列建了、daemon 启动按它过滤，但没有任何代码写它。

三层各管一段，边界与这个仓库其余部分一致：`sessionService.archive()` 只碰日志；daemon 写
Supabase 那行 + 收房间（只有它同时握着 supabase 句柄和 transport）；frameHandler 判权限。

三个判断：

1. **谁能按 = owner 或建这条会话的人**。云端没有「恢复归档」那一半（daemon 启动只捞
   `archived=false` 的房间重开），所以这是个不可逆动作，不能让任意成员替所有人按下去。
   判据在服务端；客户端那颗按钮的显隐只是 UX——渲染层不是安全边界。「建的人是谁」用清单
   那一行本来就有的 `publisherUid`，不为它再往协议里加字段。
2. **成功不回执**：`session_archived` 广播给房里每个人，那就是回执，而且是所有人都看得见的
   那一份。渲染层据此收页 + 刷清单——**判据是日志里那条事件，不是「我刚点了归档」**：谁点的
   都算，而且投影从日志推导（同一条硬规则）。只有「没生效」才需要单独说一句。
3. **先落一条人话再落状态事件**：`session_archived` 自己没有「谁干的」字段（ADR-0087 的形状，
   单机时代不需要），群里其他人只看到会话消失是很糟的体验。走 `chat_message` 与 clone 结果
   通报同一条路，客户端不必为「系统消息」另做一套。

关房间**延一拍**（2 秒）：`ws.close()` 之后排队的帧还发不发得出去是实现细节，不该赌。这期间
会话已经不在 `activeSessions` 里，新来的帧一律 `no_session`，没有「趁机往已归档会话里说话」
的窗口。

## 四、`transport.send` 回 boolean（#829）

`wsTransport.send` 有四条**不抛异常**的丢帧路径：连接已关 / 没有收件人 / socket 还没 open
（含**正在自动重连**这个完全正常的窗口）/ `sock.send` 自己抛错。四条全都只 log 一句就
return，而接口签名是 `: void`——于是调用方那里「发了」和「没发」长得一模一样。

改成回 boolean（先例：`proxyConnection` 的 `sendSealed`，ADR-0167）。它**不是送达确认**——
中继收没收到、对端解没解开这一层都不知道；它只把「压根没交给 socket」这一半从成功里
择出来。**多数调用方照旧忽略它**：聊天/投影帧丢一条人看得出，而且重连后中继会重发
`:peer`，下一轮自会补上。真正吃亏的是「用户点完就不再看」的写操作——`config` 本来要挂满
15 秒等一个永远不会来的回执，`create` 本来白等满超时才回一句「云端无响应」，把「我们没
发出去」说成「对面没回话」，方向反了，人会去查 VPS。

## 五、read_file 的上限按字节（#823）

上一版是 200_000 **字符**，于是这个上限根本不保证「这条事件发得出去」：满上限的纯 ASCII
结果 JSON 实测 200,112 字节（已超 frameHandler 的 128 KiB 分片阈值），中文 600,112 字节。
「无界」只变成了「有界但仍可能超限」。改成按 UTF-8 字节截、上限 128 KiB，切点退到完整
码点边界（按字节硬切会在正文里凭空长出一个 U+FFFD，比截断本身更难排查）。

第二半：直播扇出遇到超限事件只 `console.error` 后静默丢，而 backlog 那条路早就会回一条
可见占位。**同一件事在两条路上给出两种可见性**——客户端不做 seq 缺口检测，直播流里那个洞
只有重新 join 才看得见。`globalSend` 的编码失败分支补一条同样的占位帧。

## 六、磁盘配额：先验前提，再决定做不做（#836）

#836 的正文写着「这台 runtime VPS 现在没法验」。**这个前提是错的**，而它读起来像调查结论
（正是 ADR-0134 说的那种）：`scripts/runtime-deploy.mjs` 用的就是 2222 端口那台机器，SSH
免密可达。只读探针的结果：

```
docker info | grep -i "storage driver"   →  Storage Driver: overlayfs
df -T /var/lib/docker                    →  /dev/md2  ext4
```

overlayfs + **ext4** ⇒ `--storage-opt size=` 用不了（只在 backingfs 是 xfs + prjquota 时被
接受，ext4 上 docker 直接报错）。所以真配额剩下两条路，都要动宿主机：① 每个卷一个 loop
挂载的 ext4 镜像（内核级配额，但要在宿主上 truncate + mkfs.ext4，daemon 现在没有「在宿主
执行命令」这个能力面）；② 把 `/var/lib/docker` 迁到带 prjquota 的 xfs 上。两条都不该顺手
塞进这一批，#836 留开着。

**这一批里做的是 `--depth 1`**：卷仍然没有配额，但一个仓库最容易失控的部分是**历史**不是
工作树（linux/chromium 这种 `.git` 比 checkout 大一个量级）。代价是 `git log`/`git blame`
只看得到 tip，而这一条**水獭自己解得开**——云会话的系统提示里连解法一起给
（`git fetch --unshallow`）。只说限制不给解法，模型会以为这是个新仓库或者 blame 坏了。
