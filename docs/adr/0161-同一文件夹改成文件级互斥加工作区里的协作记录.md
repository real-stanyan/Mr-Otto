# ADR-0161：同一个文件夹改成**文件级**互斥 + 工作区里的一本协作记录

- 状态：已接受
- 日期：2026-08-28
- 关联：issue #658；回答 #654；**收窄 ADR-0152 / 0155 的适用范围**（git 仓保留，非 git 目录改走本条）；ADR-0157（成因）；ADR-0160（提示语随之调整）

## 背景

ADR-0152 的互斥是**文件夹级**的：同一个工作区，同一时刻只跑一条 turn。

危险却是**文件级**的。一只水獭写提案、一只写预算，同一个文件夹，两件事从头到尾不相干——却被一刀拦了。当初选文件夹级是因为拿不准（「只拒绝，不做魔法」），不是因为它是对的粒度。

ADR-0157 之后这道闸只对**非 git 目录**生效（git 的各自拿独立副本，根本撞不上）。也就是说：它只拦得住最不需要被拦、也最不懂为什么被拦的那批用户——把一堆文案放在一个文件夹里的人。

维护者的话：让 Mr Otto 也能并行跑，但在项目文件里留一个多 agent 交流口，好让 agent 们知道文件为什么变动了。

## 决策

非 git 目录上，文件夹级的闸拆掉，换成三件东西。

### 一、工作区里的协作记录

`Mr Otto 协作记录.md`，落在**工作区根目录**，明文，一条一行：时间 · 谁 · 哪个文件 · 一句为什么。

**为什么在工作区里，而 ADR-0155 的锁刻意不在。** 那把锁是纯噪音——会进 `git status`、会被误提交、人读了也没有任何收获，所以放机器级临时目录。这个本子反过来：它的全部意义就是**被看见**，人和水獭都要读。同一个「放哪儿」的问题，两个相反的答案，因为两件东西的读者不同。

**为什么结构化而不是自由聊天。** free-form 会长成没人读的墙，还吃上下文。字段固定，注入时才能按文件筛出「只跟你有关的那几条」。

**「为什么」哪来的。** `write_file` 多一个可选参数 `reason`，水獭自己写；没写就退回会话标题。这是这条 ADR 里最便宜也最值钱的一处：没有它，本子只能回答「谁动了什么」，而维护者要的是「为什么」。

### 二、按需注入

读到一个别的水獭最近动过的文件时，在 `read_file` 结果尾巴上补一句「它被谁改过、为什么」。

**不是每轮把整本喂进去**——本子会长，上下文不跟着长。

### 三、文件级的闸：拦一次，要求重读

要覆盖的文件在「我上次看过它」之后被别的家族改过 → 拦一次，`write_file` 压根不执行，错误信息里写清是谁改的、为什么、下一步去 `read_file`。

**不同文件一律放行。这是整条 ADR 的重点。**

维护者在三个选项里选的这一个（另两个：谁后写谁算数；都写、被盖掉的进检查点）。理由：不丢字，代价只是偶尔多一次往返。

**为什么只拦一次。** 模型收到错误后的默认反应是重试。每次都拦，一个不肯重读的模型会原地死循环，把一次协作问题变成一次挂死。拦一次已经把事实摆到它眼前（谁改的、为什么、去重读）；它坚持要写，那是带着完整信息做的决定。

**为什么「我从没看过它」也拦。** 那是闭着眼睛覆盖别人的新文件，恰恰最该拦。代价是会话重启后第一次覆盖会多挨一拦——而这是对的：重启之后我手上那份内容确实是旧的。

**同家族不互拦**（子会话 / SideChat）：它们共享工作区是故意的，父 turn 跑着的时候子会话就在跑。沿用 ADR-0152 的豁免。

### git 仓那一格不动

工作区在 git 仓里 → ADR-0152 / 0155 的文件夹级互斥**原样保留**。

判据一条：`repoOf(workspace) === null` 才走本条新路。

为什么不一视同仁：`git checkout` 抹掉的是 `.git` 里的状态，而文件级的闸看不懂 shell 命令。正常路径上这道闸根本不会响（各自拿独立副本），它只在副本建失败那一格兜底——那一格恰恰是最需要保守的。

ADR-0160 那两条提示语随之补一句「正常情况下每只水獭都拿一份独立工作副本，这次没建成」：它现在唯一的读者变成了「副本建失败的人」，不说这句他不知道系统本来打算怎么伺候他。仍然不提 git 术语。

## 落地上的两个选择

**用 `node:fs` 的 `appendFile` 写，不走 `world.fs`。** `ExecutionWorld.fs` 只有 read/write，用它就得读改写——而这个本子存在的全部理由就是两个进程同时在写，读改写会互相覆盖，正好把要解决的问题重现一遍。`O_APPEND` 内核保证小块追加不交错。这不是越过围栏：本子在工作区根目录、本来就在围栏之内，写它的是主进程的记账逻辑而不是工具（硬规则不动，先例是 imageIntake）。

**裁剪在两倍上限才触发。** 裁剪要整份重写，会和别的进程此刻的追加撞。触发点放宽 = 重写更少 = 撞上的机会更少。极小概率丢掉并发写入的一两行，接受：本子是近况，不是事实来源（事实在各自会话的 append-only 日志里）。

## 天花板（说在前面）

**`bash` 里的 `mv` / `rm` / 重定向覆盖不到。** 管线看得见 `write_file` 的参数，看不懂一条 shell 命令要动哪些文件。

这个洞是真的，接受它的理由：git 仓那条路不靠这套东西（各自拿独立副本），非 git 的文案文件夹里这类命令本来少见，而 Claude Code 在同一格上连 `write_file` 都不拦。

子会话 / SideChat 的写入不进本子（它们与父会话同家族，本来就不互拦），所以第三方水獭看不到它们改了什么。后续可补。

## 后果

- 两只水獭在同一个文案文件夹里各写各的文件 —— 从「第二只直接被拒」变成「都能跑」。
- 撞上同一个文件时不丢字，且双方都知道为什么。
- 用户的文件夹里多出一个明文文件。这是**故意的**，抬头第一句就写了它是什么、删掉不会坏事。
- 推翻这条的前提：本子被证明是噪音（用户第一件事就是删掉它），或者文件级的闸在真实使用里响得太频繁——那说明「两只水獭同一个文件夹」这个用法本身就不该鼓励，该回到「一只一个文件夹」的引导。
