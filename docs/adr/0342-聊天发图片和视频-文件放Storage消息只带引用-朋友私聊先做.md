# ADR-0342：聊天发图片和视频——文件放 Storage、消息只带引用，朋友私聊先做

日期：2026-10-04 · issue #1443（P1）· 维护者拍板设计稿 v1 的 8 条全部按推荐

## 决定

1. **文件放 Supabase Storage，不走中继分片**。两个私有 bucket（migration 0052）：`dm-media`（朋友私聊）、
   `chat-media`（云会话，P2 起用，策略这次一并建好）。中继单帧 256 KiB，传一段视频要分片加重传，
   而 Storage 的 RLS 在 0014 / 0036 已经有先例可抄。
2. **路径就是权限判据**。`dm-media`：`<发送方>/<接收方>/<uuid>.<扩展名>`，写要求第一段是自己、第二段是已接受的好友
   （同 messages 的 insert 策略），读是收发双方；删了好友之后旧消息里的图照样读得到。`chat-media`：
   `<团队>/<会话>/<sha256>.<扩展名>`，在籍成员或这条会话的客人，且会话真的属于路径里那个团队。
   判据里不把路径段 cast 成 uuid：乱写的路径只会「对不上」，不会让整条语句抛错（同 0043）。
   两个 bucket 都没有 update 策略，客户端一律 `x-upsert: false`。
3. **朋友私聊：`messages.media`（jsonb，1..9 个）**。纯媒体消息的 body 写占位 `[图片]` / `[视频]`，0001 那条
   body 1..4000 的 check 一个字不动。老客户端、会话列表第二行、推送正文都照常读 body，自动显示成「[图片]」——
   降级由构造保证，不靠每个读者各自认得新的一格。新客户端带着解析得出的媒体、且正文就是占位时才不画字。
4. **那一格逐格验，一处不对整份丢**（`parseDmMedia`）：形状、格式、字节数，以及每个对象键（含封面）都要落在
   `<发送方>/<接收方>/` 下。RLS 只管「读的人读不读得到」，一条消息引用了读者恰好读得到的、另一段对话里的对象，
   库不会拦。整份丢掉时那条照画占位正文，说的仍是实话。
5. **上限**：一条最多 9 样；图片长边 2048、≤4MB，沿 `imageFit` 的阶梯一级一级试（同一张表，两端同一个画质），
   HEIC 一律转 JPEG（桌面解不了、模型不收），小的 JPEG/PNG 原样传（截图不白转一道把字糊掉）；视频 ≤60 秒、≤50MB，
   MP4 / MOV。50MB 也写在 bucket 的 `file_size_limit` 上（Supabase Free 档单文件上限就是 50MB）。
6. **一次挑了好几样：图片攒成一条（满 9 换下一条），视频一条一个**（`planMediaMessages`）。一段视频加几张图
   在一个气泡里没有好的排法，而视频是要点开看的东西。
7. **先传文件、再写消息；半路失败把已传的收掉**（`sendMediaMessage`）。反过来对方会先收到一条点不开的消息；
   不收的话就是 bucket 里没人引用的孤儿，而私聊永久保留（第 8 条），孤儿永远没人收。视频封面传不上去不算失败。
8. **上传不把文件读进 JS 内存**：先要签名上传地址（这一步按 insert 策略判权限），再由 `expo-file-system` 的
   `File.upload` 原样 PUT——头与 storage-js 的 `uploadToSignedUrl` 对原始字节那一支逐格相同，另带 `apikey`
   （这条请求不经过 supabase-js 的 fetch）。读用 `createSignedUrls` 批量签、一小时、同一个对象一直拿同一个地址
   （RN 的 Image 按 URL 缓存，每次重签就是每次重下）。
9. **这一期只走热更新**：只用原生包 1.0.1 (4) 里已经有的模块（image-picker / image-manipulator / file-system /
   video / crypto），图标补三个是生成的 JS。视频封面用 `expo-video` 的 `generateThumbnailsAsync` 抽第一帧，
   5 秒抽不出来就不带封面。
10. **读私聊带 media 列，库上没有这一列时退回不带它的查询**（`missingMediaColumn` 只认 42703 / PGRST204 且提到
    media）：部署顺序反了也只是看不到图，文字照常。

## 代价

- **真机一次没跑过**：签名上传地址 + `File.upload` 的 PUT 能不能过网关、`generateThumbnailsAsync` 在刚建的播放器上
  能不能直接抽帧、PHPicker 认不认 `videoExportPreset`（已标 deprecated）都没在设备上验过；mobile tsc 与单测是绿的。
- 拍摄用 `videoQuality: Medium`（画质偏低）：High 档一分钟 1080p 大概率超 50MB。相册挑的转成 H.264 1280×720，
  一分钟仍可能超 50MB，超了在挑完那一刻说「视频超过 50MB」。
- 本地气泡只活在内存里：App 在上传途中被杀掉，已经传上去的那几个文件就是孤儿（没有消息引用、永远不删）。
- 桌面（P5 之前）看到的是占位文字「[图片]」/「[视频]」，看不到图。
- 云会话那一半（协议 23、runtime 入库、代读员、生命周期）在 P2～P6，`chat-media` 这次只建了 bucket 与策略。
- 部署顺序：**先跑 0052、再发手机热更新**。反过来：读私聊退回不带 media 的查询，发图片时上传被「bucket 不存在」拒掉，
  输入栏底下说一句「服务器还没准备好收图片和视频」，不出别的事。0052 尚未在生产执行。
