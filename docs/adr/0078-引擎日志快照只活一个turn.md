# ADR-0078 引擎日志快照只活一个 turn

日期:2026-08-24
状态:已接受
关联:issue #277(勘察自 #275,权衡体系接 ADR-0077)

## 背景

engine 的 loop 每圈(= 每次模型调用)`store.load` 全量 SELECT + 全量 JSON.parse +
deriveMessages 全量投影 + contextUsed 全量估算。15 个工具调用的 turn 就是 15 遍,
跨会话生命周期 O(事件数×步数)。

## 决策

1. **快照增量维护,但只活一个 turn**:首圈全量 load,之后每圈
   `load({ afterSeq: 快照尾 seq })` 补尾段;runTurn 的 finally 里丢掉。
   issue 里的原方向是"引擎持有本会话的内存事件数组、自己 append 的直接推进去",
   这里刻意改了两点:
   - **不跨 turn 持有**:agent 注册表里同时活着一堆会话,每个引擎常驻整段日志
     (几 MB 的工具输出)是拿常驻内存换查询。turn 内攥着是纯赚(把 O(n×步数)
     压成 O(n + 步数×尾段)),跨 turn 攥着是租金。
   - **自己 append 的也不直接推进快照,统一走尾段补齐**:带外追加(分类/建议/
     改名这些异步外挂)拿到的 seq 可能插在引擎两次 append 之间,内存里自己合并
     就要处理乱序;让 store 的 seq 定序,一条尾段查询天然有序,少一类 bug。
2. **barren 集合每圈算一次,穿给投影和占用估算**(deriveMessages / contextUsed
   各加一个缺省自算的可选参数,absorbedIndexes 已有同款先例):两边本来就必须是
   同一把尺子,现在连算都只算一遍。

**代价**:每 turn 首圈仍是一次全量 load——跨 turn 的 O(n) 没消掉,只把 turn 内的
乘数消掉了。**为什么可接受**:每 turn 一次全量正是今天 UI resume、compact 等
所有路径的既有基线;消掉它需要常驻缓存 + 失效协议(purge/compact/多写者),
复杂度和内存都不成比例。
**推翻前提**:若真实用户出现"单 turn 内存峰值过高"(快照 + 投影同时在手)或
"每 turn 首圈全量 load 可感知卡顿"的案例,再评估跨 turn 常驻 + 显式失效。

## 验证

等价性以"每次模型被调时,引擎喂的投影 === 此刻全量重读再投影"为定义,
回归测试钉在 tests/loop/engine.test.ts(含带外追加中途进投影、跨 turn 快照重建)。
