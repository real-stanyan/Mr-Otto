## 背景

桌面和手机都在 NAT 后面，中间必须有一个公网可达的会合点。仓库里已有
`services/gateway`（Hetzner VPS，验 Supabase JWT，nginx 已关 `proxy_buffering`），
但那台机器是**我们运维的**——把会话标题、待审批命令的全路径明文交给它，
等于把"人不在电脑前"这个场景里最敏感的一段内容托管给一台随时可能被入侵的 VPS。

不用 Supabase Realtime 做中继：broadcast 不落盘，手机冷启动拿不到快照。

> **订正（2026-08-25，迁云之后）**：本条的理由需要换一半。`2797488` / `84fb628` 之后，
> 库已从自托管 docker 栈迁到 Supabase Cloud 项目 `kpeemypbhkynapkjzewr`，自建栈退役。
> 于是「自托管链路不可靠」（ADR-0027 / 0055，#77 静默死了半个多月）这条前提**对本决定
> 不再成立**——Cloud 的 Realtime 不由我们运维，它的历史故障记录不能拿来推断。
>
> 但结论不变，理由改成一条**不依赖谁在运维**的：**broadcast 不落盘**。中继要的是
> 「桌面在线时点对点转字节 + 手机一连上就拿到当前快照」，而 broadcast 只保证在线者收到
> 此刻发出的消息，冷启动的手机拿不到任何东西。要补这个洞就得在服务端存快照，
> 那正是「网关零落盘」这条不变量拒绝的事。
>
> 另一半（不上 WebSocket）与迁云无关，仍成立：nginx 的 `proxy_set_header Connection '';`
> 掐 upgrade，且网关零运行时依赖。


## 决定

1. **网关是盲管道。** `/rl/v1/stream`（SSE 下行）+ `/rl/v1/send`（POST 上行），
   两端对称。它只做三件事：验 Supabase JWT 认出 `user_id`；把同一 `user_id` 名下
   桌面与手机的字节互转；手机不在线时按桌面递来的信号帧发一条 APNs。
   **不解析负载、不落盘、不打印**——三条都是安全性质，都有测试守着
   （"负载从不进日志"那条是专门写的：三个月后有人为调试加一行 `console.log(payload)`，
   端到端加密就漏了）。对端不在线时字节直接丢弃，不排队——排队就是落盘。
2. **传输是 SSE + POST，不是 WebSocket。** 两条硬理由：
   `deploy/otto-gateway/nginx-gw-location.conf` 的 `proxy_set_header Connection '';`
   直接掐死 WS upgrade；网关目前零运行时依赖，加 `ws` 破了这个性质。
   代价是 `proxy_read_timeout 600s`，下行必须有远短于它的心跳（现取 25s）。
3. **握手每连接一轮，形状约等于 Noise KK。** 双方各生成一对**临时** X25519，
   用静态 Ed25519 身份密钥签 `角色 || 设备 id || 临时公钥 || 自己那半个 nonce`
   （角色进签名，是为了让"把桌面的 hello 转发给另一台桌面"这类反射攻击签不过）。
   会话密钥 `HKDF-SHA256(X25519(ephPriv, peerEphPub), salt=connectionNonce, info=方向标签)`，
   两个方向各一套密钥 + nonce 前缀。得到前向保密（临时密钥每连接一换）+ 双向认证。
4. **配对走 TOFU，不扫码。** 需求是按账号配对。账号配对与 E2E 天然打架：
   密钥若从账号体系下发，掌握 Supabase 的人就能发一把假的，中间人当场成立。
   折中是首次信任——手机首次连某台桌面时把它的 `identity_pub` pin 进本地，
   之后对不上就**拒绝连接并红字告警**，不静默接受；换电脑要用户显式确认一次。
   两端角落各显示一个 6 位指纹，想核对的人自己核，不强制。
5. **唯一新增的持久化是 `devices` 表**（`user_id` / `device_id` / `kind` /
   `identity_pub` / `kx_pub` / `push_token` / `label` / `last_seen`，RLS 只准读写自己的行）。
   公钥进库是故意的，私钥永远不进——身份私钥走 macOS/iOS Keychain，
   **不沿用 `src/main/keyVault.ts`**（那是 `userData/keys.json` 0600 明文文件，
   对 API key 是既定权衡，对身份私钥不够）。

## 后果：挡住了什么，没挡住什么

这一节写全，包括不好看的部分。

| 威胁 | 结论 |
|---|---|
| 被动读盘/读内存的服务器 | 拿不到明文 ✅ |
| 服务器或网络**主动篡改运行中的连接** | 签名 + AEAD 挡住 ✅ |
| 服务器在手机首次 pin **之前**下发假公钥 | **中间人成立** ❌ |
| 元数据（何时有会话、何时卡审批、推了多少字节、两端何时在线） | **网关可见** ❌ |
| **重放一个旧连接的 hello** | 只能浪费一次连接，解不开任何东西 ⚠️（见下） |

第三、四行是"不扫码"和"E2E 不覆盖元数据"的固有代价，接受并记录。
要堵第三行只能补带外验证（扫码 / 强制核指纹）。

第二行**曾经是假的**：`remoteBridge.onHello` 原先不看 phase，重放一条 hello 就能让桌面
拿没换过的临时密钥重新派生出**同一把**会话密钥，而封装器又从 `counter=0` 重新起算 ——
同 key 同 nonce 加密两段不同明文，`c1^c2 = p1^p2` 直接还原桌面→手机的明文，
Poly1305 的一次性密钥也一并泄漏（连帧伪造都送）。已修：ready 之后一律不收握手包，
合法的重新握手只走 `onClose → startHandshake()`。这件事本身值得记下来 ——
**这个模块从两个不同方向踩过同一个 nonce 复用的坑**。

## 会推翻它的前提

- **transcript binding 是缺的，且这一版补不了。** 双方的签名各自只覆盖**自己**的
  临时公钥和 nonce 半段，不覆盖对端的；握手也没有 key-confirmation 那一个回合。
  后果：一条从过去某次连接录下来的 hello，**永远验得过签名**——它是当时那台设备
  真签的，而签名里没有任何东西能说明"这是哪一次连接"。
  修掉 `onHello` 的 phase 门之后，重放者仍然拿不到会话密钥（没有当时那把临时私钥，
  算不出共享秘密），所以这只是一次被浪费的连接，不是失密。
  但要说清楚：**这里的认证强度只到"连接新鲜度"为止，而本方案没有一个回合可以用来检查新鲜度。**
  现在就写下来，是为了别等 Expo 客户端把它变成真问题时才重新发现。
  真要补，两条路：签名覆盖完整 transcript（含对端 hello），或加一个
  key-confirmation 回合（各发一帧用会话密钥封的固定串）。后者更简单，代价是多一个 RTT。
- **若要防主动作恶的服务端**：TOFU 不够（威胁模型第三行），得补带外验证。
- **若一户要接多台桌面或多台手机**：现在的中继是"一户一桌面一手机、同角色重连顶掉旧的"。
  多设备会让"该发给谁"变成一个需要路由的问题，中继就不再是纯粹的盲管道。
- **若 Realtime 将来能给出「冷启动能拿到当前快照」的语义**（不只是 broadcast）：
  中继可退回去省一个端点。迁云之后稳定性不再是障碍，真正挡路的是 broadcast 不落盘
  —— 见上面的订正块。
