# ADR-0152：同一个文件夹，同一时刻只跑一条 turn——只拒绝，不做魔法

- 状态：已接受
- 日期：2026-08-28
- 关联：issue #620；#543 / ADR-0149、#623 / ADR-0150（同一个洞的仓库侧）、#449
- 相关 ADR：0031（ExecutionWorld seam）、0092（ExecutionWorld 的安全边界）、0116（记忆的项目作用域把 worktree 折叠回主仓）

## 背景

Mr Otto 的定位是「每个 bot 是一只有独立沙箱的水獭」。沙箱 = `ExecutionWorld` 圈定的**文件系统路径**。

但 git 的状态不在路径里，在 `.git` 里。两只水獭指着同一个工作目录时，一边 `git checkout` / `git reset`，另一边的未提交改动就无声消失了——**围栏一个字都拦不住**，因为那条命令的 cwd 完全合法（`src/tools/bash.ts` 的 cwd = 工程文件夹；`src/world/checkpoints.ts` 直接 spawn git 二进制，两条路都能改共享 `.git`）。

这不是假想。本仓自己的 agent lane 已经踩过三次：#543（改动被 `git checkout` 无声重置三次，同一批改动以不同 SHA 落在两条分支上）、#449（prune 删掉另一条活 lane 的分支）、#616（同一需求做两遍）。修法是 ADR-0149/0150：一次性 worktree + 主 checkout 只读 + 机制兜底。

但那套是**给会读 AGENTS.md 的 agent 立的规矩**。用户的水獭不读 AGENTS.md。我们自己踩的坑，就是产品未来给用户的坑，区别只在于我们能写协议、用户不能。

## 决策

**同一个工作区，同一时刻只允许一条 turn 起跑。撞上就拒绝，不做任何补救动作。**

### 与 git 自己同构：只拒绝

git 不会替你把分支挪到别处，它只说：

```
fatal: 'main' is already used by worktree at '/Users/stanyan/Github/Mr_Otto'
```

这里照做：不自动开 worktree、不自动换目录、不排队等待。只是不让第二条 turn 起跑，并说清楚谁占着、为什么拦、怎么继续（`conflictMessage`）。理由是补救动作都要替用户做出他没做的决定——自动开 worktree 会改掉围栏根，进而影响检查点、项目指令、记忆作用域；自动排队会让「发出去的消息什么时候真的跑」变成不可预测。拒绝是唯一一个不需要猜用户意图的选项。

### 判据是「turn 在跑」，不是「会话存在」

两个会话指着同一个文件夹但都闲着，什么事都没有；真正会互相踩的是**同时执行**。

这个选择还有一个附带好处：**机制自己维护自己**。没有需要 release 的锁——状态就是 `runningSessions`，问一次就有答案。忘记解锁、进程崩溃留下死锁这类失败模式根本不存在。

### 同家族不互斥

子会话（`spawnedBy`）和 SideChat 与父会话共享 workspace 是**故意的**（`startSideSession` 就是拿 `from.workspace` 开的），而且子会话本来就在父 turn 跑着的时候跑。所以互斥按**家族**算，不按会话算：顺着 `spawnedFrom` 爬到家族根，同根之间放行。

### 落点

- `src/shared/workspaceExclusion.ts`：纯函数（`turnConflict` / `familyRootOf` / `conflictMessage`），零 IO；
- `src/main/index.ts` 的 turn 起跑处，紧挨着已有的 `runningSessions.has(sessionId)` 那条自检——同一类判断放在同一个地方，别散成两处。

## 为什么不选另外两条（issue #620 列的）

| 候选 | 否决理由 |
|---|---|
| `ExecutionWorld` 检测到工作区是 git 仓就自动开一次性 worktree | 改掉围栏根会连锁影响检查点（影子 git 的落点）、`project_instructions`（按工作区爬升）、记忆作用域（ADR-0116 把 worktree 折叠回主仓，那是为**读**设计的，不是为「我们替用户造了一个 worktree」设计的）。而且它替用户做了决定：他可能就是想在主 checkout 上干活 |
| 划到 v2 的 Docker per bot 一起解 | v2 会顺带解决，但 v1 用户现在就能把两只水獭指到同一个文件夹。等一个大改造期间保持已知的数据丢失风险，代价不对等。且本 ADR 的互斥在 v2 之后仍然成立——容器隔离的是文件系统，两个容器挂同一个宿主目录照样撞 |

## 后果

- 接受：两个会话在同一文件夹里**交替**工作时，第二条消息会被拒一次。这是有意的摩擦——它正好是让用户意识到「这两只水獭在抢同一个目录」的那一下。
- 接受：拒绝发生在消息发送时刻，不是打字时刻。更早的提示（composer 上的常驻警告）留给 UI 层，本 ADR 不做。
- 不覆盖：**跨进程**（两个 app 实例，比如 dev 版和正式版指着同一个文件夹）。`runningSessions` 是进程内状态。要覆盖得上文件锁，那是另一件事，等真出现再说——现在写下来，免得下一班以为已经防住了。
- 不覆盖：同一个仓库的**不同 worktree**。那是安全的，git 自己保证同一分支不会被两处 checkout，两个目录的 HEAD 互不影响（ADR-0149 的整个论点）。
