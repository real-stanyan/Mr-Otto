# ADR-0147：@好友 fork——跨账号一次性快照共享

- 状态：已接受
- 日期：2026-08-28
- 关联：issue #612；ADR-0141（日志是唯一事实来源）、ADR-0055（好友在场）、ADR-0009（附件/快照本机引用）

## 背景

用户想要一个 `@` 功能：在桌面端输入框 `@好友`，把**本次会话**同步给这位好友，好友那边把这份同步作为一个 fork 继续执行。`@好友` 后面可以留一句话，交代好友的 fork 去干什么。

本仓已有 fork 机制（`store.fork`，`session_created.forkedFrom`），但它是**本机单库**语义：父会话和分支同库，`load()` 沿 `forkedFrom` 链读父前缀，`purge()` 的 fork 保护查询假定 fork 链同库。跨账号同步撞上三个硬约束：

1. 好友机器上没有源会话（父不存在），`forkedFrom` 链读不到；
2. 事件日志里混着本机引用（`checkpoint_created`/附件 ref 指向本机快照库/附件库）和纯审计/隐私事件（`reasoning`/`usage`/`request_envelope`/`memory_loaded`），跨机全是死链或不该给别人的东西；
3. sessionId 本地生成（`s-<时间戳>-<随机>`），跨机无全局唯一性协调。

## 决策

### 1. 同步内容 = 「投影所需最小事件集」，不是字面的「模型视野」

「只同步模型可见事件」不够：`deriveMessages` 的正确性依赖几个**模型不可见但投影需要**的事件——`turn_ended`（`barrenEventIndexes` 的空跑判定）、`skill_released`（`activeSkills` 台账）、`context_compacted`/`micro_compacted`（压缩投影）、`tool_execution_started`（悬空工具自愈）。漏了它们，接收端投影会失真。

导出时按白名单保留 + 字段级剥离：

| 事件类型 | 处理 | 理由 |
|---|---|---|
| `session_created` | 剥离 `workspace`/`workspaceKind`/`forkedFrom`/`spawnedBy`/`title` | 工作区路径是本机隐私；接收端 workspace 重写；fork 链跨机无意义 |
| `user_message` | 保留 `content`/`textFiles`/`origin`/`backgroundTaskIds`；剥离 `attachments` | 图片 ref 指向本机附件库（ADR-0009），死链；`textFiles` 是全文快照、自包含 |
| `assistant_message` | 保留 `content`/`toolCalls`/`model`；剥离 `reasoning`/`usage` | reasoning/usage 是审计和隐私，不进模型视野 |
| `tool_result` | 保留 `toolCallId`/`status`/`output`；剥离 `diffStat`/`images` | images 是本机 ref |
| `tool_execution_started` | 保留 | 悬空工具自愈依赖 |
| `turn_ended` | 保留 `outcome`/`error`/`errorClass` | 空跑判定依赖 |
| `skill_invoked`/`skill_released` | 保留 | 台账依赖 |
| `image_described` | 保留 `content`/`model` | 模型视野 |
| `context_compacted`/`micro_compacted` | 保留；剥离 `usage` | 压缩投影依赖 |
| `tool_hook` | 只保留 `action === "feedback"` 的 | 反馈包装依赖；其余是审计 |
| 其余全部 | 剥离 | 模型不可见 / 本机引用 / 审计 / 隐私 |

明确剥离：`approval_decision`（模型不消费，denied 已在 `tool_result` 体现）、`model_changed`（`assistant_message.model` 已带）、`session_archived`/`session_unarchived`/`session_renamed`/`session_autotitled`、`section_classified`/`suggestions_generated`、`subagent_spawned`/`subagent_briefed`（第一期不支持跨机子会话）、`memory_loaded`/`memory_user_edit`/`memory_nudge`（源用户的记忆是隐私，接收端用自己的）、`project_instructions`（本机路径 + 文件内容，接收端按自己的工作区重生成）、`request_envelope`（含工具表审计快照）、`background_task_*`、`checkpoint_created`/`workspace_restored`、`branch_checked_out`。

**导出/导入是纯函数**（`src/shared/` 下，同 `friendsQuery.ts` 的先例），白名单和剥离规则可单测钉住。

### 2. 传输 = Supabase 新表 `session_shares` + Realtime 推送

没有 Storage 先例，走 PostgREST 表读写（照 `insertMessage`/`upsert` 模板）。新表：

```sql
create table public.session_shares (
  id uuid primary key default gen_random_uuid(),
  sender uuid not null references auth.users(id) on delete cascade,
  recipient uuid not null references auth.users(id) on delete cascade,
  title text not null default '',
  message text not null default '',   -- 那句交代
  payload jsonb not null,             -- { version, sourceSessionId, events: [...] }
  status text not null default 'pending' check (status in ('pending','accepted','declined')),
  created_at timestamptz not null default now(),
  check (sender <> recipient)
);
```

RLS：`select` 仅 sender/recipient；`insert` 仅 `sender = auth.uid()` 且 `status = 'pending'`；`update` 仅 recipient 改 `status`。进 Realtime publication，recipient 订阅 `INSERT`。

payload 体积上限 ~1MB（PostgREST request body 默认 2MB 的保守值）；超限拒绝分享并提示「会话过大」，不静默截断——静默截断 = 给好友一份残缺上下文。

### 3. 接收端 = 重建独立会话，`sharedFrom` 标记来源

不 `store.fork`（父不在本库）。接收端：

1. 生成新 sessionId（`newSessionId()`）；
2. `append` 一条 `session_created`，workspace = 好友自己的默认工作区，带可选字段 `sharedFrom: { sessionId, fromUserId, fromName, message, sharedAt }`；
3. 逐条 `append` payload.events（sessionId 重写为新 id，seq 由存储层分配，ts 保留原值——它们是历史，不参与逻辑）；
4. `append` 那句交代作为一条 `user_message`（content = 原文）；
5. 自动起 turn（那句话是分享者替朋友写的第一句话，确认接收 = 授权跑）。

`sharedFrom` 是**已知类型上的新增可选字段**，不是新事件类型——旧版本 `assertReplayable` 只拒未知类型，已知类型上的多余字段它认得，向前兼容零成本。第一期的 fork 语义不靠 `forkedFrom`（那是同库链），靠 `sharedFrom` 标记「这是分享来的会话」。

### 4. `@` 触发复用 aui trigger 机制，与 `@路径` 并存

`@` 已被 `ottoPathFormatter` 的路径高亮占用（`@某人` 现在会被错画成 path chip，纯视觉无语义）。不另造一套，顺着 `ComposerPrimitive` 的 trigger/formatter 机制加：`@` 触发后弹出菜单，好友（`friendsSnapshot.friends`）与文件路径分组展示，选中好友 = 序列化成一个可解析的 mention token，提交时识别为「分享」而非普通发送。

### 5. 分期：第一期不含凭据

凭据（API key / MCP 凭据）的临时授权走「加密打包、副本给朋友」路线，第二期做。第一期只同步对话上下文，不碰 `keyVault`/`mcp.json`/`mcp-auth.json`。

## 验证

- 导出/导入纯函数单测：白名单事件全保留、剥离项全消失、字段级剥离精确；
- 导入后 `deriveMessages(store.load(newId))` 与源会话 `deriveMessages(store.load(srcId))` 的模型视野逐字节一致（剥离项除外）；
- Supabase 侧：RLS 边界（非当事方不可见、非 sender 不可插、非 recipient 不可改 status）；
- e2e（不进门禁，随你）：真机双账号走一遍 @ 分享 → 接收 → 确认 → fork 会话起 turn。

## 后果

- 接受：跨机 fork 丢工作区文件状态（「纯对话 fork」，用户已选）；丢 checkpoint/附件（死链）；好友的 fork 跑在他自己的默认工作区，`project_instructions`/记忆按他自己的环境重生成。
- 接受：payload 体积上限，超大会话不可分享。
- 第二期（凭据临时授权）在此之上叠加，不推翻本期的 payload/传输/接收装配。
