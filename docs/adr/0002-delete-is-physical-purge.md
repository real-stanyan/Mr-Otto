# ADR-0002: 删除会话 = 物理抹除，不是归档隐藏

日期：2026-08-16
状态：已采纳

## 背景

MVP 初版把"删除会话"实现为追加 `session_archived` 事件 + 列表投影滤掉——日志一个字节不删。
维护者检查 sessions.db 时发现：UI 里删掉的会话在库里原样躺着，与用户对"删除"的
心智模型（数据没了）不符。会话日志可能含敏感内容（命令、文件路径、对话原文），
"看起来删了实际还在"是隐私上的错误默认。

## 决策

UI 的删除按钮 = 整会话物理抹除（`EventStore.purge(sessionId)`），不可逆。

与 append-only 硬规则的关系——两者不矛盾，因为挡的是不同的东西：

- **不许改写历史**：会话内事件永远不许 UPDATE、不许删一部分。trigger 继续全时值守。
  被篡改的日志会说谎（重放出从未发生过的历史），这是事件溯源的死穴。
- **允许整段遗忘**：purge 是"这段历史完整地不存在了"——要么全在、要么全无，
  不存在被篡改的中间态，重放语义完好（没有日志 = 没有会话，不会放出假历史）。

实现：事务内 `DROP TRIGGER events_no_delete` → `DELETE WHERE session_id = ?` → 重建 trigger。
better-sqlite3 单连接同步执行，事务里没有并发写者能穿过临时开的门。

## 代价（明知并接受）

- 误删无法恢复——确认框文案明确警告"不可恢复"承担告知义务
- 删掉的会话不再可审计/重放；agent 在现实世界留下的副作用（写过的文件、跑过的命令）
  失去日志佐证。用户对自己的数据有最终处置权，此代价由点删除的人自愿承担
- `session_archived` 事件类型保留为遗留类型：旧库里存在的归档标记必须永远可重放，
  `sessions()` 的归档过滤照旧（schema 向后兼容硬规则）

## 被否决的备选

- **归档 + 另设"彻底删除"两个按钮**：MVP 一个列表两种删除语义，认知成本大于收益；
  将来真需要"可恢复的归档"再加回来，事件类型都还留着
- **软删 + 定期清理**："稍后才真删"兼具两者缺点：既不可恢复预期，又不即时消失
