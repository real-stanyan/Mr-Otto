# ADR-0051: 类型检查进门禁 —— `npm test` 先跑 `tsc --noEmit`

日期：2026-08-21　状态：已接受

## 背景

门禁 `npm test` 一直等于 `vitest run`。vitest 用 esbuild 转译，esbuild **只剥类型，
不校验类型**——一个 TS strict 错误可以顶着全绿的门禁和全绿的 CI 合进 main。
这不是假设：MCP 分支上真的漏过一个，靠人工审查抓回来的。

分量最重的一处在 `src/main/mcpClient.ts`：那里有一个刻意的
`as unknown as Transport`，注释写明它绕开的是 SDK 的 `sessionId` getter 与
`Transport` 接口在 `exactOptionalPropertyTypes` 下的结构不兼容。
**SDK 升一次版把那个形状改掉，这处断言会静默失效，而 `npm test` 和 CI 全绿。**
断言绕过的正是唯一能发现它的那道检查。

## 决定

`package.json` 拆出一条 `typecheck: tsc --noEmit`，`test` 改成
`npm run typecheck && vitest run`。

**门禁命令行本身一字不改，仍是 `npm test`**，`.github/workflows/ci.yml` 也一字不改——
CI == Gate 的字节相同契约天然保持。变的是这条命令断言了什么：从"测试通过"
变成"类型检查通过 **且** 测试通过"。

顺序是先 `tsc` 后 `vitest`：类型错通常是更根本的错，先报它比让人在几十条
运行时失败里翻找便宜。

## 理由

按 ADR-0010 的口径，**加一条更严的断言是 L2**、改门禁命令行是 L1。这次两样都沾：
命令行没动（L2 那一侧），但断言的强度变了、而且这条 ADR 本身在讨论门禁的语义边界，
所以按 ADR-0012「拿不准就默认 L1」处理，走完整的 issue + ADR + PR + 维护者同意。
维护者的同意在会话内给出（单人仓，ADR-0042 保留这条路径）。

落地前先在干净的 `origin/main` 上跑过一次 `npx tsc --noEmit`：**零错误**。
所以这次收紧的代价是"以后新写的类型错会被拦下"，不含"先去修一堆存量错误"。

`skipLibCheck: true` 留着不动：它挡的是第三方 `.d.ts` 自己的毛病，
和本仓代码的类型正确性无关，打开它只会让门禁替 node_modules 背锅。

## 代价

`npm test` 从 1.6 秒变成十几秒（tsc 全量检查一次）。这是每次跑门禁都要付的钱。
接受的理由：门禁不是内循环——写代码时该跑的是 `npx vitest --watch`（它照旧只跑测试），
门禁是提交前和 CI 上跑的那一次，十几秒买"类型错误进不了 main"是便宜的。

## 什么前提倒了会推翻它

`tsc --noEmit` 的耗时涨到让门禁变成瓶颈（比如仓库大到分钟级），
或者出现一类本仓真正需要、但类型系统表达不了、只能靠 `@ts-expect-error`
成片压制的写法——那时候该重谈的是"检查放在哪一层"（比如挪进 CI 的独立 job、
本地门禁只跑测试），不是"要不要检查"。
