# ADR-0188：归属不明的存量停在 `_unclaimed`，不猜主人

日期：2026-08-29
状态：已接受
修正 ADR-0187 第四节「存量归给当前登录的账号」；相关 issue #755（#749 的回归）

## 背景

ADR-0187 把本机数据按登录账号分抽屉，并裁定：第一次实施隔离时，散在根下的存量
**归给账号 1**。实现写成了：

```ts
if (bootUid) { adoptLegacyData(root, accountData, …); }
```

没有 else。于是真实语义是**「归给升级后第一个登录的人」** —— 这两句只在
「升级那一刻人是登录着的」时候等价。

而"换账号"这件事本身就以登出开头。维护者本机上真的这么走了一遍：

1. 登出状态下升级、开 app（`bootUid` 为 null，搬家被跳过，存量原地留在根下）
2. 登录**另一个**账号 → `relaunch` → 新一轮开机 `bootUid` 有值 → 搬家这才执行
3. 上一个账号的 26 MB 会话库、记忆、API key、MCP 令牌，**整堆进了新账号的抽屉**

这正是 #749 要修的那个现象，只是换了条路径发生 —— 而且比原来更糟：原来是"没分开"，
现在是"分错了，并且分给了明确不该拿到它的那个人"。

## 决定

**能归属才归属，归属不了就不猜。**

唯一一次能证明这堆东西属于谁的机会，是**升级后第一次开机时 `auth.json` 里还有没有
session**。人一登出，证据就永远没了 —— 事后任何"聪明"的推断都是在猜，而猜错一次的
后果就是上面那三行。所以分两支：

- 根下有存量且 `bootUid` 有值 → 照旧归给它。升级时登录着是常见路径，这一支无感。
- 根下有存量且 `bootUid` 为 null → 整堆挪进 `<根>/accounts/_unclaimed/`，
  **从此不再自动归给任何账号**，并在里面留一张 `读我.txt` 说明它是什么。

**挪走这个动作本身就是修复的一半**：留在根下的话，下一个登录的人会把它顺手扫走，
而那个人多半正是你想把数据挡在外面的那个人。挪进 `_unclaimed` 之后根下空了，
后来者再也扫不走。

同时删掉 ADR-0187 里那次 `_signed-out` sweep（把未登录那格扫给第一个登录的人）：
同一类的猜测，而那格里只会有开机顺手建出的空壳，交给谁都没有正确答案。

## 后果

- 登出状态升级的人，第一次进去看到的是**空的**，数据在 `accounts/_unclaimed/` 里等着。
  这是刻意的：宁可让人多问一句"我的东西呢"，也不能让另一个账号看到它。
- 需要一个「把 `_unclaimed` 归到当前账号」的显式入口，否则那堆东西只能手动搬。
  不在本 ADR 范围，另开 issue。
- 已经踩中 #755 的机器不会自愈：数据已经在错的抽屉里了，要手工搬回去
  （抽屉名是 `sha256(uid)` 前 16 位，每间的 `who.txt` 写着是谁）。

## 备选与否决

- **一律停进 `_unclaimed`，任何情况都要人点一下**：最安全，但把"单账号机器升级"这个
  绝大多数路径也变成了"打开发现空的"。归属证据存在时不用它，是有代价的谨慎。
- **从存量里推断主人**（比如翻 sessions.db 找线索）：日志里根本没有 uid（ADR-0187
  否决过加 owner 列），而且旧 app 的那一堆本来就可能是几个账号混着攒的 —— 推断出来的
  答案会以"看起来很确定"的样子错。
- **保持 0187 的写法，只在文档里提醒"升级前先登录"**：把机制问题转嫁成用户须知。
  用户读不到，读到了也会忘。
