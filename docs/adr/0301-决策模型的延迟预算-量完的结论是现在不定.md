# ADR-0301 决策模型的延迟预算：量完的结论是「现在不定」

- 日期：2026-09-21
- 状态：已接受
- 相关：#1300（本条）/ #1281 与 ADR-0299（决策模型接入）/ #1304（网关跨 colo 慢）/ #1303（中断的调用照样计费）
- spec：`docs/superpowers/specs/2026-09-20-jev-decision-model-design.md` §8

## 背景

ADR-0299 给五处分类器各拍了一个决策模型超时（派活 1200 / Auto 1200 / 重命名 1500 / 语音 900 / 记忆 900），依据是厂商自报的 70–500ms 加「经 OpenRouter 与 edge 各多一跳」。#1296 打出第一发真调用：**1788ms**，当场超过派活那一格。#1300 因此立下一条纪律：**一个样本不是分布，先量再定**。

这条 ADR 记的是量完之后的结论。三组数全部在 2026-09-21，同一个 max 账号、同一份用**真的 `dispatchQuestions`** 生成的请求体（不重新实现形状，同 #1296 的纪律）。

## 量到了什么

**① 名册大小对延迟没有影响**（Mac，24 发背靠背）

| 问题数（名册 N+1） | 中位 | 输入 token | 每发 credit |
|---|---|---|---|
| 2（1 只） | 455ms | 658 | 28 micro |
| 4（3 只） | 461ms | 976 | 41 micro |
| 7（6 只） | 474ms | 1447 | 61 micro |

官方说「同一请求里的问题并行」，真机兑现了：**token 涨、钱涨、时间不涨**。所以名册上限那条线只为钱操心，不为延迟操心。

**② 闲得越久越慢，稳态本身就超**（Mac，每次一发，间隔递增）

| 闲置 | 0s | 30s | 60s | 120s | 300s | 600s |
|---|---|---|---|---|---|---|
| ms | 728 | 585 | 827 | 960 | **1402** | **1321** |

背靠背那 24 发是 p50 470 / p90 594 / max 725，新进程首发 728、864。所以 **1788 是冷路径不是稳态**，#1300 标题里那句「必然超时」在背靠背下不成立。

但**真实派活是零星的**——人隔几分钟在群里说一句——所以贴的是闲置那一行：五分钟之后稳定在 1.3–1.4s。`1200` 在那里不够，理由与 issue 当初猜的不同（不是「第一次冷」，是「平时就这么久」）。

**③ 但这些都不要紧，因为派活不跑在那台 Mac 上**（交叉打，同一分钟内轮流发）

| | Mac（`cf-ray` 尾 SYD） | VPS（`cf-ray` 尾 HEL） |
|---|---|---|
| `/llm/v1/decision` | 0.44 / 0.71 / 1.51s | 6.47 / 3.77 / 6.86s |
| VPS 单独连打 8 发 | — | 冷 12.8s，热 5.1–13.9s，一发 55.7s |

派活跑在 runtime 上，runtime 在那台 VPS 上。**在那条路上 `1200` 不是偏紧，是 100% 超时**，调到 2000 / 3000 / 5000 一样是 100%。

病因不在决策模型也不在这个数：`/healthz` 两边一样快（各 ~43ms），`/llm/v1/decision` 回 **400**（认证之后、`quota.hold` 之前，不碰 DO 不碰上游）两边也一样快，而**一个上游字节都不碰的 `/billing/v1/me` 是 0.35s vs 3.65s**。见 #1304——那条不只是决策模型的事，云会话每一轮 chat 都在付。

**④ 超时不是「白等」，是「全价买一个扔掉的答案」**：5 发在 300ms 中断，5h 窗掉 192 micro（每发 ~38，完整一发 41）。见 #1303。

## 决定

1. **五个常量一个字不改。** 在会真正用到它们的那条路上，没有任何值是对的；改成一个「看起来更宽松」的数，只会让下一个人以为这件事处理过了。
2. **`decisionUses.ts` 维持 `{ dispatch: "shadow" }`，在 #1304 解掉之前不许往 `on` 翻**——这条写进那个文件的头注，因为翻它只要改一行，而那一行没有任何机制拦着。`shadow` 下超时是无害的（legacy 说了算、不等它），所以门可以继续开着收形状上的对照。
3. **`DISPATCH_DECISION_TIMEOUT_MS` 的注释改掉。** 原文写着「厂商自报 70–500ms，经 OpenRouter 与 edge 各多一跳」——这是个**已经被证伪的前提**，留着它下一个人会照它调参。换成量到的数与指向本 ADR 的指针。
4. **`runtime` 的决策接线不要先于 #1304 部署。** 线上 bundle 此刻还没有它（`grep -c "llm/v1/decision" /opt/otto-runtime/runtime.mjs` → 0），所以一分钱没白花；部署之后、#1304 解掉之前，每一次派活都会全价买一个必然被扔掉的答案，而界面上一个字都不会说。
5. **spec §8 那张表不动。** 那张表是当时的设计意图，改掉等于抹掉「我们当初怎么想的」；真实数在这条 ADR 里，两者都留着才看得出偏在哪。

## 被否掉的

- **把 1200 调成 2500 / 3000**：在 SYD 那条路上能盖住闲置那一格，在 HEL 那条路上仍然 100% 超时。于是它只对「维护者自己这台 Mac」有效，而**那正是这次量出来的偏差来源**——用一个只在一处成立的数去定全局，比不改更坏。
- **对冲式并发**（决策没回就同时起 LLM，ADR-0299「被否掉的」最后一条，#1300 说「现在正是量完的时候」）：量完的结论是**现在更不该做**。对冲的前提是「决策通常比 LLM 快、偶尔慢」；在 HEL 上它**总是**慢，对冲退化成「每一次都白烧一发 LLM」。等 #1304 解掉、延迟回到一个数量级之后重判。
- **按 use 分别调**（#1300 提的：语音最敏感、派活可以慷慨）：方向对，但这次量出来「**跑在哪**」比「哪一处」重要得多——五处里派活 / 重命名 / Auto 的云那一侧跑在 runtime 上，语音 / 记忆跑在桌面上，而两条路差一个数量级。等 #1304 之后按真实分布一次定齐。

## 已知代价

- **这次的数来自一个账号、两个位置、一个时间窗**。SYD 那侧 24+6 发够看出形状，HEL 那侧只有 6+4 发。
- **`/me` 那 3.3s 没拆开**——几个顺序往返、DO 占多少、Supabase 占多少，要在 Worker 里打点才知道（记在 #1304）。
- **探针不进仓库**：一次性，且要一把会过期的用户 JWT。所以这份数据的保鲜期就是这条 ADR 本身——下次要重量得重写一遍探针。
- **`shadow` 下 runtime 侧的对照数据这段时间收不到**（第 4 条的直接后果）。

## 补记一（2026-09-21 同日）：决定 3 只落到了五格里的一格

决定 3 点名的是 `DISPATCH_DECISION_TIMEOUT_MS`，落地时也只改了它一处。但那条决定的理由（「原文是个已经被证伪的前提，留着它下一个人会照它调参」）与「是哪一格」无关，对另外四格一字不差地成立 —— 而那四格当时一个字没动，各自留着一句被这次测量证伪、或者干脆什么都不说的注释：

| 常量 | 跑在哪 | 原来那句话的问题 |
|---|---|---|
| `TITLE_DECISION_TIMEOUT_MS` 1500 | runtime（VPS/HEL） | **一个字都没有** —— 下一个人手上零信息，而 1500 在那条路上是 100% 超时 |
| `AUTO_DECISION_TIMEOUT_MS` 1200 | **桌面 + runtime 两条** | 「只有『挂住不回』才付满它」：云那侧每一发都付满，桌面那侧闲置五分钟就付满 |
| `ENDPOINT_DECISION_TIMEOUT_MS` 900 | 桌面 | 判据本身没错（上界是人重新开口的窗口，不是上游延迟），缺的是由它得出的结论 |
| `TIER_DECISION_TIMEOUT_MS` 900 | 桌面 | 「900ms 的等待不占任何东西」：它坐在一次工具调用里（模型干等），且 #1303 说它照样计费 |

所以本次把决定 3 补齐到五格，**一个数字都不改**（决定 1 不变）。顺带把两件测量已经给出答案、但当时没写进任何一处代码的事记下来：

1. **「一次定齐五处」实际是六格。** `AUTO_DECISION_TIMEOUT_MS` 住在 `src/shared/`，被 `src/main/agent.ts`（桌面）与 `services/runtime/src/autoModel.ts`（云）**同时** import，而两条路差一个数量级 —— 一个数不可能对两条都成立。「被否掉的」那一节里「跑在哪比哪一处重要」说的就是这件事，只是没说它在一个常量上正面撞了一次；真要按路分，这一格得先拆成两个。
2. **六格里有两格的上界不是延迟分布，而是别的东西**，所以它们的结论不必等 #1304：
   - `title`：**没有人在等**。`maintainTitle` 是 fire-and-forget（`void (async () => …)()`，`say()` 的回执不等这次网关往返），所以超时在这一格上不花任何用户可见的时间，只花 #1303 那笔钱。于是它该取得比其余几格慷慨得多。
   - `endpoint`：上界是人重新开口那个窗口（渲染层再等 200ms 就放弃），**调大换不到任何东西**，只换来一个「早就没人要了却照样计费」的答案。这一格的答案是「要么快到够用，要么这个能力在那一刻就用不了」，不是「等更久」。

## 补记二：决定 2 从一句注释变成一条断言

决定 2 自己写着它的弱点 —— 「翻它只要改一行，而那一行没有任何机制拦着」。补一条断言（`tests/edge/decisionUses.test.ts`）：真的那张 `DECISION_USES` 里一格都不许是 `on`，失败信息写清为什么、以及**解掉之后连这条断言一起删**（同 ADR-0258「一个用过一次的逃生门下次就是默认」）。

判据取「有没有 `on`」而不是「必须逐字等于 `{ dispatch: "shadow" }`」：后者会把「再给第二处开 shadow」也拦下来，而那正是这一档存在的目的（收形状上的对照数据），拦它等于把一条无害的路一起封了。同一个文件里还钉了第二条：表里的键与值都要落在联合类型里 —— `modeOf` 读不到的键一律当 off，所以把 `title` 拼成 `titel` 不会报错，只会让那一处安静地一个请求都不发，而「关着」本来就是它的正常状态之一，肉眼分不出来。

加一条更严的断言是 L2（gearbox ADR-0020 / ADR-0010）。

## 还是没做的：这条 issue 为什么继续开着

`#1300` 的**定数**那一半仍然没做，前提一个字没变：#1304 还开着（2026-09-21 ADR-0303 把 DO 往返从三趟砍到两趟并已部署，量出来「一趟 DO 往返在 HEL 约 0.7s、在 SYD 约 0」，但那 0.7s 被方差盖住了 —— 同一端点同一台机器在 0.83s 与 4.90s 之间跳，改动前后的 decision 四发分不开）。在那条路上仍然没有任何超时值是对的，所以六格照旧一个字不改。

## 补记三：决定 4 的那条检查**结构上不可能报出真相**，而它要防的事已经发生了

决定 4 写着「线上 bundle 此刻还没有它（`grep -c "llm/v1/decision" /opt/otto-runtime/runtime.mjs` → 0），所以一分钱没白花」。2026-09-21 在那台机器上重跑这条检查，仍然回 0 —— **但它回 0 与部署了没有无关**：那个 URL 是运行时拼出来的（`requestDecision` 里 `${deps.llmBase}/decision`，而 `llmBase` 是 `${edgeBase}/llm/v1`），所以 `llm/v1/decision` 这个字面量**在任何一版 bundle 里都不会出现**。这条检查只有一种输出。

换成会出现在 bundle 里的东西之后，答案反过来了：

```
$ ssh -p 2222 stan@…  # 2026-09-21
grep -c "llm/v1/decision" /opt/otto-runtime/runtime.mjs   →  0    ← 决定 4 用的那条，永远是 0
grep -c "said.text"      /opt/otto-runtime/runtime.mjs   →  2    ← dispatchQuestions 的字符串字面量
grep -c "dispatchVia"    /opt/otto-runtime/runtime.mjs   →  2
grep -c "requestDecisionAsOwner" …                        →  4
[otto-runtime] 就绪：… stamp=b861c150ecc7 协议=20         ← 2026-09-21 04:07:07 UTC 重启
```

**决策接线已经在线上了**，部署时刻（04:07 UTC）晚于这条 ADR 写成的时刻。所以决定 4 此刻不是「照着做」的状态，是「已经被越过」的状态。

**但还没花到钱**：同一段 journal 里 `[decision]` 一行都没有（近 6 小时 0 条），也就是说自那次部署之后没发生过一次「团队云会话里有人说话且没 @ 任何人」。这是一把上了膛没扣扳机的枪 —— 下一条这样的消息就会打出一发必然超时（1200ms 闸 vs 那条路 3.5–7.3s）、必然被扔掉、而 #1303 说照样全价计费的调用，且界面上一个字都不会说。

两条要改的：

1. **判据换成 journal 不是 bundle。** 「部署了没有」问 `grep -c "said.text"`（字符串字面量，不会被拼装也不会被改名）；「有没有真在花钱」问 `sudo journalctl -u otto-runtime --since … | grep -c "\[decision\]"` —— 后者是唯一直接的证据，因为部署了但没人触发时前者为真、后者为零，而这两种状态该做的事不一样。
2. **决定 1 在 `shadow` 这一档上被推翻了：`DISPATCH_DECISION_TIMEOUT_MS` 1200 → 20 秒。** 病灶是 `shadow` 在这条路上**既不产生对照数据也不免费**：`withDecision` 在 shadow 档下记的 `ms` 是决策那发 promise settle 的时刻，而它每次都停在 abort 上 —— 那一行日志于是是个常数不是分布，钱却照付（#1303）。而 `shadow` 档下**没有任何人在等这一发**（`withDecision` 不 await 它，legacy 说了算），所以这个数在那一档里只决定「多久之后放弃记录」。放宽它，同一笔钱换来真实延迟分布 + 真实判决 —— 正是这条 ADR 说在等的那份数据，也是 ADR-0299 §7 要的一致率与校准。取 20s 不取无上限：观测到的主体在 13.9s 以内，55.7s 那一发按右截断读就够，而这一发是个游离的 fetch，不该无限期挂着。

   这**不是**推翻决定 1 的本意（「别拍一个生产值」）—— 20 秒不是生产值，是测量窗口；决定 1 要防的是「在瞎的时候定一个数」，而这一步正是停止瞎的手段。维护者 2026-09-21 在三个选项（收回 off / 原样留着 / 放宽 shadow 期的超时）里选的是这一条。

   代价与它的栏杆：**`on` 档里人是真的在等**，20 秒在那里会变成「每条消息先干等 20 秒再走今天那条 5 秒的 LLM 路」，而界面一个字都不说。所以 `tests/edge/decisionUses.test.ts` 里是两条断言不是一条：第一条拦 `on` 本身（#1304 解掉那天被删的就是它），第二条在那一刻**接上** —— 按上面那张「谁在等」的表卡上限（`dispatch` / `auto` / `memory` 2s、`endpoint` 900ms、`title` 无上限）。第二条今天由构造跑不到，它存在的全部理由就是活过第一条的那次删除；天花板是两条一起删，那时至少读过两段写着为什么的话。

   **另外两条没选的路记在这里**：收回 `off` 会让 runtime 侧这段时间一条对照数据都收不到（本 ADR「已知代价」最后一条本来就接受了这个代价，但它换不到任何东西）；原样留着则是每条「团队云会话里没 @ 任何人的消息」花 ~40 micro 换一行写着 1200 的常数。
